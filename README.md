# Navix Router

Веб-сервис интеллектуального планирования и **живого перепланирования** маршрутов
выездных инженеров. Кейс «Билайн Бизнес» (номинация «Логистика»), ЛЦТ 2026.

Идея продукта — не «много фич», а один продуманный инструмент, которому диспетчер
доверяет: **план за секунды → карта с доступной дорожной геометрией → объяснение
каждого решения человеческим языком → измеренная надёжность дня → наглядное
перепланирование → делегирование рутинных решений ИИ-агенту**. Каждая возможность
в системе отвечает на вопрос диспетчера «почему я должен этому верить?».

> Публичный стенд: [navix.droidje.com](https://navix.droidje.com)

Вход диспетчера не хранится в документации. Для локального запуска задайте свои
`DISPATCHER_EMAIL` и `DISPATCHER_PASSWORD` в игнорируемом `.env`; доступ к публичному
стенду выдаётся контролируемым каналом владельца демо.

Для оценки по кейсу: [ядро ТЗ и назначение дополнительных функций](docs/core-and-extensions.md),
[сценарий проверки](docs/tz-acceptance.md).

## Что делает система

> **Эффективность цифрами.** Качество планирования и производительность ядра
> измерены детерминированным офлайн-бенчмарком: на одних и тех же
> бригадах Router закрывает **+122% заявок дня** к FIFO-диспетчеру (60 из 66 против
> 27, срочные 10 из 13 против 2) при **−40% дороги на заявку**. План Востока
> байт-в-байт совпадает с golden-гейтом. Полная методика и таблицы:
> [benchmarks/solver-suite-20260929](docs/benchmarks/solver-suite-20260929/README.md).
> Точность времени в пути подтверждена сверкой с Яндекс Картами на реальных маршрутах:
> офлайн-прогноз сходится с онлайн-эталоном **в среднем на 8% (максимум 11%)** —
> [валидация против Яндекса](docs/benchmarks/roads-vs-yandex-20260929/README.md).

### 1. Время в пути, которому можно верить

План стоит столько, сколько стоит его ETA. Поэтому источник и ограничения каждой
оценки в системе раскрыты:

- **Расчёт плеч.** Перед поиском Router Core подготавливает пакетную автомобильную
  матрицу Road API с временными режимами прогноза и затем обращается только к данным
  в памяти. При недоступности провайдера используется подготовленный региональный
  граф с сохранённым происхождением стоимости; прямой `StraightTravel` остаётся
  явным fallback-провайдером отдельных вызовов.
- **Дорожная геометрия.** После готового плана API может запросить у `road-api`
  полилинии отдельных плеч. Если провайдер или кэш недоступен, на карте остаётся
  явно обозначенная прямая-приближение; геометрия не меняет назначение и ETA плана.
- **Прогноз пробок на момент выезда.** Время каждого перегона оценивается на то
  время, когда инженер реально поедет, — утренний пик и вечерний час пик дают разные
  ответы. Для этого в ядре работает собственный динамический поиск: статичная
  матрица «точка → точка» не отражает изменение времени в пути в течение дня
  (`docs/solver.md`).
- **Погода.** Прогноз Open-Meteo по Москве замедляет дороги в дождь, снег и грозу;
  в грозу ходьба дорожает в 2,4 раза, и пешехода отправляют метро, если это спасает
  заявку от срыва. Погодный бейдж видно прямо на карте.
- **Метро для пеших курьеров.** При включённой настройке `metro_enabled` для пешеходов
  строится полный составной путь:
  подход к станции → вход и ожидание → перегоны с пересадками → выход → подход до
  двери. Сравниваются все станции в радиусе 1,5 км, выбирается только строго более
  быстрый вариант; метро-граф работает офлайн.

**Зачем:** окна обслуживания опираются на воспроизводимую оценку времени выезда, а
доступная дорожная геометрия помогает проверить маршрут на карте.

### 2. План, который объясняет себя сам

Объяснимость — не отчёт после факта, а основной интерфейс:

- **Каждое назначение** раскрыто по цепочке «Факты → влияние → результат»: навык,
  запас по окну, добавленная дорога, рассмотренные альтернативы и причины, по
  которым кандидатам отказано. У неназначенной заявки — человеческая причина
  (нет навыка / не помещается в окно / нет транспорта).
- **Кнопка AI** рядом с любым объяснением: при настроенном провайдере LLM пересказывает
  уже посчитанные факты одним абзацем. В `.env.example` провайдер по умолчанию выключен
  (`LLM_PROVIDER=off`), поэтому ручное объяснение всегда остаётся доступным.
- **Сравнение политик.** Шесть стратегий оптимизации (`fast`, `compact`, `sla`,
  `balanced`, `eco`, `covering`) против базового FIFO из ТЗ — по одним и тем же
  обязательным метрикам, на одном и том же дне.

**Зачем:** диспетчер перестаёт быть оператором чёрного ящика — он может ответить
любому: инженеру, клиенту, руководителю.

### 3. Перестроение, которое видно

День меняется — и это нормально. Система делает перепланирование наблюдаемым:

- **Панель дельты.** После пересборки плана дашборд показывает, что именно
  изменилось: сколько заявок передано между инженерами, сколько сдвинулось по
  времени, как изменились SLA-риски «до/после». План можно принять или отклонить,
  вернув прежнюю ревизию.
- **Метрики плана.** Отдельная панель показывает пробег, загрузку, неназначенные
  и **оценку надёжности дня**: контур «проживает» применённый план 300 раз под
  разным трафиком, длительностями и отменами и отвечает на языке диспетчера —
  «План надёжный / Можно работать / Высокий риск» и список слабых мест («заявка
  #50104 опоздает в половине вариантов дня»).
- **Самокалибровка.** Тот же контур уточняет свои разбросы по подтверждённым
  фактам исполнения (начал/завершил работу, доехал) — чем больше день отработан,
  тем точнее предсказания. Пока фактов мало, работают заводские калибровки.

**Зачем:** диспетчер видит цену решения **до** того, как его принял, — а не узнаёт
о последствиях по звонку недовольного клиента.

### 4. Живой день

- **LIVE-режим.** После запуска дня система следит за фактами: отметки визитов,
  обед и перерывы, движение инженера по текущему ребру маршрута, часы.
- **Алерты с решениями.** Координатор превышений поднимает алерты не «для истории»,
  а с вариантами действий (перенести, сдвинуть окно, продлить неявку) и формой
  подтверждения с последствиями каждого варианта.
- **System One.** При настроенном провайдере ИИ-агент диспетчера может разбирать
  алерты и выбирать политику сам — строго внутри выданных инструментов и с обычной
  приёмкой результата системой. Без провайдера остаётся ручной путь.
- **Чаты.** При настроенном AI-провайдере чаты с помощниками по роли доступны
  диспетчеру (help/fix) и инженеру; без провайдера они отключены. Живые диалоги
  диспетчера с клиентом и инженером доступны в отдельной вкладке; из карточки
  инженера можно открыть его разговор.
- **Клиентское приложение** (`/client/`): новая заявка с точкой на карте,
  подтверждение почты одноразовым кодом, история заявок и живой чат с диспетчером;
  интеграция через API описана в [integration-guide.md](docs/integration-guide.md).
- **Приложение инженера** (`/engineer/`): план дня, отметки выполнения, обед,
  паспорта объектов и заработанные баллы.

### 5. Экономика команды

- **Паспорта объектов.** База знаний зданий: тип подключения, сложность работ 1–3,
  оборудование и условия доступа. Паспорт виден в карточке заявки; устаревший
  (>45 дней) честно помечен. Паспорт заполняет инженер **после фактического
  старта работы** — из системы не выжать балл за неотработанный визит.
- **Баллы платформы.** Начисления за подтверждённые факты работы и заполненные
  паспорта, месячная плашка с итогом у инженера.
- **Статистика месяца для диспетчера.** Итоги рабочего месяца: динамика команды,
  начисления, отчёт о результативности — одним экраном, не выгрузкой.

**Зачем:** система не заканчивается на «распределила и забыла» — она делает работу
команды измеримой и подкрепляет её репутационной валютой.

### 6. Открыт для ваших агентов: MCP

Дашборд подключается к внешнему ИИ-агенту диспетчера по протоколу MCP: включается
в настройках с PIN-кодом, агент получает набор инструментов для чтения дня и
действий по плану — через ту же операционную обвязку, что и UI (идемпотентность,
версии, роли). Свой сценарий автоматизации не требует форка системы.

## Почему системе можно доверять

Это не декларация, а конструкция:

- **Детерминизм священен.** Фиксированные сиды, golden-тесты на эталонных планах,
  побайтово воспроизводимые отчёты. Изменение, сдвинувшее golden-план без
  объяснения, не проходит регресс.
- **Пять независимых проверок результата.** План ядра становится рабочим только
  после проверки режима, hash-а снимка, версии контекста, пригодности и отсутствия
  конфликта с уже свершившимися фактами дня.
- **LLM не касается плана.** Ядро и его симулятор оценивают надёжность готового
  плана; языковые модели только объясняют уже рассчитанные факты и подсказывают.
  Планирование выполняет детерминированное ядро, а приёмка результата остаётся
  системной.
- **Демо-контур живёт офлайн.** Все внешние вызовы (дороги, геокодинг, погода)
  кэшируются и деградируют явно: недоступный провайдер не ломает план, а
  переключает источник времени в пути с объявлением происхождения данных.
- **Каждое изменение — операция.** Журнал с `operationId`, идемпотентность
  повторов, оптимистичные версии — двойной клик и потерянная сеть не создают
  дубликатов.

## Быстрый запуск

Требуется Docker (с плагином `docker compose`) и pnpm 10. Node 24 LTS нужен только
для запуска вне Docker и для тестов.

```bash
git clone https://git.sourcecraft.dev/lct-hackaton-2026/case-13-field-engineer-routing-team-22 LCT_smart_router
cd LCT_smart_router
cp .env.example .env        # задать свои DISPATCHER_EMAIL и DISPATCHER_PASSWORD
pnpm install
pnpm compose:up             # postgres + миграции + router core + api + web + дорожный API (osrm, road-api) + sys1
```

|Сервис|Адрес|Что это|
|:---|:---|:---|
|Dashboard|<http://127.0.0.1:5173>|Витрина диспетчера, клиент и инженер|
|API|<http://127.0.0.1:8000/docs>|System Layer (NestJS), интерактивная документация|
|Router Core|<http://127.0.0.1:8100>|Расчётное ядро (Python), приватный API|
|PostgreSQL|127\.0.0.1:5432|Бизнес-данные и опубликованные снимки задачи|

После `compose:up` локальный контур с `DEMO_STAND=true` (значение по умолчанию)
сам поднимает день **14 заявок / 3 инженера**. Для пустого контура задайте
`DEMO_STAND=false` перед запуском — см. [docs/runbook.md](docs/runbook.md).

Полный набор ТЗ: войти диспетчером → сайдбар **+** → **«Использовать сет из ТЗ»**
(205 заявок / 35 инженеров; при замечаниях качества — подтвердить в диалоге, затем
план применяется) → далее по клик-гайду [docs/tz-acceptance.md](docs/tz-acceptance.md).

`pnpm smoke` — сквозная проверка контура с нуля. Деструктивна, только на своей машине.
Запуск без Docker и диагностика — [docs/runbook.md](docs/runbook.md).
Метрики Prometheus, трассировка OpenTelemetry и Sentry, включая независимые env-флаги,
описаны в [docs/observability.md](docs/observability.md).

## Демо-сценарий (7–10 минут)

Клики — в [docs/tz-acceptance.md](docs/tz-acceptance.md). Нить демо — «вопрос → ответ»:

1. **«Что сегодня?»** — открыть дашборд: при `DEMO_STAND` день 14/3 уже на карте;
   либо **«+» → «Использовать сет из ТЗ»** (полный набор). Погодный бейдж и план
   после подтверждения качества.
2. **«Почему так?»** — клик по заявке: факты → влияние → результат; кнопка AI
   пересказывает человеческим языком.
3. **«Насколько план надёжен?»** — панель «Метрики плана»: светофор надёжности,
   слабые места с номерами заявок.
4. **«День сломался»** — вкладка «Инженеры», снять человека с линии: новый план +
   панель дельты «передано/сдвинуто, SLA до/после» — принять или отклонить.
5. **«А если стратегия другая?»** — вкладка «Политики», сравнение с FIFO из ТЗ.
6. **«Пусть AI поможет»** — разобрать алерт вручную; при настроенном провайдере
   дополнительно показать System One и «Оптимизировать» в метриках плана.
7. **«А клиент?»** — открыть `/client/`, создать заявку с точкой на карте,
   подтвердить почту кодом, посмотреть историю и открыть чат с диспетчером.

## Как это устроено

```text
Dashboard / Client / Engineer (apps/web)  ──►  System Layer (apps/api)  ──►  PostgreSQL
                                                    │  ▲                     │
                                        снимок задачи│  │ результат           │
                                                    ▼  │ (5 проверок)        ▼
                                           Router Core (core/, Python) ◄── читает снимок
                                                    ▲
                         прогноз/погода/опциональная геометрия — кэшируемые источники
```

- **System Layer** (`apps/api`, NestJS 11 + Prisma + PostgreSQL) владеет бизнес-состоянием:
  заявки, инженеры, факты выполнения, журнал операций с идемпотентностью, алерты,
  чаты, вознаграждения, MCP-инструменты и AI-контур (объяснения, System One,
  самокалибровка предиктов). По каждому значимому событию публикует **целый снимок
  оставшейся задачи** с hash; принимает результат ядра только после пяти независимых
  проверок.
- **Router Core** (`core/`, Python) — автономный сервис: строгий контракт
  снимка/результата, точный FIFO-baseline в каждом расчёте, подготовка матриц и
  региональных fallback-источников до поиска, тёплый старт при перепланировании,
  динамический поиск по времени выезда, опциональные метро и гео-провайдеры,
  погода, передачи оборудования, структурированные объясняющие факторы и контур
  оценки надёжности (ситуационные предикты). Детерминизм закреплён golden-тестами.
- **Dashboard** (`apps/web`, React + TypeScript + Vite + Tailwind + MapLibre) —
  дашборд диспетчера, SPA инженера и клиентское приложение в одном контуре:
  карта, таймлайны, объяснения, дельта и метрики плана, алерты с действиями,
  чаты, паспорта и баллы.

Подробности: [docs/architecture.md](docs/architecture.md) (слои и блоки),
[docs/api.md](docs/api.md) (контракты API, MCP), [docs/data.md](docs/data.md)
(модель данных), [docs/solver.md](docs/solver.md) (алгоритм, дороги, метро, погода,
передачи оборудования), [docs/ml-predictions.md](docs/ml-predictions.md)

## Данные и допущения

Официальный датасет организаторов (`data/dataset/anonymized/`, кодировка cp1251,
разделитель `;`): **205 заявок** на один рабочий день 17.08.2026 в трёх независимых
регионах (Восток — 66, Юго-восток — 83, Юго-центр — 56) + контрольное распределение
по бригадам. В каждом файле скрыта строка «Адрес Офиса» — точка старта всех бригад
региона; возврат в конце дня не требуется.

Чего в датасете нет — синтезируем сами (ТЗ прямо это разрешает, при фиксации
допущений): справочник инженеров собирается из контрольного распределения бригад,
длительности работ — по четырём профилям норм (переход на официальные нормативы —
правка конфигурации), приоритет — по типу работ («Авария», «Нет линка» → Срочная),
координаты — версионированные геокод-пакеты `data/dataset/geocoded/<регион>.json`.

Явные допущения: бригада = один исполнитель; пробег считается по дорожной сети;
парковка и пропуска включены во время дороги; начать работы до открытия окна нельзя,
позже внутри окна — допустимо; заявки с окном «весь день» планируются на весь
горизонт.

## Стек и стороннее ПО

|Слой|Технологии|
|:---|:---|
|Frontend|React 19, TypeScript (strict), Vite, Tailwind, MapLibre GL, framer-motion|
|Backend|NestJS 11, Node 24 LTS, Prisma ORM, PostgreSQL 17, Zod, MCP|
|Ядро|Python 3.14, OR-Tools 9.15, собственный динамический поиск и гео-контур|
|Инфраструктура|pnpm workspaces, docker compose, node:test / pytest / vitest|

Почему так: MapLibre — открытая карта без платных ключей; PostgreSQL — единое
хранилище бизнес-данных и снимков задачи; OR-Tools остаётся рекомендованным ТЗ
инструментом (генератор кандидатов VRPTW при выключенном прогнозе), а при
включённом прогнозе пробок план считает собственный динамический поиск — время
в пути зависит от момента выезда, и статичная матрица была бы приближением там,
где нужен точный ответ (`docs/solver.md`).

## Структура репозитория

```text
apps/web          — дашборд диспетчера, приложение инженера, клиент (React)
apps/api          — System Layer (NestJS): API, операции, снимки, AI-контур, MCP
packages/shared   — общие wire-типы дашборда (`@lct/shared`)
core/             — Router Core (Python): движок, runtime, гео-контур, предикты
data/             — официальный датасет + геокод-пакеты + метро-граф
demo/             — видео-демо и скриншоты живого стенда
infra/            — docker-compose локального и демо-контура
services/         — вспомогательные сервисы контура: road-api (граф МКАД, OSRM), sys1 (System one стенда)
docs/             — документация подсистем (по-русски)
context/          — рабочие записи команды: ТЗ, QA-сессия с организаторами, решения
```

## Тесты

```bash
pnpm smoke                 # сквозной прогон контура (деструктивный сброс данных)
pnpm test                  # тесты System Layer и дашборда (нужна БД из compose)
pnpm test:regression       # изолированный релизный регресс с нуля (Docker)
python -m pytest core/tests -q   # ядро и golden-планы (из core/.venv)
```

Исторический прогон релизного цикла V1.0 (2026-09-20): api 227/227, web 53/53,
pytest 143 passed, golden-планы зелёные; см. [docs/ci.md](docs/ci.md).

### Мастер локального запуска

В [`launch/`](launch/) доступны GUI и консольные лаунчеры для Windows и Unix
(Linux/macOS): проверка установки и Docker, Full/headless, онлайн/офлайн,
OSRM, порты и получение настроек по PIN. Нужны Python 3.10+ и Docker Compose;
для GUI — Tkinter. Подробнее: [запуск и подготовка офлайн-контура](docs/launcher.md).
