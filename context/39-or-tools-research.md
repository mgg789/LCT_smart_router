## 1. Резюме (TL;DR)

1. OR-Tools — не один солвер, а набор движков. Для Router Core реальных кандидата два: **Routing Solver** (`pywrapcp`, классический VRPTW-движок) и **CP-SAT** (современный SAT/CDCL-движок, в котором с v9.13 появляются специализированные routing-cuts). Остальные модули — вспомогательные или неприменимые.
2. Routing из коробки закрывает ~90% обязательных требований ТЗ: окна, необязательные заявки со штрафами, совместимость инженер↔заявка, открытые маршруты, множественные старты/финишы, warm start. **Не** закрывает из коробки: наш обед («интервал в известной точке, не в дороге»), лексикографические политики, объяснения причин — это надстройки (так и спроектировано в `34` §8, §6, §13.5).
3. CP-SAT структурно **лучше подходит для расписаний и объяснимости**: обед — обычный optional-interval, `sufficient_assumptions_for_infeasibility` даёт системный (не выдуманный) список конфликтующих мягких ограничений, `best_objective_bound` — честная нижняя граница, hints — тёплый старт. Слабое место — моделирование VRPTW целиком вручную (мульти-циркуит + привязка к инженеру) и исторически более низкая скорость на классическом VRPTW.
4. Эмпирика на нашем масштабе (5×10 golden + 200-узловый синтетик): **план Routing байт-в-байт воспроизводим между запусками** на той же машине при неизменном бюджете (недетерминировано только wall-clock поле `solve_ms`); overhead Python-колбэков на 200 узлах / 12 инженерах не повлиял на качество за 3 c.
5. Версия 9.15 (последняя на 15.09.2026 [RN]) имеет известные проблемы wrapper'ов — `SetAllowedVehiclesForIndex` не работает в обёртках [RN, issue #4982]; в `34` §7.5 уже предложен обход через домен `VehicleVar`. Это подтверждает правило: **фиксировать wheel и прогонять smoke-test** (`34` §17.1).

## 3. Routing Solver (`pywrapcp`) — полный разбор по потребностям проекта

Все перечисленные методы подтверждены в стабах установленной версии.

### 3.1. Модель и индексация

- `RoutingIndexManager(num_nodes, num_vehicles, starts, ends)` — отдельные старт/финиш на инженера поддерживаются нативно; это ровно наша схема «старт с текущей точки».
- Три слоя нумерации, которые нельзя смешивать (бизнес-ID → node → routing index) — уже зафиксировано в `34` §7.2; API этому способствует: `manager.IndexToNode()`, `routing.Start(v)` / `routing.End(v)`.
- Открытый маршрут (без возврата в депо) делается фиктивным концом с нулевым транзитом, но **time-transit обязан включать service последней работы** — иначе «бесплатный» конец съедает длительность (`34` §7.3). API не мешает, но и не защищает от этой ошибки — только тест.

### 3.2. Transit-колбэки: четыре способа регистрации и производительность

Подтверждённые регистрации:

- `RegisterTransitCallback(fn)` — классический Python-колбэк `f(from_index, to_index) → int`;
- `RegisterTransitMatrix(matrix)` — **матрица целиком в C++**, без пересечения границы Python на каждую дугу;
- `RegisterUnaryTransitCallback(fn)` / `RegisterUnaryTransitVector(values)` — для транзитов, зависящих только от узла выхода (например, «service предыдущего узла»).

**Эмпирика (наш зонд, §3.15-методика):** полный VRP на 200 заявках × 12 инженерах, GLS, 3 c: Python-колбэк и `RegisterTransitMatrix` дали **одинаковый objective (10788)** и одинаковое время (бюджет выбирается полностью). Вывод: на нашем целевом масштабе (≈100–250 узлов, 10–15 инженеров) overhead Python-колбэка **не доминирует** — бюджет съедает сам поиск. Матричный API всё равно рекомендуется: он исключает целый класс ошибок (замыкание на чужой профиль инженера) и ускорит фазы, чувствительные к числу вызовов (PCI-конструкция, полная propagation). Для time-transit с service (зависит от «откуда») матрица per-vehicle: `N×N` int64 на профиль транспорта — мегабайты, приемлемо.

### 3.3. Измерения (dimensions): время, расстояние, ожидание

- `AddDimension(evaluator_index, slack_max, capacity, fix_start_cumul_to_zero, name)` и варианты `AddDimensionWithVehicleTransits` (per-vehicle колбэки), `AddDimensionWithVehicleCapacity`, `AddDimensionWithVehicleTransitAndCapacity`, `AddDimensionWithCumulDependentVehicleTransitAndCapacity` (транзит зависит от cumul — задел под time-dependent дороги, сейчас не нужен).
- `CumulVar(index)` — **начало обслуживания**, не прибытие; `SlackVar(index)` — ожидание. Окна: `cumul_var.SetRange(a, b)`; ожидание до открытия окна — это slack, отдельная и различимая величина (соответствует контракту `33`: ожидание ≠ дорога).
- `SetCumulVarSoftUpperBound(index, bound, coefficient)` / `SetCumulVarSoftLowerBound(...)` — мягкие границы с линейным штрафом. Применение у нас: «компактность» расписания как **штрафная** добавка, не жёсткое ограничение; либо мягкое предпочтение обеда к середине окна.
- `SetSpanUpperBoundForVehicle`, `SetSpanCostCoefficientForVehicle/All`, `SetGlobalSpanCostCoefficient` — лимит и стоимость длины смены. `GlobalSpan` — это makespan, **не** сумма дорог: не подменять критерий `fast` (уже предупреждение в `34` §7.10).
- Finalizer: `AddVariableMinimizedByFinalizer(var)`, `AddVariableTargetToFinalizer(var, target)` — конкретизация времён после выбора последовательности. Это второй (после чистого early-pass из `34` §13.1) способ получить конкретные `arrival/start/end`; у него есть плюс (делает это сам солвер, согласованно с моделью) и минус (цели финализатора нужно аккуратно выбрать: «минимизировать начала работ» — одна из политик компактности, не нейтральная).

### 3.4. Необязательные заявки: disjunctions

- `routing.AddDisjunction(indices, penalty)` — узел может быть пропущен ценой `penalty`; `ActiveVar(index)` == 0 тогда и только тогда, когда узел не обслужен.
- `AddDisjunction(indices, penalty, max_cardinality=k)` — группа: **не более k** активных из списка. Это точный механизм для «альтернатив обеда» (много узлов-копий — один обед, k=1), как спроектировано в `34` §8.4.
- Отрицательный penalty при ограниченной кардинальности — документированный способ выразить **обязательность группы** («ровно один»); альтернатива — явное ограничение через `solver().Add(...)` на сумму `ActiveVar`. Оба пути упомянуты в `34` §8.4 и должны пройти smoke-test (S1).
- `AddSoftSameVehicleConstraint(indices, cost)` — мягкое «те же машины» для группы узлов: штраф за несовпадение. Ниша для нас: страховочная связка «job ↔ его lunch-копия» (помимо жёсткой implication) или будущие парные заявки. Мягкость означает: нарушается за штраф — для обязательной привязки не годится без обдумывания величины штрафа.

### 3.5. Совместимость инженер↔заявка

- `routing.VehicleVar(index)` — переменная «какой инженер обслуживает узел», домен `[-1] + допустимые`; `-1` = не назначен. Прямое ограничение домена — рабочий способ фильтрации по навыку/транспорту; wrapper-метод `SetAllowedVehiclesForIndex(vehicles, index)` в v9.15 **сломан в обёртках** [RN issue #4982], поэтому доменный обход из `34` §7.5 — правильный путь; проверить в S1 (кейсы: один инженер, несколько, пустое множество, optional-заявка, lunch с единственным владельцем).
- Пустой список допустимых → узел делается неактивным **до** solver с сохранением причины — так неназначение остаётся доказуемым (`NO_SKILL_MATCH`/`NO_TRANSPORT_MATCH` из контракта), а не «поиск не нашёл».

### 3.6. Стоимость: дуги, фиксированные затраты, число задействованных инженеров

- `SetArcCostEvaluatorOfAllVehicles/OfVehicle`, `GetArcCostForVehicle` — отдельный от time колбэк стоимости; требование `34` §7.7 (стоимость ≠ время) выполняется естественно: один evaluator на время, другой на стоимость.
- `SetFixedCostOfVehicle(cost, v)` / `SetFixedCostOfAllVehicles(cost)` — начисляется при непустом маршруте (любой промежуточный узел). Для нас **не годится напрямую**: маршрут «только обед» сделает инженера «использованным», а `engineers_used` считается по job (`34` §7.8). Проектное решение там — начислять стоимость на входе в первый job. Подтверждённые альтернативы, которые стоит знать:
  - `SetVehicleUsedWhenEmpty(is_used, v)` — управляет учётом «использованности» **пустого** маршрута, но не различает тип узла — проблему lunch-only не решает;
  - `SetAmortizedCostFactorsOfAllVehicles/OfVehicle(linear, quadratic)` — линейная+квадратичная амортизация использования машины (ниша: policies типа `compact` с суперлинейным штрафом за флот; пока не нужно, знать о существовании);
  - `SetMaximumNumberOfActiveVehicles(n)` — жёсткий лимит одновременно активных машин (ниша: жёсткая версия `compact`).
- Это ровно тот класс мест, где «готовая фича» имеет чуть другую семантику, чем наша бизнес-метрика, — подтверждает подход `34`: считать K из реальных работ и/или начислять активацию вручную.

### 3.7. Обеды: встроенный break-API и его границы

- `RoutingDimension.SetBreakIntervalsOfVehicle(breaks, vehicle, node_visit_transits)` — существует (подтверждено) и требует `node_visit_transits`: интервалы «разрывают» движение, service при этом ведётся через node_visit_transits. Официальный пример `cvrptw_break.py` показывает паттерн [O8].
- Известные семантические расхождения с нашим обедом (уже собрано в `34` §8.1): допускается размещение break до старта/после конца маршрута; break «висит в воздухе» пути, а не в конкретной физической точке; в Python-обёртке перегрузки исторически капризны. Итог тот же, что в `34`: **break-API — не подмена нашей lunch-модели**; кандидат на сравнение в спайке (S2-бис): наша lunch-node схема против break-интервалов на одинаковом сценарии.

### 3.8. Pickup & Delivery

- `AddPickupAndDelivery(pickup, delivery)` + `SetPickupAndDeliveryPolicyOfAllVehicles/OfVehicle(policy)`; для групп — `AddPickupAndDeliverySets(pickup_disjunction, delivery_disjunction)`.
- Прямого применения в обязательном скоупе нет (нет парных заявок). Ниша на будущее: «взял запчасть на складе → установил у клиента»; также P&D-механика «одинаковый инженер + порядок» иногда используется как альтернативная связка для пар узлов. В v1 не трогаем.

### 3.9. Стратегии первого решения (подтверждённый список, 18)

`UNSET, AUTOMATIC, PATH_CHEAPEST_ARC, PATH_MOST_CONSTRAINED_ARC, EVALUATOR_STRATEGY, SAVINGS, PARALLEL_SAVINGS, SWEEP, CHRISTOFIDES, ALL_UNPERFORMED, BEST_INSERTION, PARALLEL_CHEAPEST_INSERTION, SEQUENTIAL_CHEAPEST_INSERTION, LOCAL_CHEAPEST_INSERTION, LOCAL_CHEAPEST_COST_INSERTION, GLOBAL_CHEAPEST_ARC, LOCAL_CHEAPEST_ARC, FIRST_UNBOUND_MIN_VALUE`

Особо полезные для нас:

- `PARALLEL_CHEAPEST_INSERTION` — старт по умолчанию проекта (`34` §9.1): хорошо работает с окнами и неслужебными узлами;
- `LOCAL_CHEAPEST_COST_INSERTION` — вставка по полной стоимости (дуга+штрафы); кандидат для сравнения;
- `ALL_UNPERFORMED` — «всё пропущено» как старт: **важный аварийный вход** — гарантирует первое решение даже в жёстких инстансах (даёт incumbent, от которого GLS может подниматься); стоит держать в списке fallback'ов холодного пути;
- `FIRST_UNBOUND_MIN_VALUE` — CP-шный старт, полезен при тяжёлых custom-ограничениях, когда вставочные эвристики ломаются;
- тюнинг вставок есть в параметрах: `local_cheapest_insertion_parameters`, `global_cheapest_insertion_first_solution_parameters`, `savings_parameters(neighbors_ratio, max_memory_usage_bytes, add_reverse_arcs, arc_coefficient)`.

### 3.10. Метаэвристики и операторы локального поиска

Подтверждённые метаэвристики (7): `UNSET, AUTOMATIC, GREEDY_DESCENT, GUIDED_LOCAL_SEARCH, SIMULATED_ANNEALING, TABU_SEARCH, GENERIC_TABU_SEARCH`.

- `GUIDED_LOCAL_SEARCH` — дефолт проекта; настраивается: `guided_local_search_lambda_coefficient`, `guided_local_search_penalize_with_vehicle_classes`, `guided_local_search_reset_penalties_on_new_best_solution`;
- `GREEDY_DESCENT` — детерминированный быстрый спуск до локального оптимума; хорош для REPAIR с фиксированным маленьким бюджетом и для воспроизводимых тестов;
- SA/Tabu/GenericTabu — кандидаты для сравнения в бенчмарке, менять дефолт только по результатам S-измерений.

`local_search_operators` — ~41 булев флаг, полный список вытащен из дескриптора; ключевое семейство:

| Группа | Флаги (примеры) | Зачем нам |
|---|---|---|
| Перестановки | `use_relocate`, `use_exchange`, `use_cross`, `use_two_opt`, `use_or_opt`, `use_lin_kernighan`, `use_tsp_opt` | базовое улучшение маршрутов |
| Активность | `use_make_active`, `use_make_inactive`, `use_swap_active(_chain)`, `use_relocate_and_make_active` | **возврат неназначенных заявок в план** — критично для наших U-целей |
| LNS | `use_path_lns`, `use_full_path_lns`, `use_tsp_lns`, `use_inactive_lns` | большие перестройки; `inactive_lns` прямо работает с pool неназначенных |
| Вставочные LNS | `use_global_cheapest_insertion_*_lns`, `use_local_cheapest_insertion_*_lns`, `use_relocate_path_global_cheapest_insertion_insert_unperformed` | повторная вставка пропущенных; `..._lns`-версии обычно самые продуктивные на VRPTW |
| Цепочки | `use_relocate_expensive_chain`, `use_relocate_neighbors`, `use_relocate_subtrip`, `use_exchange_subtrip` | дешёвое перемещение блоков |

Тюнинг плотности соседей: `ls_operator_neighbors_ratio`, `ls_operator_min_neighbors`, `max_swap_active_chain_size`. Составной оператор с бандитом: `use_multi_armed_bandit_concatenate_operators` + коэффициенты exploration/memory. `use_iterated_local_search_parameters` / `use_iterated_local_search` — ILS-режим. Для v1: брать `DefaultRoutingSearchParameters()` и отключать/включать по измерениям, не вслепую.

### 3.11. Параметры поиска (50 полей) — что подтверждено и noteworthy

Полный список полей `RoutingSearchParameters` получен из дескриптора. Помимо упомянутого:

- Бюджеты и лимиты: `time_limit`, `lns_time_limit`, `solution_limit`, `secondary_ls_time_limit_ratio`, `improvement_limit_parameters(improvement_rate_coefficient, improvement_rate_solutions_distance)` — **ранний стоп по плато улучшений**: кандидат на «время до первого пригодного кандидата» (контракт 33 требует публикацию, а не бесконечное ожидание);
- `number_of_solutions_to_collect` — **коллекция нескольких решений за один solve**: прямой механизм candidate pool (`34` §10.5) без ручного перезапуска;
- `AddAtSolutionCallback(callback, track_unchecked_neighbors=False)` — колбэк на каждое улучшение: сбор incumbents, кооперативная отмена (выброс исключения/остановка), телеметрия. Это же — точка интеграции для «стоп по внешнему поколению» из Runtime (`34` §12.5);
- Гибрид с CP-SAT **внутри Routing**: `use_cp`, `use_cp_sat`, `use_generalized_cp_sat`, `fallback_to_cp_sat_size_threshold`, `sat_parameters` (вложенные SatParameters!), `report_intermediate_cp_sat_solutions`, `continuous_scheduling_solver`, `mixed_integer_scheduling_solver`. То есть Routing v9.15 уже умеет подсовывать CP-SAT для подзадач (например, точная фаза вставки/расписания) — факт, который сближает В-1 и В-3 (см. раздел 7);
- `use_full_propagation` — полная propagation (дефолт проекта, `34` §9.1); `use_depth_first_search`, `use_unfiltered_first_solution_strategy` — альтернативные режимы;
- Логи: `log_search`, `log_tag`, `log_cost_scaling_factor`, `log_cost_offset` — диагностический дамп (в `34` уже зафиксировано «log_search=true только в диагностике»).

### 3.12. Статусы и жизненный цикл

Подтверждённый enum `RoutingSearchStatus` (8): `ROUTING_NOT_SOLVED, ROUTING_SUCCESS, ROUTING_PARTIAL_SUCCESS_LOCAL_OPTIMUM_NOT_REACHED, ROUTING_FAIL, ROUTING_FAIL_TIMEOUT, ROUTING_INVALID, ROUTING_INFEASIBLE, ROUTING_OPTIMAL`.

Тонкости, важные для честного контракта (`33` §8: `status`/`is_usable`/`errors`):

- `ROUTING_SUCCESS` = найдено решение в заданном бюджете, **не** оптимальность; `ROUTING_OPTIMAL` — доказанный оптимум (редко при GLS; достижим на малых инстансах и полезен как тест-оракул);
- `ROUTING_FAIL_TIMEOUT` = время вышло **без единого решения** — это не «infeasible»; в выход превращается в «поиск не дал кандидата» + fallback-логика, не в ошибку данных;
- `ROUTING_INFEASIBLE` — солвер доказал невозможность (ценность: для нашей диагностики, но доверять только при корректной модели);
- `ROUTING_INVALID` — модель собрана некорректно (наша ошибка, а не данные пользователя) — отдельный Diagnostic-код.

### 3.13. Warm start / seed

Подтверждённая цепочка: `CloseModelWithParameters(params)` → `ReadAssignmentFromRoutes(routes, ignore_inactive_indices)` → `SolveFromAssignmentWithParameters(assignment, params[, solutions])`. Есть и `SolveFromAssignmentsWithParameters(assignments, ...)` — **множественные** стартовые assignments (candidate pool в качестве стартов!). Правила соответствия ID→индексы, восстановление обедов «по смыслу engineer+anchor», ограничение `ignore_inactive_indices` — уже зафиксированы в `34` §9.3–9.4; API им полностью соответствует. Дополнительно: перечитывание seed **после** изменения модели блоками (§6.6 контракта) — тот же механизм.

### 3.14. Детерминизм: механика + эмпирика

Механика: Routing-поиск однопоточен; детерминизм обеспечивается одинаковой последовательностью операций. Время — wall-clock: `time_limit` прерывает GLS в произвольной итерации → теоретически результат зависит от скорости машины/нагрузки. `solution_limit` делает стоп воспроизводимым по числу итераций.

**Опыт (методика воспроизводима):** golden mini (5×10, seed 42), `solve_task` legacy-ядра (PCI+GLS, `use_full_propagation=True`), 3 прогона на этой машине:

| Конфигурация | Хэш плана **без** `solve_ms` | Хэш с `solve_ms` |
|---|---|---|
| `time_limit=1500ms`, без `solution_limit` | **одинаково 3/3** | 3 разных |
| `time_limit=1500ms`, `solution_limit=100` | **одинаково 3/3** | 3 разных |
| `time_limit=4000ms`, `solution_limit=100` | **одинаково 3/3** | 3 разных |

Выводы: (а) содержимое плана на этой машине воспроизводимо даже при чисто временном бюджете (на мини-инстансе ЛНС-траектория сходится к одному и тому же решению); (б) поле `solve_ms` недетерминировано по определению — **оно не должно входить ни в golden-diff, ни в hash результата** (для `input_hash` контракта это уже факт к учёту: хэшировать нормализованный снимок, не вывод); (в) гарантия для других машин/нагрузки **не следует** из этого опыта — cross-machine check включён в спайки (S4), golden-гейт должен бежать на фиксированной конфигурации.

### 3.15. Методика опытов (для воспроизведения)

1. Детерминизм: `sys.path.insert(0, "context/legacy_code")`, `generate("mini", 42)` → `solve_task(...)` × 3 → JSON `solution_to_dict` (± поле `solve_ms`) → SHA-1. 
2. Колбэки: 200 случайных точек, 12 машин, матрица манхэттен×10, PCI+GLS 3000 мс; два прогона — `RegisterTransitCallback` (Python) vs `RegisterTransitMatrix` → objective/время.

## 4. CP-SAT — полный разбор

### 4.1. Архитектура и статусы

CP-SAT — SAT-солвер (CDCL) с LP-релаксацией, presolve, портфелем LNS-воркеров и точной целочисленной арифметикой. Статусы (подтверждены): `UNKNOWN, MODEL_INVALID, FEASIBLE, INFEASIBLE, OPTIMAL`. Ключевое отличие от Routing: **доказуемые** результаты — `OPTIMAL` даёт доказательство, `INFEASIBLE` — доказательство невозможности, а `best_objective_bound` в ответе позволяет честно сказать «лучше чем X быть не может, но найдено Y» (для `33`/Reasons это разница между `constraint_check` и `calculation_outcome`).

### 4.2. Примитивы для маршрутизации (все подтверждены в `cp_model.py`)

- `add_circuit(arcs)` — гамильтонов цикл на узлах с литералами дуг; `add_multiple_circuit(arcs)` — **набор независимых циклов**: стандартная основа мульти-VRP (каждый инженер — цикл «старт → его работы → конец», конец можно соединить со стартом). Необязательная заявка = литерал «узел вне маршрута» (само-петля);
- `new_interval_var(start, size, end, name)` / `new_optional_interval_var(..., presence_literal, name)` — интервалы с опциональностью: **окна, работы, обеды и ожидания — декларативно**;
- `add_no_overlap(intervals)` — непересечение (смена инженера: работы + обед); `add_no_overlap_2d`, `add_cumulative` — на будущее (бригады/ресурсы);
- `add_exactly_one([...])` / `add_at_most_one([...])` — «ровно один исход» (обязательный обед; выбор инженера), `add_implication(a, b)`, литералы с `OnlyEnforceIf` — реефикация любых бизнес-правил;
- `minimize(linear_expr)` / `maximize` — линейная int64 цель (наша PolicySpec компилируется прямо, без «фокус-факторов» Routing-стоимости);
- `add_decision_strategy` — управляемый порядок ветвления (опционально).

Схема VRPTW на CP-SAT: для каждой дуги (i, j) булева `x[i,j]`; `add_multiple_circuit` задаёт порядок; время: `start_j >= start_i + service_i + travel(i,j) - M*(1 - x[i,j])` (big-M можно избежать через `OnlyEnforceIf`); назначение инженера — литерал на дуге или отдельные `vehicle[i]` переменные с импликациями. Это заметно больше работы, чем RoutingModel, — и это главный ценовой фактор В-3.

### 4.3. Обед и расписание в CP-SAT — естественная модель

Наш обед («единственный интервал длительности L в окне [w1, w2], в точке anchor, не перекрывая работы») в CP-SAT — это `new_optional_interval_var` + `add_no_overlap` со сменой инженера + литералы «обед следует за конкретной работой» только если хотим привязку к точке anchor. Никаких lunch-node хаков, отрицательных penalty и хрупких implications. Для `required` — `add_exactly_one` по вариантам размещения; конфликт = `INFEASIBLE` с assumptions (см. ниже).

### 4.4. Объяснимость: assumptions API (уникальное преимущество)

- `model.add_assumption(literal)` — пометить литералы «мягкими предположениями»;
- В `CpSolverResponse` (поля подтверждены): `sufficient_assumptions_for_infeasibility` — **минимальный поднабор предположений, достаточный для невыполнимости**. Если каждый `required`-обед / окно / участие инженера — это assumption, при `INFEASIBLE` система возвращает конкретный список «вот эти требования конфликтуют». Для нашей модели причин это единственный движок в OR-Tools, который даёт **систематическое** объяснение невыполнимости (в Routing — только `ROUTING_INFEASIBLE` без причин).
- Ограничение честности: список достаточный, но не минимальный-уникальный; его нужно переводить в `Reason.facts` аккуратно (что уже норма контракта: не приписывать поискам доказательств).

### 4.5. Hints и repair

- `model.add_hint(var, value)` + SatParameters: `repair_hint`, `hint_conflict_limit`, `fix_variables_to_their_hinted_value`, `debug_crash_on_bad_hint`, `polarity_exploit_ls_hints` — полноценный механизм тёплого старта, включая **починку частично устаревшего** подсказа (это ровно наш REPAIR: старый план как hint, где несуществующие заявки просто не фиксируются);
- `CpSolverSolutionCallback` — сбор incumbents; `response.additional_solutions` — набор решений при `number_of_solutions_to_collect`.

### 4.6. Routing-cuts: CP-SAT целенаправленно усиливают для маршрутизации

В SatParameters подтверждены специализированные параметры: `routing_cut_dp_effort`, `routing_cut_max_infeasible_path_length`, `routing_cut_subset_size_for_*` — с v9.13 CP-SAT получил «deep improvements to routing cuts» [RN]: подсечение (cuts) по субциклам/ёмкости/переходам, которые раньше были слабым местом на VRP. Плюс LNS-портфель (`use_lns`, `use_lns_only`, `use_rins_lns`, `use_lb_relax_lns`, `diversify_lns_params`) — аналог GLS-улучшений, но распределённый по воркерам.

### 4.7. Детерминизм и параллелизм

- `num_workers` (=1 — строго детерминированный однопоточный режим), `random_seed`;
- Детерминированный параллелизм: `interleave_search` + `interleave_batch_size` + `max_num_deterministic_batches` / `max_deterministic_time` — поиск по «детерминированным батчам», а не по wall-clock; `deterministic_time` возвращается в ответе;
- Ответ содержит `wall_time`, `user_time`, `deterministic_time`, `num_conflicts`, `num_branches`, `num_restarts`, `num_lp_iterations`, `gap_integral`, `solve_log` — готовая диагностика для дампов.
- Практическое следствие: CP-SAT даёт **конфигурируемый** уровень воспроизводимости (вплоть до детерминированного времени), чего Routing не предлагает вовсе (только «однопоточность + одинаковый бюджет»). Для golden-гейта и расследования инцидентов это серьёзный аргумент (см. В-3).

### 4.8. Масштаб параметров

`SatParameters` — 303 поля; для нас релевантные группы: workers/детерминизм (выше), hints, LNS-портфель, routing-cuts, общие cuts (`add_*_cuts`), логирование (`log_search_progress`, `log_to_stdout`). Правило то же: брать дефолты, менять по измерениям, ничего не «улучшать» вслепую.

## 7. ВАРИАНТЫ интеграции OR-Tools (не решения!)

> **Важно.** Ниже — **варианты**, подготовленные для сравнения и спайков. Это не решения и не договорённости: выбор фиксируется только строкой D-№ в `29-decision-log.md` по итогам раздела 8. Все варианты спроектированы так, чтобы **внешний контракт `33` не менялся** — отличается только начинка Engine. Опорный проект `34` = В-1 (он остаётся референсом, пока тимлид не примет иное).

### В-1. «Routing-монолит» — прямая реализация опорного проекта engine_contract_v2

**Суть.** `RoutingModel` с per-vehicle time/travel/distance измерениями; необязательные заявки — disjunctions с политическими штрафами; совместимость — домен `VehicleVar`; лексикография — скаляризация с вычисленными снизу-вверх весами (§6.5) либо блоки с закреплением достигнутых уровней (§6.6); обед — lunch-node альтернативы с implication `active(L) ⇒ next(anchor)=L` (§8); проходы REVALIDATE/REPAIR/COLD; warm start через `ReadAssignmentFromRoutes`; candidate pool — `AddAtSolutionCallback` + `number_of_solutions_to_collect`; PCI → GLS.

**Сильные стороны.** Полное соответствие уже согласованному техническому проекту (не нужно переврачивать `34`); самая быстрая реализация «до первого main» из всех вариантов; зрелый VRPTW-движок с богатыми эвристиками вставки; legacy-ядро уже доказало, что подход работает на golden-инстансе; в `sat_parameters` есть встроенная возможность подмешивать CP-SAT без смены архитектуры.

**Слабые стороны / риски.** Обед — самая хрупкая часть: custom implications под GLS/LNS требуют отдельного интеграционного теста (S2), и это главный технический риск варианта; нет системных объяснений infeasible (`ROUTING_INFEASIBLE` без причин); детерминизм — только эмпирический (wall-clock бюджет, §3.14), cross-machine требует дисциплины golden-гейта; int64-компиляция лексикографии — инженерно тонкое место с обязательными проверками диапазонов.

**Когда выбирать.** S1 и S2 зелёные, приоритет — скорость выхода на рабочий Engine по уже согласованному проекту.

### В-2. «Routing + многопроходная лексикография»

**Суть.** Та же модель, но политика выполняется **серией solve**: уровень 1 (неназначенные urgent) → фиксируем достигнутое `Uu ≤ u1*` custom-ограничением; уровень 2 (неназначенные всего) → `U ≤ u2*`; … последний уровень — travel/distance/K. Один общий бюджет, делится по уровням; между уровнями — warm start тем же assignment; candidate pool собирается со всех уровней.

**Сильные стороны.** Нет гигантских коэффициентов и риска int64 — каждый проход оптимизирует одну простую величину; поиск на простых целях обычно стабильнее; значения каждого уровня — готовые факты для `Reason.facts` и для диагностики «достигнутые уровни» из §6.6; естественно деградирует по бюджету (закончили на уровне 2 — всё равно валидный кандидат).

**Слабые стороны / риски.** Несколько построений модели = накладные расходы; закрепление уровней сужает пространство последнего уровня (качество travel может быть хуже, чем у скаляризации за тот же бюджет); больше кода coordinator'а; edge-case: уровень доказуемо недостижим до конца бюджета — нужен явный протокол «частичной иерархии» (он у `34` §6.6 уже описан в терминах блоков).

**Когда выбирать.** Если S-бенчмарк покажет, что скаляризация В-1 теряет качество/стабильность на реальном масштабе, или если для объяснений нужна прозрачная поуровневая иерархия.

### В-3. «CP-SAT кастомная модель»

**Суть.** Полная модель на CP-SAT: `add_multiple_circuit` по узлам «заявки + старты (+ виртуальные концы)», дуговые литералы с привязкой к инженеру; заявки — узлы с self-loop литералом (optional); время — импликации через `OnlyEnforceIf` по дугам; смена/работы/обед — optional intervals + `add_no_overlap`; `required`-обед — `add_exactly_one`; политика — слои `minimize` с закреплением bound'ов; warm start — `add_hint` из старого плана + `repair_hint`; детерминизм — `num_workers=1` (или `interleave_search`); объяснения — assumptions на soft-требованиях → `sufficient_assumptions_for_infeasibility`.

**Сильные стороны.** Лучший в OR-Tools профиль объяснимости (единственный системный источник «почему невыполнимо» — прямо в нашу модель `Reason`); честные `best_objective_bound` (можно публично говорить «найдено Y, лучше X быть не может»); обед/расписания — нативные интервалы, без самого хрупкого механизма В-1; конфигурируемый детерминизм вплоть до детерминированного времени — идеален для golden-гейта; движок активно развивается именно в routing-сторону (routing-cuts v9.13+, LNS-портфель) [RN].

**Слабые стороны / риски.** Самая дорогая реализация: VRPTW на circuit-литералах пишется и отлаживается руками (мульти-циркуит + консистентность инженера — главная сложность); на классическом VRPTW исторически медленнее Routing — routing-cuts сократили разрыв, но **на нашем инстансе не измерено** (S3); нет вставочных эвристик «из коробки» (PCI/GLS) — первое решение строит сам солвер/портфель; производительность callback'ов решения в Python имеет известные предупреждения [RN v9.11].

**Когда выбирать.** Если S3 покажет сопоставимое качество/время на нашем масштабе и приоритет — объяснимость infeasible + детерминизм; либо как долгосрочная платформа (движок активно развивается).

### В-4. «Гибрид: Routing строит, CP-SAT проверяет и чинит»

**Суть.** Разделение по сильным сторонам. Routing отвечает за назначение+порядок (модель В-1, но **без** lunch-nodes: проще и надёжнее). Далее два применения CP-SAT: (а) **тайминг**: на фиксированных последовательностях CP-SAT с optional intervals решает точное расписание + обеды (и это же — надёжный REVALIDATE-механизм: фиксируем next-переменные, просим feasibility, при INFEASIBLE получаем assumptions-причину); (б) **repair**: при REPAIR Routing даёт порядок, CP-SAT восстанавливает выполнимость с hints.

**Сильные стороны.** Каждый движок на своей задаче; модель Routing упрощается радикально (нет хрупких lunch-implications — S2 выпадает); обед и объяснения невыполнимости «в этой последовательности» — от CP-SAT нативно; лексикография остаётся в компараторе кандидатов (чистый Python), её не нужно компилировать ни в один движок.

**Слабые стороны / риски.** Два движка в одном Engine: зависимости, время прогрева, двойная семантика стоимости (риск расхождения «стоимость Routing ≠ оценка CP-SAT» — нужен один Owner расчёта метрик); больше движущихся частей, чем в В-1/В-3; бюджет делится; при «CP-SAT не смог починить» нужен протокол возврата в Routing (цикл).

**Когда выбирать.** Если S2 (lunch-nodes под локальным поиском) провален, а полноценный В-3 слишком дорог; если REVALIDATE-причины «почему порядок больше не работает» нужны в доказуемой форме.

### В-5. «Минимум OR-Tools: конструктор кандидатов + валидация»

**Суть.** OR-Tools используется только как **генератор начальных решений** (PCI/LCI, опционально короткий GLS-прогон) и/или на малых инстансах `ROUTING_OPTIMAL`; вся политика, лексикография, обеды и расписания — в чистом детерминированном Python (FixedOrderScheduler и early-pass, которые в любом варианте нужны для baseline/REVALIDATE). Причины — только доказуемые (элигибельность, проверка порядка, валидатор).

**Сильные стороны.** Максимальный контроль и объяснимость (каждая причина доказуема по построению); тривиальный детерминизм; минимум поверхности зависимости от библиотеки; самый быстрый путь к корректному, честному (пусть не оптимальному) MVP.

**Слабые стороны / риски.** Качество планов ограничено (нет сильного улучшения — на 100+ заявках и 10–15 инженерах чистая вставка заметно проигрывает GLS); «экономия против baseline» — главный маркетинговый показатель демо — будет скромнее; риск: потом всё равно придётся достраивать улучшение (В-1) — двойная работа.

**Когда выбирать.** Как осознанный минимум под жёсткий дедлайн; как гарантированный fallback-слой в любом другом варианте (уровень «baseline + вставка» должен существовать в любом случае по `34` §14.4).

## 9. Известные ограничения, риски и анти-варианты

**Ограничения версии 9.15 [RN]:** сломанный в обёртках `SetAllowedVehiclesForIndex` (#4982) — обход доменом, тест в S1; `solver.status_name()` TypeError в CP-SAT (#4985); смена сигнатуры callback'а `CpSolver.Solve()` (#4988) — при обновлении версии читать release notes обязательно; замедление поиска при тяжёлых Python-колбэках CP-SAT (предупреждение со времён v9.11) — держать колбэки тонкими.

**Открытый вопрос без первоисточника:** публичные заявления команды OR-Tools о «maintenance mode» Routing-библиотеки мне подтвердить не удалось (сеть в этой сессии нестабильна). Объективные признаки траектории: Routing в v9.15 активно улучшается (перформанс, search events, переработанные примеры) [RN], но CP-SAT целенаправленно усиливается в routing (cuts v9.13, routing-параметры внутри RoutingSearchParameters) [RN]. Практический вывод не зависит от разрешения вопроса: фиксировать wheel, опираться на документированное API, не использовать недокументированные поля — и учитывать, что «долгосрочная платформа» из раздела 2 — это CP-SAT.

**Анти-варианты (не рассматривать для v1):** `math_opt`/`linear_solver`/`pdlp`/`bop` — LP/MIP-мир, не для VRPTW; `packing`/`set_cover`/`scheduling` — чужие задачи или экспериментальные интерфейсы; `min_cost_flow`/`linear_sum_assignment` как **ядро** планирования (порядок не моделируют — только вспомогательные оценки); LLM внутри solver'а — прямо запрещено D-11; самописный метаэвристический движок поверх CP (дублирование Routing без преимуществ).
