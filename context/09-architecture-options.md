# Архитектура: варианты и рекомендация под команду и хакатон

> Назначение: зафиксировать целевую архитектуру до старта, чтобы все 5 человек не изобретали свои слои. Принцип: минимальное количество движущихся частей, всё в одном docker-compose, полностью работает офлайн.

---

## 1. Компонентная схема (рекомендуемая)

```
┌────────────────────────────  Browser  ────────────────────────────┐
│  React SPA: Диспетчерская консоль                                 │
│  [Карта MapLibre] [Таймлайн по инженерам] [Панель заявки/причин]  │
│  [Дашборд метрик]  состояние через TanStack Query + WebSocket/SSE │
└───────────────▲───────────────────────────────▲───────────────────┘
        REST + SSE (события, дельты плана)      │
┌───────────────┴───────────────────────────────┴───────────────────┐
│  Backend API (Node/Fastify или FastAPI)                           │
│  • CRUD заявок/инженеров/оборудования      • импорт датасета ТЗ   │
│  • геокодинг + кэш                         • матрица (OSRM + кэш) │
│  • план-версии (snapshots) + события       • метрики плана        │
│  • симулятор дня (события по расписанию)                          │
└───────▲──────────────────────────────────▲────────────────────────┘
        │ job: build/replan plan           │ OSRM /table /route
┌───────┴────────────┐            ┌────────┴────────┐   ┌───────────┐
│  Solver Worker     │            │  OSRM (docker)  │   │ Postgres  │
│  OR-Tools/Timefold │◄──────────►│  данные города  │   │ + кэш     │
│  → Plan + Reasons  │  матрица   │  .osm.pbf       │   │ матриц    │
└────────────────────┘            └─────────────────┘   └───────────┘
```

Почему так:
- **3 процесса** (API, solver-worker, OSRM) + Postgres — потолок сложности, который 5 человек отладят за неделю без греха. Всё это поднимается одним `docker compose up`.
- Solver — отдельный процесс: API не блокируется, перепланирование изолировано, солвер можно переписать (OR-Tools→Timefold) не трогая остальное.
- Матрица расстояний кэшируется (по координатным парам за день почти не меняется) — демо не зависит от живого OSRM.

## 2. Выбор стека — варианты

| Слой | Вариант A (рекоменд.) | Вариант B | Критерий выбора |
|---|---|---|---|
| Frontend | React + TS + Vite + Tailwind + MapLibre GL + framer-motion + TanStack Query | Next.js | Нужна SPA-консоль, не SSR. Вариант B только если все знают Next |
| Backend | **Fastify (Node/TS)** — один язык с фронтом, типы шарятся | FastAPI (Python) | Если 2/3 бэкендеров за Python — берём B; шаринг типов TS↔TS экономит больше всего вайбкодинга |
| Solver | Python + OR-Tools (fastapi-обёртка / queue worker) | Timefold Python | См. `05-solvers-libraries.md`, решить в день 0 |
| БД | PostgreSQL (достаточно JSONB) | SQLite | Postgres лучше для PostGIS-запросов «заявки рядом», но SQLite допустим если старт из файла |
| Realtime | SSE (односторонний поток событий) | WebSocket | SSE проще и надёжнее: сервер → клиент событий плана |
| Auth | Фейковый/единственный пользователь | — | На хакатоне не тратим время |
| Деплой | docker-compose на одной VM/ноуте | bare metal | Целостность и переносимость |

**Рекомендация:** A, с одним уточнением: если 2+ человека уверенно пишут Python-бэкенд — backend на FastAPI, но контракты описать OpenAPI и генерировать TS-клиент. Единственная жёсткая конвенция: **единый `types.ts`/schema как источник правды**, чтобы вайбкодинг пяти человек не разошёлся.

## 3. Ключевые API-контракты (черновик)

```
POST /api/plans/build          {date, weights?}      → Plan (async job, ~1-2s)
POST /api/plans/{id}/events    {type: "new_request"|"cancel"|"delay"|"engineer_down", payload}
                              → новый Plan + Diff (авто-перепланирование, п.4 ТЗ)
GET  /api/plans/{id}                                 → план: инженеры, маршруты, визиты, причины
GET  /api/plans/{id}/diff?against={prevId}             → дельта для подсветки
POST /api/requests            {address, window, work_type, ...}
PATCH /api/visits/{id}        {engineerId?, position?} — ручная правка (drag&drop)
GET  /api/metrics?planId=                           → SLA, загрузка, пробег
GET  /api/stream                                    → SSE: plan.updated, request.added, alert.*
POST /api/simulation/start     {speed}  — симулятор дня для демо
```

Diff-объект — первоклассная сущность API (moved/added/removed/changed-time + причина каждого изменения), именно он питает UX перепланирования.

## 4. Поток «новая заявка» (п.4 ТЗ) энд-ту-энд

1. UI: форма/ввод → `POST /api/requests`.
2. API: геокод → валидация совместимости (навыки/оборудование/транспорт есть ли вообще кандидаты) → событие в очередь.
3. Solver-worker: строит вход (матрица из кэша) → solve (≤1.5 c) → Plan v+1 + Diff + Reasons.
4. API: сохраняет snapshot, публикует `plan.updated` в SSE.
5. UI: анимация дельты (кто сменился/сдвинулся), тост «План пересобран за 0.8 c · 2 заявки передвинуты · SLA-рисков: 0», панель причин обновлена.

Целевой бюджет ощущаемой задержки: **< 2 c от сабмита до анимации** — выше этого «автопилот» теряет магию.

## 5. Структура монорепо (для вайбкодинга — важна дисциплина)

```
lct-fsm/
  apps/web/          # React SPA
  apps/api/          # backend
  apps/solver/       # python: model, reasons, tests на golden-датасете
  packages/shared/   # общие типы/схемы (zod/pydantic — из одного источника)
  infra/docker-compose.yml, seed/, scripts/
  data/              # датасеты: provided/, fallback/
```

Правила вайбкодинга (в корень репо CLAUDE.md/AGENTS.md):
- Контракты правит один человек; остальные не трогают.
- Каждый сервис имеет `seed` и `smoke`-тест (build plan на фиксированном датасете = известные метрики).
- UI-компоненты только из дизайн-системы (см. `10-ux-ui-design.md`), новых токенов не плодим.
- Никаких изменений схемы БД без миграции, хоть на хакатоне.

## 6. Неинфраструктурные решения, которые стоит принять заранее

- Часовой пояс: всё в локальном времени города (не UTC) — демонстрация дней не пересекает зоны.
- Хранение матрицы: пары → минуты, ключ `rounded(lat*1e5,lon*1e5)`; кэш в БД + in-memory.
- Планы неизменяемы (immutable snapshots), текущий = указатель на последнюю версию → бесплатная история и undo.
- Все причины — структурированный JSON (код фактора + параметры), UI переводит в человеческий текст. Никогда не хранить «причину» строкой на бэке.

## 7. План Б, если инфра подводит

- OSRM не поднялся → заранее сгенерированный кэш матриц для демо-датасета (см. `15-risks-pitfalls.md`).
- Solver нестабилен → «жадный+LNS» фолбэк, всегда доступный в коде.
- Нет интернета на сцене → полностью локальный стек (тайлы карты — офлайн-рendер векторного файла города или растровый бэкап; см. `10`).
