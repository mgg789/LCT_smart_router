# Онбординг агента и готовый AGENTS.md

> Назначение: любой агент (Codex/Cursor/ZCode/Qwen), подключённый к репозиторию, должен за 15 минут выйти на продуктивную работу. Часть 1 — онбординг-последовательность. Часть 2 — готовый текст для `AGENTS.md`/`CLAUDE.md` в корне репозитория (скопировать как есть).

---

## 1. Онбординг-последовательность нового агента

1. **Прочитай (в этом порядке):** `context/00-README.md` → `context/26-case-source.md` (дословное ТЗ) → `context/01-task-analysis.md` → `context/16-stack-and-plan.md` → свой файл зоны (см. §3).
2. **Проверь окружение:** Node 20+, pnpm, Python 3.11+, Docker; `pnpm i`; `docker compose -f infra/docker-compose.yml up -d`; `pnpm seed`; смоук из `context/27` §10 должен быть зелёным.
3. **Найди свой контекст:** таблица ролей `context/16` §2; контракты — `context/14` §3 и `packages/shared`; дизайн-система — `context/10`; правила вайбкодинга — `context/09` §5.
4. **Сверься с доской задач:** возьми задачу своей зоны; если задачи нет — спроси тимлида; не расширяй скоуп сам (анти-идеи: `context/12`).
5. **Работай по циклу:** ветка → код → смоук зелёный → скриншот в PR (если UI) → мерж после ревью владельца зоны.
6. **Обновляй контекст:** если реальность разошлась с файлом контекста — правь файл контекста в том же PR.

## 2. Готовый текст AGENTS.md (в корень репозитория)

```markdown
# AGENTS.md — правила работы в репозитории LCT Smart Router

## Продукт
Веб-сервис интеллектуального планирования маршрутов выездных инженеров
(кейс Билайн Бизнес на хакатоне ЛЦТ 2026). Официальное ТЗ дословно:
context/26-case-source.md. Стратегия: не «много фич», а максимально
продуманное, целостное, красивое приложение; объяснимость решений — ядро.

## Структура
- apps/web       — React SPA (Vite, TS, Tailwind, MapLibre, framer-motion)
- apps/api       — backend (Fastify или FastAPI — см. context/09 §2)
- apps/solver    — Python + OR-Tools (модель, причины, метрики)
- packages/shared— единственный источник контрактов (zod/pydantic)
- data/          — датасеты (provided от организаторов, seed fallback, aux слои города)
- context/       — исследовательский контекст проекта (читай 00-README)

## Команды
- pnpm dev            — поднять web+api
- docker compose -f infra/docker-compose.yml up -d   — osrm+postgres+solver
- pnpm seed           — залить демо-датасет
- pnpm smoke          — смоук-контур (context/27 §10), обязателен перед мержем
- pnpm demo:reset     — восстановить демо-сценарий (детерминированный seed)

## Жёсткие правила (не обсуждаем)
1. Контракты в packages/shared меняет только владелец интеграции. Не добавляй
   поля «про запас» — типы = документация.
2. Планы иммутабельны (версии-снимки). Ничего не мутируй «на месте».
3. Времена — локальные для города, целые минуты в солвере, секунды внутри OR-Tools.
4. Каждая «причина» решения — структурированный JSON с кодом фактора
   (context/11 §3), никогда не строка, сгенерированная «на глаз».
5. LLM не принимает решений и не меняет план: только текст↔структура,
   с валидацией и ручным фолбэком (context/08 §4).
6. Каждый внешний вызов (OSRM/2GIS/data.mos.ru/Overpass/Open-Meteo) кэшируется;
   демо-контур обязан работать без интернета (context/15 §4).
7. Детерминизм: фикс. seed солвера; PR, меняющий golden-план без объяснения,
   не мержится.
8. UI-компоненты — только из дизайн-системы (context/10); новые токены — через
   дизайнера. Никаких инлайн-цветов.
9. Новый функционал обязан закрывать пункт ТЗ (context/26 §2) или входить в
   скоуп context/12; всё остальное — roadmap.
10. Коммиты малые, main всегда демо-пригоден («сцена = main»).

## Definition of Done
- смоук зелёный; для UI — скриншот в PR и прохождение чек-листа полировки
  context/10 §7; для солвера — метрики golden-плана в допуске;
  контекст-файл обновлён, если поведение изменилось.
```
