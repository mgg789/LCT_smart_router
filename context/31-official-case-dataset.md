## 1. Главная новость: постановка УПРОЩЕНА

Кейс адаптирован «под студенческую команду и ограниченное время хакатона». Прямая цитата:
> «Главная идея: не нужно создавать промышленную корпоративную систему. Важно показать **работающий алгоритм, понятный интерфейс и убедительную демонстрацию**.»

Что это меняет для нас:
- Наша стратегия «продуманный и красивый инструмент» — по-прежнему рабочая (15% «Эффективность и удобство» + 10% «Презентация»), но ядро оценки — **алгоритм (30%) и корректность ограничений**, а не богатство фич.
- Всё «промышленное» из нашего контекста (объяснимость уровня L3, дельта-анимации, what-if слайдеры) остаётся как усилители, но MVP-чеклист теперь узкий и чётко определён (§3).
- Убраны из обязательных: оборудование (теперь «дополнительное усложнение»), возврат в стартовую точку, мульти-событийность (нужно ОДНО событие перепланирования на выбор).

## 2. Официальные критерии оценки (вес!)

| Критерий | Вес | Что оценивается |
|---|---|---|
| Техническая реализация | **30%** | Работоспособность алгоритма, корректный учёт ограничений, качество кода |
| Подход команды | **25%** | Понимание задачи, разумные допущения, распределение работы, завершённость сценария |
| Соответствие задаче | **20%** | Распределение, маршруты на карте, перепланирование, объяснение результата |
| Эффективность и удобство | **15%** | Кол-во исполнителей, пробег, понятность интерфейса, **сравнение с базовым вариантом** |
| Презентация | **10%** | Ясный рассказ, live-демо или видео, ответы на вопросы |

Особое внимание экспертов (5 вопросов из ТЗ):
1. Все ли обязательные ограничения **реально проверяются** алгоритмом (не декларируются)?
2. Можно ли понять результат **без изучения кода**?
3. Корректно ли решение реагирует на изменение в течение дня?
4. Есть ли **сравнение с базовым планированием** по двум обязательным метрикам?
5. Можно ли воспроизвести запуск **по README**?

## 3. Обязательный MVP (наш чек-лист)

1. Загрузка тестовых данных из CSV/JSON или встроенный демо-набор.
2. Распределение заявок между инженерами (по квалификации и доступности).
3. Порядок посещения адресов для каждого инженера.
4. Маршруты и точки заявок на карте.
5. Краткая информация по плану: кто, куда, в какое время.
6. Перепланирование после **одного события на выбор**: срочная заявка / отмена / инженер недоступен.
7. Объяснение человеческим языком: почему заявка у этого инженера, какие ограничения учтены, почему такой маршрут.

**Обязательные ограничения (ровно 3):**
| Группа | Правило |
|---|---|
| Квалификация | требуемый навык заявки ∈ навыки инженера |
| Время | работа + время в пути укладывается в смену; начало работы внутри окна заявки |
| Ресурс | требуемый тип транспорта заявки = тип транспорта инженера (если указан) |

Оборудование — опционально. Если заявка не назначена — **явная причина человеческим языком** (нет исполнителя на время / нет навыка / нет транспорта / не влезает в окно или смену).

**Две обязательные метрики:**
1. Количество задействованных исполнителей (минимизировать).
2. Пробег по каждому исполнителю и суммарный.

**Базовый вариант для сравнения (определён ТЗ!):** заявки по порядку поступления → первому подходящему инженеру по порядку во входных данных; порядок посещения = порядок назначения; никакой оптимизации. Наш «жадный режим» из `12` (B5) теперь **обязательная функция**, а не усилитель — и раз наш датасет сконструирован так, что FIFO даёт менее эффективный план, разрыв с базой будет виден.

**Допустимо (из ТЗ):** готовая библиотека (OR-Tools упомянут прямо в технологиях!), простая эвристика, своя логика. Математический оптимум доказывать не нужно. Доп. критерии (время в пути, макс. выполненных) — по желанию.

## 4. Справочники и формат данных (из ТЗ)

- **Навыки (3):** 1. Локальные работы 2. Работы на подключение и дозаказы 3. Аварийные работы. У заявки — ровно один требуемый навык; у инженера — 1–3 навыка.
- **Транспорт (4):** Автомобиль, Пешеход, Велосипед, Общественный транспорт. У инженера — один тип.
- **Приоритет:** Обычная / Срочная (срочная выше при перепланировании).
- **Единицы:** время HH:MM, длительности/пути — минуты, расстояние — км, координаты — lat/lon.
- **MVP-маршрут:** старт от точки инженера, возврат не требуется.
- **Допущения разрешены:** расстояние можно считать упрощённо (гаверсинус × коэффициент) с описанием допущения — наша OSRM-связка (`06`) останется преимуществом, но не требованием.

## 5. Требования к сдаче

**Промежуточная:** репозиторий с кодом; чтение тестовых данных; первая версия распределения; краткий план оставшихся работ и проблем.
**Финальная (артефакты):** рабочий прототип (запуск по инструкции) · алгоритм (3 группы ограничений + один сценарий перепланирования) · визуализация на карте · объяснения (назначение + причина неназначения) · метрики с сравнением с базой · README + презентация + код.
**Сопроводительная документация:** README с запуском; схема решения (интерфейс/алгоритм/данные); логика оптимизации, метрики, ограничения; описание тестового набора (поля, единицы, справочники); известные ограничения и идеи развития.
**Демо:** 5–7 минут, live или видео, сценарий из 7 шагов: загрузка данных → автопланирование → карта → объяснение одной заявки → событие → перестройка с показом изменений → **сравнение с базовым по метрикам**.
**Аппаратно:** ноутбук + интернет. Не требуется: FSM-платформа, мобильное приложение, авторизация, Kafka, микросервисы, тысячи заявок. Публичный стенд приветствуется.

## 6. Датасет: структура и статистика

Расположение: `data/Датасет/обезличено/Обезличивание/` (CSV, **кодировка cp1251**, разделитель `;`). Два слоя: «Синтетические данные» (входные заявки) и «Контрольное распределение» (эталон от организаторов). Все даты — 17.08.2026 (один рабочий день).

| Регион | Заявок (непустых) | Районов | Типов работ HD | Бригад в контроле | Без бригады |
|---|---|---|---|---|---|
| Восток | 67 | 9 | 15 | 13 | 2 |
| Юго-восток | 84 | 11 | 15 | 12 | 0 |
| Югоцентр | 57 | 12 | 14 | 11 | 0 |
| **Итого** | **208** | 32 | ~19 уникальных | 36 | 2 |

Прим.: ТЗ обещало «10–15 инженеров и ≤100 заявок» — по факту 208 заявок на 3 региона; вероятно, регион выбирается как сценарий. В MVP поддержать выбор файла/региона.

### 6.1 Колонки

**Синтетические данные:** `Заявка` (id) · `Тип заявки BK` (=«Подключение») · `Тип заявки HD` (тип работ, словарь ниже) · `Начало` / `Окончание` (окно, `17.08.2026 HH:MM`) · `Район` · `Адрес` (строка; бывает без квартиры) · `Подключение` (только Восток: FMC/FTTB) · `Гигабитное подключение` (Да/Нет).

**Контрольное распределение** = те же строки + `Статус BK` (Отправлена/Не отправлена) + `Бригада` (назначение; «Бригада Фамилия» или «Фамилия Имя»). Восток: 2 заявки без бригады (пример неназначенных!). ID заявок в контроле **другие** (обезличены иначе) — сопоставление позиционное (проверено: совпадение по адресу/окну/типу ≈100%; контроль = синтетика минус 1 строка в регионе).

### 6.2 Аномалии данных (обработать в импортере)

1. Пустые строки (по 1–2 на файл) — фильтровать.
2. Пустое окно (`''`/`''`) — заявка без окна: трактовать как «весь день» или исключить с объяснением.
3. Окно `0:01–23:59` (Юго-восток) — «весь день».
4. Пустой `Район` в нескольких строках.
5. Дробные адреса вида `д. 128 к 5`, `1А` — для геокодинга.
6. Кодировка cp1251, `;`-разделитель, русские заголовки — importer обязан декодировать явно.

### 6.3 Чего нет в датасете (синтезируем сами — это разрешено ТЗ)

- **Справочник инженеров** — главный пробел. Решение: **инженеры = уникальные бригады из контрольного распределения** (11–13 на регион, реальные ФИО обезличены) с назначением навыков (1–3) и типа транспорта так, чтобы: все 3 навыка встречались, комбинации разные, все 4 типа транспорта были; заявки без бригады в контроле (Восток, 2 шт.) должны остаться неназначаемыми в базовом сценарии — с нашей причиной.
- **Длительность работ** — нет колонки. Решение: карта «тип работ → длительность» (например: замена приставки/роутера 30–40 мин, конвергенция 45–60, подключение 60–90, авария/кабель 60–120) — фиксируем допущение в README и контексте.
- **Приоритет** — нет колонки. Решение: «Авария», «Нет линка» → Срочная; остальные → Обычная.
- **Событие перепланирования** — ТЗ обещало «одно событие», в архиве его нет. Готовим сами по формату из ТЗ §2.4 (тип, время, id) — у нас уже есть симулятор (`13` §2).
- **Координаты** — только адреса; геокодинг заранее (стратегия `06` §5), для ~200 адресов это один прогон.

### 6.4 Глубокий анализ (второй проход)

**Скрытые адреса офисов (важнейшая находка).** «Пустая» последняя строка каждого файла — это не мусор, а подпись `Адрес Офиса` (адрес в колонке `Тип заявки BK`):
- Восток: `г. Москва, ул Юных Ленинцев, д 83с4` (метро Волгоградский проспект)
- Юго-восток: `г. Москва, ул Бирюлёвская, д 1с1`
- Югоцентр: `г. Москва, проезд Симферопольский, д.7`

Это закрывает вопрос депо: **все инженеры региона стартуют из одного офиса** (ТЗ: «маршрут начинается в стартовой точке инженера»).

**Контрольное распределение — это реальный «грязный» план, а не эталон допустимости:**
- У 8–9 бригад из 11–13 окна заявок **перекрываются** — эталон физически невыполним при последовательном обходе. Нельзя брать его как ориентир флаг-проверки; можно — как «реальность против нашего плана».
- Есть статусы-исходы: `Выполнена / Просрочена / Отменена / В работе / В пути / Отправлена / Не отправлена`. **Просрочено реально: Восток — 4, Юго-восток — 6 (из них 3 в дальней Кашире), Югоцентр — 0.** Готовый слайд: «реальный план просрочил 4–6 заявок в день, наш — 0 при полном охвате».
- `Отменена`: 6/10/5 — **натуральные кандидаты на событие «отмена заявки»** в перепланировании (берём одну из них).
- Загрузка бригад неравномерна: Юго-восток — от 1 до 14 заявок на бригаду (иллюстрация «неравномерной загрузки» из кейса).
- Территориальность полу-жёсткая: в среднем 1.8–2.4 района на бригаду, 3–7 бригад работают строго в одном районе.

**Дальний Юго-восток.** Регион вылезает за МКАД: Домодедово (11 заявок, ~17 км от офиса), **Кашира (9) и Ступино (2) — 90–115 км от офиса**. Плюс нестандартные префиксы адресов: `МО` (9), `г.Город Москва` (9), `обл.Московская область` (1), `Москва Бирюлевская ул. д. 44` без запятых. Импортер обязан нормализовать префиксы; OSRM обязателен для честного пробега (гаверсинус занизит десятки км). Две заявки Каширы с окнами 12:00–16:00 при старте из Бирюлёво — заведомо жёсткая задача (дорога ~1,5 ч в одну сторону): вероятный источник реальных просрочек и хороший материал для объяснений «почему не назначено/почему так рано выезд».

**Повторные адреса (батчинг).** 10 адресов с двумя заявками; в Юго-востоке 5 пар — в **одном и том же окне** (например, `Домодедово, ул.Зеленая, д. 85`). Оптимизатор должен склеивать такие в бэк-ту-бэк визиты — легкая демонстрация умного планирования.

**Пиковая скученность.** Вдвое больше заявок, чем бригад, попадает в пиковые 2-часовые окна: Восток 15/12:00 при 12 бригадах, Юго-восток 18/12:00, Югоцентр 11/16:00 при 11 бригадах — с учётом переездов слот дефицитный, FIFO-жадность на этом ломается (ТЗ обещало «конфликт, при котором последовательное распределение даёт менее эффективный план» — вот он).

**Восток: 2 «Не отправлена» без бригады** = заявки, которые даже не были отправлены в работу (позиции 0 и 31, `Конвергенция` 20:00–22:00 и `Дозаказ оборудования` 18:00–20:00). В нашем базовом сценарии — кандидаты на «не назначена» с объяснением, либо на «срочную» в перепланировании.

**Флаги.** `Гигабитное подключение`: только Восток, всего 2 из 67. `FMC` 32 / `FTTB` 2 / пусто 33 (только Восток) — аналитический балласт, на планирование не влияет. `Тип заявки BK` = «Подключение» везде — тоже балласт.

**Вывод для импортера (обновляет §9.1):** парсить офисную строку → `depots` по регионам; фильтровать по `Заявка.isdigit()`; нормализовать префиксы адресов; контрол-файлы парсить ради бригад/статусов, а не допустимости.

### 6.5 Маппинг «тип работ HD → навык» (черновик, утвердить в задаче)

| Навык (по ТЗ) | Типы работ HD |
|---|---|
| Аварийные работы | Авария, Нет линка, Разрывы, IP-адрес 169..., Рост ошибок на порту, Низкая скорость |
| Работы на подключение и дозаказы | Заявка на подключение, Заказ подключения/Дозаказ оборудования, Дозаказ оборудования, Конвергенция абонента, Переключение на Гбит/с, Роутер. Замена, ТВ/TVE/ENT. Замена приставки |
| Локальные работы | Работа с кабелем, Мониторинг, Информация, TVE/ENT. Другие ошибки, прочее |

`Гигабитное подключение=Да` → доп. маркер (например, требует навыка «Переключение на Гбит/с» внутри подключения) — упрощаем: влияет только на длительность. `FMC/FTTB` — только аналитика.

## 8. Корректировки нашего скоупа (сверка с `12`/`25`)

| Было | Стало |
|---|---|
| B5 «жадный режим» — усилитель | **Обязателен**: базовый вариант определён ТЗ, сравнение по 2 метрикам — критерий «Эффективность 15%» |
| Объяснимость L1–L3 | L1 (почему назначение + ограничения + неназначение) — **обязательна**; L2/L3 — усилители |
| Оборудование | Опционально (наши матрицы остаются как «сверх ТЗ») |
| Несколько событий перепланирования | Достаточно одного (у нас симулятор — остаётся усилителем) |
| Обработка 100 заявок | Фактически до 86 на регион (208 суммарно) — солвер справляется легко |
| Число исполнителей не критерием | **Количество задействованных исполнителей — обязательная метрика** (учитывать в целевой функции: штраф за каждого задействованного) |

Целевая функция корректируется: `min задействованных исполнителей (сильно) → min суммарного пробега` (+ SLA/окна как hard-ограничения). Балансировка загрузки уходит из обязательных (не противоречит, но метрики ТЗ — число людей и пробег).

## 9. Что делаем прямо сейчас (в порядке приоритета)

1. Импортер CSV (cp1251/`;`) → канонический JSON по `14` §3 + чистка аномалий (§6.2) + маппинг навыков (§6.4) + синтез справочника инженеров из бригад (§6.3) + геокодинг адресов заранее.
2. Солвер: 3 обязательных ограничения + целевая функция «min людей → min пробега» + режим «базовый FIFO» + причины назначения/неназначения.
3. UI: карта + список «кто/куда/когда» + карточка заявки с объяснением + неназначенные с причинами + переключатель «оптимум vs база» с метриками рядом.
4. Одно перепланирование (событие из ТЗ) + наглядный показ изменений.
5. README (запуск по инструкции — критерий!), схема решения, описание данных и допущений.
6. Презентация на официальном шаблоне + демо 5–7 минут по 7 шагам ТЗ.

**Итого на QA-сессию (ответов в материалах нет):**

1. Обмен оборудованием между инженерами в течение дня (вопрос #9) — нужна ли механика?
