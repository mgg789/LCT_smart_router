# INDEX — карта контекста проекта

**LCT Smart Router** — сервис интеллектуального планирования маршрутов выездных инженеров (кейс «Билайн Бизнес», ЛЦТ 2026). Стратегия: не «много фич», а продуманный, целостный, красивый продукт с объяснимостью как ядром доверия.

**Как пользоваться:** `AGENTS.md` → этот файл → нужный документ. Не знаешь, где что лежит, — ищи здесь. Перед созданием нового файла — прочитай [§ Правила](#правила-создания-и-изменения-файлов).

**Приоритет источников по ТЗ:** `18-official-case-dataset.md` (официальное ТЗ, получено 15.09) > `26-case-source.md` (дословный текст кейса) > архив `01` (наш разбор до открытия кейса).

## Статусные поправки к старым файлам

Канон — комплект v14 (§2 этого индекса). В файлах §3–4 при чтении держи в голове:

1. **Цели оптимизации** — не «SLA > баланс > пробег» (D-2 старая редакция), а политика диспетчера; default `fast` (32 §6.2); официальные цели — 18 §2.
2. **Время** — Unix-time целые секунды везде (33 §4); локальные даты только на границах ввода (старые «минуты/локальный город» в 09/14 — архив).
3. **Транспорт** — 4 профиля: авто / пешеход / велосипед / общественный (18 §6.3); не только car.
4. **Возврат в депо не требуется**; маршруты открытые (18, 34 §5).
5. **Оборудование** — опциональное усложнение, не ядро (18 §3/§7).
6. **Обеды** — полноценная модель v14 (`lunch_taken`, required, окно — 32 §8); старые нормативы «45 мин 12:00–14:30» (21) — не утверждены.
7. **Чаты в скоупе** (32 §5.6, §6.3); «не делаем мессенджер» из 10 — снято.
8. **MVP** — 7 пунктов 18 §3; статусы «в скоупе: да» в 20–25 не пережили упрощения ТЗ.
9. **Датасет** — официальный: 208 заявок, 3 региона, 17.08.2026 (18 §6); «80 заявок / 10 инженеров» из старых файлов — fallback-генератор, теперь запаска.
10. **Подложка карты** — D-6 (Яндекс free → CARTO) пересматривается: приоритет уточнить при детализации UI, проверить ToS.
11. **Бэкенд-фреймворк** — открыт заново (D-8): «Node+Nest» в 32 §19 — запись с доски, не выбор; AGENTS.md сохраняет Fastify|FastAPI до решения тимлида.

## Правила создания и изменения файлов

1. **Сначала поиск.** Перед созданием файла найди место темы в этом индексе. Если тема уже покрыта — **обновляй существующий файл**, а не плоди новый. Дублирование формулировок запрещено: в одном месте канон, в других — ссылка вида «см. 32 §N».
2. **Гармонизация.** Новый/изменённый файл не должен противоречить `32` (канон системы), `29` (решениям) и `18` (ТЗ/скоупу). Расходится — либо исправь, либо явно пометь статус («проект», «требует решения тимлида»), либо заведи строку в `29`.
3. **Имя.** `NN-короткая_тема.md`: номер — следующий свободный (сейчас **42**), кебаб/снейк без пробелов; новая редакция целого документа — суффикс `_vN`, старая уходит в `archive/` с баннером.
4. **Индекс.** Файл добавляется в этот INDEX **тем же коммитом** — файл без записи в INDEX считается не существующим.
5. **Устаревание.** Файл больше не актуален → `archive/` + баннер «что читать вместо» + правка строки в INDEX. Не удаляй файлы, на которые ссылаются цитаты D-№.
6. **Статусы.** В тексте различай: «Согласовано» (решено пользователем), «Проект реализации» (инженерная конкретизация), «Требует решения». Не выдавай проект за принятое.
