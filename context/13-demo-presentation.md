# Стратегия демо и презентации

> Назначение: демо решает исход хакатона сильнее кода. Здесь: сценарий выступления, репетиционный план, подготовка отказоустойчивости, готовые ответы на вопросы жюри.

---

## 1. Структура выступления (базово 7 минут — подстроить под регламент ЛЦТ)

| Мин | Блок | Суть | На экране |
|---|---|---|---|
| 0:00–0:45 | Боль | «Диспетчер каждое утро 40 минут раскладывает 80 заявок по 10 инженерам в Excel. К 11:30 приходит срочная заявка — и день рассыпается: 4 опоздания, 2 переноса, один инженер перегружен вдвое» | Слайд с «ручным» планом (нарочно кривой) |
| 0:45–1:15 | Решение одним взглядом | «Сервис строит оптимальный план дня за секунду, сам перестраивает его при событиях и объясняет каждое решение» | Скрин/живой главный экран |
| 1:15–4:30 | **Живое демо** (сценарий ниже) | | Продукт |
| 4:30–5:30 | Как это работает | Иерархия целей (SLA>баланс>путь), regret insertion + локальный поиск, перепланирование <2 c, объяснения rule-based. **1 слайд схемы, без кода** | Слайд |
| 5:30–6:15 | Метрики | Сравнение «ручной vs наш»: пробег −23%, опоздания 4→0, загрузка ровнее; перепланирование 0.8 c | Слайд с цифрами из продукта |
| 6:15–7:00 | Развитие + команда | Roadmap: интеграция с CRM, ML-оценка длительностей, мобильный вид инженера | Слайд |

Правило: **продукт — главный слайд**. Слайдов ≤ 7, текста мало, цифры крупные.

## 2. Живой сценарий демо (репетируемый, seed-данные D2)

1. **Утро.** Загружен датасет (80 заявок, 10 инженеров). Жму «Построить план» → секунда → карта+таймлайн расцветают. Показываю панель метрик: «0 нарушений SLA, загрузка ровная».
2. **Доверие.** Кликаю «проблемную» заявку → панель «Почему так»: навыки, ближайший маршрут, альтернативы («Петров дал бы +18 мин»). Открываю «всех кандидатов» — таблица причин. *Здесь жюри видит п.5 ТЗ.*
3. **Событие.** (Симуляция 11:30 или кнопка) «Срочная заявка: видеонаблюдение, окно 12:00–14:00, VIP». Форма с LLM-вводом (или ручная — запасной вариант). Отправляю.
4. **Магия.** «Пересборка… 0.8 c» → дельта-анимация: 2 заявки переданы, 3 сдвинуты, риски 2→1. Открываю ленту событий — всё задокументировано. *Здесь п.4 ТЗ.*
5. **Человечность.** Перетаскиваю одну заявку вручную — вижу превью последствий до отпускания, отпускаю, план обновляется, показываю undo.
6. **Честность.** Переключаю «жадный режим» — сравнение планов: −23% пути. (Опционально: what-if слайдер весов.)
7. **Контрольный.** «Инженер Сидоров сломался» → перепланирование — день спасён. Конец.

Резервные ходы (если спросили/осталось время): симулятор дня со scrubber'ом, тёмная тема, вид инженера.

## 3. Распределение ролей на выступлении

- **Спикер** — лучший рассказчик (не обязательно автор кода): ведёт сценарий по секундам.
- **Оператор** — за ноутбуком, кликает по команде спикера (двойное управление страхует от «промаха» на сцене).
- Остальные — в зале: фиксируют вопросы, готовы подхватить Q&A по своей зоне (алгоритм/архитектура/дизайн).
- Если формат позволяет видеовставку — 15-секундный клип «день из жизни диспетчера» как заставка.

## 4. Отказоустойчивость (грим-план)

- **Локальный стенд:** всё поднимается на ноутбуке без интернета (OSRM-кэш, офлайн-тайлы или снимки экрана, локальный LLM). Демонстрационная машина = личный ноутбук + HDMI-переходники заранее.
- **Видео-бэкап:** полная запись демо-сценария (та же последовательность, 3–4 мин) — включаем при необратимом сбое, продолжаем рассказ без паузы.
- **Прогретое состояние:** перед выходом открыть вкладки, прогреть солвер (первый solve всегда дольше), отключить уведомления ОС, курсор крупный.
- **Seed-фабрика:** демо-сценарий восстанавливается одной командой (`pnpm demo:reset`) — если что-то пошло не так, 10 секунд и мы снова на сценарии.
- Правило: **на сцене не показываем ничего, что не отрепетировано ≥3 раз.**

## 5. Подготовка ответов на вопросы жюри (Q&A-заготовки)

- *«Почему не машинное обучение?»* — На таком масштабе классическая метаэвристика даёт окно 1–3% от оптимума за миллисекунды, объяснима и детерминированна; ML-нужен там, где есть история: предсказание длительностей и задержек — это в roadmap (см. `08`). Мы сознательно строим честное ядро + объяснимость.
- *«Насколько ваш план оптимальный?»* — Метрика разрыва с жадным базлайном и (опц.) с HGS-эталоном на нашем датасете; на малом масштабе локальный поиск сходится близко к оптимуму.
- *«А если заявок 1000?»* — Архитектура солвера масштабируется (кластеризация по районам → декомпозиция, матрица считается батчами), UI сгруппирует по районам. Сейчас задача Билайна — десятки.
- *«Пробки?»* — Time-dependent коэффициенты по часам; реальные потоковые данные (Яндекс/TomTom) юридически недоступны третьим лицам в РФ — roadmap договорной интеграции.
- *«Чем отличается от Route4Me/OptimoRoute?»* — Объяснимость каждого решения (их нет), дельта-перепланирование как первоклассный UX, локализация и правила Билайна, открытость. (см. `03`)
- *«Сколько стоит внедрить?»* — Готовы посчитать: сервис + гео-данные, без лицензионных платежей (open-source стек), TCO ниже SaaS.
- *«Почему SLA важнее минимизации пути?»* — Опоздание = перенос = повторный выезд = двойная стоимость; пробег дешевле. Формула штрафов — слайд.

- [ ] Видео-бэкап записан и проверен на машине выступления.
- [ ] `demo:reset` отрабатывает < 30 c; seed соответствует рассказу.
- [ ] Все экраны продукта прошли чек-лист полировки (`10-ux-ui-design.md` §7).
- [ ] Слайды: ≤7, цифры совпадают с реальными метриками продукта.
- [ ] Репетиция Q&A: каждый член команды отвечает на 5 вопросов по своей зоне.
- [ ] Ноутбук: питание, HDMI/VGA/USB-C, отключены обновления, второй профиль браузера чист.
