# AI и внешний SMTP — концепция модулей v3

**Редакция:** 15 сентября 2026 года.  
**Основа:** `ai_smtp_concept_v2.md`, сохранённые границы `system_concept_v14.md` и ответы пользователя на D1–D4.  
**Статус:** D1–D4 закрыты: собственный статус инженера, вызов человека-диспетчера, единое подтверждение email перед чатом и отсутствие письма о задержке внутри клиентского окна. По разрешению пользователя выбран один код входа без повторного кода при отправке заявки в действующей сессии; содержание заявки подтверждается отдельно. Технические детали, ещё не согласованные, отмечены предложениями. Реализация, подключение к серверам и интеграционные испытания не выполнялись.

Этот документ заменяет v2 по двум модулям. Он не изменяет алгоритм Router и не переопределяет его входной сектор. Последние решения по AI имеют приоритет над более широкими предварительными перечнями инструментов и прежней схемой email-подтверждения в v14; остальные документы в этой операции не перезаписываются.

## 1. Общая граница

**AI** получает сообщение, доверенный ролевой контекст и разрешённые знания, вызывает API модели и запрашивает системные действия. **System Layer** определяет права, исполняет tools, проверяет подтверждения, хранит факты и формирует письма. **Внешний SMTP** принимает готовые письма, хранит собственную очередь и отправляет их дальше.

```text
Клиент / инженер / диспетчер
          ↓
System Layer: сессия, роль, квота, живые данные
          ↕
AI-gateway ↔ AI runtime ↔ официальное API DeepSeek
                   ↓
            разрешённые tools
                   ↓
System Layer: проверки → бизнес-операция → результат
                   ↓ при наличии почтового события
          готовое письмо и код от sys
                   ↓
             SMTP-gateway
                   ↓
       TLS через VPN / защищённый резерв
                   ↓
     отдельный SMTP-сервер и его очередь
```

AI не подключается к SMTP напрямую. Почтовые учётные данные, одноразовые коды и сессионные токены не включаются в промпт. Успешное изменение данных, успешный ответ модели и принятие письма внешним сервером — три отдельных результата.

## 2. Принятые решения AI

| Область | Решение |
|---|---|
| Модель | DeepSeek‑V4.1‑Flash через официальное API DeepSeek |
| Клиент API | OpenAI SDK; Agents SDK допустим после проверки стабильности конкретной интеграции |
| Роли | Клиентский, инженерный и диспетчерский агенты с разными наборами tools |
| Вход | Сначала email и код входа, затем доступ к AI-чату; гостевой разговор не используется |
| Расход | Жёсткая суточная квота на подтверждённый email; конкретные значения ещё не заданы |
| Отправка клиентской заявки | Email уже подтверждён кодом при входе; содержание заявки подтверждается в чате, второй email-код в действующей сессии не требуется |
| Инженер | `change_status_to(status: 0 \| 1)` меняет доступность только инженера текущей сессии; `0` — offline с кнопкой подтверждения, `1` — online без дополнительной кнопки |
| Диспетчер | `read-only` без записи; в `fix` полный набор системных действий своей роли, показ действий в чате и возможность остановки |
| Контекст | История и актуальные данные через sys; документация через `search_documentation()` |
| Векторные знания | Три раздельных сегмента; клиенту и инженеру — только свой, диспетчеру — все три |
| UI | Текст; текст с кнопкой; текст с кнопкой и отменой; текст с подтверждением |
| Сбой | Ограниченные retries → настроенный fallback → панель «AI сейчас недоступен» |
| Позвать оператора | `call_dispatch_helper()` обращается к человеку-диспетчеру для ответа вместо AI; это не вызов другого агента |

### 2.1. Модель и API-идентификатор

Название, выбранное пользователем, — **DeepSeek‑V4.1‑Flash**. Из v2 сохранена конфигурационная запись `model="deepseek-flash"` с адресом `https://api.deepseek.com` и ссылкой [W1]. В этой редакции доступность модели и соответствие алиаса повторно не проверялись; перед подключением их требуется проверить на официальном API. Выбранная пользователем модель не заменяется другим семейством без отдельного решения.

```text
provider: DeepSeek official API
model_label: DeepSeek-V4.1-Flash
model_id: deepseek-flash
base_url: https://api.deepseek.com
sdk: OpenAI SDK
agents_sdk: только после проверки интеграции
fallback_profile: ещё не выбран
```

Идентификатор хранится в конфигурации. Перед развёртыванием его доступность проверяется коротким тестом на реальном API; смена провайдером содержимого алиаса не считается проверенной нами автоматически.

**Проект реализации:** один AI runtime, три ролевых профиля, общий адаптер провайдера. Не нужны три отдельные реализации агентного цикла. Выбор профиля делает sys по доверенному контексту сессии, а не модель по словам пользователя.

Для первого подключения предлагается Chat Completions через OpenAI SDK. Agents SDK не объявляется ни гарантированно стабильным, ни непригодным: его проверяют с выбранной моделью, tools, историей и отменой. Официальный Agents SDK допускает настройку совместимого endpoint и выбор Chat Completions вместо Responses. [W2]

Проверка должна включать обычный текст, последовательность нескольких tools, сохранение истории, поток при его использовании, отмену, ошибки, квоты и переход на резерв. Внешний экспорт трассировок предлагается отключить до отдельного решения о получателях данных; внутренний журнал sys остаётся.

**Особенность адаптера:** при включённом thinking-режиме с tools документация DeepSeek требует сохранять и передавать обратно соответствующее `reasoning_content`. Это служебная часть протокола, не обязательный текст интерфейса. Поддержка такого обмена входит в проверку SDK. [W3]

Режим thinking и его бюджет пока не выбраны. История для человека и техническое состояние provider-диалога не обязаны совпадать: компактное резюме для UI не должно ломать обязательную последовательность сообщений провайдера. Публичный журнал действий строится по реально выполняемым tools, не по скрытым рассуждениям.

## 3. Email до AI и подтверждение отправки заявки

### 3.1. Доступ к чату — согласовано

```text
Email
→ код входа от System Layer через SMTP
→ проверка кода / создание или получение клиентской учётной записи
→ авторизованная сессия
→ проверка суточной квоты email
→ AI-чат или обычный интерфейс
```

Сам ввод адреса без проверки кода не открывает платный AI. Клиент не получает чужие данные, просто назвав их email в сообщении. Вход инженера и диспетчера использует их существующую роль; подтверждённый email сам по себе не назначает привилегированную роль.

Одноразовый код вводится в обычный экран авторизации, не в контекст модели. Отказ от дополнительных полей внутри AI-сообщения не отменяет системную форму ввода кода.

### 3.2. Единое email-подтверждение — выбранный вариант после D3

Пользователь разрешил объединить проверки вместо двух обязательных email-кодов. Для проекта выбран следующий порядок: **email подтверждается один раз при входе до AI-чата; в действующей подтверждённой сессии отдельный код отправки заявки не запрашивается**.

Это не повторное использование одноразового кода. Sys проверяет и погашает код входа, создаёт сессию; дальнейшая авторизация опирается на сессию. Подтверждённый адрес связывает клиента, заявку и дневной бюджет. Новый чат не сбрасывает квоту.

Подтверждение адреса и согласие с содержанием заявки — разные действия. После сбора сведений клиент видит итоговый текст и явно подтверждает отправку. Для этого используется уже согласованный тип `text_confirmation`, а не второе письмо с кодом.

```text
Email → код входа → подтверждённая сессия
  → AI собирает данные
  → create_request(data) подготавливает собственную заявку в sys
  → итоговое текстовое сообщение и подтверждение отправки
  → sys проверяет сессию и подтверждённую версию данных
  → заявка становится pending и доступной для планирования
  → письмо «Заявка отправлена, её обработают»
  → после принятого назначения — письмо «Мастер назначен и приедет»
```

**Техническая реализация подтверждения:** `create_request(data)` может вернуть подготовленную sys-операцию с `operation_id` и состоянием `awaiting_confirmation`. Кнопка подтверждает эту операцию через sys, не через дополнительный tool чтения кода. Промежуточная подготовка не является активной заявкой в Router.

Подтверждение связывается с текущими данными заявки и авторизованным клиентом. При существенной правке после показа итогового текста следует повторно показать и подтвердить новую версию — без нового email-кода. Повтор одного и того же действия не создаёт второй заявки.

Если сессия истекла или требуется вход под другим email, sys снова выполняет обычную авторизацию. Это новый код входа, а не обязательный второй код на каждую заявку. Сохранившийся текст в чате сам по себе не доказывает наличие действующей сессии.

Имена промежуточных бизнес-статусов и срок сессии детализируются в System Layer / auth-engine. `create_request(data)` не подтверждает факт назначения мастера и не меняет маршрут напрямую.

## 4. Точные ролевые инструменты

### 4.1. Клиентский агент

| Имя, заданное пользователем | Назначение и граница |
|---|---|
| `create_request(data)` | Подготовить собственную заявку в подтверждённой сессии; активная отправка — после подтверждения содержания в чате, без второго email-кода |
| `search_documentation()` | Найти разрешённые клиенту справочные материалы в клиентском сегменте |
| `call_dispatch_helper()` | Позвать человека-диспетчера для ответа в текущем клиентском чате вместо AI |

На этом этапе не добавляются отдельные tools отмены, переноса, записи в чужую заявку или изменения маршрута. При необходимости разрешённые данные своей заявки sys передаёт как контекст обращения; дополнительные инструменты чтения не считаются уже запрошенными.

Нормативная длительность, требуемый навык и транспорт формируются системой по согласованным правилам. AI помогает собрать пользовательские сведения, но не имеет права произвольно придумать технические нормативы ради завершения вызова.

### 4.2. Инженерный агент

| Имя, заданное пользователем | Назначение и граница |
|---|---|
| `change_status_to(status: 0 \| 1)` | Изменить рабочую доступность инженера текущей сессии: `1` — online, `0` — offline |
| `call_dispatch_helper()` | Позвать человека-диспетчера для ответа в текущем инженерном чате вместо AI |
| `search_documentation()` | Поиск в инженерном сегменте |

**D1 подтверждён:** один аргумент `status: 0 | 1`, где `1` — online, `0` — offline. Инструмент меняет статус только **инженера текущей авторизованной сессии**, а не диспетчера и не другого сотрудника.

ID действующего инженера определяет sys по сессии; модель не выбирает произвольный субъект операции. `change_status_to` не изменяет состояние сети, статус заявки или факт её выполнения.

Для подтверждаемой операции sys показывает текст с целевым действием и кнопками подтверждения / отмены. Без подтверждения не выполняется `offline`. Для `online` отдельная кнопка не требуется по принятому правилу, если операция однозначна и допустима.

Прежняя идея произвольных AI-tools прибытия, начала, завершения и создания обращений заменена последним конкретным списком пользователя. **Сами фактические отметки в Engineer App сохраняются**, но не выдаются агенту как дополнительные tools без отдельного решения. `change_status_to` не превращается в универсальную запись любых состояний заявки.

### 4.3. Диспетчерский агент

Пользователь определил категории, а не окончательные имена методов:

| Категория | Содержание |
|---|---|
| Чтение | Разрешённые диспетчеру заявки, инженеры, применённый план, alerts, политики, связанные данные |
| Объяснение | Системные основания решений, метрики и сравнения, разбор проблем |
| Изменения | Политики и доступные диспетчеру запросы изменения через System Layer |
| Документация | `search_documentation()` с доступом ко всем трём сегментам |

**`read-only`:** tools записи недоступны на сервере независимо от ответа модели.

**`fix`:** полный набор бизнес-действий, предоставленных текущей роли диспетчера через sys. Для обычных разрешённых операций не добавляется обязательное подтверждение каждой записи. Действия выводятся в чат, работа агента может быть остановлена.

«Полный доступ» не означает SQL / shell, раскрытие секретов, доступ от имени другого пользователя или прямую запись в память Router. Это тот же системный контур прав, что у диспетчера. Перечень реальных sys-операций, включая доступ к экстренному режиму и технической настройке, синхронизируется с будущим контрактом System Layer, а не изобретается отдельно AI-модулем.

Возможность конкретной операции подтверждается capability роли. Если у роли есть разрешённая операция, `fix` не должен вводить произвольный дополнительный запрет только потому, что действие выполняет агент. Если capability ещё не определена, само слово `fix` не создаёт её автоматически.

## 5. Исполнение tools, журнал и остановка

**Принято:** диспетчер видит действия и может остановить агент. **Ниже — предложенная техническая семантика**, необходимая для однозначной реализации.

Для каждого изменяющего tool sys создаёт операцию с устойчивым ID. Сначала публикуется понятное описание намерения, затем состояние исполнения, затем фактический результат. Эти сообщения опираются на инструментальный журнал, а не только на обещание модели.

```text
Агент: «Меняю политику на fast»
Sys: операция подготовлена
Sys: операция выполнена / отклонена / остановлена до применения
Агент: объяснение только с учётом полученного результата
```

Кнопка «Остановить» привязана к конкретному `run_id`. После её принятия runtime прекращает планировать новые model/tool-вызовы и отменяет ещё не начатые действия данного запуска. Перед бизнес-записью sys повторно проверяет текущие права, режим и сигнал остановки.

Если операция уже завершила фиксацию данных, остановка не делает вид, что её не было. Она останавливает последующие действия; отмена уже совершённого изменения — отдельная разрешённая бизнес-операция. Для выполняющейся операции интерфейс дожидается достоверного исхода или показывает неопределённость, а не ложное «всё отменено».

**Предложение для простоты:** изменяющие tools одного запуска выполняются последовательно. Чтения можно объединять, если сохраняются квоты и права. Остановка run прекращает его ещё не начатые model/tool-вызовы и fallback. Уже созданное обращение к человеку-диспетчеру не отменяется автоматически остановкой AI: это отдельная системная сущность, а не вложенный model-run.

Повтор после сетевого сбоя возвращает сохранённый результат той же sys-операции. Идентификатор model tool-call не заменяет бизнес-идемпотентность: при смене модели вызов может получить другой технический ID.

Если `fix` переключили в `read-only`, последующие записи блокируются независимо от того, когда модель получила старый каталог tools. Уже выполненные действия остаются в журнале.

## 6. `call_dispatch_helper()` — позвать человека-диспетчера

**D2 согласован:** инструмент вызывает самого человека-диспетчера для ответа вместо AI — аналог «Позвать оператора». Он не запускает диспетчерского AI, не делегирует вопрос другому LLM и не наследует режим `fix`.

Инструмент доступен клиентскому и инженерному агентам. Через sys создаётся обращение, связанное с текущим диалогом, инициатором и относящимися к ситуации объектами. Ответ человека возвращается в тот же чат с явным авторством «Диспетчер».

### Минимальный рабочий сценарий

```text
Пользователь / агент вызывает call_dispatch_helper()
  → sys фиксирует обращение в текущем диалоге
  → Dashboard показывает запрос человеку-диспетчеру
  → пользователь видит «Диспетчер приглашён, ожидаем ответа»
  → человек принимает обращение и отвечает в этом чате
```

**Предлагаемая техническая детализация:** пока обращение ожидает человека или уже обрабатывается им, AI не генерирует параллельные ответы в этом диалоге и не продолжает менять данные в фоне. После успешной регистрации обращения текущий AI-run прекращает дальнейшие автоматические действия; сообщение об ожидании можно вернуть системно, без дополнительной генерации.

Входящие сообщения пользователя в этом режиме сохраняются sys и показываются оператору. Наличие обращения не означает, что человек уже подключился: если никто не принял запрос, интерфейс честно показывает ожидание, не обещая немедленного ответа.

Предлагаемые минимальные состояния общения: AI, ожидание диспетчера, ответ диспетчера. Они относятся к диалогу, а не к online/offline инженера и не к AUTO/MANUAL маршрутов. Правило закрытия обращения и явного возврата к AI определяется в System Layer; молчаливое автоматическое включение AI при открытом человеческом диалоге не предлагается.

Повторный вызов в том же открытом обращении должен возвращать существующее обращение вместо нескольких дубликатов. Связанные ID, автор и разрешённый контекст назначаются sys. Диспетчер получает только относящиеся к обращению сведения в рамках своих прав; коды и сервисные секреты не передаются.

**Права клиента и инженера не расширяются.** Доступ человека-диспетчера к своим данным не выдаёт вызывающему диспетчерский токен, глобальный `fix` или другой сегмент векторной базы. Ответ человека маркируется человеком и не маскируется под ответ AI.

Сам системный вызов и человеческие сообщения не создают model-вызовов. Генерация, в ходе которой агент решил вызвать инструмент, учитывается в обычном AI-бюджете. Для обращения не нужен отдельный резервный LLM; ограничения частоты обращений и выбор свободного диспетчера — детали sys, без добавления нового интеллектуального маршрутизатора.

## 7. История, актуальные данные и три сегмента знаний

**Принято:** история конкретного диалога хранится через sys; runtime получает разрешённую часть истории и при необходимости её резюме. Текущее состояние заявки / плана читается из системных данных, не из старого резюме. Документация поступает через `search_documentation()`; прямой AI-доступ к БД не используется.

| Авторизованный контур | Клиентский сегмент | Инженерный сегмент | Диспетчерский сегмент |
|---|---:|---:|---:|
| Клиент | Да | Нет | Нет |
| Инженер | Нет | Да | Нет |
| Диспетчер | Да | Да | Да |

Это три изолированные области знаний. Физическое представление — отдельные таблицы, схемы или другой проверяемый механизм — определяется при детализации Data Layer. Логическая изоляция уже обязательна.

**Предлагаемые проверки:** допустимые сегменты назначает сервер до поиска; параметры модели не расширяют их. Результаты поиска и цитаты проверяются по тем же правам. Нельзя получить закрытый сегмент сменой аргумента, формулировкой запроса или вызовом другого агента.

Материалы документации считаются данными, не инструкциями на изменение роли или выдачу секретов. Истории разных клиентов не смешиваются. В общем инженерном чате сохраняется автор: инженер, диспетчер или AI.

В MANUAL агент объясняет применённый ручной план sys, а не закрытый шиной фоновый результат Router. При несовпадении hash / контекста старый план явно отличается от ожидаемого нового.

Каталог документов, обновление индекса, размер фрагментов, сроки хранения и физическая организация описываются с Data Layer.

## 8. UI-ответ и общение

Приняты ровно следующие формы:

| Тип | Содержимое |
|---|---|
| `text` | Текстовое сообщение |
| `text_action` | Текст и одна кнопка действия |
| `text_action_cancel` | Текст, кнопка действия и отмена |
| `text_confirmation` | Текст с подтверждением операции |

Технические названия типов — оформление данного контракта. Встроенные поля произвольной формы, календарь или карта внутри генерируемого AI-сообщения не требуются. Недостающие сведения человек пишет в обычный чат. Системные формы вне AI-чата сохраняются там, где они нужны приложению.

Кнопка содержит ссылку на разрешённое системное действие, а не произвольный JavaScript, SQL или URL от модели. Текст не считается фактом изменения. UI использует фактический ответ sys для статусов операции.

Потоковый текст допустим, если адаптер проходит проверку. Частично полученные аргументы tool не исполняются. Остановка показывается отдельно от кнопки подтверждения конкретного действия: остановить run и отменить ещё не подтверждённый offline — разные операции.

Предусмотрены отдельные системные состояния: «AI сейчас недоступен», «Дневная квота исчерпана», «Требуется вход», «Запуск остановлен». Квота не маскируется как сбой провайдера.

## 9. Суточные квоты и fallback

### 9.1. Что принято

Доступ к платному AI — после подтверждения email. Квота жёсткая, на email в день. Используются ограниченные повторы, резервный профиль и панель недоступности.

### 9.2. Предлагаемая реализация квоты

Лимит проверяет sys **до** запроса к модели. Новый диалог или вкладка не создают новый суточный бюджет. Параллельные запросы резервируют бюджет атомарно; иначе два запуска могут одновременно пройти одну и ту же проверку остатка.

Для ограничения реального расхода предлагается учитывать не только количество пользовательских сообщений, но и токенный / денежный предел цепочки. Все генерации одного run, retries, fallback и автоматические резюме относятся к бюджету пользователя. `call_dispatch_helper()` и ответ человека не запускают дополнительную модель; генерация, предшествовавшая вызову, учитывается как обычно. Один длинный tool-цикл не становится бесплатным из-за того, что начинался одним сообщением.

Резервируется верхняя оценка разрешённой попытки; после достоверного usage резерв уточняется. Если расход не известен после обрыва, резерв не возвращается полностью без основания. Это проектный способ ограничить расходы, не гарантия совпадения счётчика с провайдерским биллингом при любых сбоях.

Число сообщений, token/budget limit, максимальная длина ответа, число model-вызовов и единая временная зона суточного сброса ещё не заданы. Суточная граница вычисляется сервером, не временем браузера. Нужно также определить лимиты для инженерных и диспетчерских аккаунтов; требование по клиентскому email уже принято.

Квоты AI не заменяют ограничение запросов email-кодов. Вход по email не защищает от создания множества разных адресов; дополнительные ограничения стоимости на сервере можно определить без изменения AI-tools.

### 9.3. Повторы и резерв

**Проект реализации:** retries разрешены для подходящих временных сетевых ошибок и ограничений провайдера; они ограничены общим бюджетом run. Ошибка авторизации, запрет sys-tool, отмена пользователем и исчерпание квоты не запускают бесконечные повторы или fallback в обход ограничений.

Должен быть один согласованный хозяин retry-логики. Встроенные повторы SDK и внешние повторы runtime не должны незаметно перемножать попытки.

Резервная модель / endpoint ещё не выбраны. Fallback использует тот же каталог полномочий и тот же серверный журнал операций; переход на него не пересоздаёт уже подтверждённую заявку. После полного отказа показывается панель «AI сейчас недоступен».

Сбой финального текста после успешного tool не откатывает бизнес-операцию. При остановке run резерв не запускается автоматически для продолжения уже остановленной цепочки.

## 10. SMTP: исходная инфраструктура и обязанности

### 10.1. Исходное состояние — сведения пользователя

На отдельном сервере пока есть только VPN Hysteria; почтовое ПО не развёрнуто. Нужные порты открыты. По сообщению пользователя, прямые и обратные DNS-записи домена настроены. Это исходные условия проекта, не независимая проверка конфигурации сервера.

Почтовую часть необходимо развернуть с нуля: вход для sys, TLS, авторизацию, очередь, отправку, heartbeat и управление резервным доступом. Наличие DNS и открытых портов не считается выполненной установкой SMTP.

**Предложение по реализации:** использовать готовое SMTP/MTA-ПО с устойчивой очередью, а не писать собственный протокол и транспорт писем. Собственная небольшая часть — heartbeat и переключение сетевого доступа. Конкретный пакет, сертификаты, способ сервисной авторизации и параметры очереди ещё не выбраны.

Проверка отправляющего домена, политики отправителя, прямого / обратного DNS и нужных механизмов аутентификации домена относится к развёртыванию. Секреты и пароли не передаются в чат и не включаются в документ.

### 10.2. Разделение ответственности — согласовано

| Компонент | Делает | Не делает |
|---|---|---|
| System Layer | Формирует код, выбирает шаблон, получателя, текст и ссылку; связывает письмо с событием | Не обслуживает очередь доставки внешнего SMTP после приёма письма |
| SMTP-gateway | Передаёт готовое письмо, фиксирует результат приёма, проверяет доступность нужного пути | Не решает, назначен ли мастер |
| Внешний SMTP | Принимает письмо, обслуживает очередь, отправляет дальше | Не создаёт коды и бизнес-уведомления |
| Heartbeat/watchdog | Проверяет доступность основы через VPN и управляет резервным входом | Не доказывает конечную доставку письма |


## 11. Сеть и heartbeat

### 11.1. Принятая логика

**Основной режим:** только защищённый TLS-доступ к приёму писем через VPN.

**Проверяющая сторона:** heartbeat на SMTP-сервере обращается к основному серверу по VPN. Если не может связаться, SMTP-сервер дополнительно открывает защищённый TLS-вход вне VPN.

```text
SMTP-сервер → heartbeat к основному серверу по VPN
                       │
                связь есть
                       ↓
                 VPN_ONLY

                связи нет
                       ↓
              VPN_PLUS_DIRECT_TLS
```

Это политика допуска к приёму писем **от основного приложения**. Она не означает открытый relay для всех и не описывает публичный SMTP всего Интернета.

### 11.2. Проектные детали безопасности и восстановления

TLS и проверка сертификата сохраняются на обоих путях. Для почтового submission TLS и проверка идентичности сервера описаны в RFC 8314. [W4] Открытие резервного пути не разрешает отключить сертификат или сервисную авторизацию.

На резервном входе предлагаются те же сервисные credentials либо mTLS и, когда известен стабильный внешний адрес основы, сетевое ограничение отправителей. Одного наличия TLS недостаточно как нашей политики допуска: сервер должен принимать исходящие задания только от авторизованного приложения.

Heartbeat предлагается аутентифицировать и привязать к конкретному основному серверу / контуру. Переключение выполняет отдельный небольшой watchdog с минимальными правами на нужное правило доступа, а не процесс AI и не произвольный shell-tool.

**Для устойчивости предлагается:** открывать резерв после нескольких неудачных проб; после нескольких успешных проб VPN возвращать состояние `VPN_ONLY`, прекращая новые прямые подключения и корректно завершая уже принятые передачи. Число проб, интервалы и режим возврата пока не утверждены.

Sys со своей стороны знает оба адреса: сначала пытается использовать VPN-вход; при его недоступности проверяет разрешённый прямой TLS-вход. Открытие firewall внешним сервером само по себе не переключает клиентское соединение.

Отказ пути SMTP → основа через VPN может означать сетевую проблему, а не падение SMTP. Полное падение основного приложения не устраняется открытием резервного порта: некому передать новые письма. Уже принятые письма остаются во внешней очереди и обрабатываются независимо.

### 11.3. Проверка здоровья SMTP для sys

По требованию пользователя достаточно знать, что внешний почтовый сервер жив и принимает задания. **Проектная детализация:** heartbeat должен отражать работоспособность почтового процесса и возможность принять письмо в очередь, а не только ответ ОС на ping. Это не проверка почтового ящика получателя.

Для sys предлагаются `healthy / unreachable / degraded` и время последней успешной проверки. Наличие/открытие прямого резерва отображается отдельным сетевым состоянием, а не статусом конкретного письма.

## 12. Каталог писем — уточнён после D3–D4

Все шаблоны и данные формирует sys. Технические имена ниже — обозначения для реализации, не дополнительные сценарии.

| Категория | Письмо | Основание |
|---|---|---|
| `account_login_code` | Код входа клиента, инженера или диспетчера; для клиента одновременно подтверждает email до чата и последующей заявки | Запрос обычной авторизации; у клиента создаётся либо открывается его учётная запись |
| `visit_change_required` | Мастер не сможет приехать в согласованное окно либо задерживается за его пределы; ссылка на смену даты и окна | Принятое системное состояние установило необходимость пересогласовать окно или невозможность визита в нём |
| `request_received` | Заявка отправлена и будет обработана | В подтверждённой сессии клиент подтвердил содержание и sys перевёл заявку в обработку |
| `engineer_assigned` | Мастер назначен и приедет | Sys принял актуальное назначение и выполнил соответствующий бизнес-переход |

**Отдельная обязательная категория `request_submit_code` исключена из текущего сценария.** Вход уже подтвердил email; после сбора заявки нужен осознанный выбор отправки, а не ещё одно письмо с кодом. Истечение сессии требует нового обычного входа. Это не повторное использование погашенного кода.

`request_received` и `engineer_assigned` остаются разными письмами. Первое не обещает назначенного мастера или конкретного расчётного времени. Повторное чтение результата или подтверждения не создаёт новые письма по тому же бизнес-переходу.

### Когда отправляется письмо о переносе

**D4 согласован:** если прогноз визита / начала работы остаётся в согласованном клиентском окне, **письмо о задержке не отправляется**. Величина отклонения от прежнего ETA сама по себе не меняет это правило.

Например, при окне 14:00–16:00 изменение расчётного времени с 15:00 на 15:30 не вызывает `visit_change_required`. Если после системной обработки установлено, что визит в этом окне обеспечить нельзя и требуется другое окно, используется письмо с предложением переноса. Пример иллюстрирует границу уведомления, не задаёт величину внутреннего допуска Router.

Нажатие «Опаздываю», неподтверждённое прибытие, продолжающийся перерасчёт или техническая ошибка не считаются сами по себе установленной невозможностью визита. Выход предварительного прогноза за окно рассматривает sys; до определённого бизнес-перехода нельзя выдавать ожидающий расчёт за отказ.

В MANUAL применяются те же клиентские условия, но источник — рабочий ручной план и действия sys, а не закрытый шиной фоновый результат Router. Внутренние отметки и уведомления диспетчеру могут обрабатываться независимо от клиентского письма. Отсутствие письма внутри окна не означает запрет обновлять внутренний прогноз.

Не добавляются письма о завершении, рекламные рассылки и автоматические напоминания перед визитом. Публичные ответы клиента на письма не превращаются в чат; обращение к человеку в текущем диалоге через `call_dispatch_helper()` — другой канал.

## 13. Передача и граница контроля

**Принято:** System Layer контролирует передачу внешнему SMTP-серверу и его heartbeat. Конечная доставка в ящик получателя не отслеживается приложением.

Успешная передача — это однозначный положительный результат приёма полного письма сервером, не просто успешное TLS-соединение. RFC 5321 связывает финальный положительный ответ после DATA с принятием ответственности сервером. Он не является доказательством попадания письма во «Входящие»; потеря финального ответа может оставить неоднозначность и риск дублирования. [W5]

**Проектные состояния учёта sys:**

| Состояние | Смысл |
|---|---|
| `pending_submission` | Готовое письмо ещё не принято внешним сервером |
| `accepted_by_server` | Получен положительный ответ о приёме |
| `rejected` | Получен однозначный отказ |
| `submission_unknown` | Передача могла состояться, но достоверного финального результата нет |
| `expired_before_submission` | Основание / срок письма истёк до передачи |

Статуса `delivered` в прикладном контракте нет. «Heartbeat в порядке» не превращает неизвестный результат отдельной передачи в принятие письма. И наоборот, последующий сбой heartbeat не отменяет ранее подтверждённый приём.

Sys хранит одно намерение отправки на бизнес-событие. После `accepted_by_server` он не повторяет письмо из-за отсутствия конечного подтверждения; доставкой и её повторами занимается внешняя очередь. Одинаковый Message-ID сам по себе не объявляется гарантией внешней дедупликации.

При `submission_unknown` не следует немедленно посылать второй экземпляр по прямому резерву: сначала применяется согласованная политика неоднозначных попыток. Повтор безопасной попытки использует тот же подготовленный код и письмо; новый код — отдельный запрос sys. Такая защита не обещает невозможных абсолютных гарантий доставки без дублей.

Отказ конечного домена может оставаться в серверных журналах / стандартной почтовой обработке, но в приложении не строится контур конечного tracking. Это не отменяет обязанность внешнего почтового ПО корректно обслуживать принятую очередь.

## 14. Ссылки и действия после письма

Принят обычный экран заявки с проверкой доступа. При действующей сессии клиент открывает разрешённую заявку; без сессии проходит email-код. Ссылка не является самодостаточной авторизацией и сама не меняет дату / окно.

Право доступа определяется сервером, не наличием ID в URL. Страница показывает текущие условия, даже если текст письма относится к предыдущему состоянию. Сроки действия, попытки и погашение кодов — ответственность auth-engine.

Факт успешной передачи письма не означает успешной проверки кода. Просроченный код не принимается даже после позднего получения. Если SMTP недоступен, показывается ошибка или ожидание передачи, а не фиктивное подтверждение отправки.

## 15. Рабочие объекты обмена

Это проектная разметка для детализации sys, без выбора HTTP-адресов и без выдачи её за реализованные endpoints.

### 15.1. `AiRunInput`: sys → AI

`run_id`, `conversation_id`, `actor_id`, `actor_role`, `mode`, `message`, разрешённая история, контекст объектов, разрешённый каталог tools, scope знаний и ссылка на серверный бюджет / отмену.

Роль, режим, email-владелец бюджета и scopes формируются доверенным sys. Пользовательский текст не переопределяет их. В объект для модели не включаются credentials, коды и полный внутренний auth-контекст.

### 15.2. `AiRunEvent`: AI runtime → sys / UI

Текст, один из принятых типов сообщения, описание начатого действия, ожидание подтверждения, результат sys-операции, завершение, остановка, ошибка или исчерпание квоты. Внутренние технические события не расширяют визуальный набор генерируемых форм. Для вызова человека sys также сообщает о созданном обращении и режиме ожидания; это не поток ответа диспетчерского AI.

Поля для действия: `operation_id`, тип операции, связанные разрешённые объекты, состояние и безопасный публичный итог. Возможные состояния операции — `prepared`, `awaiting_confirmation`, `running`, `applied`, `rejected`, `cancelled_before_apply`, `outcome_unknown`.

### 15.3. `DispatchHelpRequest`: обращение к человеку через sys

Предлагаемый минимальный объект: `help_request_id`, `conversation_id`, доверенный `actor_id / actor_role`, связанные разрешённые ID заявки / инженера, время создания и состояние ожидания / принятия обращения. Назначение человека хранит sys; конкретные поля и состояния уточняются вместе с Dashboard.

Факт создания обращения отличается от факта ответа диспетчера. Человеческое сообщение содержит достоверный тип автора и его системный идентификатор. Возврат tool сообщает ID и статус обращения, а не имитирует уже полученную консультацию.

### 15.4. `MailSubmission`: sys → SMTP-gateway

Системный `mail_id`, категория, ID бизнес-события / подтверждения, получатель, утверждённый отправитель, тема, готовый текст и при необходимости готовый HTML, системная ссылка, срок актуальности до передачи.

Эти поля не означают, что SMTP-протокол понимает бизнес-события, TTL или idempotency-key. Часть относится исключительно к учёту sys. Содержание сообщения готово до внешней передачи.

### 15.5. `MailSubmissionResult` и `MailHealth`

Результат передачи: `mail_id`, выбранный путь, системный статус, код / безопасное описание ошибки, время попытки и доступный ID очереди при наличии.

Здоровье: состояние SMTP-процесса / готовности приёма, последняя успешная проверка, текущее состояние VPN-доступа и прямого резерва. Никаких полей, выдающих heartbeat за подтверждение конечной доставки.

Времена используют согласованный общий формат — Unix-time в целых секундах.

## 16. Проверки, которые должна пройти реализация

| Проверка | Ожидаемый результат |
|---|---|
| Не подтверждён email | AI-вызов провайдера не начинается |
| Превышена дневная квота | Явное ограничение, без нового платного вызова или обхода через fallback; человеческие ответы сами по себе не являются AI-вызовами |
| Две вкладки одновременно | Общий бюджет не расходуется сверх разрешённого параллельными проверками |
| Клиент меняет роль / сегмент в аргументах | Доступ остаётся клиентским |
| Инженерный agent запрашивает иной tool | Sys отклоняет неизвестную / неразрешённую операцию |
| Offline без принятого подтверждения | Не применяется |
| Инженер пытается выбрать чужой субъект change_status_to | Меняется только собственная доступность из доверенной сессии; чужое изменение запрещено |
| Диспетчер `read-only` вызывает запись | Запись отклоняется |
| Диспетчер `fix` выполняет разрешённое действие | Оно отображается и исполняется без дополнительной универсальной кнопки |
| Остановка во время цепочки | Новые действия не начинаются; выполненные не выдаются за отменённые |
| Провайдер оборвался после успешного sys-tool | Сохраняется результат операции; повтор не создаёт дубль |
| Helper вызван клиентом / инженером | Sys создаёт обращение человеку; не запускается диспетчерский AI и не выдаются его права |
| Человек ещё не принял обращение | Отображается ожидание, а не ложное «диспетчер подключён» |
| Повторный helper для того же открытого обращения | Не создаёт дубликатов обращения |
| Передача человеку состоялась | AI не продолжает параллельно отвечать и менять данные в этом диалоге; правило реализации проверяется отдельно |
| Поиск документации | Соблюдается матрица трёх сегментов |
| Смена SDK | Не теряются нужные provider-поля истории и привязка tool-результатов |
| Повтор `create_request` / кнопки отправки | Нет второй заявки и повторного письма для той же подтверждённой операции |
| Email подтверждён, сессия активна | Отправка подтверждённого содержания не требует второго email-кода |
| Сессия истекла перед отправкой | Нужен обычный повторный вход; старый код не используется повторно |
| Данные изменились после показа подтверждения | Подтверждается новая версия содержания, не создаётся скрыто другая заявка |
| VPN недоступен | После условия watchdog доступен только разрешённый прямой TLS-вход |
| Неавторизованный SMTP-клиент | Relay запрещён и в VPN, и в прямом режиме |
| Сервер жив, но SMTP-процесс не работает | Health не показывает готовность передачи |
| Письмо принято, heartbeat потом пропал | Приём не откатывается и письмо не отправляется повторно только поэтому |
| Финальный ответ передачи потерян | Показывается неопределённость, не ложная доставка |
| Задержка остаётся внутри клиентского окна | Письмо о задержке не отправляется независимо от отличия от прежнего ETA |
| Sys установил необходимость нового окна | Формируется visit_change_required с обычной ссылкой и проверкой доступа |
| Перерасчёт ещё не завершён / ошибка Router | Не отправляется ложное письмо о невозможности визита |
| `request_received` | Не обещает назначенного мастера |
| Старая ссылка в письме | Проверяются права и текущее состояние |

Это критерии приёмки будущего кода; факт прохождения не заявляется.

## 17. Итог D1–D4 и оставшиеся настройки

### Смысловые решения закрыты

| Пункт | Зафиксированное решение |
|---|---|
| D1 | `change_status_to(status: 0 \| 1)` относится только к текущему авторизованному инженеру. Offline подтверждается кнопкой, online — без дополнительной кнопки |
| D2 | `call_dispatch_helper()` зовёт человека-диспетчера для ответа вместо AI; прежнее предложение о консультации другого LLM снято |
| D3 | По разрешению пользователя выбран единый вход по email-коду до чата. В действующей сессии второй код отправки не нужен; итоговое содержание заявки подтверждается в чате |
| D4 | Внутри согласованного клиентского окна письма о задержке нет. Для установленной необходимости изменить окно / невозможности визита применяется письмо с предложением переноса |

### Настройки и детали реализации, а не повторное согласование D1–D4

| Настройка | Состояние |
|---|---|
| Суточные квоты, лимиты цепочки, граница суток | Значения ещё не заданы |
| Fallback model / endpoint | Конкретный профиль ещё не выбран |
| Параметры thinking / лимиты API | Требуют проверки стоимости и совместимости |
| MTA, SMTP-авторизация и сертификаты | Выбираются при установке пустого почтового сервера |
| Интервалы heartbeat, пороги переходов, возврат VPN_ONLY | Проектная политика без произвольных чисел |
| Сроки кодов / сессии / актуальности письма, retries при неопределённости | Детализация auth-engine / SMTP-gateway |
| Имена диспетчерских sys-tools | После списка реальных системных операций |
| Ожидание человека, назначение диспетчера, закрытие обращения и возврат к AI | Детализация System Layer / Dashboard; не вызов диспетчерской модели |
| Материалы RAG, индексация и хранение | Этап Data Layer |

Прекращение AI-ответов при передаче человеку, идентификаторы операций, проверка версии подтверждаемой заявки и защита от дублей описаны как проект реализации. Они не объявляются уже реализованными или протестированными функциями.

## 18. История уточнений

### v2 — предыдущая редакция

Гостевой AI-черновик заменён входом по email-коду до разговора. Зафиксированы суточная квота, выбранная модель, конкретные инструменты, диспетчерский `read-only / fix`, журнал и остановка, три сегмента знаний, текстовые формы, retries/fallback и панель недоступности.

Почтовый сервер описан как ещё не развёрнутое почтовое ПО на отдельном сервере. Приняты heartbeat со стороны SMTP, открытие защищённого прямого резерва, шаблонные письма от sys и граница контроля на принятии сервером. Вопросы субъекта offline, helper, двух кодов и задержки были оставлены D1–D4.

### v3 — текущая редакция

- Закрыт D1: один целевой статус, только собственный инженер, offline с кнопочным подтверждением.
- Закрыт D2: helper создаёт обращение человеку-диспетчеру; убраны AI-консультация, вложенный LLM-run и его отдельный расход.
- Описано ожидание и ответ человека в том же чате; пауза автоматических ответов и защита от дублей — проектная детализация sys.
- После D3 выбрано единое подтверждение email при входе; отдельно подтверждается содержание заявки, но не вторым email-кодом. Убрана активная категория request_submit_code.
- Закрыт D4: задержка внутри окна не вызывает письмо. Уведомление о переносе требует установленной необходимости пересогласовать клиентское окно.
- Согласованы таблицы tools, расхода, писем, объектов обмена и тестов. Остальные архитектурные границы, сетевой резерв и контроль передачи сохранены.
- Основные файлы системы и Router не перезаписаны; интеграционных испытаний не выполнялось.
