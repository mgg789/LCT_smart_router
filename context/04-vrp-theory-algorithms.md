# Теория VRP/VRPTW: классы задач и алгоритмы — что нам подходит

> Назначение: выбрать семейство алгоритмов осознанно и уметь его защитить перед жюри. Практический вывод в конце: на нашем масштабе (20–100 заявок) побеждает связка «жадное построение + локальный поиск (LNS/ALNS/GLS)», реализованная в готовом солвере.

---

## 1. Где наша задача на карте VRP

Базовая задача — **CVRP** (capacitated VRP): развести заказы по машинам, минимальный пробег, ограничение ёмкости. Наша — значительно богаче, по слоям:

| Слой | Классическое имя | В нашей задаче |
|---|---|---|
| Временные окна | VRPTW | Окна визитов + смена инженера |
| Разнородный парк | HF (Heterogeneous Fleet) | Инженеры различаются навыками, стартом, транспортом |
| Навыки/совместимость | Technician Routing Problem (TRP), MD-PDPTW-подобные навыки | Работа→навык, работа→оборудование, работа→транспорт |
| Мульти-депо | MDVRP | Инженеры стартуют из офиса/дома |
| Динамика | Dynamic VRP (DVRP) | Новая заявка/опоздание в течение дня |
| Мульти-цели | — | SLA > балансировка > пробег (лексикографически) |

Справочные точки: классификация в работах Toth & Vigo «Vehicle Routing» (2 тома, стандарт отрасли), обзоры Pillac et al. 2013 (dynamic VRP), Vidal et al. по HGS.

## 2. Семейства алгоритмов

### 2.1 Точные методы
- **MILP + branch-and-cut** — для VRPTW реалистично до ~15–25 узлов.
- **Branch-and-Price-and-Cut (column generation)** — до ~100 узлов при удачной структуре, но реализация — месяц работы команды. На хакатоне нет.
- **CP (Constraint Programming) / CP-SAT** — хорош для scheduling с навыками; VRP-секвенирование выражается сложнее.
- Вывод: точное решение нам не нужно (масштаб маленький, эвристики дают 1–3% от оптимума за миллисекунды), но упоминание «задача NP-трудная, поэтому применяем эвристики с гарантиями качества на практике» — обязательно в презентации.

### 2.2 Конструктивные эвристики (строим первый план)
- **Nearest neighbor** — жадно ближайший сосед. Быстро, плохо.
- **Clarke-Wright savings** — объединение маршрутов по «экономии». Классика, для нас слабо применима (навыки/окна).
- **Cheapest insertion** — вставляем каждую заявку в самое дешёвое место любого маршрута. Основа почти всех промышленных систем.
- **Regret-k insertion ( regrets)** — сначала вставляем заявку, для которой «потеря от ожидания» максимальна (regret = разница между лучшим и вторым вариантом). **Лучший выбор для динамической вставки срочных заявок** — так делают промышленные диспетчеры. Понятная «причина»: «заявку Б нужно назначить первым делом — иначе у неё не остаётся допустимых мест».
- Для нашего масштаба конструирование + один проход улучшения уже даёт приличный план — это и есть «скоростной путь» и запасной план, если готовый солвер закапризничает.

### 2.3 Локальный поиск и метаэвристики (улучшаем план)
Операторы перемещения (нужны для объяснения «как мы улучшили»):
- relocate (перенос визита), swap (обмен), 2-opt* (обмен хвостами маршрутов), or-opt (перенос цепочки), route elimination.

Метаэвристики:
- **Guided Local Search (GLS)** — локальный поиск + штрафы на часто повторяющиеся рёбра. **Так работает Google OR-Tools Routing из коробки.** Надёжная, быстрая, легко тюнится лимитом времени.
- **Tabu search** — классика для VRPTW (Cordeau), сегодня редко лучший выбор.
- **Simulated annealing** — простая, уступает ALNS/HGS.
- **Large Neighborhood Search (LNS)** — разрушить часть плана (убрать 10–30% заявок) → вставить обратно по regret. Просто, мощно, идеально объясняется («мы перестраиваем только проблемный кусок дня»).
- **ALNS (Adaptive LNS)** — LNS + несколько операторов разрушения/вставки, вероятности которых адаптируются по результату. **Промышленный стандарт для VRPTW с богатыми ограничениями** (Ropke & Pisinger 2006; использовался в системах планирования выездных сервисов). Главный плюс для нас: **легко добавлять кастомные мягкие ограничения и мульти-цели** — каждая цель просто становится частью принимающей функции.
- **HGS (Hybrid Genetic Search, Vidal)** — генетика + локальный поиск, текущий SOTA на классических бенчмарках CVRP/VRPTW (PyVRP — его реализация). Минус: сложнее адаптировать к экзотическим ограничениям (наши навыки/оборудование влезают, но дороже).

### 2.4 Сравнение применимости к НАШЕЙ задаче

| Критерий | GLS (OR-Tools) | ALNS (сам) | HGS (PyVRP) |
|---|---|---|---|
| VRPTW + навыки + мульти-депо | ✅ из коробки | ✅ (сам задаём) | ⚠️ частично |
| Мульти-цели (SLA>баланс>путь) | ⚠️ через штрафы-веса | ✅ полно | ⚠️ |
| Объяснимость (кто что получил и почему) | ⚠️ разбираем переменные | ✅ свои события | ❌ сложнее всего |
| Время внедрения | дни | неделя+ | дни |
| Риск на хакатоне | низкий | средний | низкий |

## 3. Как моделируются наши ограничения (практика)

- **Временные окна:** на узле [start, end] + time dimension в маршруте; время прибытия позднее старта окна → ожидание (waiting). Показывать в UI «инженер ждёт 20 мин» — признак неоптимальности/особенности плана.
- **Навыки:** visit → допустимые инженеры (allowed vehicles в OR-Tools; в самописном ALNS — просто фильтр). 
- **Оборудование:** два подхода: (а) как «навык» — совместимость инженер×работа (у инженера есть комплект); (б) как ёмкость — счётчик инстансов на маршруте. Для ТЗ достаточно (а) + проверка наличия на старте дня, количественные лимиты — если будут в данных.
- **Смена:** horizon маршрута = смена; время возвращения на базу учитывается (DepotEnd).
- **SLA:** три уровня: жёсткое окно (hard), мягкое окно (штраф ~ квадратич по опозданию), приоритет очереди при перепланировании.
- **Балансировка:** либо штраф за дисперсию загрузки (считать сложно в OR-Tools напрямую), либо мягкое ограничение max часов на маршруте. Практично: после оптимизации пробега — пост-шаг «переместить визит между парами инженеров, если снижает дисбаланс без роста SLA».
- **Travel-время по времени суток:** статическая матрица умножается на коэффициент часа (пик 1.4, ночь 0.9) — честный time-dependent-lite, легко объяснить.

## 4. Мульти-целевая функция (рекомендация для проекта)

Лексикографически через большой штраф (как в OR-Tools):

```
cost = 1_000_000 × (число незапланированных заявок)
     +   100_000 × (суммарные минуты опозданий, квадратично)
     +    5_000  × (перегруз инженера сверх 8ч)
     +      500  × (дисбаланс загрузки, минуты сверх среднего)
     +        1  × (суммарное время в пути)
```

Принцип: следующий критерий включается, только когда предыдущий насытился. Числа — тюнить на датасете. Эта формула — готовый слайд для жюри: «вот как мы формализуем приоритеты бизнеса».

## 5. Что презентовать жюри про алгоритм (без перегруза)

1. Задача NP-трудная (VRPTW с навыками), точные методы не масштабируются → промышленные эвристики.
2. Конструктив: regret insertion → улучшение: локальный поиск (GLS/LNS) с ограничением по времени решения.
3. Мульти-цель: иерархия SLA > баланс > путь (показать формулу штрафов).
4. Динамическое перепланирование: пересборка за <1 c + стабильность (см. `07-dynamic-replanning.md`).
5. (Опционально) упомянуть, что существует SOTA-зоопарк (HGS, нейрометоды — см. `08-ml-ai-neural-vrp.md`), и обосновать выбор.

## 6. Точки отказа и как их обойти

- OR-Tools не даёт «причины» напрямую → снимаем значения переменных (кто, когда, slack) и строим объяснения сами (см. `11-explainability.md`).
- Нестабильность планов между пересчётами → фиксируем «начало дня» и оптимизируем только хвост; или штраф за изменения относительно предыдущего плана.
- Waiting time может съесть окно маршрута → в метриках показываем отдельно «простой/ожидание».
- Гео-матрица: если движок роутинга упал — заранее сохранённый кэш матрицы на демо-датасет (см. `15-risks-pitfalls.md`).
