# Объяснимость: «показывает причины выбора маршрута» (п.5 ТЗ)

> Назначение: это единственный пункт ТЗ, который большинство команд сделает формально (одна строчка под картой). Для нас — ядро доверия и главный дифференциатор. Здесь: что считать «причиной», как её получить из солвера, как показать.

---

## 1. Три уровня объяснений

| Уровень | Вопрос пользователя | Что показываем |
|---|---|---|
| **L1. Почему эта заявка у этого инженера** | «Почему Иванов, а не Петров?» | Факторы назначения + контрфакты: «Иванов: навык ✅, до объекта 8 мин; Петров: навык ❌ (нет видеонаблюдения)» |
| **L2. Почему маршрут такой** | «Почему сначала Б, потом А?» | Порядок: «Б раньше: окно 10–12 жёсткое, А — до 17; объезд добавил бы +18 мин» |
| **L3. Почему план такой (глобально)** | «Почему сегодня 2 рискованных заявки?» | Сводка плана: дефицит инженеров с навыком X, тесные окна в пике, предложение что изменить |

## 2. Откуда брать факты для причин

Солвер возвращает решение (кто, когда, порядок) — причин он не знает. Но причины **вычислимы из данных и решения**:

1. **Кандидаты и их отсев (L1):** для каждой заявки заранее считаем список допустимых инженеров (навык ∩ оборудование ∩ транспорт ∩ смена ∞ окно). Кто отсеялся и почему — уже готовая причина. Хранится в `request.candidates[]`.
2. **Стоимость альтернативы (L1):** для каждого допустимого кандидата считаем вставочную стоимость (маргинальные минуты пути + риск SLA). Итог: ранжированный список «почему он лучший». Это дешёвый расчёт (N × M вставок) поверх готового плана.
3. **Порядок (L2):** сравнение фактического порядка с альтернативой (swap соседей в маршруте → изменение cost) — объяснение «почему не наоборот».
4. **Глобальные факторы (L3):** агрегаты: сколько заявок требуют навык X при наличии 2 инженеров; окно попадает в пик 17:00–19:00 (коэффициент трафика); единственный инженер в районе.

Это **rule-based объяснимость** — детерминированная, честная, не зависящая от LLM. LLM (локальный Qwen) может лишь переложить факты в гладкий текст — поверх, с фолбэком на шаблоны (см. `08-ml-ai-neural-vrp.md`).

## 3. Структура данных (контракт между солвером и UI)

```jsonc
// request.reasons
{
  "assignment": {
    "chosen": "eng_ivanov",
    "factors": [                              // в порядке важности
      { "code": "skill_match",  "ok": true,  "detail": "Владение видеонаблюдением" },
      { "code": "travel_delta", "value": 0,  "detail": "Ближайший к предыдущей точке (+8 мин)" },
      { "code": "sla_margin",   "value": 34, "detail": "Запас до конца окна 34 мин" },
      { "code": "load_balance", "value": -12,"detail": "У Иванова день короче на 12 мин" }
    ],
    "alternatives": [                         // контрфакты — почему не другие
      { "engineer": "eng_petrov", "blocked": false, "cost_delta": 18,
        "why_not": "Навык есть, но +18 мин пути и SLA-запас падает до 6 мин" },
      { "engineer": "eng_sidorov", "blocked": true,
        "why_not": "Нет требуемого оборудования (тепловизор)" }
    ]
  },
  "sequence": [
    { "swap_with": "req_231", "cost_delta": 11, "why": "Окно req_231 жёсткое 10:00–12:00" }
  ]
}
```

Правила: факторы — конечный словарь кодов (UI рисует их иконками и переводит в текст); альтернативы — минимум 2, если существуют; всё это **считается на бэке**, фронт только рендерит.

## 4. Где причины живут в интерфейсе

1. **Панель заявки** — блок «Почему так»: топ-3 фактора строками + разворот «показать всех кандидатов» (таблица: инженер / время / +мин / причина отказа).
2. **Тултип на карте/таймлайне** — одна строка: «Иванов: ближайший (+8 мин), запас 34 мин».
3. **Панель перепланирования (дельта)** — причина каждого изменения: «req_124 → Сидоров: освобождающийся слот 13:20, рисков было 2 → 1».
4. **План целиком** — вкладка «Обзор плана»: топ-факторы дня + «что можно улучшить» (например: «если дать Сидорову навык X — минус 1 риск»); кнопка what-if.
5. **Экспорт** — кнопка «Скачать объяснение плана (PDF/MD)» для передачи руководству — плюс к «продуктовости» в глазах жюри.

## 5. Тон и стиль текста причин

- Человеческий язык без жаргона VRP: не «CumulVar вне окна», а «инженер не успевает к окну: приехал бы в 14:20 при окне до 14:00».
- Всегда с числами: «+18 мин пути», «запас 6 мин» — числа создают доверие.
- Никаких оправданий: если план плохой — честно показать причину (дефицит ресурса), это лучше, чем уверенный тон при плохом плане.

## 6. Словарь кодов факторов (стартовый)

| Код | Текст-шаблон |
|---|---|
| skill_match / skill_missing | «Навык соответствует» / «Нет навыка: {skill}» |
| equipment_ok / equipment_missing | «Комплект на борту» / «Не хватает: {item}» |
| travel_delta | «{+n} мин пути относительно лучшего варианта» |
| sla_margin | «Запас до конца окна {n} мин» |
| window_tight | «Окно узкое: {start}–{end}» |
| load_balance | «Выравнивает загрузку дня ({n} мин)» |
| cluster | «Близко к маршруту по району ({district})» |
| urgent_priority | «Срочная заявка — приоритет по SLA {class}» |

## 7. Что НЕ делаем

- Не объясняем внутренности метаэвристики («итерация 47 GLS улучшила на 0.3») — это не то, что нужно диспетчеру.
- Не выдумываем причины, которых не считали: каждая строка «почему» обязана быть вычислена, иначе это декорация (жюри любит спросить: «а проверьте, правда ли Петров дал бы +18?»).
- Не строим «AI-объяснитель» без фактов под ним.
