# Динамическое перепланирование: стратегии, стабильность, UX, реализации

> Назначение: п.4 ТЗ «автоматически перепланирует день при поступлении новой заявки» + наша фишка «дельта с объяснением». Здесь теория (обзоры DVRP), стратегии реакции, стабильность плана, архитектура событий, паттерны в солверах и UX живого обновления.

---

## 1. Классификация событий и постановка

Обзоры: Pillac et al., «A review of dynamic vehicle routing problems» (2013, [HAL](https://hal.science/hal-00739779/document)) — каноническая таксономия (степень динамизма: доля информации, раскрываемой по ходу дня); также [обзор DVRP со случайными заявками (2022)](https://research.tue.nl/files/257489379/1_s2.0_S0925527322003334_main.pdf), [Larsen, DTU](https://core.ac.uk/download/pdf/13737995.pdf).

События нашего дня:

| Событие | Влияние | Сложность реакции |
|---|---|---|
| Новая заявка (обычная/срочная) | Вставка в план | Низкая |
| Отмена заявки | Удаление, возможно «слишком много дыр» | Низкая |
| Опоздание инженера (задержка на предыдущей точке) | Сдвиг хвоста маршрута, риск SLA | Средняя |
| Инженер недоступен (болезнь, поломка ТС) | Расформирование маршрута | Средняя |
| Клиент сдвинул окно | Локальный сдвиг / глобальный пересчёт | Средняя |
| Освободилось оборудование (вернули из ремонта) | Возможность вернуть «отложенную» заявку | Низкая |

Ключевой параметр — **какая часть дня уже зафиксирована**: заявки, к которым инженер уже выехал или выполнил, менять нельзя (реальность), остальное — «живая зона» перепланирования.

## 2. Стратегии реакции

### 2.1 Полная пересборка (наш базовый выбор)
Честный пересчёт модели с фиксированием уже совершённых действий. На нашем масштабе (≤100 заявок) — **сотни миллисекунд**. Плюсы: простота, всегда консистентный оптимум под текущие данные, легко объяснить. Минусы: может «трясти» план (см. §3).

### 2.2 Тёплый старт + локальный поиск
Предыдущий план загружается как начальное решение, локальный поиск улучшает с учётом события. В OR-Tools: `ReadAssignmentFromRoutes` / `SolveFromAssignmentWithParameters` ([официальная документация](https://developers.google.com/optimization/routing/routing_tasks); нюанс с search-параметрами — [обсуждение](https://groups.google.com/g/or-tools-discuss/c/ousalyiYpwc)). Плюсы: план меняется минимально (естественная стабильность), быстрее. Это наш основной режим для событий в течение дня.

### 2.3 Инкрементальная вставка (для срочной заявки «мгновенно»)
Cheapest/regret insertion новой заявки в текущий план — микросекунды, предварительный ответ UI сразу, затем фоновая переоптимизация (2.2) уточняет план. Двухступенчатая реакция: «заявку принял — оптимальную раскладку покажем через секунду».

### 2.4 Переоптимизация затронутых маршрутов
LNS на подмножестве маршрутов (только инженеры, у которых изменился день). Компромисс качество/стабильность. Реализация — при наличии времени; не критична.

### 2.5 Rolling horizon
Периодическое фоновое улучшение плана (раз в N минут) + мгновенная реакция на события. Полезно как «автопилот качества». Для хакатона — опционально.

## 3. Стабильность плана (критично для доверия)

Пересчитанный «с нуля» план может передвинуть 30% заявок, хотя вставка новой изменила только соседний район. Для диспетчера и клиентов это катастрофа UX. Литература называет это route consistency / plan stability.

Практики:
1. **Тёплый старт** (§2.2) — стабильность почти бесплатно.
2. **Штраф за изменения:** в целевую функцию добавляем `w_stab × (число передвинутых заявок + сдвинутых минут)` относительно текущего плана. Вес ниже SLA/пути, но заметный. Параметр «силы стабилизации» — наш what-if слайдер.
3. **Фиксация выполненного/начатого:** заявки «в пути» — hard constraints; заявки «следующая точка» — мягко предпочтительны.
4. **Порог чувствительности:** если дельта от пересчёта «дешёвая» (< N минут выигрыша) — не применять вовсе («тишина — тоже решение»), показывать это в ленте.
5. **Метрика дельты** в UI всегда: «передано 2, сдвинуто 3, средний сдвиг 11 мин».

Объяснение пользователю: «Мы не перетряхиваем день: меняем только то, что обязаны, чтобы не потерять SLA».

## 4. Event-driven архитектура (см. также `09` §4)

```
UI/симулятор ──► POST /requests | /events ──► API
                                   │ (валидация, гео, валидация совместимости)
                                   ▼
                              очередь событий
                                   │
                                   ▼
                        Solver Worker: build input (fix = выполненное)
                        → warm start prev plan → solve(≤1.5 c)
                        → Plan v+1 + Diff + Reasons
                                   │
                                   ▼
        API: snapshot в БД, SSE plan.updated ──► UI: анимация дельты
```

Правила:
- Планы иммутабельны (v1, v2, ...) — история, undo, диффы бесплатно (`14`).
- Каждое событие и каждое решение логируется с причиной — лента событий в UI.
- Идемпотентность: повторное событие не создаёт дубль-версии.
- Конфликт ручной правки и авто-перепланирования: ручные закрепления (pinned) живут до снятия; солвер уважает pinned; в UI — метка «закреплено вручную».
- **Режимы автономии** (одна настройка): `Авто` (применять сразу, показывать дельту) / `Предлагать` (дельта ждёт подтверждения) / `Ручной`. Для демо — Авто.

## 5. Реализации в солверах

### OR-Tools
- Пересборка модели на событие — норма для нашего масштаба; tешплый старт через `SolveFromAssignmentWithParameters`.
- Фиксация: `routing.CloseModelWithParameters` + начальное решение; выполненные заявки — просто исключить из входа, оставив в маршруте как «пройденные» узлы с нулевой оптимизацией (или задать `SetAllowedVehiclesForIndex` только на одного инженера).
- Штраф стабильности: пост-расчёт дельты → вес на узле «изменённость» проще всего посчитать вне модели и выбрать стратегию (2.1 vs 2.2) по порогу.

### Timefold (ex-OptaPlanner)
- Real-time planning из коробки: solver живёт демоном, события через problem fact changes, инкрементальный пересчёт с сохранением плана ([репозиторий Python-версии](https://github.com/TimefoldAI/timefold-solver-python)). Это архитектурно «правильнее», но требует держать solver постоянно живым.

### VROOM
- Пересборка job на событие; стабильность — на нашей стороне.

## 6. Предсказание опозданий и проактивность

- **Прогноз ETA** по текущему положению (симуляция движения по маршруту с коэффициентами трафика — см. `14` §5.2).
- Каждую минуту симуляции: `ETA(следующего визита) vs конец окна` → если запас < 15 мин → риск-бейдж; < 0 → нарушение + предложение: «перепланировать хвост маршрута» одной кнопкой.
- В демо это самая «живая» фича: жюри видит, как система **предупреждает** до того, как случилось.

## 7. UX живого перепланирования (паттерны)

1. **Видимость процесса:** бейдж с прогрессом «Пересборка плана…» — никогда не молча.
2. **Дельта как событие:** карточка «Что изменилось»: передано/сдвинуто/риски до→после; каждый пункт кликабелен (открывает заявку с причиной).
3. **Автопринятие с отсрочкой:** кнопки «Принять/Отменить», авто-принятие через 10 c — спокойствие и контроль.
4. **Подсветка изменённого:** изменённые блоки на таймлайне и маркеры на карте помечены до следующего взаимодействия.
5. **История:** лента «11:42 срочная заявка → v4: 2 переданы; 11:58 отмена → v5: дыра 25 мин у Иванова».
6. **Антипаттерн:** перерисовка всего экрана без объяснений — убивает доверие; «тихая» оптимизация в фоне без дельты — тоже.

## 8. Демо-сценарии перепланирования (для репетиции, seed-детерминированные)

1. **Срочная VIP-заявка** (узкое окно, дефицитный навык) — основной сценарий `13` §2.
2. **Отмена** — «дыра» у инженера → фоновая оптимизация аккуратно подтянула соседнюю заявку вперёд.
3. **Опоздание:** инженер застрял (симуляция +30 мин) → риски → предложено перепланирование хвоста.
4. **Поломка:** инженер недоступен → его 8 заявок распределились по остальным, SLA удержан — сильный финальный аккорд.
