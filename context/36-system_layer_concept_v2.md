## 1. Назначение System Layer

**Согласовано:** System Layer — основной backend приложения и единая точка применения разрешённых бизнес-изменений. Он знает действующих пользователей, состояния заявок и инженеров, фактические события, рабочий план, подтверждения, переписку и почтовые события.

Router решает подготовленную задачу дальнейшего распределения. Sys не повторяет его оптимизацию, не редактирует память маршрутов и не придумывает факты выполнения по расписанию. Исключение — согласованная узкая служебная настройка допуска, а не универсальные команды ядру.

### Согласованная основа с уточнениями v2

| Область | Действующее решение |
|---|---|
| Время | Unix-time в целых секундах; длительности отдельно, тоже в секундах |
| Фактическое выполнение | Источник начала и завершения — явные отметки инженера; отдельное автоматическое завершение новым ответом не задано |
| Прогноз без отклонения | Нет обращения или явного изменения — сохраняется предположение «по плану»; истечение времени/отсутствие отметки не публикуют новый сектор |
| Живое состояние | События, чаты и продвижение плана обрабатывает sys; телеметрии нет — GPS исключён из продукта ([50](./50-concept-changes-after-qa.md) §2) |
| Специальный сектор | Опубликованный целостный снимок оставшейся задачи, не копия каждой записи базы |
| Старты Router | `start_location + available_from`; текущая начатая работа вне свободного пула; активная работа якорит старт в своей точке |
| Публикация | Значимые изменения задач, доступности, политики, обедов, подготовленных прогнозов и фактов исполнения с материальными временными последствиями; `planning_as_of` фиксируется с публикацией, не тикает отдельно |
| Актуальность | `input_hash` и активная `router_context_version`; отдельно — пригодность main и совместимость с фактами |
| Применение | Повтор одного результата не возвращает выполненные работы и не дублирует письма |
| MANUAL | Отключается Router → sys; ядро продолжает работу, рабочий план редактирует диспетчер |
| Политика | Иерархию целей задаёт каталог политик; первая политика по умолчанию `compact` ([50](./50-concept-changes-after-qa.md) §1) |
| Обед | `lunch_taken` по инженеру и дню устанавливается при фактическом начале; второго обеда нет; глобально обеды по умолчанию выключены ([50](./50-concept-changes-after-qa.md) §3) |
| Восстановление обеда | `lunch.required` и исключение явно выбранных заявок одной системной операцией |
| Клиентский вход | Email-код до AI; далее действующая сессия и подтверждение содержания заявки без второго обязательного кода |
| AI | Ролевые инструменты исполняет sys; диспетчерский fix использует разрешённые бизнес-операции, журнал и остановку |
| Оператор | Один человек-диспетчер; обращения появляются на странице «Чаты», AI в переданном диалоге отключён до завершения диспетчером |
| Диспетчерский вход | Email-код либо пароль из серверной конфигурации `.env`; парольный путь не зависит от SMTP |
| Перенос заявки | После «Подтвердить» дата/окно сразу меняются у той же заявки; двух активных вариантов нет |
| Письмо о задержке | Внутри согласованного окна письма нет; одно «Опаздываю» не является основанием переноса |
| Почта | Sys формирует письмо, внешний SMTP принимает и обслуживает очередь; конечный tracking не вводится |

## 2. SL1 — внутренние блоки и общий механизм операций: согласовано

### Принятая организация

Один логический backend, разделённый на внутренние модули. Приведённые блоки не означают по отдельному серверу или контейнеру на каждый. Сохраняем названия из исходного обсуждения.

| Блок | Ответственность |
|---|---|
| `REST API` | Приём обращений четырёх внешних контуров, проверка формы, передача в системные операции, выдача разрешённых представлений |
| `auth-engine` | Email-коды, парольный вход единственного диспетчера, учётные записи, сессии, права роли и доступ к конкретному объекту |
| `orchestrator backend` | Сценарии заявок, инженеров, обедов, передачи чата, подтверждений и бизнес-уведомлений; координация, не расчёт маршрутов |
| `dataengine` | Чтение/запись бизнес-данных, истории и результатов операций; согласованная фиксация изменений и проверка версий |
| `mount-data-eng` | Подготовка и публикация целой актуальной проекции в специальный сектор |
| `ROUTER-gateway` | Получение результата, проверка его принадлежности, управление приёмом AUTO/MANUAL; отдельный разрешённый конфигурационный запрос |
| `AI-gateway` | Доверенный контекст, проверка бюджета, доступ к sys-tools, подтверждения, остановка и журнал run |
| `SMTP-gateway` | Передача готовых писем, учёт ответа приёма, health и выбор разрешённого сетевого пути |

Бизнес-правило существует в одном обработчике. Интерфейс, интеграционный API и AI-tool не реализуют три независимо расходящихся варианта создания заявки или изменения доступности. Они отличаются полномочиями, источником и необходимостью подтверждения.

```text
Вход: UI / API / AI-tool
  → доверенный автор и его права
  → проверка данных, текущего состояния и подтверждения
  → системная операция
  → согласованная запись изменения и истории
  → запись необходимых последующих действий
  → результат операции для инициатора

После записи:
  → публикация снимка, когда изменились условия планирования
  → обновление представлений интерфейсов
  → отправка письма, когда есть соответствующее бизнес-событие
```

### Граница фиксации

Бизнес-изменение, запись о его авторе и намерения необходимых последующих действий сохраняются согласованно. Само обращение к AI, Router или внешнему SMTP не удерживает запись открытой до завершения сетевого ожидания. Техника такой фиксации будет выбрана вместе с Data Layer.

Пример: заявка уже создана и находится в обработке, а письмо пока не принято SMTP. Sys возвращает оба факта отдельно. Отказ почты не превращает сохранённую заявку в несуществующую и не требует создать её повторно. Публикация снимка также имеет наблюдаемый исход; нельзя бесшумно потерять её после успешной записи заявки.

Это не предложение внедрить универсальную платформу событий или отдельный брокер. Нужен ограниченный учёт незавершённых системных действий по нашим сценариям.

**SL1 принят:** один backend, общие обработчики и согласованное сохранение бизнес-изменения с необходимыми последующими действиями. Физическая транзакционная реализация выбирается позднее.

## 3. SL2 — раздельные состояния заявки: согласовано

### Принятая модель

Не смешивать в одном статусе бизнес-стадию, результат распределения, движение инженера и состояние расчёта. `pending` сохраняется как ожидание результата назначения, а не становится синонимом технической ошибки или недоставленного письма.

| Группа | Значения рабочей разметки | Кто изменяет |
|---|---|---|
| Жизненный цикл | `draft`, `submitted`, `in_progress`, `completed`, `cancelled` | Sys по разрешённым действиям и подтверждённым фактам |
| Назначение | `pending`, `assigned`, `unassigned` | Sys из принятого автоматического или действующего ручного плана |
| Ход визита | Расчётное ожидание; явно сообщённые выезд/прибытие/ожидание доступа и проблема | Sys; точные UI-кнопки ещё отдельный предмет |
| Свежесть расчёта | Ожидание актуального результата, актуален, ошибка | Проверки sys, а не стадия выполнения заявки |

Смысл разделения и перечисленные стадии согласованы. Приведённые коды фиксируют рабочую разметку; окончательную форму endpoints они не определяют. Для клиента системное представление может показывать одно понятное состояние, но оно строится из соответствующих признаков.

```text
Черновик
  → подтверждение отправки в действующей сессии
  → submitted + pending
  → после принятого назначения: submitted + assigned
  → инженер начал: in_progress
  → инженер завершил: completed
```

Другой исход расчёта: `submitted + unassigned` и конкретная причина. Если нужен перенос, sys показывает соответствующее действие. Отмена не получается автоматически из неназначения. Продолжающийся расчёт и ошибка Router не превращают заявку в `unassigned` с ложной причиной невозможности визита.

Текущий `assigned` привязан к версии условий заявки и применённому плану. Начало фонового пересчёта само по себе не стирает все принятые назначения: свежесть и актуальность условий показываются отдельно. После изменения клиентского окна прежнее назначение не считается подтверждением нового окна.

Начатая или завершённая работа не возвращается в свободный пул при приёме результата. Для истории сохраняются фактический исполнитель и назначения, которые действовали раньше.

**SL2 принят:** жизненный цикл, назначение, ход визита и свежесть плана не сводятся в один монолитный статус.

## 4. SL3 — немедленное изменение даты и окна: согласовано

Клиент выбирает новую дату и временное окно, затем нажимает **«Подтвердить»**. До нажатия выбор остаётся локальным/подготовленным изменением интерфейса; после успешной проверки и сохранения sys новые условия становятся единственными действующими условиями **той же заявки**.

```text
Выбор даты и окна
  → «Подтвердить»
  → sys проверяет пользователя, версию и допустимость операции
  → у существующего request_id сохраняются новые дата и окно
  → прежнее назначение не подтверждает новые условия
  → результат назначения pending
  → опубликован новый целостный снимок
  → Router самостоятельно обрабатывает его
  → sys принимает актуальный результат
```

Новая заявка-копия, две активные версии визита и пара «старое действующее окно / новое желаемое окно» не создаются. История прежних условий сохраняется для журнала, но не является вторым активным обещанием клиенту.

Перенос не ждёт успешного назначения в новом окне. Если новый расчёт не дал назначения, старое окно автоматически не восстанавливается. Неуспешная проверка прав или конфликт версии не являются успешным подтверждением: в таком случае новые условия не записываются, интерфейс показывает причину.

Изменение условий не является командой на запись маршрута в Router. Sys фиксирует бизнес-факт переноса, не вычисляет самостоятельно новое назначение. Повтор того же подтверждения не создаёт дубликат операции, заявки или почтового события.

### Что этим ответом не было окончательно определено

Пользователь выбрал немедленную модель переноса. Точные правила **отмены** и допустимость переноса **после фактического начала работы** отдельно не подтверждены. Из v1 сохраняется только предложение для последующей детализации: обычный клиентский перенос/отмена до начала; после начала — разбор с диспетчером. Это не выдаётся за уже принятый запрет или за право автоматически прерывать начатую работу.

При одновременном переносе и отметке начала sys должен проверить актуальное состояние перед записью. Какой переход разрешён в такой ситуации, задаётся системным контрактом, не молчаливой перезаписью факта.

## 5. SL4 — прогноз по умолчанию и строгая граница триггеров

### 5.1. Новое согласованное правило

**Если инженер не сообщил об отклонении и не обратился за помощью, для планирования считаем, что ситуация штатная и он укладывается в свой период.** Продолжаем использовать принятый план как прогноз. Отсутствие новой отметки само по себе не означает новое отклонение, которое надо отправить Router.

**Нет триггера для перестроения → нет публикации новых данных сектора → нет перестроения только по этой причине.**

Снято прежнее предложение v1: автоматически превращать истечение ожидаемого срока в `available_from=null`, публиковать однократный снимок и запускать перерасчёт. Его нельзя вернуть под другим названием «служебное событие неизвестности» без нового решения.

```text
Часы идут / новой отметки нет
  → sys продолжает сопровождать текущий план
  → сам по себе новый снимок не публикуется
  → planning_as_of не сдвигается по таймеру

Поступило явное изменение условий или обращение о проблеме
  → sys разбирает содержание события
  → при установленном изменении задачи готовит новую проекцию
  → публикует изменившийся снимок вместе с planning_as_of
```

**Реализованное уточнение MVP-контура (17.09):** факты исполнения с материальными временными последствиями — старт работы, отклонение длительности за порогами (`early_finish_replan_threshold_sec` / `task_overrun_tolerance_sec` из технической ревизии Router) и выявленное превышение — публикуют проекцию с обновлёнными якорями `start_location + available_from`; отклонение внутри порогов не публикует ничего. Единственное событие по времени — фоновый координатор превышения: он **только фиксирует** `overrunDetectedAt` у начатой работы, вышедшей за допуск, публикует проекцию и выводит инженера из задачи; он не достраивает фактов, не перестраивает план и не отменяет SL4 — «срок истёк» без начатой работы по-прежнему не триггер.

### 5.2. Прогноз и факты — разные слои

Последнее уточнение задаёт оптимистичную политику прогноза и публикации. Отдельная команда автоматически ставить «прибыл», «начал», «выполнено», `lunch_taken=true` или online в нём не задана. Поэтому прежняя граница фактов сохраняется: фактические начало и завершение берутся из отметок инженера, а прогноз по расписанию не является новой отметкой.

Отсутствие сообщения о проблеме позволяет продолжать прогноз «по плану»; оно не даёт Router права переписать фактическую историю. Sys может показать прогноз и отдельно факт последней подтверждённой стадии.

Ранее принятые напоминания о ключевых отметках и сообщения диспетчеру остаются интерфейсными/операционными механизмами, не автоматическим каналом публикации сектора. Включение напоминания в UI не создаёт само по себе новый вход Router, offline или письмо клиенту о переносе. Конкретные интервалы напоминаний всё ещё не заданы.

### 5.3. Обращение за помощью

Пользователь определил обращение за помощью как сигнал, что нужно разобрать нештатную ситуацию. Sys фиксирует обращение и предоставляет возможность вмешательства. Сам факт открытия чата или вызова человека не содержит достоверного числа минут задержки и не означает автоматического offline.

**Проектная детализация, не отдельное принятое правило классификации:** сначала установить, что именно изменилось — занятость, техническая доступность, ожидаемое прибытие или другое условие. Затем, если появился новый расчётный факт/прогноз, публиковать его через обычный механизм. Не придумывать задержку по одному тексту «нужна помощь». Передача чата человеку сама по себе обслуживается sys, не создавая обязательного изменения географии или назначения.

### 5.4. Сохраняемые различия

| Вид информации | Какой смысл нельзя потерять |
|---|---|
| Задержка текущей работы | Инженер ещё занят в точке выполнения; явное уточнение может изменить ожидаемое освобождение |
| Техническая остановка | Рабочая доступность `online/offline` и предполагаемый возврат; не состояние сетевой связи |
| Прогноз прибытия | ETA к конкретной следующей точке, а не время освобождения в произвольной другой точке |
| Штатное движение без сообщения о проблеме | Продолжение действующего прогноза; не самостоятельный повод пересчитывать |
| Отметка начала/завершения | Факт, который хранит sys; не автоматически созданная стадия Router |

`available_from` относится именно к `start_location`. Нельзя записать ETA на другой адрес как время освобождения в текущей точке и затем второй раз прибавить всю дорогу. Подготовку прогноза и различение перечисленных ситуаций выполняет sys; вычисление нового маршрута — Router.

`online` по-прежнему не означает «свободен прямо сейчас». Технический порог малого отклонения остаётся внутри Router, меняется только предусмотренной специальной операцией и не становится политикой sys.

### 5.5. Оставшаяся узкая деталь проекции

Если **независимый реальный триггер** (например, новая заявка) требует нового снимка после того, как плановый срок старой работы уже прошёл, а отметки завершения ещё нет, нужно определить, как sys выразит оптимистичный прогноз в паре `start_location + available_from` и как сохранит незавершённый факт вне свободного пула. Это вопрос подготовки снимка при уже имеющемся триггере, а не повод создать триггер по таймеру.

Не утверждается ни автоматическое закрытие старой работы, ни прежнее правило «срок истёк → null». Автоматическое превращение любого неизвестного значения в текущий момент также не вводится. Поле `null` остаётся возможным представлением действительно не подготовленного значения; его появление только из молчания инженера не согласовано.

## 6. SL5 — план при загрузке и момент актуальности

### Уже согласованные проверки

Sys применяет автоматический результат только при разрешённом приёме, совпадающих `input_hash` и активной `router_context_version`, `main.is_usable=true` и отсутствии конфликта с текущими фактами. `ready` с неназначенными работами отличается от `error` и `pending`.

Повторное чтение того же `result_id` не повторяет применение. Выход из MANUAL — отдельная явная операция, а не обычное повторное чтение, поэтому один только журнал встречавшихся ID не запрещает вернуть подходящий автоматический план.

### Предлагаемый порядок принятия

Проверить форму и принадлежность результата; повторно сверить режим и текущие условия непосредственно перед сохранением; одним согласованным изменением записать новую версию применённого плана и необходимые события. После фиксации обновить интерфейсы и передать необходимые уведомления.

Проверка живых фактов не означает требование полного побайтового равенства журнала снимку. Важно, чтобы предложенные будущие действия не возвращали выполненные/начатые работы в распределение, не назначали второй обед и не начинались из уже неприменимых стартовых условий. Если есть установленный конфликт с явными фактами, sys не ремонтирует результат собственным оптимизатором: готовит актуальную проекцию и ждёт нового результата. Это не разрешает признать конфликтом одно течение времени или молчание инженера вопреки SL4.

### Отображение ожидания — согласовано

**Последний применённый план остаётся на экране с пометкой «Перестраивается» и указанием момента, на который этот план актуален.** Весь рабочий день не очищается. Живые факты могут обновляться отдельно от показанного расчётного плана.

**Проектная привязка времени к уже существующим полям:** для автоматического плана использовать `planning_as_of` того результата, который действительно был применён, и подпись «План по состоянию на HH:MM:SS». Не подставлять `planning_as_of` нового ещё не рассчитанного снимка. `computed_at` — время расчёта, а момент применения — другое событие; они не подменяют момент исходных данных. Все времена хранятся в секундах Unix-time и отображаются в нужной временной зоне.

Для ручного плана следует отдельно показывать, что он ручной, и время соответствующего ручного изменения. Точная подпись/поле — деталь UI и системного контракта, не дата фонового результата Router.

Известно отменённая работа, снятое назначение или данные недоступного инженера не показываются как действующее указание только потому, что старый план ещё виден. Sys отражает действующие бизнес-факты, но не выбирает новое назначение самостоятельно. Состояние отдельного спорного визита — «ожидается обновление», а не обещание старого уже невозможного времени.

При ошибке расчёта остаются последний принятый план, факты и видимая ошибка. Ошибка не маскируется вечной загрузкой или новым успешным распределением.

### Предложение о границе AUTO/MANUAL

Момент включения MANUAL и право применения автоматического результата должны проверяться согласованно. Результат, уже находившийся в обработке, не проходит запись после принятого переключения. Для реализации можно использовать внутреннюю версию управляющего состояния sys; это не новый вход Router.

На возврате AUTO сверяется актуальная проекция, в том числе использованный обед и начатые работы. До подходящего результата прежний ручной план виден как последний применённый, а не как результат новой автоматики. Сохранение режима после рестарта остаётся предложением v1: пользователь явно подтвердил отображение плана, но отдельно не ответил на вопрос восстановления MANUAL при перезапуске. Оно не объявляется новым согласованным поведением.

**SL5 принят в части интерфейса:** последний применённый план, «Перестраивается» и момент его актуальности. Проверки применения уже установлены контрактом Router; техника переключения и восстановление процесса детализируются отдельно.

## 7. SL6 — диспетчер из .env и создание инженеров

### 7.1. Один диспетчер, два способа входа — согласовано

В текущей конфигурации **один человек-диспетчер**. Его email и пароль заранее заданы в серверном `.env`. Диспетчер может войти:

- по email с одноразовым кодом;
- по настроенному паролю, независимо от SMTP.

Оба способа открывают **одну и ту же диспетчерскую учётную запись и роль**, а не две учётки с разными данными. Парольный путь нужен, чтобы доступ к Dashboard не зависел от работоспособности почтового контура. На нём не требуется дождаться SMTP или получить дополнительный email-код.

```text
Диспетчер
  ├── email → код через SMTP → проверка auth-engine
  └── настроенный пароль → проверка auth-engine без SMTP
                                ↓
                  одна диспетчерская сессия / роль
                                ↓
                     Dashboard и страница «Чаты»
```

**Рабочие имена переменных:** `DISPATCHER_EMAIL`, `DISPATCHER_PASSWORD`. Имена — проектная разметка; реальные значения в документ не включаются. Под «заданы заранее» понимается серверная конфигурация, не пароль во frontend или жёсткий литерал в публичном исходном коде.

**Предлагаемые границы реализации:** конфигурация читается auth-engine на сервере; пароль не возвращается в API/AI, чат или журнал; реальный `.env` не включается в репозиторий, `.env.example` содержит только имена и пустые значения. Способ проверки/хранения производного секрета, смена пароля, срок сессии и ограничения попыток оформляются при техническом контракте auth-engine. Это не основание попросить пользователя прислать пароль в переписку.

### 7.2. Инженеров создаёт диспетчер — согласовано

После входа диспетчер сам добавляет инженеров, указывая их email. Публичный вход по произвольному адресу не выдаёт роль инженера. Email-код открывает уже созданную инженерную роль; новый парольный механизм инженерам автоматически не добавляется.

Добавление email создаёт учётную запись/роль инженера, но само по себе не даёт Router отсутствующие навыки, смену, транспорт и стартовую точку. Источник этих обязательных полей — профиль, датасет или дальнейший ввод в пределах согласованных правил. Недостающие значения не заполняются выдуманными нормативами. Форма редактирования профиля — следующий этап интерфейса.

Не требуется заранее завести всех инженеров вне Dashboard. Прежнее предложение v1 о только предварительном списке сотрудников заменено этим сценарием.

### 7.3. Клиенты — согласовано

Клиентская учётная запись создаётся при первом успешном входе по email-коду либо открывается уже существующая. AI доступен после этого входа и проверки дневной квоты. В действующей сессии клиент подтверждает содержание заявки без второго обязательного email-кода.

Подтверждение email не повышает роль до инженера или диспетчера. Совпадение email с уже существующей учёткой и возможное совмещение ролей потребуют явного правила auth-engine; новых ролей по тексту запроса не выдаётся.

### 7.4. Полномочия и ещё не выбранные детали

Инженерный AI меняет `online/offline` только своего инженера; offline требует кнопочного подтверждения. Диспетчерский `fix` использует бизнес-возможности своей роли с журналом и остановкой, а не сырой SQL/доступ к памяти Router. Специальная настройка допуска остаётся отдельной служебной возможностью.

Пользователь определил создание инженеров, но отдельно не ответил, **кто может менять skills, транспорт и офис**. Прежнее предложение «только диспетчер» не превращается в утверждённое право; этот пункт остаётся в матрице полномочий для следующей детализации.

## 8. SL7 — конфликты: предотвращать в UI, не перетирать на сервере

**Согласовано:** UI/UX должен снижать вероятность одновременных конфликтующих действий, но молчаливая перезапись данных недопустима. Идемпотентность повторной операции сохраняется. Интерфейсные меры не заменяют проверку на стороне sys.

### Предлагаемый технический механизм принятого правила

Каждая изменяющая операция получает устойчивый `operation_id` и указывает ожидаемую версию затрагиваемых данных, когда действие основано на их просмотре или подтверждении.

Повтор той же операции возвращает прежний результат. Другие параметры под тем же ID — ошибка, не новая запись. Подтверждение подготовленной заявки связывается с конкретной версией содержания и владельцем.

Если другой человек или агент уже изменил нужные условия, sys возвращает конфликт с актуальной версией; не перетирает новое значение по принципу «последняя запись победила». Проверять следует связанные с операцией данные, а не любую запись чата во всей системе, иначе обычная активность будет мешать всем действиям.

```text
Клиент открыл окно заявки
  → диспетчер изменил его
  → клиент подтвердил старый экран
  → sys сообщает об изменении условий и просит обновить подтверждение
```

Для AI в fix конфликт не означает вечную остановку: агент читает новое состояние, показывает новое намерение и выполняет новую разрешённую операцию. Он не повторяет запись со снятой проверкой версии. Дополнительное подтверждение зависит от уже согласованных правил конкретного действия, а не добавляется ко всем записям автоматически.

Журнал показывает автора и источник: человек через UI, интеграция либо конкретный AI-run от имени пользователя. Остановка run блокирует ещё не применённые действия, но не стирает завершённые записи. Права и режим read-only/fix проверяются повторно перед записью.

**SL7 принят:** без silent overwrite. Версии объектов, `operation_id` и конкретный ответ конфликта — рабочая реализационная форма этого правила; точный внешний код ответа определяется в gateway-контракте.

## 9. SL8 — один диспетчер и отдельная страница «Чаты»

### 9.1. Принятый сценарий передачи

`call_dispatch_helper()` вызывает **человека-диспетчера** для ответа вместо AI в текущем клиентском или инженерном диалоге. Передача начинается по вызову. Обращение появляется отдельным чатом/вкладкой на странице **«Чаты»** в Dashboard.

Все такие чаты обслуживает один диспетчер. Отдельное распределение между операторами, назначение владельца и обязательная стадия «Принять обращение» не требуются выбранным сценарием. Открытие вкладки диспетчером не является условием выключения агента: он отключается уже при передаче.

```text
Диалог с AI
  → вызов call_dispatch_helper()
  → sys регистрирует передачу текущего чата человеку
  → AI у обратившегося отключается
  → на странице «Чаты» диспетчера появляется этот диалог
  → пользователь пишет; отвечает только человек-диспетчер
  → диспетчер нажимает «Завершить передачу»
  → контекст и история сохраняются
  → активная вкладка исчезает со страницы диспетчера
  → агент возвращается в тот же пользовательский диалог
```

«AI отключается» относится к переданному диалогу, а не к AI-модулю целиком, не к другим пользователям и не к самому диспетчерскому помощнику.

### 9.2. Состояния общения — рабочая разметка

Достаточно двух смысловых режимов `ai` и `dispatcher`. Названия кодов — проектное оформление. Отдельный признак непрочитанности или ожидания первого человеческого ответа может быть UI-данными; он не является обязательным шагом принятия обращения несколькими диспетчерами.

Пока режим `dispatcher`, AI не пишет параллельные ответы и не продолжает от имени этого диалога изменять данные в фоне. Новые сообщения пользователя хранятся sys и отображаются в соответствующей вкладке диспетчера. Ответ человека имеет явное авторство «Диспетчер».

Наличие вкладки не означает мгновенного ответа: пока человек не написал, интерфейс может честно показывать ожидание. Само ожидание не переключает пользователя обратно к AI.

### 9.3. Завершение только действием диспетчера

Когда диспетчер считает ответ завершённым, он нажимает кнопку завершения передачи. Это возвращает AI, убирает вкладку из активной страницы «Чаты» и **не удаляет историю диалога**. Созданные заявки, изменённая доступность и другие уже применённые действия также не отменяются закрытием чата.

Прежнее предложение v1 о завершении передачи самим клиентом/инженером не включается в текущий сценарий. Автоматический возврат по таймеру, закрытию вкладки браузера или молчанию диспетчера не вводится.

Возвращённый агент получает разрешённый контекст того же диалога, включая относящиеся к нему человеческие сообщения. Внутренние данные других чатов и закрытые для этой роли справочные материалы не добавляются в контекст автоматически. Сам возврат разрешает дальнейшую работу AI; необходимость немедленной дополнительной генерации без сообщения пользователя не задана.

### 9.4. Технические защиты — предложения для реализации

Повторный вызов при уже открытой передаче возвращает существующее обращение, не создавая несколько активных вкладок. После закрытия следующий реальный вызов может начать новый эпизод передачи того же диалога; история остаётся общей.

Передача и завершение должны проверяться sys согласованно с действиями AI. Если генерация или tool были начаты до переключения, после передачи не должны публиковаться новые автоматические ответы или применяться ещё не зафиксированные записи из этого запуска. Уже выполненные бизнес-действия не исчезают: их исход остаётся в журнале.

Позднее сообщение диспетчера из закрытой вкладки не должно молча открыть закрытую передачу либо столкнуться с новым ответом AI. Проверяется состояние конкретного диалога/эпизода; это не глобальная блокировка всех чатов.

### 9.5. Отделение от других режимов

Передача человеку не означает технический offline инженера, не переключает AUTO/MANUAL маршрутизации и не даёт пользователю диспетчерские права. Сам вызов и человеческие ответы не создают LLM-запросов. Дневная квота AI после возвращения агента сохраняется, а не начинается заново.

Наличие отдельной кнопки «Позвать диспетчера» вне tool, например при исчерпанной квоте, не было подтверждено новым ответом. Такая кнопка остаётся допустимым предложением интерфейса, но не добавляется как уже принятое требование.

|---|---|
| Запрос входа по email-коду | `account_login_code`; код создаёт и проверяет auth-engine. Парольный вход диспетчера такого письма не требует |
| Подтверждённая отправка заявки | `request_received`; не обещает назначения |
| Sys принял назначение | `engineer_assigned` по соответствующему бизнес-переходу |
| Установлена необходимость пересогласовать клиентское окно | `visit_change_required` со ссылкой на экран заявки |

Парольный вход диспетчера не зависит от SMTP. Нет второго обязательного кода отправки в действующей клиентской сессии. Задержка внутри окна не вызывает письмо. Отсутствие отметки, техническая ошибка Router и продолжающийся расчёт не доказывают невозможность визита. Письма создаёт sys, не модель и не SMTP.

### Предложения реализации

Намерение отправки привязать к бизнес-событию/эпизоду, а не к каждому `result_id`. Новый результат может повторять то же назначение: это не новый повод отправлять подтверждение. Для запроса переноса важно отличать продолжающийся эпизод от действительно новых согласованных условий клиента.

Если письмо ещё не передано, перед отправкой проверить, что его основание не утратило смысл. Уже принятое SMTP письмо нельзя «отозвать» изменением строки базы. Точную обработку восстановившегося назначения после отправленного запроса переноса определить в сценарии заявок, не в транспортном SMTP-коде.

Готовый usable-план с неназначенной заявкой не означает математически доказанной невозможности. Сообщение клиенту следует формулировать как результат текущей обработки: назначение в выбранных условиях не получено, предлагается изменить окно. Причину диспетчер видит в исходных результатах. Непригодный план или ошибка не создают массовый автоматический отказ.

Для обеда системная операция восстановления сохраняет локальное required-условие и явный перечень снятых работ. Предлагаемая проверка побочных отказов остаётся: если новый план снимает дополнительные прежние назначения, не отправлять такие отказы молча как уже подтверждённый выбор диспетчера. Сам алгоритм sys не исправляет.

## 11. Чтение для интерфейсов, авторизация и квоты

Четыре внешних входа получают разрешённые представления sys. Не нужно отдавать полный объект внутреннего хранилища клиенту лишь для показа одной карточки.

Предлагаемые представления: клиентские активные заявки; инженерный текущий рабочий план/карточка; диспетчерский обзор и отдельная страница активных переданных чатов; ролевые ответы интеграционного API. Конкретные endpoints, подписки и формат доставки обновлений — отдельные gateway-контракты.

Сессия, роль, scope знаний и владелец дневного бюджета назначаются сервером. Квота AI на email не сбрасывается новым диалогом, вкладкой или вызовом другого инструмента. Вызов человека и его сообщения не являются новой платной LLM-генерацией. Ограничения email-кодов и частоты обращений человека — отдельные настройки, не тот же счётчик AI.

Сроки сессий, погашение/переотправка кодов, парольный вход диспетчера, точные ограничения и обработка секретов будут детализированы в auth-engine. Email/пароль диспетчера берутся из серверного `.env` по принятому SL6. В этом раунде не задаются неподтверждённые численные значения.

## 12. Рабочая разметка системной операции

Общий механизм операций принят в SL1. Поля ниже — его проектная логическая форма, не утверждённые HTTP endpoints:

| Поле | Смысл |
|---|---|
| `operation_id` | Устойчивый ID одной бизнес-операции |
| `actor` | Проверенный пользователь/интеграция и роль, сформированные sys |
| `source` | UI, интеграция либо AI-run; источник не заменяет полномочия |
| `action` | Разрешённое действие из системного каталога |
| `target` | Объект/объекты операции |
| `expected_version` | Версия данных, на которой основан просмотр/подтверждение, когда нужна |
| `payload` | Проверенные аргументы конкретной операции |
| `confirmation` | Ссылка на подтверждённое намерение там, где оно обязательно |
| `run_id` | Связь с AI и остановкой, если действие пришло от агента |

Ответ отличает применённую запись, ожидание подтверждения, конфликт версии, запрет, отмену до записи и неизвестный исход. Не обязательно копировать все поля этого объекта в внешний интерфейс. Сам tool-call ID провайдера не является достаточным ключом бизнес-идемпотентности.

У операции создания заявки, изменения окна, отметки инженера и переключения MANUAL разные допустимые состояния и последствия. Единая обёртка не означает универсального метода записи произвольного поля базы.

## 13. Проверки будущей реализации

Это сценарии приёмки, а не результаты проведённых испытаний.

| Сценарий | Ожидаемое поведение |
|---|---|
| Повтор подтверждения отправки заявки | Один активный request_id и одно событие отправки |
| До подтверждения изменилась версия заявки | Старое подтверждение не активирует новое содержание без согласия |
| Клиент выбирает дату, но ещё не нажал «Подтвердить» | Действующие условия заявки не изменены |
| Клиент подтвердил новую дату/окно | Немедленная запись новых условий той же заявки; без второго активного окна |
| В новом окне назначения нет | Старое окно не восстанавливается автоматически |
| Человек/агент меняют устаревшие условия | Конфликт, а не молчаливая перезапись |
| Часы прошли ожидаемый срок, новых сообщений нет | Штатный прогноз сохраняется; сам по себе сектор не переписывается и Router не запускается |
| Напоминание об отсутствующей отметке | UI/обращение не превращаются автоматически в публикацию, offline или письмо о переносе |
| Штатное выполнение без материального отклонения | Живые данные sys обновляются без снимка; якоря остаются прежними |
| Выявленное превышение начатой работы | Только `overrunDetectedAt`, проекция и вывод инженера из задачи; факт завершения не создаётся |
| Сообщён ETA к следующему адресу | Не записывается без проверки как освобождение в другой точке с повторным добавлением дороги |
| Явно сообщил о проблеме/технической остановке | Sys разбирает вид изменения; не подставляет выдуманную задержку |
| Отображается старый план во время расчёта | Есть «Перестраивается» и момент состояния именно показанного плана |
| Router вернул тот же result_id | Нет повторного применения, возврата выполненных пунктов и повторных писем |
| Работа началась во время расчёта | Явный факт не отменяется новым распределением |
| MANUAL включён во время приёма результата | Запоздалая автоматическая запись не заменяет ручной план |
| Возврат AUTO после использованного обеда | Факт lunch_taken соблюдён; второй обед не создаётся |
| SMTP недоступен, диспетчер вводит правильный настроенный пароль | Вход в ту же диспетчерскую роль не ждёт email-кода |
| Неправильный пароль диспетчера | Вход не предоставляется; детали лимитов определяет auth-engine |
| Клиент ввёл email на экране инженерного входа | Роль инженера не создаётся автоматически |
| Диспетчер добавил email инженера | Создан соответствующий доступ; параметры маршрутизации не выдумываются |
| Создана передача чата | У диспетчера появляется вкладка на странице «Чаты», AI данного диалога прекращает автоматические ответы/действия |
| Диспетчер ещё не открыл вкладку | AI не включается обратно только по этой причине; пользователь видит ожидание |
| Повторный вызов в открытом эпизоде | Нет второй активной вкладки этого обращения |
| Диспетчер завершил передачу | Вкладка исчезла из активных, история сохранена, агент возвращён |
| Поздний AI-ответ после передачи | Не публикуется как параллельный ответ пользователю |
| Оператор завершил один из нескольких чатов | Остальные переданные чаты остаются за ним; глобального переключения AI нет |
| Ошибка SMTP после сохранения заявки | Заявка существует, состояние письма отдельное |
| Задержка внутри клиентского окна | Письмо о переносе не создаётся |
| AI-run остановлен | Новые записи не выполняются; завершённые не выдаются за отменённые |
| Повтор восстановить обед | Нет второго исключения заявок или сброса lunch_taken |

## 14. Что далее формализовать, без повторного раунда SL1–SL8

### 14.1. Принятые решения уже можно положить в основу системных операций

Следующая разметка описывает для каждого обработчика вход, права, допустимое состояние, подтверждение, сохраняемый результат, необходимость публикации снимка и уведомления. Она не переносит оптимизацию маршрутов в sys.

Основные группы: вход по email; парольный вход диспетчера; создание инженера по email; подготовка/подтверждение заявки; немедленный перенос её условий; фактические отметки и доступность; публикация снимка; приём результата; AUTO/MANUAL; открытие/завершение передачи чата; письмо; исполнение/остановка AI-операции.

### 14.2. Узкие оставшиеся детали

| Деталь | Статус после ответа |
|---|---|
| Пара старта при независимом новом триггере, если плановый срок работы прошёл без отметки | Нужна конкретизация проекции; запрещено создавать такой триггер только по часам |
| Отмена и перенос уже начатой работы | Пользователь утвердил немедленность переноса, но не все ограничения этих сценариев |
| Кто меняет skills/транспорт/офис инженера | Вопрос прав не закрыт созданием инженера по email |
| Поведение MANUAL после рестарта | Осталось предложением, не частью явного ответа SL5 |
| Прямая UI-кнопка вызова человека | Tool принят; дополнительный способ вызова — деталь будущего UI |
| Форматы версий, транзакции и доставки обновлений | Проектная реализация; выбираются без изменения принятой логики |
| Сроки сессий/кодов, ограничения попыток, интервалы напоминаний и квоты | Значения ещё не названы, не назначаются произвольно |

Эти детали не возвращают уже принятые SL1, SL2, немедленный перенос, отсутствие таймерного пересчёта, резервный парольный вход и единственную диспетчерскую страницу «Чаты» на повторное согласование.

### 14.3. Последующая синхронизация других документов

В основной концепции и AI/SMTP потребуется отразить парольный вход единственного диспетчера, создание им инженеров и точный lifecycle передачи чата. В местах router/engine-документов, где неизвестное освобождение из-за истёкшего прогноза было лишь рабочей интерпретацией, нужно снять её автоматическое применение по таймеру. Поля `start_location`, `available_from`, hash и context_version не меняются этим ответом; изменяется ответственность sys за основание и момент публикации.

Другие файлы здесь не редактируются скрыто. Их устаревшие предложения не получают приоритет над настоящим уточнением SL4.

## 15. Источники и статус решений

Приоритетный источник этой редакции — последний ответ пользователя на SL1–SL8. Подтверждены SL1 и SL2; в SL3 выбран немедленный перенос после кнопки; SL4 отверг автоматическую публикацию при молчании/истечении прогноза; в SL5 принят старый видимый план с моментом актуальности; SL6 задал один диспетчерский аккаунт из `.env` с двумя входами и создание инженеров; SL7 запретил перезапись; SL8 задал страницу «Чаты» одного диспетчера и завершение им передачи.

Использованы `system_layer_concept_v1.md` (прочитан целиком), ранее полученные разделы `system_concept_v14.md`, `router_contract_v2.md`, `ai_smtp_concept_v3.md` и текущая переписка. Исходная концепция с доски задаёт имена блоков, но не отменяет более поздние ограничения. ТЗ «Билайн Бизнес» задаёт предмет задачи — маршруты, ограничения, перепланирование и объяснения, а не конкретные механизмы sys.

Конкретные механизмы версий операций, отображение полей времени, проверки перехода диалога, защита секретов и некоторые формы данных описаны как проектные детали. Они не приписываются пользователю как дословные требования. Новый ответ не считается подтверждением оставшихся под-вопросов, на которые он не отвечал.

## 16. Изменения v2 относительно v1

- Внутренние units, общий механизм операций и разделение состояний переведены в согласованные решения.
- Немедленный перенос привязан к кнопке «Подтвердить», сохраняет request_id и не создаёт два активных окна.
- Убрано прежнее автоматическое правило «прогноз истёк → null → публикация»; без триггера сохраняется штатный прогноз, сектор не меняется по часам.
- Сохранено различие прогноза и явных фактов; оставшаяся проекция при независимом триггере обозначена отдельно.
- При расчёте показывается последний применённый план, «Перестраивается» и момент, к которому относится этот план.
- Вход единственного диспетчера: email-код или пароль из серверного `.env`, без SMTP-зависимости парольного пути. Инженеров создаёт диспетчер по email.
- Запрет silent overwrite закреплён независимо от мер предотвращения конфликтов в UI.
- Общая очередь нескольких операторов заменена страницей «Чаты» одного диспетчера. AI отключается по вызову и возвращается по кнопке диспетчера; контекст сохраняется, активная вкладка исчезает.
- Сценарии будущих проверок обновлены; неподтверждённые подпункты не объявлены закрытыми.
