# Рекомендуемый стек и план работ (подготовка 3 дня + хакатон)

> Назначение: договориться до старта, кто что делает и в каком порядке. План учитывает: 3 полныхstack, 1 frontend, 1 дизайнер, все вайбкодят. Приоритет — ядро ТЗ с Apple-полировкой, усилители по остатку (`12`).

---

## 1. Стек (рекомендация — Вариант A из `09`)

| Слой | Технология | Почему |
|---|---|---|
| Frontend | React + TypeScript + Vite, Tailwind, MapLibre GL JS, framer-motion, TanStack Query | Скорость вайбкодинга, контроль дизайна, красивые анимации |
| Backend | Fastify (Node/TS) — или FastAPI, если 2+ уверенно за Python | Один язык с фронтом → шаринг типов |
| Solver | Python + OR-Tools (worker, FastAPI-обёртка); прототип Timefold в день 0 | Зрелость, наша модель ограничений; выбор по `05` |
| БД | PostgreSQL (+ опц. PostGIS), Prisma/Drizzle | Скорость и типизация; SQLite как минимум-вариант |
| Realtime | SSE | Простота, авто-реконнект |
| Гео | OSRM в docker (город-вырезка), геокодинг заранее + кэш | Офлайн, бесплатно (`06`) |
| LLM (опционально) | Локальный Qwen (vLLM/Ollama, OpenAI-compatible API) | Ввод заявки текстом; только надёжные structured output |
| Инфра | pnpm monorepo, docker-compose, GitHub Actions (смоук) | Целостность |

## 3. План подготовки (сегодня + 2 дня до старта)

**День 0 (сегодня, вечер):**
- Репо-скелет, docker-compose, «hello» всех сервисов, CI-смоук.
- Прототип солвера: OR-Tools на 10×10 мини-датасте (окна+навыки) — проверить, что модель собирается за вечер. Параллельно Timefold-прототип — сравнить, выбрать.
- OSRM: вырезка города, `/table` работает.
- Дизайнер: мудборд + токены + ключевые экраны глав-консоли в Figma (можно low-fi).

**День 1 (завтра):**
- Импорт датасета + fallback-датасет (`14`), геокодинг демо-адресов, кэш матриц.
- Солвер-сервис: полный ввод/вывод по контракту, причины (v1), метрики, тест на golden-датасете.
- Фронт: каркас главного экрана (карта + список), тема, дизайн-система в коде.

**День 2 (последний до старта):**
- Перепланирование: события, версии планов, диффы, SSE.
- Главный экран: таймлайн v1, панель заявки с «Почему так» v1.
- Смоук демо-сценария (кнопки-триггеры), `demo:reset`.
- Зафиксировать: всё, что не сделано — не делаем (заморозка скоупа).

## 4. План хакатона (дни старта → сдача)

**День Х1 (старт, получаем реальные данные):**
- Утро: адаптер к их формату, валидатор, вопросы организаторам (`01` §8).
- День: таймлайн до продакшн-качества (окна, drag&drop с превью), панель причин v2, дельта-анимация v1.
- Вечер: первый полный прогон демо-сценария, список багов.

**День Х2:**
- Дельта-анимация, симулятор дня (scrubber + события), риски SLA.
- Полировка по чек-листу `10` §7 (первый проход).
- Что-if слайдеры весов, «жадный режим» сравнения.
- Вечер: прогон демо №2 с таймером.

**День Х3 (перед сдачей):**
- Утро: LLM-ввод заявки (если ядро стабильно), вид инженера, экспорт.
- День: финальная полировка, метрики в продукте совпадают со слайдами.
- Вечер: **прогон №3**, запись видео-бэкапа, чек-лист `13` §6.

**День сдачи:**
- Только репетиции и мелкие фиксы. Никакого нового кода после обеда.

## 5. Definition of Done (по горизонтам)

- **MVP (конец Х1):** импорт → план за секунды → карта+таймлайн → причины → новая заявка → дельта. Работает без интернета.
- **Полный (конец Х2):** + анимации дельты, симуляция, риски, сравнение режимов, полировка v1.
- **Презентационный (Х3):** + LLM-ввод, метрики/слайды, видео-бэкап, 3 прогона.

## 6. Правила совместной работы (зафиксировать в репо)

1. Схема контрактов (`packages/shared`) меняет только владелец интеграции; остальные подтягивают.
2. Утро: 15-мин стендап — вчера/сегодня/блокеры; доска задач актуальна.
3. Каждый PR: смоук-тест зелёный, UI-изменения — скриншот в PR.
4. Дизайн-ревью сборки каждый вечер (дизайнер смотрит билд, даёт список правок).
5. Новые фичи в разгар хакатона — только через вопрос «какая строка ТЗ это закрывает?»
6. Все коммиты малые; `main` всегда деплоится и демо-пригоден (правило «сцена = main»).
