# Внешний API — концепция v2

**Редакция:** 15 сентября 2026 года.  
**Основа:** `external_api_concept_v1.md`, исходный набросок API, последние ответы пользователя на API1–API7 и ранее согласованные границы системы.  
**Статус:** принята упрощённая модель — токены единственного диспетчера, полный доступ внутри типа `client / eng / master`, без разделения по конечным пользователям, бессрочный ключ до удаления. Внешний доступ к AI исключён. Письма отправляет наша система. API заменяет соответствующие UI-действия и предоставляет системную отладку.

Последний ответ пользователя имеет приоритет над предложениями v1 о ключах отдельных приложений, дополнительной пользовательской авторизации, индивидуальных scopes, сроках ключей, внешнем AI и выборе владельца уведомлений. Эти варианты не являются действующим контрактом.

Каталог операций System Layer и подробные endpoints по просьбе пользователя сейчас не составляются. Другие документы комплекта не перезаписываются. Токены не выпускались и не удалялись; изменения серверов, данных и программного кода не выполнялись. Этот файл фиксирует концепцию, не результаты испытаний.

## 1. Назначение API

> **API — программная замена соответствующих UI-действий с дополнительными отладочными возможностями. Все обращения проходят через System Layer.**

Вместо нажатия кнопки или чтения карточки внешняя программа передаёт запрос. Системное правило, проверка состояния объекта и результат действия остаются общими с приложением. API не содержит второго варианта бизнес-логики.

```text
Внешняя программа
    → действующий токен диспетчера: client / eng / master
    → внешний API: проверка токена и категории
    → System Layer: тот же обработчик, состояние и проверки
        ├── Data Layer
        ├── опубликованный вход Router — только при действительном триггере
        ├── применённый рабочий план и доступные расчётные сведения
        └── формирование писем → SMTP-gateway → внешний SMTP
```

Внешних вызовов AI в этой схеме нет. Исключение AI из внешнего API не отключает собственные AI-чаты приложения.

У API остаётся исходное назначение: подключение системы к уже существующим проектам. Для этого не вводятся несколько организаций, арендаторов, отдельные владельцы интеграций или собственная система управления конечными пользователями API.

## 2. Итог API1–API7

| Пункт | Принятое решение |
|---|---|
| API1 | Все токены принадлежат единственному диспетчеру; по конечным пользователям не разделяются |
| API2 | Все токены бессрочные и дают полный доступ внутри категории; при создании только название и тип; секрет показывается один раз; затем ключ можно удалить в Dashboard |
| API3 | Всё через sys; полный категорийный доступ и отладочные возможности, без дополнительных выдаваемых scopes |
| API4 | Достаточно догрузки, связи внешних ID с внутренними и принятой защиты от дублей/перезаписи; автоматического двустороннего зеркалирования нет |
| API5 | Отдельные внешние уведомления и подписки не нужны; обычные запросы чтения данных остаются способом получить состояние |
| API6 | Внешний доступ к dashboard AI отменён; другие агенты через этот API также не открываются |
| API7 | Бизнес-письма отправляет наша система; переключаемого варианта «уведомляет внешняя интеграция» нет |

Последнее общее уточнение пользователя: права API — замена прав соответствующего UI, плюс дополнительные отладочные системные возможности. Полный доступ означает полноту категории, а не отмену границ модулей или бизнес-ограничений.

## 3. API1 — владелец токена и выбор объекта

### 3.1. Один владелец

**Владелец каждого ключа — один и тот же диспетчер.** Категория определяет набор доступных функций, не другого владельца и не персонального клиента/инженера.

Для обращения по API-токену не требуется дополнительно входить email-кодом от имени выбранного клиента или инженера. Не вводятся пользовательские токены, обязательная вторая сессия, федерация внешней авторизации либо делегирование от каждого конечного пользователя.

Это отдельный способ авторизации машинного обращения. Обычные UI-входы клиента, инженера и диспетчера сохраняют свои уже согласованные правила.

### 3.2. ID объекта — не авторизованный пользователь

`request_id`, `client_id`, `engineer_id` и аналогичные идентификаторы могут указывать, с каким объектом работает запрос. Они **не делят токены по пользователям** и не подменяют владельца ключа.

Например, инженерный ключ не закреплён за инженером А: он позволяет выполнить инженерную системную функцию для выбранного допустимого инженерного объекта. Клиентский ключ не ограничен одной личной заявкой владельца email. Персональная проверка «объект принадлежит конечному пользователю токена» из v1 здесь не действует, потому что такого конечного пользователя у ключа нет.

При этом сохраняются существование объекта, его допустимое состояние, связи данных и категория запрошенной функции. Выбор объекта не позволяет использовать инженерный ключ как master или изменить уже начатую заявку вопреки общему правилу.

### 3.3. Что остаётся в журнале

Для разбора действий можно сохранять ID/название использованного ключа, категорию, владельца-диспетчера и источник `external_api`. Это проектная детализация журнала, не новая модель индивидуальных полномочий.

Машинное действие не требуется подписывать как личный клик клиента или ручной клик диспетчера. Наличие действующего ключа подтверждает право API-вызова, но само по себе не доказывает, что владелец указанного в данных email прошёл проверку адреса.

## 4. API2 — создание и удаление токенов

### 4.1. Dashboard

При создании вводятся ровно два пользовательских параметра:

| Параметр | Значение |
|---|---|
| Название | Удобная диспетчеру подпись ключа |
| Тип | `client`, `eng` или `master` |

Не добавляются выбор срока действия, персональный пользователь, список объектов, отдельные разрешения или обязательная регистрация внешнего приложения.

```text
Диспетчер ввёл название и выбрал тип
    → создал токен
    → получил полное значение один раз
    → сохранил его у себя для обращения к API

Позднее в Dashboard:
    → видит запись ключа без повторного раскрытия секрета
    → может удалить ключ
```

### 4.2. Срок и полнота прав

**Все ключи бессрочные: действуют до удаления.** Периодическое истечение, refresh-токен и обязательная ротация по расписанию не вводятся. Обычный перезапуск не отзывает ключи сам по себе.

Каждый ключ имеет полный доступ внутри своего типа. Нет клиентских ключей с произвольным подмножеством клиентских функций или master-ключей, которым надо отдельно включить import/debug/reset.

### 4.3. Однократный показ и удаление

После создания полный секрет повторно не показывается. Если значение потеряно, можно создать новый ключ; прежний при необходимости удалить. Это следствие однократного показа, не новый обязательный мастер ротации.

Удаление ключа означает прекращение его использования для новых обращений. Оно не удаляет созданные с ним заявки и не откатывает уже зафиксированные изменения. Технически допускается сохранить несекретную запись о прежнем ключе для истории, но удалённый ключ больше не должен приниматься.

Необходимость проверки удаления перед отложенной записью, способ хранения проверочного представления секрета и формат заголовка — технические детали общего механизма, не дополнительные scopes. Реальные значения ключей в документ не включаются.

## 5. Категории и соответствие интерфейсам

| Тип при создании | Исходное обозначение | Доступ |
|---|---|---|
| `client` | `client-app-token` | Полный набор клиентских системных функций категории, без привязки ключа к одному клиенту |
| `eng` | `eng-app-token` | Полный набор инженерных системных функций категории, без привязки ключа к одному инженеру |
| `master` | `master-token` | Полный диспетчерский набор и дополнительные отладочные системные возможности |

Примеры предметных областей, не каталог endpoints:

- **Client:** создание/подтверждение и состояние заявок, разрешённое изменение клиентских условий.
- **Eng:** инженерные задания и рабочий план, предусмотренные фактические действия, доступность, настройки профиля.
- **Master:** данные диспетчерского контура, планы и причины, политики, управление предусмотренными данными и настройки/отладка через sys.

Типы `client` и `eng` не получают master-функции только потому, что их владелец тоже диспетчер. Граница проходит между категориями функций, а не между личными аккаунтами владельцев объектов.

**Явное исключение из замены UI: внешние AI-вызовы отсутствуют даже у master.** Наличие чата с моделью в собственном интерфейсе не создаёт соответствующий endpoint автоматически. Конкретные системные действия, которые умеет выполнять агент, могут быть доступны без него в своей обычной категории.

## 6. API3 — полный доступ и отладочные возможности через sys

### 6.1. Дополнительных привилегий внутри master нет

Предложение v1 отдельно выдавать права на отладку, импорт, управление ключами, сбросы и техническую настройку снято. Если функция принадлежит принятому системному master-каталогу, её доступность не зависит от дополнительного scope конкретного master-токена.

Это не утверждает существование ещё не спроектированных операций и не определяет за пользователя неотвеченные бизнес-сценарии Dashboard. Полнота доступа отвечает на вопрос «кто может вызвать существующее действие», а не создаёт отсутствующее действие и не определяет его последствия.

### 6.2. Отладка

**Принято наличие дополнительных отладочных возможностей.** Возможное содержимое для последующей технической разметки: текущий опубликованный снимок, его hash, активная версия контекста Router, последний принятый расчётный пакет, применённый план, системные состояния и история обработки.

Точный перечень и формы запросов сейчас не составляются. Это не только данные, которые уже нарисованы на экранной карточке: отладочная выдача может быть подробнее UI.

Через sys может выполняться и предусмотренная специальная техническая настройка допуска Router. Дополнительное персональное разрешение master-ключу для неё не проектируется; сама узкая конфигурационная граница Router сохраняется.

### 6.3. Сохраняемые архитектурные ограничения

«Всё через sys» означает именно общий системный контур, а не туннель для произвольных запросов к любому внутреннему серверу.

Не появляются прямое подключение внешнего клиента к PostgreSQL, произвольный SQL, запись в память маршрутов, подмена `input_hash` или замена снимка произвольным payload в обход `mount-data-eng`. Отладочные возможности не являются универсальным proxy к модели или интерфейсом раскрытия серверных credentials.

В AUTO изменения бизнес-данных при действительном триггере формируют новую задачу; Router обнаруживает её автономно. В MANUAL внешний запрос получает/меняет применённый ручной план в рамках соответствующих системных функций, а не фоновый автоматический маршрут.

**Ради диагностики не восстанавливается отключённая шина Router → sys.** Ранее принятый автоматический пакет доступен только как ранее принятый, с его собственной актуальностью, а не как результат текущего фонового расчёта.

## 7. API4 — догрузка и внешние идентификаторы

### 7.1. Догрузка

Используется тот же импорт sys, что и в Dashboard. Для общего пакета данных действует master-категория без отдельного разрешения импорта.

Сохраняются принятые правила: проверить весь пакет; при ошибке или конфликте не применять его частично; повтор того же пакета не создаёт дубли; существующие ручные правки не перетираются новой загрузкой молча. Обновление объекта и повтор первоначальной догрузки — разные намерения.

Автоматическое двустороннее зеркалирование сторонней базы не добавляется. Конкретный приоритет данных из набора и системно формируемых технических параметров остаётся вопросом данных, а не скрытым правилом API.

### 7.2. Связь ID

Сохраняется принятая возможность связать внешний идентификатор с внутренним:

```text
источник данных + тип сущности + внешний ID → внутренний ID
```

Источник — техническая принадлежность импортированных данных. **Он не становится новым владельцем токена, tenant или отдельной областью полномочий.** В интерфейсе создания ключа по-прежнему только название и тип.

Конкретное поле источника/его привязка к пакетам уточняется при реализации. Оно не обязано быть ID ключа: удаление ключа не должно делать недоступной смысловую связь ранее импортированных объектов.

Служебное сопоставление хранится в Data Layer/адаптере; добавлять его в `RouterTaskSnapshot` лишь ради интеграции не требуется. Совпадение внешнего ID или email не является само по себе подтверждением личности или основанием повысить роль учётной записи.

## 8. API5 — обычные запросы без внешнего контура уведомлений

**Отдельные уведомления внешней системе не нужны.** Не добавляются webhook, подписки, callback-адреса, очередь доставки внешних событий или специальный поток обновлений.

Обычная возможность прочитать карточку, список либо рабочий план остаётся частью API как замены UI. Внешний код получает состояние, когда обращается за ним. Автоматический график polling, интервалы и отдельный механизм постоянного опроса этим документом не назначаются.

Сохранение изменения и готовность нового маршрута остаются разными событиями. Успешная запись не выдаётся за завершённую оптимизацию. Ответ/последующее чтение отражают действительное состояние sys; для нового расчёта не нужно повторно создавать заявку.

```text
Запрос изменения → sys сохранил изменение → ответ о фактическом исходе

Когда программе нужны данные:
запрос чтения → текущее разрешённое состояние sys
```

Последний применённый план может быть виден во время пересчёта с моментом его состояния. Ручной план отличается от автоматического; незавершённый расчёт — от готового плана с неназначенными заявками и от ошибки. Чтение не публикует снимок, не двигает `planning_as_of` и не создаёт почтовое событие.

Отказ от внешних уведомлений не отменяет пользовательские письма нашей системы и не выбирает транспорт обновления собственных веб-интерфейсов.

## 9. API6 — AI через внешнее API не открывается

**Прежний пункт доски «запросы к dashboard AI — master-token» отменён последним решением пользователя.** Он остаётся только на исторической фотографии, не в действующем функциональном составе.

Нет внешнего доступа к диспетчерскому, клиентскому или инженерному агенту, проксирования к провайдеру, отдельного API агентных запусков, их журнала управления и остановки. Модель не вызывается внешней программой через универсальную отладочную ручку.

Собственные UI продолжают использовать AI по ранее согласованным правилам. Удаление внешнего AI не меняет их роли, квоты, передачу человеку или инструменты.

Не нужны предложенные в v1 квоты именно для внешних AI-запусков и разрешения на `read-only / fix` через интеграционные ключи. Диагностическое чтение состояния AI-сервиса, если предусмотрено sys, не является запуском модели.

## 10. API7 — письма отправляет наша система

**Единственный принятый ответственный за бизнес-письма — наша система.** Sys связывает уведомление с системным событием, формирует готовое письмо и передаёт его через SMTP-gateway внешнему почтовому серверу.

Не вводятся режимы `system / external` на ключе или настройка «уведомляет подключённый проект». Отсутствие webhook по API5 не отключает эти письма.

Каталог остаётся общим с приложением: вход по email-коду в тех UI-сценариях, где он требуется; заявка получена; мастер назначен; необходимо пересогласовать окно. Сам API-токен не требует дополнительного пользовательского email-входа, чтобы выполнить разрешённое действие.

Задержка, укладывающаяся в согласованное окно, не создаёт письмо о переносе. Чтение плана, продолжающийся расчёт или техническая ошибка не становятся ложным основанием для отказа клиенту.

Для отправки должны быть сохранены необходимые реальные контактные данные. API-авторизация диспетчерским ключом не подменяет факт личной проверки клиентского email. Импорт тестовых строк не изображается личной отправкой заявок всеми указанными клиентами и не вводит новую массовую рассылку.

Подтверждение содержания или другой предусмотренный шаг UI может быть выражен машинным запросом через sys, без открытия наших экранов. Его допустимость определяется авторизацией ключа и общими условиями конкретного действия. Полный доступ не означает удаление всех бизнес-подтверждений, но отдельная обязательная сессия конечного пользователя из v1 больше не требуется. Подробную форму таких запросов определит отложенный системный контракт.

Контроль почты по-прежнему заканчивается на принятии внешним SMTP и его здоровье; конечный tracking не добавляется. Повтор той же операции не создаёт повторное письмо по тому же бизнес-переходу.

## 11. Общие правила данных не меняются от категории доступа

| Правило | Смысл для API |
|---|---|
| Начатая работа | Обычное изменение закрыто; токен вместо UI не является обходом |
| Перенос | Один `request_id` и одно действующее окно после принятого изменения |
| Идемпотентность | Повтор одной операции не создаёт вторую заявку или отметку |
| Конкурентная запись | Новая чужая правка не перетирается устаревшим запросом |
| Публикация | Нет реального триггера — нет нового сектора; чтение и ход времени не инициируют пересчёт |
| GPS | Необязательный сбор; наличие внешнего инженерного запроса не превращает GPS в обязательный вход |
| Факты | Подтверждённое событие не создаётся из истёкшего таймера |
| Router | Его память и алгоритм не редактируются внешним API |
| MANUAL | Работает применённый ручной план; фоновые результаты не обходят отключение |
| Время | Unix-time в целых секундах, длительности отдельно |
| Бизнес-ошибка | Полный категорийный доступ не делает некорректные данные допустимыми |

Эти проверки не являются вновь введённой системой индивидуальных scopes. Они одинаково применяются к разрешённому действию независимо от транспорта.

## 12. Технические детали, не меняющие согласованные права

REST сохраняется из общей архитектуры. JSON по HTTPS и передача ключа в согласованном заголовке, а не в URL, остаются рабочими предложениями реализации из v1. Конкретные маршруты, названия headers, коды ошибок и способ проверки секрета здесь не выбираются.

Такой токен не является безопасным персональным ограничителем конечного пользователя: полномочия шире одной личной заявки/одного инженера. Проектная граница развёртывания — выдавать его доверенной программе диспетчерского контура, не публиковать как общий секрет во frontend каждого клиента. Это не возвращает отклонённую вторую пользовательскую авторизацию.

Детализация алгоритмов хранения токенов, системного журнала и защиты транспорта не выдаётся за проведённую настройку. Новый поиск внешних стандартов в этой редакции не проводился; изменения основаны на решениях проекта.

## 13. Что снято относительно v1

| Прежнее предложение | Действующая версия |
|---|---|
| Отдельный владелец-интеграция + конечный пользователь | Все токены принадлежат одному диспетчеру |
| Проверка принадлежности объекта конкретному клиенту/инженеру токена | Токен не связан с конечным пользователем; проверяются категория и системные условия выбранного объекта |
| Email-вход как второй обязательный контекст API | Для токенового обращения отдельная пользовательская сессия не требуется |
| Выбираемый срок, список scopes и контур объектов | Только название и тип; полный доступ внутри категории; срок до удаления |
| Отдельно выдаваемые master-привилегии | Полный master-каталог и системная отладка без дополнительных scopes |
| Обязательный первый вариант с polling | Обычные чтения; отдельный постоянный механизм обновлений не требуется |
| Dashboard AI по master | Отменён; внешнего AI нет |
| Выбор нашей или внешней отправки писем | Отправляет наша система |

Сохраняются догрузка без скрытого upsert, техническое сопоставление ID, общий путь через sys, истории и бизнес-ограничения. Исходная фотография не удаляется, но отменённые пункты не возвращаются в требования из её наличия.

## 14. Проверки будущей реализации

Это критерии будущего кода, не отчёт об испытаниях.

| Сценарий | Ожидаемый результат |
|---|---|
| Создание ключа | Достаточно названия и типа; срок и пользователь не запрашиваются |
| Повторное открытие записи ключа | Полный секрет не показывается повторно |
| Прошло время / обычный рестарт | Неудалённый ключ остаётся действующим |
| Ключ удалён | Новые обращения не принимаются; созданные прежде данные не удаляются автоматически |
| Два токена одного типа | Один и тот же полный набор функций категории, без скрытых различий прав |
| Client-ключ выбирает другую клиентскую заявку | Нет запрета только из-за отсутствия персональной привязки; общие условия функции соблюдаются |
| Eng-ключ выбирает другого инженера | Нет требования личного совпадения с владельцем токена; категория и состояние проверяются |
| Client/eng вызывает master-функцию | Категория не подходит, действие не выполняется |
| Master вызывает предусмотренную отладочную функцию | Общий sys-путь без отдельного diagnostic-scope |
| Master запрашивает внешний AI | Такой сценарий не открыт |
| Токеновый запрос без email-сессии конечного пользователя | Не отвергается только из-за отсутствия не предусмотренного второго входа |
| Передан email как данные | Не проставляется фиктивное подтверждение адреса |
| Работа начата | Обычный перенос не проходит несмотря на полный доступ категории |
| Повтор записи после потерянного ответа | Возвращается исход той же операции, без дубля |
| Конфликтный импорт | Пакет не применяется частично и не перетирает существующие значения |
| Удалён ключ, использованный для импорта | Объекты и сопоставление внешних ID не исчезают вместе с секретом |
| Обычное чтение состояния | Возвращаются данные sys; нет публикации сектора от самого чтения |
| Запрошена внешняя подписка/webhook | Отдельного контура уведомлений не создаётся |
| Возникло предусмотренное почтовое событие | Письмо формирует и передаёт наша система |
| MANUAL | Нет чтения фонового Router через скрытую отладочную шину |

## 15. Остаточная детализация и синхронизация

Основные решения API1–API7 закрыты. Конкретный состав отладочных методов, формат токенов/заголовков, реализация сопоставления источников и формы подтверждений относятся к последующей технической детализации, а не к новому раунду выбора владельца ключа или срока.

Предложения DB1–DB7 из `dashboard_concept_v1.md`, на которые пользователь ещё не ответил, не объявляются автоматически принятыми. Ответы по API закрывают соответствующие общие вопросы **прав**: создание ключа с названием/типом, бессрочность, удаление, полный master-доступ без scopes и отсутствие внешнего AI. Они не выбирают состав полного сброса данных, макет редактора политики или ручного плана.

При последующей общей сборке потребуется согласовать:

- **Dashboard:** создание ключа только с названием и типом; показ один раз; удаление; без выбора срока/scopes.
- **System Layer:** доверенный API-контекст единственного диспетчера с категорией вместо обязательной второй сессии конечного пользователя.
- **Data Layer:** владелец и категория токена; отсутствие персональной привязки; удаление ключа не равно удалению импортированных объектов.
- **AI/SMTP:** внешнего вызова моделей нет, пользовательские UI-агенты сохраняются; уведомляет наша система.
- **Общая концепция:** пункт dashboard AI исходного API-наброска отменён; полные типы client/eng/master и системная отладка действуют по настоящему документу.

Остальные файлы в этой редакции не перезаписываются; более ранние противоречащие предложения не получают приоритет над последним ответом.
