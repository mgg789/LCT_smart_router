# Router Core — контракт входа, выхода и специального сектора

**router_contract_v2 · редакция комплекта v14 · 15.09.2026**  
Форма данных: `schema_version="1.0"`. Название артефакта сохранено по запросу; это согласованная редакция предыдущего `router_contract_v2.md`, а не два параллельных контракта.

Связанные документы: [вся система](./32-system_concept_v14.md), [внутреннее устройство](./34-engine_contract_v2.md), [обзор для команды](./19-short_concept.md).

**Назначение:** нормативная форма внешнего обмена Router Core, смысл каждого поля, границы специального сектора и условия применения. Согласованные решения переписки сохранены. Подробные системные действия при неизвестном освобождении по-прежнему отделены как консервативная рабочая интерпретация; численные настройки обеда и допуска не выдуманы. Технические формы полей оформляют согласованную модель, но не доказывают наличие реализованного API.

**Последнее уточнение:** всю иерархию оптимизации задаёт политика диспетчера; первая политика по умолчанию — `fast`. Бизнес-приоритеты не являются жёстко зашитой последовательностью Engine. Обязательная выполнимость от них независима.

**Основания:** текущая переписка, исходная концепция с доски, `system_concept_v13.md`; ТЗ «Билайн Бизнес», стр. 3–5: ограничения, baseline, входные поля и формат результата. Детальная интеграция API и проект алгоритма — в engine-документе с официальными источниками. Этот файл не требует конкретной БД, HTTP URL или способа размещения памяти.

## 1. Зафиксированные границы

System Layer владеет жизненным циклом заявок, фактами выполнения, текущей стадией инженера и применённым планом. Он готовит задачу **оставшегося распределения**: ещё не начатые работы и стартовые условия инженеров. Router не читает полный журнал стадий, не подтверждает выполнение и не возвращает завершённую работу в свободный пул.

Router остаётся единым модулем с двумя внутренними юнитами. Его расчётный вход — опубликованный специальный сектор, а отдельно подключённые ресурсы — карта и техническая настройка допуска. Выход — основной и базовый планы, их основания, метрики и служебная принадлежность к использованным данным.

Память результатов Router не редактируется извне. В AUTO sys принимает актуальный результат; в MANUAL шина Router → sys отключена, но Router продолжает работу. Специальная настройка допуска — узкое исключение, не команда изменить назначения или алгоритм. Режим `AI fix` не предоставляет это право автоматически.

## 2. Внутренние юниты и границы их данных

| Юнит | Получает | Выдаёт / выполняет | Не делает |
|---|---|---|---|
| **Router Runtime** | Целостный `RouterTaskSnapshot`, отдельную карту, внутренние технические настройки | Проверку входа, подготовку дорожных данных, baseline, упаковку ответа, служебное состояние | Не меняет бизнес-состояния; не переставляет заявки и не исправляет основной маршрут после Engine |
| **Routing Engine** | Тот же снимок или его эквивалентное расчётное представление, подготовленные дорожные данные, действующий допуск | Основной `Plan`: назначения, порядок, расписание, обеды и основания | Не читает живую БД, не рассылает письма, не считает baseline и не подтверждает работу инженера |

**Внутренний input Engine** логически состоит из `task_snapshot`, `travel_context` и `technical_settings`. Это не новый внешний сектор и не выбор матрицы вместо графа: конкретный вид `travel_context` определяется при проектировании модели. Runtime сохраняет связь с теми исходными данными, по которым подготовлен вход.

**Внутренний output Engine** — основной план и диагностика основного расчёта. Общий `result_id`, `input_hash`, статус публикации и baseline добавляет Runtime. Факты, на которых основаны объяснения главного плана, предоставляет Engine; Runtime их не придумывает.

Основной план и baseline используют один снимок, одни дорожные условия и обязательные ограничения. Правило baseline не меняется: заявки по порядку поступления, первый подходящий доступный инженер по порядку входа, посещения по порядку назначения, без глобальной оптимизации. Способ вставки обеда без изменения этой последовательности относится к модели; сравнение не должно скрыто исключать обеды только из одного варианта.

## 3. Четыре разных места хранения / обмена

| Область | Содержимое | Кто пишет |
|---|---|---|
| **Специальный сектор — `RouterTaskSnapshot`** | Оставшиеся заявки, инженеры и стартовые условия, обеды, политика, `planning_as_of` | Только sys через `mount-data-eng` |
| **Ресурсы и настройки Router** | Карта, подготовленные дорожные данные, технический допуск | Загрузка ресурса и разрешённая специальная настройка; не обычная политика |
| **Результат Router — `RouterResult`** | Основной и базовый планы, hash, ID, расчётные сведения | Router |
| **Живое состояние приложения** | Факты, статусы, активная часть применённого плана, история, `lunch_taken`, сессии и письма | System Layer; значения для расчёта проецируются в следующий снимок |

Карта, сырые GPS-треки, почта, персональные контакты, чаты, векторы AI, журналы и готовые маршруты не копируются в специальный сектор. `input_hash` хранится рядом с данными или вычисляется из них, но не входит в собственное хэшируемое содержимое. AUTO / MANUAL регулирует приём результата и не является переключателем модели внутри сектора.

## 4. Типы, единицы и справочники

| Тип / соглашение | Значение |
|---|---|
| `UnixSeconds` | Целое число секунд Unix-time. Все абсолютные моменты, включая `planning_as_of`, окна, смены и расчётное расписание |
| `DurationSeconds` | Целый неотрицательный интервал в секундах; длительность работы / обеда — положительная |
| `ID` | Непустая строка. ID заявки и инженера стабильны между снимками |
| `GeoPoint` | Объект `{lat: number, lon: number}`. Широта от −90 до 90, долгота от −180 до 180 |
| Расстояние | `distance_km: number`, неотрицательные километры; это сохраняет рекомендованную единицу ТЗ |
| `null` | Явное отсутствие / неизвестность там, где разрешено. Не ноль, не «немедленно свободен», не пустая точка |
| Массивы | Пустой массив допустим. ID и порядковые номера в пределах соответствующего набора уникальны |
| `schema_version` | Версия формы данных, не бизнес-политика и не время опроса. Рабочая маркировка формы данных — `1.0`; это версия структуры, не заявление о завершённой реализации |

Внутренний обмен sys ↔ Router остаётся числовым. Локальное время превращается в Unix-time при вводе, форматируется обратно на выводе. Временная зона приложения не подменяется прибавлением смещения к сохранённому timestamp. Обеденное окно заранее разворачивает sys в абсолютные секунды для нужного рабочего дня.

Для однозначности контракта назначены следующие технические коды; русские значения взяты из ТЗ:

| Справочник | Код | Значение |
|---|---|---|
| Навык | `local` | Локальные работы |
| Навык | `connection` | Работы на подключение и дозаказы |
| Навык | `emergency` | Аварийные работы |
| Транспорт | `car` | Автомобиль |
| Транспорт | `walk` | Пешеход |
| Транспорт | `bike` | Велосипед |
| Транспорт | `transit` | Общественный транспорт |
| Приоритет | `normal` / `urgent` | Обычная / срочная |

У заявки один требуемый навык; у инженера от одного до трёх. У инженера один тип транспорта; у заявки ограничение транспорта может отсутствовать. Неизвестные коды не заменяются ближайшим знакомым кодом без явной обработки ошибки.

## 5. INPUT: точная разметка специального сектора

Сектор — **полный снимок**, а не пачка команд `create/update/delete`. Sys удаляет из свободного пула завершённые, отменённые и уже выполняемые работы до публикации. Поэтому Router не нужно отдельное поле полного бизнес-статуса каждой заявки.

### Корневой объект `RouterTaskSnapshot`

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `schema_version` | `string` | Да | Форма контракта |
| `planning_as_of` | `UnixSeconds` | Да | Время публикации изменения других данных снимка |
| `horizon_start_at` | `UnixSeconds` | Да | Начало рассматриваемого рабочего периода; не обязательно время текущего пересчёта |
| `horizon_end_at` | `UnixSeconds` | Да | Конец периода; должен быть позже начала |
| `requests` | `Request[]` | Да | Только заявки, доступные для нового распределения |
| `engineers` | `Engineer[]` | Да | Исполнители с подготовленными стартами и условиями участия |
| `policy` | `Policy` | Да | Выбранная политика и допустимые для неё предпочтения |

По утреннему снимку рассчитывается весь будущий рабочий день; по дневному — оставшаяся часть от переданных стартов. Поле `planning_as_of` не обновляется просто из-за очередного чтения. Метрики результата относятся к задаче этого снимка, а не автоматически ко всему уже прошедшему и будущему дню.

### `Request`

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `request_id` | `ID` | Да | Стабильный ID |
| `arrival_order` | `integer >= 0` | Да | Порядок поступления для baseline; не случайный порядок чтения БД |
| `location` | `GeoPoint` | Да | Точка работы; подготовлена sys |
| `service_duration_sec` | `DurationSeconds > 0` | Да | Ожидаемая длительность работы |
| `window_start_at` | `UnixSeconds` | Да | Начало клиентского окна начала работы |
| `window_end_at` | `UnixSeconds` | Да | Конец этого окна; не раньше начала |
| `priority` | `normal / urgent` | Да | Приоритет заявки |
| `required_skill` | Код навыка | Да | Один требуемый навык |
| `required_transport` | Код транспорта или `null` | Да, nullable | `null` — ограничения транспорта нет |

Временное окно относится к началу работы, а не к её окончанию. Работа и дорога должны укладываться в смену. Конкретные длительности и требования берутся из датасета либо системно формируются по локации / типу работы; отсутствующие значения не выдумываются Router.

`assigned_engineer_id`, текущее расчётное ETA и порядок будущих посещений не возвращаются в этот объект как обязательный вход. Детальное описание проблемы, ФИО и email остаются в приложении и подставляются по ID.

### `Engineer`

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `engineer_id` | `ID` | Да | Стабильный ID |
| `input_order` | `integer >= 0` | Да | Порядок выбора инженера в baseline |
| `skills` | Массив 1–3 разных кодов | Да | Квалификация |
| `transport_type` | Код транспорта | Да | Способ перемещения |
| `shift_start_at` | `UnixSeconds` | Да | Начало смены |
| `shift_end_at` | `UnixSeconds` | Да | Конец смены, позже начала |
| `start_location` | `GeoPoint` | Да | Точка начала нового оставшегося маршрута; выбирается sys |
| `available_from` | `UnixSeconds` или `null` | Да, nullable; консервативная интерпретация — раздел 9 | Не раньше какого времени из этой точки можно продолжить. Это может быть прогноз, не факт завершения |
| `position_observed_at` | `UnixSeconds` или `null` | Да, nullable | Время использованного наблюдения позиции; `null`, если старт задан не GPS-наблюдением. Не подтверждает фактическое прибытие |
| `availability` | `online / offline` | Да | Рабочая доступность, не состояние сети |
| `expected_online_at` | `UnixSeconds` или `null` | Да, nullable; детали прогнозного использования — раздел 9 | Прогноз возврата из технической остановки. Для online обычно `null` |
| `lunch_taken` | `boolean` | Да; устанавливает sys при фактическом начале обеда | Был ли использован обед в этом рабочем дне. Если `true`, новый обед не назначается |
| `lunch` | `LunchInput` | Да | Нормализованные условия обеда этого инженера |

`available_from` и `expected_online_at` не дублируют друг друга: первый отражает готовность продолжить маршрут, второй — прогноз выхода из offline. Online-инженер может ещё работать. Само наступление прогнозного времени не создаёт факта окончания работы или выхода online.

`available_from` всегда относится именно к `start_location`: «из этой точки можно продолжить не раньше этого времени». ETA прибытия на другой адрес нельзя автоматически записать как время освобождения в текущей GPS-точке — иначе получится двойной учёт дороги или неверная география. Для свободного перенаправляемого инженера в пути sys готовит текущую пригодную точку и время продолжения из неё. Для ещё работающего — точку работы и ожидаемое освобождение. Преобразование сообщения о задержке в такую проекцию требует системной интерпретации; Engine не выводит её из текста сообщения.

Новый маршрут не начинается раньше `planning_as_of`, начала смены и известного `available_from`. При принятии прогнозного возврата offline дополнительно учитывается `expected_online_at`. Это ограничения стартового момента, а не автоматические изменения фактических статусов.

Начатая работа остаётся в sys вне свободного `requests[]`. Её занятость проецируется в `start_location + available_from`; Router не обязан видеть историю этапов. Если старые данные не позволяют выбрать пригодную стартовую точку, это проблема подготовки входа, а не разрешение заменить её на офис или координаты ноль.

### `LunchInput`

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `enabled` | `boolean` | Да | Действует ли подбор обеда для этого инженера. Общий переключатель Dashboard можно развернуть в одинаковые значения |
| `duration_sec` | Положительная длительность или `null` | Да, nullable | При `enabled=true` и `lunch_taken=false` значение обязательно. Число задаётся конфигурацией приложения, значение ещё не названо |
| `window_start_at` | `UnixSeconds` или `null` | Да, nullable | Начало допустимого периода обеда. Абсолютное время, нормализованное sys; конкретные часы ещё не названы |
| `window_end_at` | `UnixSeconds` или `null` | Да, nullable | Конец допустимого периода обеда; весь обед должен помещаться в этом окне; правило принято |
| `required` | `boolean` | Да; принято в v13 | Разовое требование сохранить обед после явного выбора диспетчера; в обычной автоматике `false` |

`lunch_taken` принадлежит инженеру и конкретному рабочему дню, не всей его учётной записи навсегда. Флаг хранит sys и включает в следующий снимок. Router не меняет его на `true`, просто запланировав обед. Отключение / повторное включение обедов и возврат AUTO сами по себе флаг не сбрасывают.

Если обед уже идёт, его оставшуюся занятость sys учитывает в `available_from`. Принято: sys устанавливает `lunch_taken=true` при подтверждённом фактическом начале обеда, не при публикации плана. Флаг означает использование единственного обеда дня, а не факт его окончания. Завершение обеда и возвращение к работе по-прежнему фиксируются sys отдельно.

### `Policy`

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `policy_id` | `ID` | Да | Согласованная политика из системного каталога |
| `parameters` | Объект скалярных значений | Да; допустим `{}` | Только поддержанные этой политикой предпочтения |

Состав параметров, веса и порядок целей определяются выбранной политикой диспетчера, а не неизменным порядком внутри Engine. Здесь не вводится исполняемый код / текст команд агенту. Значение малого допуска и обязательные требования квалификации, времени и транспорта не превращаются в отключаемые предпочтения. Семантику уже используемого ID политики нельзя незаметно менять; изменённая политика должна быть отличима по ID или собственным данным.


### Политика по умолчанию и границы настройки — уточнение v14

`policy.policy_id="fast"` — первая политика по умолчанию. Значение выставляет sys при подготовке начальной задачи, если диспетчер ещё не выбрал другое. Во внешнем контракте поле остаётся обязательным: отсутствие или неизвестный ID не маскируются молчаливой заменой внутри Router.

**Вся иерархия целей — содержимое политики.** Engine не навязывает всем политикам постоянные старшие уровни. Стартовый профиль `fast`, оформленный из обсуждения: неназначенные срочные → неназначенные всего → пропущенные включённые обычные обеды → сумма времени дороги → пробег → число инженеров с работой. Последний ресурсный блок отличает `fast` от возможного `compact`. Это исходный пресет каталога, не универсальный порядок ядра.

Политика не отменяет обязательные окна / смены, квалификацию, транспорт, отсутствие пересечений, запрет второго обеда и установленный `lunch.required`. В ней нельзя передать произвольный исполняемый код. Поддержанные изменения рангов / весов должны иметь явные имена параметров либо отдельный ID каталога. Полный каталог и произвольный редактор политик не объявляются уже реализованными.

Форма `parameters` остаётся объектом скалярных значений; для начального пресета достаточно `{}`. Внутренняя упорядоченная структура `PolicySpec` — задача PolicyCompiler в engine-документе, а не новый обязательный массив во внешнем снимке.

Точная семантика ID должна быть воспроизводима. При изменении определения политики создаётся отличимое определение / ID либо меняется версия контекста сборки, использующей этот каталог. Один и тот же идентификатор не должен молча означать другую цель при тех же версиях входа и Router.

## 6. Обед: минимальная операция восстановления

**Принято:** обычный обед размещает Router по загрузке в середине дня. При конфликте «заявка или обед» приоритет имеет заявка; пропущенный включённый обед вызывает alert. Второго обеда нет, что выражается `lunch_taken`.

**Принято в v13:** не вводить универсальную систему ручных ограничений и не переключать глобальную политику. Использовать только `lunch.required` для конкретного инженера / дня и обычное системное действие отказа от явно выбранной заявки.

Одна операция sys связывает ID alert / результата, инженера и явно выбранные заявки: проверяет, что основание не устарело и обед ещё не использован, исключает только подтверждённые диспетчером заявки из текущего пула и устанавливает `lunch.required=true`. Эти изменения публикуются одним снимком с новым `planning_as_of`. Интервал по-прежнему подбирает Router; памяти готового маршрута никто не касается.

Отказ от заявки относится к sys: изменение участия в текущем распределении, бизнес-статус и клиентское сообщение не делаются оптимизатором. Это не обязательно безвозвратное удаление заявки из системы. Дополнительные заявки не отменяются молча. Если выбранного изменения недостаточно, Router явно сообщает о конфликте; нельзя назвать непоместившийся обязательный обед восстановленным или скрыто поставить `required=false`.

В структуре ниже допускается кандидат `restore_option` в alert, но только для действительно проверенного варианта. Если гарантированного списка отказов нет, поле `null`: интерфейс не обещает, что удаление любой одной заявки решит задачу. Более сложные preview-режимы, несколько альтернативных веток и автоматическая массовая отмена сейчас не включаются.

В MANUAL действует обычное самостоятельное редактирование диспетчером; временно отключённый выход Router не становится скрытым каналом проверки его плана. `lunch_taken` и текущая занятость соблюдаются на стороне sys и в следующей проекции.

## 7. Публикация, hash и применение результата

### Согласованная организация

Живые данные sys обновляются по событиям. Специальный сектор — отдельный опубликованный снимок, а не автоматическое зеркало каждой записи. Штатные GPS-обновления, ход часов и обычное выполнение принятого плана сами по себе не требуют новой оптимизации. Принято: новый снимок формируется при изменениях заявок, доступности, политики, условий обеда и значимых сообщениях об ожидаемом прибытии/освобождении. Сырые события и GPS сначала обрабатывает sys; сектор не является потоковым обработчиком.

При основании для нового планирования sys собирает целый снимок из текущих данных: оставшиеся работы, актуальные старты / освобождение, доступность, обеды и политика. В рамках одной публикации фиксируется `planning_as_of`. Проверка «данные изменились» проводится до обновления времени; повторная запись того же содержимого не вызывает вечную последовательность новых timestamp.

Router читает целый снимок, сохраняет его неизменным на время соответствующего расчёта и возвращает hash именно этих данных. Сериализация и алгоритм hash ещё выбираются при реализации, но должны быть одинаковыми у sys и Runtime. `arrival_order` и `input_order` сохраняют бизнес-смысл независимо от технической сортировки объектов.

### Согласованное принятие

Sys проверяет AUTO / MANUAL отдельно от hash. В AUTO несовпадение `input_hash` с опубликованным сектором означает ожидание нового результата. Готовый ответ с неназначенными заявками не означает бесконечную загрузку. Техническая ошибка должна быть видимой ошибкой, а не неразличимым вечным ожиданием.

После применения sys продвигает активный план по фактам. Обычное повторное чтение того же `result_id` не применяет план заново, не возвращает завершённые пункты и не повторяет уведомления. Исходный результат Router и история при этом не редактируются.

Явный возврат из MANUAL — отдельная операция перехода, а не обычное повторное чтение. На этой границе автоматический план может однократно заменить ручное будущее распределение; защита от дублей не должна навсегда запрещать возврат только потому, что этот результат уже встречался до перехвата. Новый активный план не отменяет факты и начатые работы.

**Следствие разделения живых данных и снимка:** совпадение hash не доказывает, что sys с тех пор не исполнил часть плана. Поэтому при приёме действительно нового результата sys сверяет его с текущими фактами. Если план конфликтует с уже начавшейся работой или не соответствует текущим стартовым условиям, нельзя «подрезать и починить» его собственным оптимизатором: нужно не применять конфликтующий результат и опубликовать актуальную проекцию. Завершённая история не превращается обратно в активный список.

При возврате AUTO также проверяется соответствие опубликованного снимка текущей проекции, включая `lunch_taken`. Совпадение со старым снимком не даёт права возродить уже использованный обед.

### Изменения вне сектора — принято в v13

`router_context_version` обозначает активную карту и технические настройки Router. Runtime фиксирует эту версию на время расчёта и возвращает реально использованное значение с результатом. Активная версия доступна sys через отдельное служебное состояние, а не определяется по прежнему ответу.

Для применения нужны совпадение `input_hash`, совпадение активной `router_context_version`, AUTO, `main.is_usable=true` и отсутствие конфликта с текущими фактами sys. Одна проверка не заменяет остальные. Смена контекста делает прежний ответ непригодным к новому применению; Runtime сам инициирует обработку действующей задачи в новой среде, не требуя записи карты/допуска в сектор. Старому расчёту запрещено приписывать новую версию.

При публикации и применении необходимо исключить смешение версий в середине операции. Конкретная реализация согласованного чтения и смены ресурса относится к Runtime, не к математическим ограничениям маршрута.

## 8. OUTPUT: разметка результата Router Core

### Общий ответ `RouterResult`

| Поле | Тип | Обязательность / условие | Смысл |
|---|---|---|---|
| `schema_version` | `string` | Да | Версия формы ответа |
| `status` | `pending / ready / error` | Да | Состояние получения нового результата, не статус выполнения заявок |
| `result_id` | `ID` или `null` | При `ready` обязателен | ID опубликованного результата; обычные повторные чтения возвращают тот же ID |
| `input_hash` | `string` или `null` | При `ready` обязателен | Hash использованного снимка; при отсутствии читаемого входа может быть `null` |
| `planning_as_of` | `UnixSeconds` или `null` | При `ready` обязателен | Время состояния из входного снимка |
| `computed_at` | `UnixSeconds` или `null` | При `ready` обязателен | Время формирования результата; не замена `planning_as_of` |
| `router_context_version` | `string` или `null` | При `ready` обязателен | Версия реально использованных карты и настроек; у ранней ошибки без контекста может отсутствовать |
| `main` | `Plan` или `null` | При `ready` обязателен | Основной рассчитанный план |
| `baseline` | `Plan` или `null` | При `ready` обязателен | Сопоставимый базовый план |
| `errors` | `Diagnostic[]` | Да; при нормальном результате `[]` | Ошибки подготовки / расчёта, не перечень неназначенных заявок |

Для простой первой формы ответа `ready` обозначает наличие обоих планов на одном входе. Раздельная публикация main / baseline не включена в эту разметку; параллельность внутренних расчётов определяется позже. Старый сохранённый применённый план sys не подменяет `main` ожидаемого нового ответа.

Точный процент выполнения не обязателен. Совпадение hash не гарантирует математический оптимум или назначение всех заявок. Пустой пул заявок может иметь корректный готовый результат. Если остаётся подлежащий планированию обед, его время не обязано быть нулевым; число назначенных заявок и engineers_used при этом равно нулю.

### `Plan` — одинаковая форма для main и baseline

| Поле | Тип | Смысл |
|---|---|---|
| `is_usable` | `boolean` | Есть ли допустимый основной / базовый план для применения или сравнения. `false` не доказывает глобальную невозможность, но запрещает применять этот вариант как рабочий |
| `metric_scope` | `snapshot_remaining` | Расчётная область — задача снимка, то есть будущая оставшаяся часть |
| `routes` | `EngineerRoute[]` | План каждого переданного инженера, включая пустой маршрут |
| `assignments` | `Assignment[]` | Ровно один исход по каждой входной заявке |
| `summary` | `PlanMetrics` | Метрики именно этого плана / снимка |
| `alerts` | `PlanningAlert[]` | Объяснимые проблемы, включая непоместившийся обед |

`ready` обозначает завершённый ответ, а не доказанную применимость каждого варианта. Sys принимает только `main.is_usable=true`. План с неназначенными заявками может быть допустимым, если его назначенная часть соблюдает ограничения. Если не получено допустимого плана (в том числе при неразрешённом обязательном обеде), вариант помечается `is_usable=false` с причинами и не заменяет действующий план. В таком случае `routes` не выдаются как исполнимый маршрут; сравнение экономии с этим вариантом не выполняется. Это не техническое падение, не вечная загрузка и не автоматическая отмена всех заявок.

При утреннем расчёте эта область может совпадать со всем рабочим днём. После дневного пересчёта полный день отображает sys, соединяя фактическую историю и новый будущий план. Он не складывает счётчики уникальных инженеров механически и не сравнивает остаток основного плана с полным днём baseline. Для чистого итогового сравнения исходный дневной снимок сохраняется отдельно.

### `Assignment`

| Поле | Тип | Смысл |
|---|---|---|
| `request_id` | `ID` | Заявка из снимка |
| `status` | `assigned / unassigned` | Исход планирования |
| `engineer_id` | `ID` или `null` | Назначенный инженер либо отсутствие назначения |
| `stop_id` | `ID` или `null` | Ссылка на пункт маршрута при назначении |
| `reasons` | `Reason[]` | Проверяемые основания назначения / неназначения |

Для `unassigned` инженер и пункт равны `null`, а причина не пуста. Для `assigned` указан существующий инженер и единственный соответствующий `job` в его маршруте. Здесь нет `in_progress / completed`: это не менеджмент стадий приложения.

### `EngineerRoute`

| Поле | Тип | Смысл |
|---|---|---|
| `engineer_id` | `ID` | Исполнитель |
| `start_location` | `GeoPoint` | Использованный старт остатка маршрута |
| `start_at` / `finish_at` | `UnixSeconds` или `null` | Границы непустого будущего маршрута; для пустого могут быть `null` |
| `stops` | `RouteStop[]` | Упорядоченные работы, ожидания и обед |
| `legs` | `RouteLeg[]` | Переезды, согласованные с пунктами и временем |
| `lunch` | `LunchResult` | Отдельно различимый исход по обеду |
| `metrics` | `RouteMetrics` | Пробег и расчётные времена |
| `reasons` | `Reason[]` | Основания выбора маршрута и учтённых ограничений |

`RouteStop`: `stop_id`, `sequence`, `kind` (`job / lunch / wait`), `request_id` (ID заявки для `job`, `null` для `lunch / wait`), `location`, `arrival_at`, `start_at`, `end_at`. Время прибытия не позже начала, начало не позже конца. Для работы используются расчётные начало и конец, для обеда / ожидания — границы интервала. Времена не являются фактическими отметками.

`RouteLeg`: `leg_id`, `from_stop_id` (`null` для старта маршрута), `to_stop_id`, `departure_at`, `arrival_at`, `travel_time_sec`, `distance_km`, `geometry` (опционально `{points: GeoPoint[]}` или `null`; технический выбор для первой реализации). Транспорт известен по инженеру. Отсутствующий / непроходимый путь не превращается в переезд с нулевой длительностью. Нулевая дорога допустима только там, где она действительно следует из использованной модели.

Порядок задаётся явно; одна заявка не встречается дважды. У инженера нет пересекающихся работ, переездов и обеда. Возвращение в офис в конце дня не требуется. Ограничения окна и смены проверяются по всей рассчитанной последовательности, не только по отдельной заявке.

### `LunchResult`

| Поле | Тип | Смысл |
|---|---|---|
| `status` | `disabled / already_taken / scheduled / skipped_for_work / not_scheduled / required_conflict` | Различимые исходы, включая конфликт принятого обязательного обеда |
| `stop_id` | `ID` или `null` | Пункт `lunch` при наличии |
| `reasons` | `Reason[]` | Основание, особенно при пропуске / конфликте |
| `alert_id` | `ID` или `null` | Связанный alert диспетчеру |

`lunch_taken=true` исключает новый пункт `lunch` независимо от enabled / required. `scheduled` не переключает входной факт. `skipped_for_work` используется только при соответствующей причине, а не для любого отсутствующего обеда. Непоместившийся обязательный обед не отображается как успешно запланированный.

### Метрики

`RouteMetrics`: `distance_km`, `travel_time_sec`, `work_time_sec`, `waiting_time_sec`, `lunch_time_sec`, `assigned_count`.

`PlanMetrics`: `requests_total`, `assigned_count`, `unassigned_count`, `urgent_total`, `urgent_assigned_count`, `engineers_used`, `distance_km`, `travel_time_sec`, `work_time_sec`, `waiting_time_sec`, `lunch_time_sec`.

`engineers_used` — количество разных инженеров хотя бы с одной назначенной заявкой, не с одним лишь обедом. `assigned_count + unassigned_count = requests_total`. Время работы складывается только из `job`, обед не маскируется под работу. Наличие поля метрики не задаёт её приоритет. Порядок и коэффициенты определяет политика диспетчера; по умолчанию — fast.

### Причины, alerts и ошибки

`Reason`: `code`, `text`, `basis` (`constraint_check / calculation_outcome`), `facts` (объект относящихся к объяснению числовых / строковых / булевых значений). Объяснение не приписывает доказанную невозможность поиску, который только не нашёл вариант. Примеры рабочих кодов: `NO_SKILL_MATCH`, `NO_TRANSPORT_MATCH`, `NO_AVAILABLE_ENGINEER`, `NO_FEASIBLE_ASSIGNMENT_FOUND`, `CONSTRAINTS_SATISFIED`.

`PlanningAlert`: `alert_id`, `code`, `severity` (`info / warning / error`), `engineer_ids`, `request_ids`, `reasons`, `restore_option` (опциональный проверенный вариант восстановления, иначе `null`). Для обеда можно использовать `LUNCH_SKIPPED_FOR_WORK` и `REQUIRED_LUNCH_UNPLACED`. Невыполненное обязательное требование не скрывается за `is_usable=true`. Указанный связанный ID не означает автоматическую отмену заявки.

Опциональный `restore_option`: `engineer_id` и `reject_request_ids` только для проверенного предложения; принадлежность к расчёту задаётся внешними `result_id / input_hash` и контекстом. Не превращать предположительную причинную связь в гарантированный список «достаточно отменить это».

`Diagnostic`: `code`, `message`, `field_path` (`null`, если нет одного поля), `entity_id` (`null`, если не относится к одной сущности). Ошибка отсутствующей длительности — не нормальная неназначенная заявка с выдуманной длительностью. Конкретный перечень диагностических кодов расширяется при реализации без изменения бизнес-правил.

### Отдельный конфигурационный обмен — не часть сектора

Согласована только возможность специальной настройки допуска. Проектная форма запроса: `operation_id`, `tolerance_sec` (целое неотрицательное), `expected_context_version` для принятой проверки контекста. Ответ: `operation_id`, `accepted / rejected`, применённое значение и активная версия контекста либо явная ошибка. Права проверяет sys, Runtime не принимает произвольные параметры маршрута под видом этой операции.

Реальный HTTP URL, метод, хранение конфигурации и форма подключения карты пока не выбираются. При использовании версии контекста активное значение требуется читать отдельно от старого рассчитанного пакета. Смена версии в процессе расчёта не позволяет пометить старый результат новым значением.

## 9. Итог согласования и неблокирующие параметры

| Прежний пункт | Результат последнего ответа |
|---|---|
| Q1 | Версия контекста принята; `input_hash` и `router_context_version` проверяются совместно |
| Q2 — перенаправление | Едущего инженера можно направить на другую ещё не начатую заявку, когда это улучшает план. Это разрешение, а не требование менять цель при каждом обновлении |
| Q3 | События и GPS обрабатывает sys; значимые изменения публикуются целым снимком. Поток координат и штатное выполнение не копируются в сектор автоматически |
| Q4 | `lunch_taken` устанавливается при фактическом начале обеда; второе назначение запрещено. Текущий обед занимает инженера до `available_from`. Весь планируемый обед помещается в заданное окно; для первой конфигурации — общий переключатель Dashboard |
| Q5 | Принято минимальное восстановление через `lunch.required` и исключение явно выбранных заявок одной операцией sys |
| Q6 | Пользователь разрешил технический выбор. Предпочтение чистому разделению графа и финального пути не требует передачи целого графа frontend |

**Геометрия — техническое решение этой версии:** Runtime хранит дорожный граф/ресурс внутри. После выбора последовательности можно получить линии только используемых участков и заполнить опциональное `geometry`; при отсутствии геометрии — `null`. Формирование линии не выбирает заново другие времена/расстояния. Иной способ визуализации допустим без нового бизнес-раунда; нельзя изображать прямую линию как доказанный дорожный путь.

**Не выдуманные параметры:** длительность и часы обеденного окна ещё не названы, но места для них в контракте есть. Значения задаются sys до запуска функции обедов; они не являются условием начала обсуждения модели. Размер технического допуска, транспортный источник карты и бюджеты поиска также предстоит выбрать при конфигурации/испытании.

**Частично не отвеченная часть прежнего Q2:** пользователь явно подтвердил перенаправление в дороге, но не отдельно весь предложенный сценарий неизвестного освобождения и прогнозного online. Для обсуждения модели сохраняется консервативная рабочая интерпретация: `available_from=null` не означает «свободен сейчас»; при неизвестности новые назначения не строятся до уточнения, возвращается диагностика. Прогнозный online учитывается только при явно подготовленном sys будущем времени, а не создаёт факт выхода на линию. Источник оценки и действия при её просрочке остаются настройкой системного сценария; это не приписывается последнему ответу пользователя.

**Внутренняя реализация вынесена в [engine_contract_v2.md](./34-engine_contract_v2.md).** Приняты три пути Engine: проверка малого отклонения с сохранением допустимого порядка; восстановление и улучшение при существенном изменении; новое решение при отсутствии пригодного кандидата. Это не меняет форму внешнего снимка.

## 10. Инварианты схемы и обработка противоречий

### 10.1. Типы и диапазоны

Все абсолютные времена — целые Unix-секунды, не миллисекунды. Длительности — целые секунды. Не допускаются `NaN`, бесконечности, пустые ID и смешение единиц. `null` допустим только в полях, отмеченных nullable. Булевы значения не заменяются строками `"true"`.

В пределах снимка уникальны ID заявок, ID инженеров, `arrival_order` заявок и `input_order` инженеров. Уникальность задаётся отдельно для каждого набора. Одинаковые координаты разных заявок допустимы и не объединяют их ID. Порядковые номера не переопределяются сортировкой по ID.

### 10.2. Окна, горизонты и неизвестность

`horizon_end_at > horizon_start_at`; смена имеет положительную длительность; окно начала работы может быть точечным (`start == end`), если работа физически выполнима. Конец работы не обязан помещаться в окно начала, но обязан помещаться в смену / горизонт. Отрицательная длительность — ошибка данных, а не причина нормального неназначения.

Корректное окно, целиком оставшееся в прошлом относительно точки планирования, может привести к неназначению с основанием, а не к переносу окна Router. Некорректная пара границ — ошибка. Поле `planning_as_of` не продвигается автоматически во время чтения.

Консервативная интерпретация неизвестного освобождения: `available_from=null` не предоставляет ресурсу старт «прямо сейчас». Подробная логика получения оценки / обработки просрочки остаётся на стороне sys. Если будущий прогноз участия используется, он влияет на расписание, но не создаёт фактический online или completed.

### 10.3. Обед

При `lunch_taken=true` новый обед не создаётся. Sys в следующем снимке нормализует `required=false`; даже если старый `required=true` ещё присутствует, он не даёт права на второй обед. Факт имеет приоритет над прежним требованием будущего интервала.

Если обед ещё не использован, сочетание `required=true` и `enabled=false` противоречиво: его нужно отклонить как некорректное условие, а не выбрать удобную половину данных. При включённом неиспользованном обеде обязательны длительность и обе границы окна. Если валидная длительность не помещается в валидное окно, это различимая проблема размещения; обязательный вариант не становится `is_usable=true` без исполнения требования.

Входной `lunch_taken` не изменяется Router. При `scheduled` есть ровно один соответствующий stop. Для `already_taken` такого будущего stop нет. При обеде без единой заявки у инженера `engineers_used` не увеличивается: он считается по job, а не по любому внутреннему узлу solver.

### 10.4. Связи результата

Для пригодного плана каждая переданная заявка встречается ровно в одном `Assignment`. `assigned` соответствует ровно одному `job` нужного инженера; `unassigned` не имеет `stop_id` и имеет непустую причину. ID вне входного снимка не появляются как новые клиентские заявки.

`sequence` задаёт порядок. `stops` и `legs` описывают совместимое расписание. Для реального переезда `arrival_at - departure_at == travel_time_sec`. Ожидание не включается скрыто во время в пути. Обед, работа и ожидание учитываются раздельно и не перекрываются.

Внешний результат не содержит фиктивный возврат в офис, искусственные индексы OR-Tools или все внутренние альтернативные копии обеда. Он содержит только выбранные реальные работы / интервалы. Геометрия может быть `null`, но не может противоречить использованным расстояниям и времени.

### 10.5. Непригодный план и ошибка

`status=error` сообщает о некорректных входных данных, сбое подготовки / вычисления или внутренней ошибке, а не просто об отсутствии назначения. В `errors` есть хотя бы одна диагностика.

`status=ready` с `main.is_usable=false` сообщает о завершённой обработке, не предоставившей пригодного основного плана. По каждой задаче сохраняется различимый исход / причина, но diagnostic-вариант маршрута не используется для исполнения или вычисления «экономии». Допустимый baseline не становится автоматически разрешением sys поменять `main` местами: выбор fallback делает Engine / Runtime с указанием происхождения.

`status=pending` означает ожидание результата текущей задачи. Старый применённый план sys может продолжать отображаться отдельно с честным состоянием; он не подставляется в ответ нового расчёта под его hash.

## 11. Идентификация снимка, контекста и применения

| Идентификатор | Значение | Не заменяет |
|---|---|---|
| `schema_version` | Форму объекта | Версию карты или очередность событий |
| `input_hash` | Содержимое реально использованного снимка | Текущее состояние живого исполнения |
| `planning_as_of` | Момент публикации других изменившихся данных | Уникальный номер версии: два события могут быть в одну секунду |
| `router_context_version` | Использованную карту и технический контекст | Hash бизнес-входа |
| `result_id` | Одну опубликованную выдачу | Политику и факт её применения |

Hash непрозрачен для сортировки: большее / меньшее текстовое значение не означает новую / старую версию. Runtime при необходимости использует внутренний счётчик поколений, который не входит в специальный сектор как ещё одно бизнес-условие.

Sys независимо проверяет применимость: AUTO, результат ready, обе версии совпадают, main пригоден, новый результат не конфликтует с фактическим исполнением. Обычный дубль `result_id` не запускает применение. При возврате MANUAL действует отдельный контролируемый переход. Точная реализация транзакции принадлежит sys, а не solver.

Изменение карты / настройки допуска не маскируется записью времени в сектор. Runtime меняет активный контекст и самостоятельно обрабатывает текущий снимок. Старый результат остаётся старым по версии, даже если его получили уже после изменения.

Сериализация и конкретная hash-функция пока не назначены согласованным пользовательским решением. Реализация обязана выбрать одну общую спецификацию нормализации и целостную публикацию. Кеш вычисленного hash не является правом доверять произвольному hash без связи с данными.

## 13. Проверка границ ответственности на примерах

| Изменение | Кто обрабатывает | Что видит Router |
|---|---|---|
| Клиент изменил email | Sys | Ничего нового в расчётном секторе |
| Изменено окно / место / требование заявки | Sys публикует проекцию | Новый полный снимок и новый hash |
| Инженер выполнил очередную работу по плану | Sys фиксирует и продвигает план | Не обязан получать новый снимок только из-за штатного исполнения |
| Появилась срочная после нескольких выполнений | Sys собирает состояние целиком | Уже без завершённых / начатых работ, с новой срочной и текущими стартами |
| Инженер начал обед | Sys ставит lunch_taken, учитывает текущую занятость | При следующем снимке нет права на второй обед |
| Диспетчер меняет политику | Sys обновляет policy | Новый критерий выбора на том же формате данных |
| Диспетчер включает MANUAL | Sys отключает шину результата | Нет обязательных ручных назначений в Engine |
| Специально изменён допуск | Runtime по разрешённому запросу | Новая версия технического контекста, не новая бизнес-политика |
