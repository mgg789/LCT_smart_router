# Dashboard — концепция интерфейса v2

**Редакция:** 15 сентября 2026 года.  
**Основа:** `dashboard_concept_v1.md`, исходная фотография Dashboard и последние ответы пользователя на DB1–DB7.  
**Статус:** приняты создание/отмена ещё не начатой заявки, разделение просмотра и устранения alerts, выбор готовых политик без редактора, начало человеческого диалога первым сообщением диспетчера, ручная смена исполнителя и drag-and-drop порядка в MANUAL, read-only по умолчанию и ручное подтверждение сбросов. Полный сброс определён как «всё в ноль», а не очистка только заявок с сохранением сотрудников. Технические следствия, которые не выбирались отдельным ответом, обозначены как детализация.

**Следующий контур:** внешнее интеграционное API. Каталог операций System Layer сейчас не описывается.

Последние ответы имеют приоритет над предложениями v1. В частности, сняты групповой черновик ручного плана с общей кнопкой «Применить изменения», обязательный ввод времён для каждой ручной перестановки и редактор политик/весов. «Оператор на заявке» в ответе DB5 означает назначенного исполнителя — инженера, не единственного человека-диспетчера в чатах.

Сохраняемые источники: фотография `camphoto_1483920592(1).jpeg`; исходный раздел Dashboard; `system_concept_v14.md`; `router_contract_v2.md`; `ai_smtp_concept_v3.md`; `system_layer_concept_v2.md`; `data_layer_concept_v2.md`; `client_engineer_concept_v3.md` и согласования переписки.

Этот документ не перезаписывает остальные файлы. Макеты, программный код, пользователи и токены не создавались; импорт и сброс реальных данных не выполнялись. Файл фиксирует концепцию функций, не HTTP endpoints или SQL-команды.

## 1. Исходный набросок — состав и порядок сохранены

На фотографии указано:

1. **Список всех заявок на день:** объяснение по каждой и подробности при hover.
2. **Alerts для невозможных мест роутинга.**
3. **Карта со слоями:** заявки, маршруты, инженеры.
4. **Выбор стратегии роутинга.**
5. **Список инженеров:** данные, позиция, статус и чат. Для инженера сообщения приходят в его AI-chat. Ручное отключение инженера.
6. **Ручное управление заявками:** смена времени, локации, приоритета.
7. **AI-chat:** объяснение роутинга, alerts, стратегий и просьбы о корректировке.

Пометка у AI-chat — **«самый сложный агент»**. Она характеризует роль диспетчерского помощника, но сама по себе не задаёт новую модель, не разрешает произвольный SQL и не отменяет права System Layer.

Перечень выше сохраняет исходный набросок. Создание/отмена, правила alerts, первый исходящий человеческий ответ, ручные жесты и сбросы уточнены последующей перепиской в разделах 3–10. Они не приписываются исходной фотографии.

## 2. Уже принятые дополнения и ограничения

| Область | Действующее решение |
|---|---|
| Один диспетчер | Email-код либо пароль из серверного `.env`; оба пути открывают одну роль, парольный вход не зависит от SMTP |
| Источник интерфейса | Все данные и изменения через sys. Нет прямого чтения БД или обхода отключённой шины Router |
| Результаты | Применённый план, отдельный список неназначенных с причинами, метрики, baseline и видимые изменения после перепланирования |
| Политики | По умолчанию `fast`; в Dashboard выбирается готовая политика. Редактора порядка критериев, коэффициентов и произвольных параметров нет |
| Ограничения | Навыки, временные окна, смены и транспорт не становятся отключаемыми предпочтениями |
| AUTO | Правки заявок, добавление, отмена и выбор политики через sys; непосредственное назначение и порядок не редактируются |
| MANUAL | Отключён только выход Router → sys. Исполнитель меняется на заявке; порядок ещё не начатых работ — drag-and-drop в списке выбранного инженера |
| Возврат AUTO | Актуальный пригодный результат заменяет будущее ручное распределение, не факты и не историю |
| Рестарт | Режим, рабочий план, чаты и остальное согласованное состояние сохраняются; MANUAL сам не отменяется |
| Ожидание | Последний применённый план виден с «Перестраивается» и моментом, к которому относится показанный план |
| Состояния | Жизненный цикл, назначение, рабочая доступность, связь, факты и прогноз различаются |
| Нет триггера | Часы, обычный GPS и молчание инженера сами не публикуют новый сектор и не вызывают перестроение |
| Инженеры | Диспетчер создаёт инженеров добавлением email; инженер сам может менять свои skills, транспорт и офис |
| Начатая заявка | Обычное изменение условий начатой работы закрыто; новый вход клиента и роль диспетчера не создают неутверждённый обход |
| Обеды | Включение/выключение, подбор Router, единственный `lunch_taken`, alert и восстановление через `lunch.required` с явным исключением выбранных заявок |
| Чаты | Отдельная страница «Чаты», один человек. Первое отправленное сообщение диспетчера инженеру также включает человеческий режим; AI выключен до завершения |
| Вызов человека | Со стороны клиента/инженера нет постоянной кнопки вызова; основания — решение агента либо неответ провайдера |
| Диспетчерский AI | Новый диалог в `read-only`; `fix` с разрешёнными действиями, журналом и остановкой. Два сброса всегда требуют подтверждения человеком |
| GPS | Необязательный сбор в отдельную таблицу; нет обязательной живой позиции, траектории и влияния телеметрии на расчёт |
| Данные | Догрузка, восстановление тестового набора и полный нулевой старт — три действия. Полный сброс не оставляет клиентские/инженерные аккаунты и рабочую историю |
| Интеграции | Токены создаются в Dashboard; полные scopes и внешний API обсуждаются следующим контуром |
| Дизайн | Компоновку и навигацию определяет дизайнер; новые функции здесь не превращаются в обязательные отдельные страницы |

Последний принцип применяем и к Dashboard: не предписываем расположение карты слева, AI справа, число вкладок или название каждой страницы. Уже явно выбранная **страница «Чаты»** сохраняется. Hover остаётся исходной функцией, а доступ к тем же подробностям нажатием/клавиатурой ниже предлагается как дополнение.

## 3. DB1 — заявки, создание и отмена: принято

### 3.1. Список дня

**Исходная функция:** все заявки на день, объяснения, подробности при наведении.

**Предложение к представлению:** для выбранного рабочего дня доступны все относящиеся к нему заявки, включая начатые, завершённые и отменённые, с фильтрами. Это не клиентский список, из которого завершённая работа исчезает. Конкретный набор колонок выбирает дизайнер, но данные должны позволять увидеть:

| Сведения | Назначение |
|---|---|
| ID, адрес, тип/проблема | Найти и различить заявку |
| Приоритет | Понять срочность |
| Согласованное окно и расчётный момент | Не спутать условия клиента с прогнозом визита |
| Назначенный инженер либо причина неназначения | Понять результат распределения |
| Жизненный цикл и последние явные отметки | Отличить прогноз от выполняемой работы |
| Источник/момент применённого плана | Видеть актуальность при перерасчёте |
| Объяснение | Понять проверенные ограничения и основания |

Предлагаемые фильтры — назначенные/неназначенные, срочность, инженер, жизненный цикл. Они только меняют представление и не запускают Router. В интерфейсе нужна и возможность раскрыть подробности без hover; это проектная деталь, не изменение исходных данных.

### 3.2. Объяснения доступны без обязательной генерации

Список и карточка показывают причины и факты из sys/принятого результата. AI может расширить объяснение по запросу, но его недоступность не должна прятать уже полученную причину неназначения. Такое объяснение не обещает доказанный оптимум, если расчёт лишь нашёл допустимый вариант.

В MANUAL источник объяснения — сохранённые ручные действия/доступные данные sys. Не приписывать человеку мотивы Engine и не читать фоновый Router для имитации объяснения его решения.

### 3.3. Правки из доски

Смена времени/окна, локации и приоритета выполняется через sys. В AUTO это изменение условий задачи, а не способ непосредственно назначить мастера. Условия не заменяются автоматически «более удобными» ради выполнимости.

После фактического начала обычное изменение заявки не предлагается ни через UI, ни как обход через AI fix. Фиксация дальнейших фактов и завершение работы остаются возможны. Отдельный сценарий прерывания, переоформления или исправления ошибочной отметки не вводится этим документом.

### 3.4. Создать или отменить ещё не начатую заявку — согласовано

Диспетчер может вручную создать заявку и отменить ещё не начатую работу. Это дополнение к смене времени/окна, локации и приоритета. В AUTO результат создания либо отмены меняет задачу через sys и опубликованный снимок; сам Dashboard не выбирает за Router исполнителя.

При создании используются действительные введённые данные и системные проверки. Не создаётся фиктивное подтверждение клиентского email и не подставляются выдуманные сведения. Связь созданной диспетчером заявки с клиентским аккаунтом и почтовыми событиями остаётся технической детализацией общего сценария.

Отмена — изменение состояния с сохранением истории, не физическое удаление строки. Запрет обычного изменения начатой работы сохраняется для UI, AI и MANUAL. Принятое право диспетчера отменять не означает автоматически отдельную кнопку отмены у клиента.

**Итог DB1:** создание и отмена до фактического начала приняты; правки исходной доски сохранены. Полный каталог операций по просьбе пользователя не разрабатывается.

## 4. DB2 — просмотр и устранение alerts: принято

### 4.1. Состав по источникам

Исходные alerts о невозможных местах роутинга сохраняются. Их основа — неназначенные заявки, причины и ошибки допустимости результата. Уже согласованные дополнительные проблемы: не поместившийся включённый обед, конфликт восстановленного обязательного обеда, явно сообщённые инженером затруднения.

Операционные сигналы и техническую недоступность предлагаем различать визуально:

| Вид | Источник | Не следует выводить |
|---|---|---|
| Неназначенная заявка | Пригодный принятый результат и конкретная причина | «Система ещё считает» |
| Конфликт обеда | Результат обеда/alert | «Инженер уже пообедал» |
| Обращение инженера | Полученное сообщение/событие sys | Произвольное число минут задержки |
| Нет подтверждения ключевой отметки | Принятый ранее механизм напоминаний | Автоматический offline, публикацию сектора или сорванный визит |
| Расчёт отстаёт | Проверки входа/контекста | Невозможность всех заявок |
| Сбой сервиса | Реальный системный исход | Отказ клиента или выполненную передачу письма |

Предлагаемые данные alert: к чему относится, понятная причина, источник и момент состояния, доступное связанное действие. Это не новая модель вычисления риска.

### 4.2. Работа с карточкой

Из предупреждения можно перейти к заявке/инженеру, открыть системное объяснение либо попросить диспетчерского AI разобрать этот объект. Корректирующее действие всегда проходит обычные права sys; alert не выдаёт привилегированный доступ.

**Согласовано:** «просмотрено» и «устранено» — разные признаки. Диспетчер может отметить просмотр, но нерешённая неназначенность или конфликт обеда не исчезают из действующих данных от закрытия карточки. Когда sys подтвердил изменение состояния, предупреждение становится неактуальным/закрытым; история хранится по правилам Data Layer.

Закрытие/просмотр alert не является командой перерасчёта. Повторные результаты с той же проблемой не должны создавать бессмысленные дубликаты; точный ключ эпизода — будущая деталь sys.

### 4.3. Обед

Сохраняется выбор: оставить заявку и пропуск обеда либо восстановить обед с явным исключением выбранных работ. Диспетчер видит последствия до подтверждения. Нельзя без основания обещать, что отмены любой одной заявки достаточно.

`lunch.required` не снимается молча, дополнительные отказы не объявляются уже подтверждёнными человеком. Сам факт просмотра/скрытия alert не возвращает обед и не меняет `lunch_taken`.

**Итог DB2:** отметка просмотра не устраняет причину. Конкретные подписи и оформление выбирает дизайнер, но текущая проблема остаётся различимой до реального изменения состояния.

## 5. Карта со слоями и сравнение — уточнение представления

### 5.1. Три исходных слоя

| Слой с доски | Что можно достоверно отобразить сейчас |
|---|---|
| Заявки | Их заданные локации и связь со списком |
| Маршруты | Порядок и доступную геометрию применённого плана; в MANUAL — ручной рабочий план, а не фоновый автоматический |
| Инженеры | Предлагается показывать известные плановые стартовые точки с явной подписью их смысла, а не анимированную «живую» позицию |

**Важное разграничение с исходной доской:** на ней написано «позиция», но позднее GPS оставлен только необязательным сбором. Мы не удаляем слой инженеров, однако не обещаем текущую физическую позицию без источника. Представление плановых стартов — предложение адаптации слоя к принятому ограничению, не факт наличия живого трекинга.

Таблица `gps_observations` сама по себе не добавляет на Dashboard живую карту, траекторию или применение GPS в Router. Если позже потребуется показывать отдельное последнее наблюдение, это отдельное включение с timestamp, а не скрытое изменение настоящей версии. Нет точки — нет выдуманной позиции.

Предлагается выбирать инженера/заявку в списке и выделять связанный маршрут на карте; подробности доступны и через карту. Способ расположения выбирает дизайнер.

Передача локации в Google Карты утверждена для поездки инженера. Она не определяет поставщика подложки Dashboard и не передаёт управление планом внешнему навигатору.

### 5.2. Уже согласованные показатели

Показать число инженеров с хотя бы одной заявкой, пробег каждого и суммарно. Дополнительные принятые показатели — покрытие заявок, срочные, расчётное время перемещений, работы, ожидания и обедов. Для fast сумма времени перемещений важна, но обязательные показатели персонала/пробега не исчезают.

### 5.3. Два разных сравнения

**Main против baseline:** одни входные данные, карта и условия. Показываются назначения и показатели, а не только процент «улучшения». Если один вариант обслужил меньше заявок, это видно рядом с экономией; непригодный вариант не объявляется выгодным рабочим планом.

**До и после перепланирования:** предыдущий применённый план sys против нового принятого плана. Это показывает изменения исполнителя, порядка и времени, а не сравнение любых двух внутренних кандидатов Router.

`metric_scope=snapshot_remaining` означает остаток задачи снимка. Его нельзя сравнить как будто это тот же полный прошедший день. Состоявшиеся события показывает sys отдельно.

### 5.4. Пока считается новый план

Последний применённый план остаётся с «Перестраивается» и моментом состояния показанного плана. `planning_as_of` нового незавершённого расчёта не приписывается старому. Техническая ошибка показывается ошибкой, не вечной загрузкой.

В MANUAL прежние автоматические показатели можно сохранить как архивные с явной пометкой. Нельзя выдавать их за заново рассчитанную стоимость изменённого ручного маршрута. Простые счётчики текущих назначений sys может показать без оптимизации; недостающие дорожные оценки не придумываются.

## 6. DB3 — готовые политики без редактора: принято

**Согласовано:** Dashboard предоставляет выбор готовой политики. Редактора формул, порядка критериев, весов, произвольных параметров или настроек OR-Tools нет. Предыдущий вариант «каталог плюс редактирование поддержанных параметров» не превращается в отдельный интерфейс настройки коэффициентов.

По умолчанию — `fast`. Иерархия целей всё ещё принадлежит содержимому политики, а не неизменному бизнес-порядку Engine. Отсутствие редактора на Dashboard не требует зашивать каталог внутрь алгоритма.

### 6.1. Доступное управление в AUTO

Диспетчер выбирает политику и меняет условия через список/карточки заявок: время и окно, локацию, приоритет; добавляет и отменяет ещё не начатые заявки. Сохраняется управление доступностью инженеров и ранее принятый переключатель обедов.

Эти действия проходят через sys. Изменившийся вход Router публикуется существующим механизмом, после чего ядро самостоятельно обрабатывает его. В AUTO нет прямой правки назначения инженера или порядка маршрута и нет редактирования результата ядра через карту.

### 6.2. Выбор и отображение политики

Название и понятное описание приоритетов помогают отличить варианты. Способ выбора и подтверждения сохранения определяет дизайнер. Интерфейс не объявляет новый маршрут полученным только потому, что селектор уже показывает новую политику.

Пока расчёт идёт, различаются новая выбранная политика и происхождение ещё показанного последнего применённого плана. Обязательные навыки, окно, смена и транспорт не отключаются выбором пресета. Внутренний допуск не становится обычным параметром Dashboard.

### 6.3. Не путать с ручным режимом

Прямое ручное управление исполнителем и порядком разрешено в отдельном MANUAL из раздела 8. Отключается выход Router → sys, а не ядро и не его чтение входа.

В MANUAL смена политики может изменить фоновую задачу Router, но не перезаписывает ручной план через закрытую шину. После возврата AUTO принимается актуальный результат действующей политики.

**Итог DB3:** только выбор готовых политик и действия с исходными данными; редактор политик и прямое управление маршрутом в AUTO не добавляются.

## 7. DB4 — инженеры и исходящий человеческий диалог: принято

### 7.1. Список и управление

Сохраняются данные, позиция с указанным смыслом, статус, чат и ручное отключение. Уже согласованы создание инженера по email и его самостоятельное редактирование собственного профиля.

В списке предлагается показывать email/имя, навыки, транспорт, офис, смену, рабочую доступность, текущую/следующую работу и обед. Эти сведения не должны превращаться в один смешанный статус «работает/нет сети/не назначен».

Позиция — по правилам раздела 5, не автоматически поток GPS. Исходящее сообщение приходит в существующий инженерный чат, а не в отдельную копию переписки.

Предлагаемый диспетчерский контроль профиля — правка тех же расчётных сведений и смены через обычные права sys. Это не ограничивает уже принятое право самого инженера. Конкурентные правки не перетираются. Детальные границы этого дополнительного редактирования ещё нужно выразить в правах, не в новом каталоге операций сейчас.

Ручное отключение меняет рабочую доступность. Оно не подтверждает завершение уже начатой работы и не перебрасывает её другому автоматически. Прогнозный возврат может быть указан при известном временном перерыве; часы сами не подтверждают online.

### 7.2. Уже определённая страница «Чаты»

Передачи от агента/системы появляются у единственного диспетчера. Отдельных стадий распределения и принятия несколькими людьми нет. AI выключается сразу при передаче; диспетчер отвечает; его кнопка завершения возвращает AI и убирает активную вкладку, сохраняя контекст.

Переключение диалога и ручной перехват маршрутов не связаны. Завершение одного из нескольких чатов не закрывает остальные. Нет автозавершения по молчанию.

### 7.3. Первое сообщение диспетчера начинает передачу — согласовано

Открытие чата из списка инженеров само по себе ничего не переключает. **Фактическая отправка первого сообщения человеком-диспетчером** включает человеческий режим текущего инженерного диалога.

```text
Диспетчер открыл инженерный чат
→ режим пока не изменился
→ отправил первое сообщение
→ sys фиксирует сообщение и передачу диалога человеку
→ AI этого диалога приостанавливается
→ чат находится на странице «Чаты»
→ диспетчер отвечает и нажимает «Завершить передачу»
→ активная вкладка исчезает, история остаётся, AI возвращается
```

Это дополнительное согласованное основание со стороны самого диспетчера. Постоянной кнопки «Позвать человека» у клиента/инженера по-прежнему нет; их прежние основания — решение агента либо неответ провайдера — не изменяются.

Если диалог уже находится у диспетчера, новое сообщение не создаёт второй эпизод или вкладку. Приостановка касается только этого разговора. Прежнее сообщение AI, запущенное до передачи, не должно после неё появляться как параллельный автоматический ответ; техника согласования относится к sys.

**Итог DB4:** выбран полноценный человеческий диалог с паузой AI, не разовое сообщение поверх продолжающего отвечать агента.

## 8. DB5 — смена исполнителя и drag-and-drop в MANUAL: принято

### 8.1. Граница ручного режима сохраняется

Экстренная кнопка фиксирует текущее применённое состояние и отключает шину **Router → sys**. Ядро продолжает читать сектор, считать main/baseline и хранить свои результаты. Dashboard не получает их по скрытому каналу проверки ручных правок.

Диспетчер меняет рабочий план sys, не память Router и не обязательные входные назначения. Уже начатые работы и факты остаются защищены; ручное управление касается будущей, ещё не начатой части.

### 8.2. Два согласованных действия

| Действие | Интерфейсный способ | Граница |
|---|---|---|
| Сменить исполнителя заявки | На конкретной заявке выбрать другого инженера | Только в MANUAL и до фактического начала |
| Изменить порядок работ инженера | Открыть список заявок этого инженера и переставить заявки drag-and-drop | Только в MANUAL; не менять ход уже выполняемой работы |

Запись «поменять оператора на заявке» трактуется по контексту ответа как смена назначенного инженера. Она не меняет единственного оператора человеческих чатов.

```text
MANUAL
├── Заявка → выбор другого инженера → сохранение через sys
└── Инженер → его список заявок → drag-and-drop → сохранение нового порядка через sys
```

Точное оформление селектора, строки, перетаскивания и уведомлений выбирает дизайнер. Но два указанных механизма — уже согласованные функции, а не варианты на выбор.

### 8.3. Без группового черновика и общей кнопки применения

Предложение v1 «накопить связанные правки → Применить изменения» отвергнуто. Не вводится отдельный редактируемый пакет, который нужно целиком утверждать перед показом инженерам.

**Рабочая детализация простого поведения:** завершённая смена исполнителя либо drop отправляет одно изменение в sys. После успешной записи меняется действующий рабочий план. Промежуточное движение курсора не является серией сохранённых перестановок.

При смене исполнителя одна согласованная запись отражает уход заявки из прежней очереди и появление у нового инженера; заявка не должна одновременно дублироваться у обоих. Позиция добавления в новую очередь и её показ — техническая/дизайнерская деталь; диспетчер затем может изменить порядок согласованным drag-and-drop.

При сохранении проверяются режим MANUAL, актуальная версия, права и ещё не начатое состояние работы. При конфликте возвращается реальное состояние, не происходит перезапись чужой правки. Ни UI, ни sys не выдают неуспешное действие за применённое. Это реализация ранее принятой целостности, не расчёт допустимости маршрута самим sys.

### 8.4. Не добавлять обязательный ввод времён

В v1 предлагалось вместе с ручными правками обязать диспетчера задавать плановое время. Это не входит в выбранный пользователем простой сценарий: **для смены исполнителя или порядка не требуется отдельный обязательный ввод ETA, длительности дороги или расписания каждой заявки**.

Изменение клиентского окна через карточку — отдельная уже разрешённая правка исходных условий. Оно не является обязанностью изменить окно всякий раз, когда заявку перетащили в списке.

Предложение мини-оптимизатора в sys либо фоновой проверки у Router не вводится. Старые автоматические ETA, геометрия и суммарные дорожные показатели не становятся заново рассчитанными после ручной перестановки. Обзор может показывать точки и ручной порядок; точное представление ещё не пересчитанного времени — оставшаяся техническая деталь, без изменения принятых жестов и без выдуманных расчётов.

### 8.5. Возврат автоматики

Явное включение AUTO восстанавливает приём Router. Sys проверяет hash, контекст, пригодность и явные факты; актуальный результат заменяет будущее ручное распределение. Это не слияние с ручным порядком и не откат истории.

Прежнее понятие «отключить роутер» здесь означает только отключение шины результата. Обычный перезапуск сохраняет MANUAL и рабочий план, как принято в Data Layer.

**Итог DB5:** смена исполнителя на заявке и drag-and-drop в списке конкретного инженера; без группового применения и без обязательного ручного заполнения времён.

## 9. DB6 — read-only по умолчанию и подтверждение сбросов: принято

### 9.1. Что уже определено

Диспетчерский агент объясняет routing, alerts и стратегии, получает разрешённые данные и запрашивает изменения через sys. Доступ ко всем трём сегментам знаний не означает передачу этих знаний в чужой клиентский/инженерный контекст.

В read-only записи запрещены сервером. В fix — полный набор разрешённых диспетчерской роли бизнес-действий, публичный журнал намерений/результатов и возможность остановки. Уже выполненные записи не выдаются за отменённые при нажатии «Остановить».

AI read-only/fix независим от AUTO/MANUAL маршрутов и режима передачи пользовательского чата. Общего глобального «автоматический/ручной» переключателя на все эти функции нет.

### 9.2. Начальный режим и подтверждения

Из заявки/alert предлагается открыть разбор в собственном диспетчерском AI-чате с явным контекстом объекта. Это не сообщение клиенту и не передача пользовательского чата обратно модели.

**Согласовано: начальный режим нового диспетчерского AI-диалога — `read-only`.** `fix` включается явно. Возврат в read-only после каждого сообщения не требуется выбранной моделью.

**Согласовано:** обычные разрешённые изменения в fix не требуют универсального дополнительного подтверждения. Но «Сбросить к тестовым данным» и «Полный сброс» всегда требуют явного подтверждения человеком с перечнем последствий, даже если подготовку инициировал AI. Агент не подтверждает такой сброс сам за диспетчера.

Права специальной настройки Router и интеграционных секретов определяются их отдельным capability/контрактом. Термин «самый сложный агент» не создаёт таких прав. Код, пароль, сессионный секрет не выводятся в публичный журнал действий.

**Итог DB6:** приняты read-only по умолчанию, обычный fix с журналом/остановкой и отдельное человеческое подтверждение обоих сбросов. Наличие режима fix не делает недоступную в AUTO ручную перестановку разрешённой: действуют общие системные ограничения.

## 10. DB7 — догрузка и полный сброс «всё в ноль»: принято

### 10.1. Три разные функции

| Действие | Результат |
|---|---|
| «Догрузить данные» | Проверить пакет и добавить новые записи без очистки существующих |
| «Сбросить к тестовым данным» | Очистить текущий демонстрационный сценарий и восстановить исходный тестовый набор |
| «Полный сброс» | Обнулить данные приложения для нового пустого старта; не сохранять прежние клиентские/инженерные данные и не загружать seed автоматически |

Догрузка сохраняет принятые правила: при ошибке/конфликте пакет не применяется частично, повтор не создаёт дубликаты, чужая правка не перетирается. Отчёт о проверке — отображение фактического результата sys.

Оба сброса требуют подтверждения человеком по DB6. Это описание будущих кнопок; **в рамках подготовки этого документа никакие данные не сбрасывались**.

### 10.2. Объём полного сброса

**Решение пользователя: «Полностью сбрасываем всё в ноль».** Прежняя развилка «оставить инженеров/аккаунты» снята. Полный сброс не означает очистку только списка заявок с сохранением прежнего рабочего состояния где-то рядом.

Конкретизация полного нуля на уровне данных приложения:

| Данные приложения | После полного сброса |
|---|---|
| Клиентские и инженерные аккаунты, роли и профили | Прежних записей нет; инженеров снова создаёт диспетчер, клиенты регистрируются заново |
| Заявки, старые условия, назначения и факты выполнения | Удалены из рабочего хранилища вместе с относящейся историей |
| Рабочие дни, обеды, текущие планы, принятые пакеты и снимки старого запуска | Старое состояние не активно и не восстанавливается при чтении |
| Диалоги, сообщения, эпизоды передачи, пользовательские резюме | Прежних пользовательских чатов и контекста нет |
| GPS-наблюдения | Старых наблюдений нет |
| Журналы прежнего запуска, результаты действий, импорты и учёт писем | Старые записи не продолжают действовать в новой системе |
| Пользовательские сессии, интеграционные доступы старого состояния, активные подтверждения | Не дают доступа к новому пустому контуру |
| Внутренние пользовательские счётчики/резервы AI и иные изменяемые настройки старого запуска | Нулевое либо начальное состояние, без скрытого сохранения прежнего пользовательского набора |

Эта таблица раскрывает фразу «всё в ноль» как **полный сброс данных приложения**, а не подтверждение уничтожения серверов. Предложение v1 сохранить дневной расход AI как исключение не было выбрано и здесь не выдаётся за принятое. После очистки первоначальные лимиты снова действуют на новые запросы; обнуление внутреннего учёта не отменяет фактически совершённые внешние обращения.

Сохранение прежних пользовательских чатов, профилей или истории в доступном рабочем архиве не называется полным сбросом. Возможность внешней резервной копии и порядок её хранения — отдельная настройка эксплуатации, не скрытое продолжение старого состояния.

### 10.3. Граница с развёртыванием — техническая трактовка

Подтверждена очистка данных, а не удаление приложения, его исходного кода, `.env`, схемы БД, файла карты и исходных файлов `knowledge`. Чтобы пустая система могла работать, из конфигурации восстанавливается единственный диспетчер и необходимые исходные каталоги/параметры, без клиентских или инженерных seed-записей.

Это **техническая трактовка границы сброса**, а не отдельный ответ пользователя о каждом инфраструктурном файле. Изменённые во время работы настройки/каталоги не сохраняются под видом исходной конфигурации: начальные значения берутся из источников развёртывания. Производные индексы знаний могут пересоздаваться из `knowledge`; точный порядок очистки/инициализации обсуждается при реализации, не как новые пользовательские данные.

Доступ диспетчера из `.env` остаётся способом снова войти после сброса. Судьба текущей браузерной сессии и необходимость повторного входа определяются реализацией; старые роли и токены не восстанавливаются автоматически лишь потому, что у них совпал ID.

### 10.4. Не оживлять старую работу

**Технические следствия, без выбора SQL/API:** закрыть или инвалидировать старые AI-run, незавершённые попытки импорта и ещё не переданные почтовые намерения; не допустить, чтобы поздний ответ старой операции записался в новое состояние.

После очистки публикуется новый корректный пустой/начальный снимок через существующий механизм. Router не получает команду редактировать память маршрутов. Старое применение не становится действующим новым планом из-за совпадения ID; граница нового запуска проверяется sys.

Очередь после приёма письма принадлежит отдельному SMTP-серверу. Очистка данных приложения не заявляется отзывом уже принятых им писем. Фактический сетевой или провайдерский учёт также не «отменяется» локальным сбросом.

### 10.5. Отличие от тестового сброса и обычного рестарта

При тестовом сбросе новый состав инженеров/заявок загружается из исходного тестового набора. При полном сбросе он не загружается. Признак намеренно пустой инициализированной системы должен переживать последующий обычный рестарт: пустая таблица не повод автоматически вернуть тестовые заявки.

Обычный рестарт по-прежнему сохраняет данные, MANUAL, чаты и квоты. Разрушительный сброс — отдельное подтверждённое действие, не способ обработки запуска процесса.

Прежнее предложение «после обоих намеренных сбросов всегда AUTO» не получило отдельного ответа. Режим после явного сброса остаётся узкой начальной настройкой, не блокирующей утверждение полного нулевого состояния. Он должен быть обозначен при реализации и не выводится молча из правила сохранения MANUAL при обычном рестарте.

**Итог DB7:** полный сброс действительно полный на уровне данных приложения; оставить инженеров и клиентов не предлагается. Три отдельные кнопки, подтверждения и запрет автоматического возврата seed сохраняются.

## 11. Интеграционные токены — функция Dashboard, контракт позднее

В исходной концепции токены client-app / eng-app / master создаются в Dashboard. Эта возможность сохраняется. Полные области доступа, сроки, отзыв, технический формат ключа и соответствующие endpoints — следующий отдельный раунд внешнего API.

Для интерфейса достаточно сейчас не потерять наличие управления интеграционным доступом. Не объявляем все действия с токенами заранее разрешёнными AI и не добавляем SQL/прямую запись Router в значение master-token.

Предложение безопасности отображения ключа и список метаданных можно уточнить вместе с API; этот документ не создаёт реальные credentials.

## 12. Проверки будущего Dashboard

Это критерии проектируемого поведения, не результаты испытаний.

| Сценарий | Что должно быть видно / сохранено |
|---|---|
| Вход без SMTP | Парольный путь открывает того же диспетчера |
| Результат ещё считается | Последний применённый план и его момент состояния, не ложный отказ |
| Неназначенная заявка | Конкретная причина и связь с текущим результатом |
| AI недоступен | Системные основания и обычные ручные функции остаются доступны при работающем sys |
| Показ слоя инженеров | Источник точки указан; нет фиктивного движения без GPS |
| Выбор инженера/заявки | Связанная информация списка и карты, без изменения самого маршрута |
| Смена политики | Выбор готового варианта через sys без редактора весов; старый план не объявляется новым |
| Переключение MANUAL | Вход Router работает, новые фоновые результаты не попадают в рабочий план |
| Запоздавший результат после MANUAL | Не перезаписывает ручную работу |
| Возврат AUTO | Замена будущего ручного распределения актуальным допустимым результатом |
| Рестарт в MANUAL | Режим и рабочий план сохраняются |
| Уже начатая работа | Нет обычного изменения условий/переназначения через UI или AI |
| Просмотр alert | Не устраняет его причину автоматически |
| Обед восстановлен | Только явно подтверждённые исключения, без второго обеда и скрытого снятия required |
| Main и baseline | Сопоставимый снимок, видно покрытие и пригодность |
| Ручной план изменён | Прежние автоматические дорожные метрики не выдаются за новые; ввод новых ETA не обязателен для смены порядка |
| Чат передан от агента/системы | Один существующий диалог, AI выключен, завершает диспетчер |
| Диспетчер отправил первое сообщение | Диалог переходит человеку, AI приостановлен; простое открытие чата этого не делает |
| Кнопка завершения чата | Активная вкладка исчезает, история и другие чаты остаются |
| AI fix остановлен | Новые действия не начинаются; уже применённые не названы отменёнными |
| Повтор догрузки | Нет дублей и частичного применения ошибочного пакета |
| Полный сброс | Старые клиенты, инженеры, рабочие данные и пользовательская история очищены; после инициализации пустой старт без seed |
| Конкурентная правка инженера и диспетчера | Нет silent overwrite |
| Исполнитель выбран в MANUAL | Заявка меняет инженера согласованно, без двух активных назначений |
| Drag-and-drop в списке инженера | Сохраняется новый порядок после sys, без общей кнопки применения |
| Попытка прямой перестановки в AUTO | Действие недоступно; остаются изменения заявок и политики |
| Перетаскивание начатой работы | Не меняет её исполнителя и фактическую историю |
| Новый диспетчерский AI-диалог | Начинается в read-only |
| AI предложил любой из двух сбросов | Выполнение ждёт подтверждения человеком |
| Полный сброс, затем рестарт | Демо-заявки не возвращаются, старые фоновые действия не оживают |
| Сброс к тестовым данным | Новый сценарий соответствует тестовому набору, а не смеси двух прогонов |

## 13. Итог DB1–DB7 и дальнейшая детализация

| Код | Зафиксированное решение |
|---|---|
| DB1 | Диспетчер создаёт и отменяет ещё не начатые заявки; правки времени/локации/приоритета сохраняются |
| DB2 | Просмотр alert отдельно от действительного устранения его причины |
| DB3 | Только выбор готовых политик, без редактора; прямые изменения маршрута в AUTO отсутствуют |
| DB4 | Первое отправленное сообщение диспетчера инженеру начинает человеческий диалог с паузой AI |
| DB5 | Исполнитель меняется на заявке; порядок в списке инженера — drag-and-drop в MANUAL; группового применения и обязательного ввода времён нет |
| DB6 | Read-only по умолчанию, fix с журналом/остановкой; оба сброса требуют подтверждения человеком |
| DB7 | Полный сброс всех данных приложения до нулевого состояния, не вариант с сохранением сотрудников |

### 13.1. Неблокирующие детали

Способ показа времени/геометрии после ручной перестановки, позиция заявки при смене исполнителя, начальный AUTO/MANUAL после явного сброса, техническая граница инфраструктурной инициализации и связь ручного создания с клиентским аккаунтом/почтой ещё не описаны до уровня реализации. Эти детали не считаются получившими отдельное подтверждение и не превращаются в новый раунд по уже выбранным жестам.

Плановые стартовые маркеры инженеров и связь карты со списками остаются предложением представления с учётом необязательного GPS. Подробный дизайн у дизайнера; не вводятся live-трекинг и новый расчётный сервис.

### 13.2. Последующая синхронизация

В основной концепции нужно отразить отсутствие редактора политик и точные жесты MANUAL. В System Layer/AI — исходящее первое сообщение человека, начальный read-only и подтверждение сбросов. В Data Layer — полный объём очистки и снятие прежнего варианта сохранения инженеров/клиентов при полном сбросе. Остальные документы этой правкой не перезаписываются.

Следующий самостоятельный контур — внешнее интеграционное API. Каталог системных операций остаётся отложенным.
