## 1. Итог одним абзацем

Сессия закрыла главные неизвестные (критерии оценки, статус контрольных данных, границы прототипа) и почти полностью подтвердила нашу архитектуру: движок, транспортные профили, семантика окон, навыки, мультизоны и однодневный горизонт уже соответствуют официальным ответам. Содержательный разворот один — **порядок целей оптимизации**: официально «больше выполненных → меньше исполнителей», а наш default `fast` ставит «исполнители» последним. Главный дефицит после сессии — не солвер (готов и местами избыточен), а **витрина**: `apps/web` пуст, при том что «соответствие задаче» (20%) и «удобство» (15%) оцениваются по UI-демо.

## 3. Что изменилось (развороты)

### 3.1 Порядок критериев оптимизации — главное изменение

Официально (47 §9): 1) **больше выполненных заявок**, 2) **меньше исполнителей**, остальное (пробег, время в пути) — на усмотрение команды. У нас coverage первый во всех политиках, причём строже официального (urgent лексикографически старше любых обычных, 34 §6.2) — но default `fast` = coverage → travel_time → distance → **engineers_used**: исполнители последние.

**Решение (Проект реализации):** сделать порядок `compact` (coverage → engineers_used → …) базовым для официального датасета/демо — переключить default или переопределить `fast`; обновить 33 §5, 34 §6.2, `core/policy.py`; golden-планы изменятся намеренно — зафиксировать в теле коммита (AGENTS §4.8). В презентации критерии №1/№2 называем дословно как озвучено.

### 3.2 Границы прототипа: диспетчер и один день

Пользователь прототипа — только диспетчер; инженеру «достаточно маршрута вне системы»; мобильное приложение не требуется (47 §13). Client/Engineer App (32 §4–5, 38) и так помечены расширениями (32 §1.1) — теперь они расширения и по официальной позиции, с нулевым весом в приёмке. Engineer App сохраняем как технический источник фактов (старт/финиш/опоздания), но демо-сценарий перепланирования гоняем через API (`engineer.controller` уже отдаёт facts) — без UI инженера.

### 3.3 Объяснения: компактно

«Портянки» по каждой заявке не нужны — ценно обоснование **нераспределённых** (47 §15). Наша L1 (rule-based причины из солвера, D-3; коды `Reason` в 33 §8) — ровно обязательный минимум по ТЗ (18 §3). Per-assign `PlanEvidence` оставляем как структуру для UI (факторы, не рассказ): у назначенных — компактные факторы, у неназначенных — выпуклая причина (39 §3).

### 3.4 Данные и сценарий

Статусы «отменена/выполнена» — только в контроле и референсом не служат; статуса «отказано» нет; невыполненное уходит «в другой день» и для задачи сценарий заканчивается (47 §1/§10). В синтезе таких переходов не изобретаем. «7 заявок в окне» — овербукинг, не модель: **не воспроизводим** и объясняем на защите как особенность реального контроля.

## 4. Неожиданно хорошо (не ждали)

1. **Развёртывание «за кадром» легитимно** (47 §13) — наш MGG-сервер и офлайн-контур не нужно прятать; риска «запустите при экспертах локально» нет.
2. **Нормативы ≪ окон** (подключка ~1,5 ч; локальные/дозаказы <1 ч — примерно вдвое меньше окна, 47 §4) — «желательно уместить всё» физически реализуемо. Наш east-golden **65/66 назначено против 44/66 у FIFO** — готовая история для обязательного сравнения с базой (18 §5).
3. **Аварии официально «под наблюдением»** (47 §5): вытеснение визитов + аварийная день-в-день — это ровно наш REPAIR-триггер `new_urgent_request`; сильнейшая демонстрация стала центром внимания оценки.
4. **Скепсис постановщика к LLM** — D-11 теперь можно цитировать как позицию компании, а не только нашу.
5. **Нет мультибригадных заявок, зависимостей между заявками и мультидня** (47 §1/§12) — всё, чего нет в нашей модели, официально и не нужно: солвер не усложняется.
6. **Аномалии контроля объявлены овербукингом** — снимает риск вопроса «почему план не как в контроле».
7. **Мобильное приложение не требуется** — большой кусок работ отпал; адаптивность витрины — «второй эшелон».
8. **Нормативы обещаны официально** (48 §14) — уйдёт главное допущение в длительностях.

## 6. Что убрать / поменять (противоречит или вредно после сессии)

1. **Default-политика** — см. 3.1. Единственное содержательное «поменять» в движке.
2. **Обеды** (Требует решения тимлида): организаторы обеды вообще не учитывают (47 §7), а у нас required-обед может сделать план неиспользуемым (`REQUIRED_LUNCH_UNPLACED`, 33 §6) и ухудшить критерий №1. Для официального датасета: обеды optional либо `lunches_enabled=false`, причём **одинаково для main и FIFO-baseline** — иначе сравнение метрик нечестное. Реализацию v14 сохраняем как демонстрацию «второго эшелона».
3. **UI-объяснения**: не строить построчные «рассказы алгоритма»; проверить бэклоги 10/13 и убрать такие идеи.
4. **Engineer/Client App снять с критического пути приёмки**: в 32 §17.3 пометить соответствующие сценарии как extension; факты для демо — через API.
5. **Приоритеты не расширять**: каталог `normal|urgent` (33 §4) достаточен; «новые подключения приоритетнее» (47 §5) — только опциональный демо-акцент.
6. **Слоты/бронирование на месяцы вперёд не проектировать** — в концепте и не было (только «дата+окно» одной заявки); это продукт Бикипер, не наша задача.
7. **Таймзоны**: per-scenario `config.timezone` (33 §4) достаточно; per-client зоны не делаем — датасет московский (48 §7).
