# Система диспетчеризации инженеров — краткий концепт для команды

**Комплект v14 · 15.09.2026 · default policy: `compact` (обновлено после QA 16.09, [50](./50-concept-changes-after-qa.md))**

Подробности: [вся система](./32-system_concept_v14.md), [input/output Router](./33-router_contract_v2.md), [модель и внутренности](./34-engine_contract_v2.md).

## Что делаем

Сервис принимает клиентские заявки, распределяет их между выездными инженерами, строит порядок посещений и расписание, показывает маршруты и объясняет решения. При изменении задач или доступности инженеров рассчитывается оставшаяся часть дня. Диспетчер управляет условиями и политикой, а при необходимости полностью перехватывает рабочий план.

Для кейса «Билайн Бизнес» обязательны навыки, временные окна, смены и требуемый транспорт; неназначенные работы с причинами; карта; перепланирование; число задействованных инженеров и пробег по каждому / суммарно. Наши AI, почта, обеды и отдельные приложения расширяют этот прототип. [ТЗ, стр. 2–6]

## Из чего состоит система

| Зона | Ответственность |
|---|---|
| **Client App** | Форма или AI-диалог, подтверждение заявки, состояние и условия визита |
| **Engineer App** | План дня, маршрут, online/offline, начало / завершение работы и проблемы (без телеметрии) |
| **Dashboard** | Карта, объяснения, alerts, политики, импорт, сравнение с baseline и ручной перехват |
| **Integration API** | Подключение существующих приложений через права sys |
| **System Layer** | Живые состояния, операции, применённый план, вход для Router, применение результата, AI-tools и письма |
| **Router Core** | Автономный расчёт: Runtime + Engine |
| **Data Layer** | Бизнес-данные, опубликованный вход, применённый план, события и история |
| **AI / SMTP** | Три ролевых агента; отдельно внешний почтовый сервис на другом сервере |

```text
Четыре внешних входа → System Layer ↔ Data Layer
                           ↓
                 опубликованный снимок
                           ↓
                Router Runtime ↔ Engine
                           ↓
              main + baseline + hash + context
                           ↓
             System Layer → план в приложениях
```

## Главный принцип данных

**Sys знает, что происходит; Router рассчитывает, что делать дальше.**

Инженер явно отмечает начало и завершение. Sys ведёт стадии, выполнение и уже начатые пункты: старт работы якорит инженера в её точке с ожидаемым освобождением, существенно отклонившаяся или превысившая допуск работа обновляет якорь, инженер с превышением временно выводится из задачи. Router получает не всю историю, а оставшиеся не начатые заявки и для каждого инженера **точку продолжения + время доступности** (`start_location + available_from`).

Специальный сектор — целый опубликованный снимок, не поток событий. Он содержит время состояния, горизонт, заявки, инженеров, доступность, обеды и политику. Карта, матрицы / кеши дорог и технический допуск находятся отдельно у Router. Контакты, авторизация и чаты не являются входом оптимизатора.

Время внутри системы — Unix-time в целых секундах. `planning_as_of` обновляется при публикации других изменившихся данных, не каждую секунду. Штатное выполнение без материального отклонения пересчёта не требует; материальное отклонение длительности или превышение допуска публикует проекцию с новыми якорями. При значимом изменении публикуется актуальная проекция целиком.

## Как работает Router

**Runtime** читает снимок, проверяет вход, готовит дорожные время / расстояния, считает baseline, управляет вычислительными заданиями и собирает выдачу. **Engine** совместно выбирает назначения, порядок, расписание и обеды. Runtime не исправляет основной маршрут после Engine.

Опорный технический проект — OR-Tools Routing Solver с нашей логикой вокруг: совместимость навыков / транспорта, окна и смены, открытые маршруты, политика целей, обеды, seeds и проверка результата. Первое решение предлагается строить вставками, затем улучшать локальным поиском. Подробная интеграция и настройки для испытаний описаны в engine-документе; измеренная производительность пока не заявлена.

Три принятых пути: **малое отклонение — проверить и сохранить допустимый порядок; существенное изменение — восстановить и улучшить прежний кандидат; первый запуск / нет пригодного кандидата — построить заново.** Старый результат не получает новый hash без проверки.

**Политика задаёт всю иерархию целей.** Default `compact` — сначала покрытие, затем число занятых инженеров (официальные критерии QA 16.09); пробег и время дороги — следующие уровни. Каталог сохраняет пресеты `fast`, `sla`, `balanced`, `eco`; это настройка каталога, не постоянный порядок внутри Engine. Hard constraints политикой не отключаются. Обеды по умолчанию выключены и включаются переключателем в дашборде. Едущего инженера можно перенаправить на другую не начатую заявку, если план улучшается.

Baseline неизменен по ТЗ: заявки в порядке поступления, первый подходящий инженер в порядке входных данных, посещения в порядке назначения, без глобальной оптимизации. Он использует тот же снимок и карту, что main.

## Как результат становится рабочим

Router возвращает main, baseline, назначения / причины, расписания, маршруты, метрики, `result_id`, `input_hash` и `router_context_version`. Sys сравнивает hash со снимком и контекст с активной картой / настройками Router. Несовпадение — загрузка; готовое неназначение — отдельный объяснимый результат, не вечный spinner.

Применяется только пригодный результат в AUTO, без конфликта с текущими фактами. Повторное чтение одного ID не возвращает завершённые пункты и не повторяет письма. Sys сам продвигает уже применённый план по отметкам инженера.

## Ручной режим, обеды и уведомления

**MANUAL:** экстренная кнопка фиксирует применённый план и отключает только Router→sys. Диспетчер сам меняет назначения; Router параллельно продолжает считать, но его выдача не обрабатывается наверху. Возврат AUTO заменяет будущее ручное распределение актуальным результатом, не отменяя выполненные / начатые работы.

**Обед:** Dashboard включает функцию, Router ищет окно. В обычном конфликте заявка важнее необязательного обеда, но возникает alert. `lunch_taken` устанавливается sys при фактическом начале — второго обеда нет. «Вернуть обед» означает `lunch.required=true` и исключение только явно подтверждённой заявки одной операцией sys. Дополнительные отказы не делаются молча.

**Заявка:** после подтверждения отправки — pending; затем письмо о назначении либо стандартное предложение поменять дату / окно. «Опаздываю» само по себе письмо не отправляет. «Буду вовремя» необязательно; отсутствие обязательной отметки означает неопределённость, напоминание и предупреждение диспетчеру, не автоматическое «всё хорошо».

AI действует в рамках трёх ролей; диспетчерский агент имеет read-only/fix. SMTP только отправляет подготовленное sys письмо и не находится в основной Docker-сети.

## Что дальше

Реальный датасет, длительность / часы обеда, величина допуска и окончательные поисковые бюджеты ещё требуют настройки / проверки; цифры не подставлены как якобы согласованные нормативы. Следующая детализация: **System Layer → четыре внешних шлюза → AI → внешний SMTP → Data Layer**. Данный комплект — база разработки и испытаний, не отчёт о готовом коде.
