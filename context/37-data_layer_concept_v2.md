# Data Layer — концепция v2

**Редакция:** 15 сентября 2026 года.  
**Основа:** `data_layer_concept_v1.md`, ответы пользователя на DL1–DL7, приложенная фотография доски, `system_layer_concept_v2.md` и последние согласованные границы Router и AI/SMTP.  
**Статус:** решения о PostgreSQL, снимках, восстановлении, знаниях и импорте приняты. GPS уточнён до необязательного сбора без использования в расчёте. Добавлены три отдельных действия Dashboard для работы с наборами данных. Точные физические имена таблиц, сроки хранения и состав полного сброса ещё требуют технической конкретизации; предложения по этим вопросам обозначены явно.

Каталог операций System Layer остаётся отложенным. Документ описывает данные, владение ими и последствия их загрузки/сброса, а не endpoints и не SQL-миграции. Существующие файлы комплекта не перезаписываются. Создание базы, импорт, удаление данных и тесты работающей системы при подготовке документа не выполнялись.

## 1. Согласованные решения этого раунда

| Область | Решение |
|---|---|
| Основное хранение | Одна PostgreSQL с pgvector; отдельной векторной БД нет |
| Redis | Только backlog, не обязательная зависимость текущей архитектуры |
| Логические области | Сохраняются категории с доски; общий аккаунт с ролями/профилями допустим |
| Специальный сектор | Неизменяемые полные снимки и активный указатель в PostgreSQL |
| Доступ Router | Прямое чтение опубликованного сектора, без бизнес-записи и чтения всей базы |
| Представление снимка | Точный JSON для одинакового вычисления hash; технические метаданные не входят в его payload |
| Живые данные и публикация | Разделены; запись любого события в базу не создаёт новый снимок автоматически |
| История | Принятые планы и значимые события сохраняются с ограниченным сроком хранения; `eternal-log` — название, не бессрочность |
| GPS | Отдельная таблица `timestamp + user + position`, только необязательный сбор; без обязательной траектории и использования в маршрутизации |
| Чаты | Один диалог, сообщения и эпизоды передачи одному диспетчеру; закрытие вкладки не удаляет переписку |
| Знания | Три группы таблиц; исходники в `knowledge/client`, `knowledge/engineer`, `knowledge/dispatch` |
| Перезапуск | Сохраняются рабочий план, AUTO/MANUAL, использованный обед, чаты, квоты и служебный учёт |
| Импорт | Проверка всего пакета, отсутствие дублей и молчаливой перезаписи, отказ всего пакета при ошибке/конфликте |
| Управление данными | Догрузка; сброс к тестовому набору; полный сброс к пустому рабочему состоянию — три разных действия |

### 1.1. Что Data Layer не делает

System Layer определяет права, бизнес-переходы, поводы для писем и публикации входа. Router выбирает распределение, маршрут и расписание. Data Layer сохраняет данные и обеспечивает предусмотренные связи и целостность.

Ни имя `Routing policy`, ни наличие JSON/векторов не превращают базу в самостоятельного планировщика. В ней не вводится правило «истёк срок / обновился GPS / инженер молчит → пересчитать».

Прогноз «по плану» не создаёт подтверждённые факты начала/завершения. Их источник остаётся прежним — отметки инженера. Unix-time и длительности представлены целыми секундами, форматирование происходит на границах приложения.

## 2. Структура с доски и её уточнение

Фотография сохраняет исходную организацию: пользователи, сессии, заявки, письма, решения, логи, отдельный Routing policy, pgvec и other data. Принимаем её как карту смысловых областей. Она не обязывает реализовать каждый прямоугольник отдельной базой, сервером или строго одной таблицей.

| Блок на фотографии | Исходные названия | Как используется в текущей концепции |
|---|---|---|
| Пользователи | `engineers`, `clients`, `admins` | Общая идентичность/вход и выданные роли; соответствующие профили и пользовательские представления |
| Сессии | `sessions` | Действующие сессии и связанный серверный учёт авторизации |
| Заявки | `requests` | Одни текущие условия заявки, клиент, технические параметры, отдельные жизненный цикл и назначение |
| Письма | `sent` | Учёт подготовки/передачи письма со стороны sys; не внешняя очередь доставки |
| Решения | `admin-moves`, `decisions`, `politic-catalog` | Действия диспетчера, основания/история решений и каталог поддержанных политик |
| Логи | `eternal-log` | Журнал с выбранным сроком хранения; название не означает бесконечное накопление |
| Routing policy | Переменные, таблицы и списки для текущего routing | Отдельный опубликованный `RouterTaskSnapshot` и ссылка на его действующую версию |
| pgvec | Векторные данные для AI-чатов | Три изолированные группы документации/фрагментов/векторов |
| Other data | Дополнительные данные | Явно определённые вспомогательные сущности, а не бесструктурный склад произвольных данных |

На фото указано, что вход routing формируется механизмом взаимодействия sys и data (`mount-data-eng`), а Router читает его напрямую. Это сохранено. Надпись о возможной прямой шине AI является ранней гипотезой: более позднее решение оставляет поиск и бизнес-доступ AI через System Layer. Приоритет имеют последние согласования.

### 2.1. Физическая основа

**Принято:** одна база приложения PostgreSQL с расширением pgvector. Области разделяются таблицами и при необходимости схемами. Redis зафиксирован в backlog.

ID, связи, текущие статусы, окна, времена и версии имеют обычные поля. Полные планы, структурированные причины и ограниченные конфигурации могут храниться документами. Для хэшируемого входа предусмотрено отдельное точное представление, описанное в разделе 4. Вся база не превращается в один изменяемый JSON.

Названия с дефисами на доске сохранены в документе как исходные обозначения. Окончательное SQL-именование и соответствие таблиц, представлений и схем выбираются при миграциях; переименование технического объекта не должно потерять смысл исходной области.

### 2.2. Четыре раздельных состояния

| Состояние | Источник и назначение |
|---|---|
| Живые данные приложения | Действующие условия, роли, доступность, факты, переписка и отдельно необязательная телеметрия |
| Опубликованный вход | Неизменяемая проекция следующей задачи планирования |
| Полученный результат Router | Main, baseline, расчётные сведения и принадлежность к использованному входу/контексту |
| Применённый план | То, по чему работают интерфейсы; в AUTO — принятый результат, в MANUAL — редакция диспетчера |

История фиксирует прежние состояния, но не является ещё одним независимо редактируемым источником текущего назначения.

## 3. Пользователи, рабочий день, заявки и служебные данные

### 3.1. Учётная запись и профиль

Общий идентификатор учётной записи, выданные роли и профили допустимы и приняты на смысловом уровне. `clients`, `engineers`, `admins` остаются понятными ролевыми областями. Это не разрешает выбирать роль в запросе или автоматически повышать её по совпадению email.

Единственный диспетчер имеет стабильную учётную запись. Email и пароль берутся из серверной конфигурации; два способа входа открывают одну роль. Обычный рестарт не создаёт второго диспетчера. Пароль не копируется в публичный профиль, логи, документы знаний или AI-контекст.

Диспетчер добавляет инженеров по email. Клиент создаётся при первом подтверждённом email-входе. Добавление учётной записи инженера не заполняет неизвестные навыки, транспорт, смену или старт выдуманными значениями.

**Проектная деталь импорта:** инженерная запись тестового набора без email может существовать как расчётный профиль без действующего пользовательского логина. Последующая привязка к аккаунту выполняется явно; конкретный механизм ещё не задан.

### 3.2. Инженер в конкретном рабочем дне

Профиль описывает устойчивые свойства — навыки, транспорт, офис/обычный старт. Отдельное состояние «инженер + рабочий день» содержит смену, доступность, подготовленные прогнозы, условия обеда и `lunch_taken`.

Флаг использованного обеда относится к этому дню. Его устанавливает sys при фактическом начале. Рестарт, переключение AUTO/MANUAL или выключение/включение обедов не создают новый обед. История прошедшего дня не обнуляется ради начала следующего.

Внутренний ключ дня не становится автоматически новым обязательным полем `RouterTaskSnapshot`. Временные границы подготавливает sys по согласованному рабочему периоду.

### 3.3. Заявка и история условий

У заявки один стабильный `request_id` и одно текущее окно. Нажатие клиентом «Подтвердить» после выбора новой даты/времени меняет текущие условия существующей заявки; старые сохраняются только в истории. Второго активного визита в другом окне не появляется.

Жизненный цикл, результат назначения и фактическое выполнение разделены. Расчётное время не заменяет фактическую отметку. Назначение в карточке связывается с применённым планом и редакцией условий, которую он учитывал.

Для быстрого чтения можно хранить производное представление назначения, но его writer — тот же sys: это не второй независимо изменяемый маршрут.

Технические поля заявки хранят происхождение: импорт, ручной ввод или правило системного формирования. Приоритет уже переданных датасетом значений и системных правил уточняется по реальным данным, не молчаливым замещением.

### 3.4. Согласованная запись и ограничения доступа

Бизнес-данные, история авторства и необходимые последующие действия сохраняются согласованно. Реализация не должна потерять необходимость публикации или передачи письма после уже подтверждённой записи заявки. Внешняя передача не подменяет факт существования заявки.

Для предотвращения перезаписи предусмотрены версии затронутых объектов и сохранённые результаты повторяемых действий. GPS и сообщения не должны изменять версию несвязанных квалификационных полей. Конкретные ключи, транзакционные границы и ограничения определяются при реализации, без возвращения к каталогу операций сейчас.

Sys остаётся прикладным writer-контура. Router получает только права чтения специального сектора. AI не получает самостоятельный SQL-доступ. Разделение схем/таблиц сопровождается реальными правами доступа, а не только названиями.

## 4. Специальный сектор в PostgreSQL — принято

### 4.1. Документ и активный указатель

```text
Живые таблицы приложения
        ↓ только при установленном sys основании публикации
mount-data-eng
        ↓
routing_snapshots: неизменяемые полные RouterTaskSnapshot
        ↑
routing_current: указатель на действующий опубликованный снимок
        ↓ прямое read-only чтение
Router Runtime
```

`routing_snapshots` и `routing_current` — рабочие имена. Храним документ и указатель, а не две независимо редактируемые копии входа. Снимок содержит ровно контракт задачи: `planning_as_of`, период, оставшиеся заявки, инженеры, обеды и политику.

Технический ID публикации, hash учёта, указатель и внутренние сведения хранения находятся вне хэшируемого payload. Собственный hash не включается в свои исходные данные. Карта, техническая ревизия Router и результаты Router в сектор не копируются.

### 4.2. Публикация и чтение

Sys собирает проекцию из согласованного бизнес-состояния. Новый полный документ и переключение активного указателя фиксируются одной транзакцией. `planning_as_of` ставится в той же публикации; не обновляется отдельным таймером.

Router получает активный документ согласованно — одним чтением либо по уже полученному неизменяемому ID. Solver работает с собственной копией этого входа, а не с меняющимися запросами к живым заявкам. Чтение не удерживается на весь расчёт.

Поздний publisher не должен вернуть указатель к устаревшему снимку. Сериализация работы writer или проверка ожидаемой версии указателя — технические способы реализации, а не команды пересчёта Router.

**Принцип остаётся строгим:** запись GPS, сообщения, хода часов или отсутствующей отметки не вызывает публикацию автоматически. Очистка старых логов и пересборка документации также не меняют задачу маршрутизации. Data Layer не возвращает отклонённую ранее таймерную политику под именем триггера БД.

### 4.3. Точный JSON и hash

**Принято и реализовано в Router V2:** сохранять согласованное точное JSON-представление снимка. Sys и Router независимо считают lowercase SHA-256 одних и тех же UTF-8-байтов, а не разных форматирований одного объекта.

Поля, целочисленные времена, порядки `arrival_order` и `input_order` сохраняют смысл контракта. Сохранённый рядом hash не отменяет независимую проверку sys. Любое различие точных байтов, включая пробелы и порядок JSON-ключей, создаёт другую идентичность публикации.

Хранилище точного документа может быть оформлено как `text` или текстосохраняющий JSON с валидацией. Произвольная пересериализация документной проекции не используется как второй независимый источник байтов. Окончательный SQL-тип не выдается за уже выполненную миграцию.

### 4.4. Прямой reader Router

Sys предоставляет SELECT-only представление `router_active_snapshot` ровно с одной строкой и пятью колонками: `publication_id`, монотонный `publication_seq`, `payload_utf8`, `payload_sha256`, `published_at_epoch`. Router отклоняет ноль/несколько строк, невалидный hash, payload больше 16 MiB и откат sequence. Подключение не изменяет данные и не читает сессии, почту, диалоги, персональные контакты, векторные сегменты или таблицу необязательного GPS.

Результат подтверждает использованные `input_publication_id`, `input_hash`,
`router_context_version`, политику и полную техническую ревизию. Sys отдельно проверяет
актуальность, режим, пригодность и совместимость с фактами. Архивный документ не
становится готовым планом только из-за совпадения имени или рабочего дня.

## 5. GPS — отдельный необязательный сбор, не вход расчёта

### 5.1. Последнее согласованное ограничение

**Текущий вариант проектируется без зависимости от GPS. Инженер может не включать геолокацию. Реализуем только сбор полученных точек; дальнейшее использование в маршрутизации — отдельный backlog.**

Не вводятся восстановление траектории, геозоны, автоматическая отметка прибытия, вычисление фактического пробега и публикация снимков по координатам. Отсутствие разрешения GPS не запрещает инженеру пользоваться приложением, получать работы и делать явные отметки.

Это уточнение заменяет прежнее предложение хранить только последнее значение с возможным использованием при расчёте. Теперь принимается самостоятельная таблица наблюдений, но не обязательный трекер маршрута.

### 5.2. Таблица наблюдений

Рабочее имя — `gps_observations`. Смысловой состав соответствует запросу пользователя:

| Поле | Содержание |
|---|---|
| `timestamp` | Время наблюдения, Unix-time в целых секундах |
| `user_id` | Пользователь-инженер, к которому относится наблюдение |
| `position` | Координаты, например `{lat, lon}` |

Технический первичный ключ допустим как деталь таблицы. `user_id` определяется авторизованным sys, не свободным выбором чужого пользователя в payload. Точки поступают только при включённом сборе.

Наблюдения могут сохраняться строками до установленного срока очистки. Это не означает, что интерфейс обязан соединять их в траекторию. Для получения последней известной позиции выбирается последнее пригодное наблюдение по времени измерения; точный способ разрешения одинаковых timestamp — техническая деталь.

**Последняя известная точка не равна гарантированному положению «прямо сейчас».** Если наблюдения отсутствуют, выключены или устарели, отображение не должно придумывать позицию или выдавать старую за текущую. Поле времени сохраняется именно для этого различия. Отдельный TTL свежести и срок удаления истории ещё не заданы.

### 5.3. Разрыв связи с Router в текущем варианте

```text
Включённый GPS инженера → System Layer → gps_observations
                                            │
                                     учёт наблюдений
                                            ×
                                  не автоматический вход Router
```

`start_location` по контракту Router по-прежнему обязателен, но **не обязан происходить из GPS**. Исходный старт берётся из подготовленного набора/профиля/офиса или явно заданной точки. При дальнейшей работе sys опирается на согласованные данные выполнения и подготовленные условия; прогноз нельзя выдавать за реальное GPS-наблюдение.

Конкретная проекция старта при перепланировании в середине дороги без телеметрии ещё относится к системной модели. GPS не делается обязательным решением этой неопределённости. В текущем варианте `position_observed_at` может быть `null`, если старт не связан с геонаблюдением.

Позднее подключение собранной геолокации к подготовке старта, оценке отклонений или карте — отдельное изменение, не скрытая часть этой реализации.

## 6. Планы, решения, логи и сроки хранения

### 6.1. Планы и факты

Сохраняются полные пакеты main + baseline вместе с `main_evidence` /
`baseline_evidence`, порядком policy-критериев, техническими настройками и связью с
использованной публикацией/контекстом. Применённый план имеет собственную редакцию и
происхождение: автоматический результат или ручное изменение.

Фактические отметки и продвижение по плану хранятся отдельно от исходного пакета Router. Просмотр карточки и штатная отметка не требуют каждый раз дублировать весь пакет. В MANUAL ручное изменение создаёт новую редакцию рабочего плана.

Сведения времени различаются: `planning_as_of` показанного автоматического плана, `computed_at`, время применения и время ручной редакции. Новый ещё не рассчитанный timestamp не подставляется в подпись старого плана.

Sys не получает фоновые результаты Router через скрытый обход при отключённой в MANUAL шине. Промежуточные кандидаты solver не становятся обязательной бизнес-историей.

### 6.2. Решения и журналы

Область «Решения» сохраняет `admin-moves`, `decisions` и `politic-catalog`: кто изменил условия, что было принято, какие основания вернул расчёт, какая политика действовала. Каталог политик описывает поддержанные правила, не произвольный исполняемый текст.

Область «Логи» сохраняет имя `eternal-log`. **Пользователь прямо уточнил, что eternal — только название; время жизни данных необходимо.** Бизнес-история и технические логи могут иметь разные правила хранения. Технический лог не дублирует секреты и весь закрытый контекст в одну общую ленту.

Не вводится обязательное восстановление всей системы проигрыванием вечного журнала: текущие таблицы содержат текущее состояние, журнал — его историю.

### 6.3. Ограниченные сроки и безопасная очистка

Для следующих классов должны быть явно заданы сроки: технические логи, бизнес-история/версии, GPS-наблюдения, переписка, завершённые подтверждения/сессии и служебные результаты повторяемых действий. Числа не названы пользователем и здесь не подставляются.

**Проектные правила очистки:** не удалять активный снимок, действующий план, открытый диалог или запись, необходимую для ещё не завершённого действия. Связанные архивные записи удалять/архивировать согласованно, чтобы ссылки на сохраняемый результат не становились неразрешимыми. Срок предотвращения повторного применения должен быть учтён отдельно от срока отображения журнала.

Плановая очистка не меняет активную задачу маршрутизации и не создаёт новый `planning_as_of`. Перезапуск, очистка по сроку и явный полный сброс — разные процессы.

## 7. Диалоги и документация

### 7.1. Один диалог и эпизоды передачи

**Принято:** одна сущность диалога, сообщения с авторами и эпизоды передачи человеку. Передача не создаёт второй экземпляр переписки.

На странице «Чаты» единственного диспетчера отображаются активные передачи. AI данного диалога отключается при передаче. Диспетчер завершает её кнопкой; активная вкладка исчезает, история сохраняется, агент возвращается в тот же диалог. Новый вызов позднее начинает новый эпизод, не новую копию истории.

Режим чата, эпизод и его версия позволяют не публиковать запоздалый AI-ответ после передачи и не принять ответ человека из уже закрытого эпизода. Это предложение к реализации согласованного поведения; новых операторов и назначения владельцев не вводится.

Резюме связано с границей охваченных сообщений. Оно не заменяет исходную историю, не получает контекст чужих чатов и не является источником текущего назначения инженера.

### 7.2. Три группы таблиц знаний — принято

В одной PostgreSQL находятся отдельные клиентская, инженерная и диспетчерская группы таблиц источников, фрагментов и векторов.

| Контур обращения | Доступные группы |
|---|---|
| Клиент | Только client |
| Инженер | Только engineer |
| Диспетчер | Client, engineer, dispatch |

Ролевой sys-обработчик выбирает допустимые источники до поиска. Модель не задаёт произвольную таблицу, SQL или более широкий scope. Вызов человека не расширяет права вызывающего клиента/инженера.

Для документа/фрагмента сохраняются исходный путь/название, текст, версия содержания, сегмент, положение фрагмента и связанный вектор. Текст новой редакции не выдаётся вместе со старым вектором как актуальный индекс.

**Проект подготовки обновлений:** новую редакцию подготовить целиком и активировать согласованно. Индексирование документации не публикует routing-снимок. Модель векторизации, размерность и параметры индекса обсуждаются в отдельном стеке, не выбираются в этой редакции.

### 7.3. Точная структура репозитория

```text
knowledge/
├── client/
├── engineer/
└── dispatch/
```

Используется именно `dispatch`, не автоматически переименованный `dispatcher`. Папки задают три источника индексирования соответствующих ролевых групп. Физические SQL-имена могут быть отдельными рабочими именами; отображение папки в сегмент должно быть явным.

Собственный редактор знаний в Dashboard сейчас не добавляется. Чаты и ответы AI не становятся документацией автоматически. Повторное индексирование того же содержимого не должно плодить дубликаты; конкретная стратегия чанкинга и идентификации определяется при реализации.

## 8. Восстановление после обычного перезапуска — принято

Сохраняются учётные записи/роли, заявки, факты, рабочий план, использованный обед, настройки дня, опубликованный снимок, диалоги/передачи, дневные квоты, сведения применения результатов и передачи писем, незавершённые системные намерения.

**AUTO/MANUAL сохраняется вместе с рабочим планом.** После рестарта в MANUAL приём Router не включается сам. В AUTO показанный из базы последний план не объявляется свежим расчётом: актуальность проверяется обычным путём.

Перезапуск не выдаёт новую квоту, не возвращает AI в переданный чат, не сбрасывает `lunch_taken`, не повторяет подтверждённую отправку письма и не восстанавливает демонстрационный набор поверх живых данных.

Сеансы восстанавливаются только в пределах их срока и действительности; сохранение записи сессии не продлевает её бессрочно. Истёкшие коды не становятся действующими после рестарта.

SMTP продолжает обслуживать свою внешнюю очередь. Data Layer сохраняет прикладные сведения `pending_submission`, `accepted_by_server` и другие предусмотренные исходы, а не выполняет доставку вместо SMTP.

**Проект размещения:** постоянный том базы и проверяемая возможность резервного копирования. Сам факт сохранения данных в БД не считается отчётом об уже настроенном backup; схема резервирования и интервалы ещё не выбраны.

## 9. Импорт и три действия Dashboard

### 9.1. Общие принятые правила

Начальный тестовый набор находится в репозитории. На первой предусмотренной инициализации он загружается автоматически. Обычный рестарт не переписывает ручные изменения и не создаёт дубли.

Перед применением проверяется весь пакет. Повтор того же набора распознаётся по происхождению/содержимому, а не только по имени файла. Новые записи добавляются после проверки. Совпавший ID с иным содержимым — конфликт, не молчаливое обновление. При ошибке или конфликте весь пакет не применяется частично.

Сохраняются источник, редакция и исходные ID. Совпадение адреса/окна не доказывает идентичность заявок. Значимые порядки заявок и инженеров для baseline не теряются. Отсутствующие нормативы не придумываются импортёром.

Повторное нажатие кнопки не создаёт ещё один импорт того же пакета. Детальная форма идемпотентности относится к реализации общего sys-механизма, не к новому каталогу операций.

### 9.2. Три самостоятельные кнопки — согласовано

| Кнопка | Назначение | Что её отличает |
|---|---|---|
| **«Догрузить данные»** | Добавить проверенный CSV/JSON к текущему состоянию | Не очищает действующие записи и не перезаписывает конфликты |
| **«Сбросить к тестовым данным»** | Вернуться к предусмотренному исходному демонстрационному состоянию | Не догружает seed поверх текущего рабочего дня, а восстанавливает тестовый набор |
| **«Полный сброс»** | Получить пустое рабочее состояние для начала сбора заявок с нуля | Не загружает демонстрационные заявки автоматически после очистки |

Это проект кнопок и правил состояния. Никакой фактический сброс при подготовке документа не выполняется.

Кнопки располагаются в диспетчерском контуре. **Проектная защита:** сбросы требуют явного подтверждения с перечнем затрагиваемых данных; обычная догрузка не должна выглядеть как такой же безобидный вариант destructive-действия. Права AI на новые действия сброса отдельно не выдаются данным документом.

### 9.3. Сброс к тестовому набору

**Согласован смысл:** повторяемое возвращение к тестовым данным. Переносы, выполненные работы и ручные изменения текущего демонстрационного сценария не должны незаметно смешиваться с загруженным исходным состоянием.

**Проектная реализация:** подготовить/проверить тестовый пакет до его активации; затем согласованно заменить выбранные рабочие данные, очистить их активные планы и соответствующие факты текущего запуска, опубликовать новый вход по обычному механизму. Начальное состояние `lunch_taken` берётся из нового тестового дня, а не переносится из завершённого прогона. Режим AUTO/MANUAL после намеренного сброса задаётся явно, а не выводится из правила обычного рестарта; конкретное значение ещё не выбрано.

Указанные данные не обязательно физически удаляются безвозвратно: может быть архив предыдущего прогона. Поскольку пользователь не выбрал delete или archive и не перечислил все категории, способ хранения старой истории не объявляется согласованным.

### 9.4. Полный сброс и пустой старт

**Согласован смысл:** начать работу без текущих тестовых/клиентских заявок и планов, собирая новые заявки с нуля. Пустой список — допустимое рабочее состояние, не ошибка и не команда автоматической повторной загрузки seed.

**Принятый объём «полного» сброса (DB7, «всё в ноль» — 39 §10.2):** очистить данные приложения целиком — клиентские и инженерные аккаунты, роли и профили; заявки со старыми условиями, назначениями и фактами; рабочие дни с обедами; текущие планы, принятые пакеты и снимки старого запуска; диалоги, сообщения и эпизоды передачи; GPS-наблюдения; журналы прежнего запуска и учёт писем; сессии и интеграционные доступы старого состояния; внутренние счётчики/резервы AI. Развилка «оставить инженеров» снята: инженеров снова создаёт диспетчер, клиенты регистрируются заново; предложение сохранить дневной расход AI как исключение не было выбрано.

**Исключения — граница с развёртыванием (39 §10.3):** очищаются данные, а не приложение: исходный код, `.env`, схема БД, файл карты и исходные файлы `knowledge` сохраняются; единственный диспетчер и необходимые каталоги/параметры восстанавливаются из источников развёртывания, изменённые во время работы настройки не сохраняются под видом исходной конфигурации.

После очистки sys публикует валидную пустую/подготовленную задачу через существующий механизм. Он не редактирует память Router вручную. Старый применённый план не используется как активное указание в новом пустом состоянии.

### 9.5. Не загружать seed снова после полного сброса

**Необходимое следствие принятой функции пустого старта:** отсутствие строк в `requests` не может быть единственным критерием «система ещё не инициализирована».

**Проект:** сохранять отдельный признак выполненной инициализации и выбранного состояния запуска (`demo`/`empty` — рабочие названия). Он переживает обычный рестарт. После намеренного пустого сброса перезапуск не возвращает тестовые заявки; вернуть их можно отдельной кнопкой.

Это служебное состояние приложения, не периодическое поле сектора и не новая цель Router.

### 9.6. Сброс на фоне вычислений — проектные защиты

Сброс не должен оживить старые действия после завершения очистки. Нужно согласовать смену рабочего набора с начатыми AI-run, импортом, обработкой результата Router и ещё не переданными письмами.

Предлагается отмечать границу нового рабочего состояния внутренним поколением sys либо эквивалентной защитой. Завершающаяся запись старого поколения не применяется к новому набору. Это не новое обязательное поле `RouterTaskSnapshot` и не команда изменения маршрутов: внешний контракт hash/контекста сохраняется.

Старое совпадение ID не является достаточным основанием заново применить результат. Повторное использование действительно идентичного входа, hash и допустимого результата требует явного решения на границе нового запуска, а не автоматического восстановления старого будущего плана. Точный механизм относится к реализации.

Не переданные уведомления старого запуска предлагается отменять/инвалидировать. Уже принятые внешним SMTP письма нельзя объявлять отозванными из-за очистки прикладной базы. Демонстрационные записи не должны автоматически вызывать рассылку реальным адресатам; режим такого импорта ещё нужно явно настроить.

## 10. Что теперь находится в backlog и что ещё выбрать

| Пункт | Статус |
|---|---|
| Redis | Backlog; внедрять только под конкретную потребность |
| Использование GPS в расчётах/стартовой проекции | Backlog; текущая реализация только собирает наблюдения |
| Траектория, геозоны, автоматическое прибытие, фактический GPS-пробег | Не входят в текущий вариант; не добавляются только из-за наличия таблицы |
| Индексы/ORM/полная SQL-схема | Техническая детализация после смысловой модели |
| Сроки хранения каждого класса | Обязательны к заданию, конкретные числа не выбраны |
| Точный состав полного сброса | Нужен перечень очищаемых и сохраняемых категорий, включая инженерные аккаунты/профили |
| Архивирование либо удаление предыдущего тестового прогона | Не выбрано |
| Режим AUTO/MANUAL после явного сброса | Не выбран; правило рестарта уже принято и отдельно сохраняется |
| Резервное копирование и подтверждения опасных действий | Проектные меры реализации, не выполненная настройка |
| Стартовая проекция в дороге без GPS | Системная деталь; нельзя молча сделать геолокацию обязательной |

Каталог операций sys не разворачивается в этом документе. Поля таблиц наблюдений, области сброса и связи хранилищ не являются обходом этой договорённости.

## 11. Проверки будущей реализации

| Сценарий | Ожидаемое поведение |
|---|---|
| Перенос после подтверждения | Один request_id и одно действующее окно, старое — в истории |
| GPS выключен или разрешение не дано | Приложение и основной расчёт не зависят от геолокации |
| Пришла GPS-точка | Сохранено наблюдение пользователя; специальный сектор не изменился только по этой причине |
| Получено запоздалое наблюдение | Оно не выдаётся за более свежую текущую позицию |
| Инженер молчит после планового срока | Нет таймерной публикации/автоматического null из одного молчания |
| Чтение во время публикации | Router получает один полный снимок |
| Одинаковые payload-байты | Sys и Router независимо получают одинаковый hash |
| Поздний publisher | Не возвращает указатель на старую проекцию |
| Router обращается к auth/чатам/GPS | Прямой reader не получает такого доступа |
| Принят новый результат | Сохранились пакет, связь со снимком и происхождение применённого плана |
| Повтор result_id | Нет возврата выполненных работ и повторного письма |
| Изменён документ knowledge | Текст и активные векторы относятся к одной редакции |
| Клиент/инженер запрашивает чужой сегмент | Права не расширяются |
| Завершена передача чата | Вкладка исчезла, история сохранилась, AI возвращён |
| Рестарт в MANUAL | Сохранены режим и рабочий план, выход Router не включается сам |
| Рестарт в переданном чате | AI не возвращается до действия диспетчера |
| Рестарт после использованного обеда/расхода квоты | Эти данные не обнуляются |
| Повторная догрузка | Нет дубликатов |
| Ошибка/конфликт в пакете | Нет частично применённого набора и перезаписанной ручной правки |
| Сброс к тестовому набору | Тестовое состояние не смешалось с активными данными прошлого прогона |
| Полный сброс | Пустой рабочий старт без самовольной загрузки демонстрационных заявок |
| Рестарт после полного сброса | Сохранился пустой режим, seed не вернулся автоматически |
| Запоздалый run/результат после сброса | Не восстанавливает старые данные в новом запуске |
| Очистка по сроку | Не уничтожает используемый активный документ или незавершённый диалог |

Это критерии приёмки будущего кода, не отчёт о проведённых тестах.

## 12. Изменения v2 и синхронизация комплекта

DL1–DL7 переведены из вопросов в принятые решения в той части, которую подтвердил пользователь. Исходная группировка с фотографии сохранена и сопоставлена с логическими областями. Redis вынесен в backlog.

GPS изменён с предложения «только последнее значение для возможного расчёта» на отдельный необязательный сбор `timestamp/user/position` без маршрутизационной зависимости. В логах и истории закреплён ограниченный срок жизни. Для знаний зафиксированы именно папки `knowledge/client`, `knowledge/engineer`, `knowledge/dispatch`.

Сохранение MANUAL после рестарта теперь принято. Импорт подтверждён как целостный, без дублей и перезаписи. Добавлены две явные кнопки сброса помимо догрузки; границы удаления и защитные меры отделены от самого согласованного наличия этих кнопок.

При следующей синхронизации основной концепции, sys, краткого описания и упоминаний стартовой проекции нужно отразить отсутствие зависимости от GPS, сохранение MANUAL и три сценария работы с данными. Сами поля Router и принятая логика его вычисления в этой редакции не меняются. Остальные файлы здесь не переписаны.

## 13. Основания и ограничения источников

Приоритетный источник — последний ответ пользователя на DL1–DL7. Фотография доски показывает исходные названия групп и прямой вход Router; более поздняя переписка уточняет физическое хранение, права AI и необязательность GPS. Из изображения не выводятся дополнительные требования к таблицам, авторизации, индексам или сбросу.

Использованы `data_layer_concept_v1.md` (прочитан целиком), текущий `system_layer_concept_v2.md`, основные согласованные разделы `system_concept_v14.md`, контракты Router/Engine, AI/SMTP и исходная расшифровка Data Layer. ТЗ «Билайн Бизнес» задаёт маршрутизацию, ограничения, данные и демонстрацию, а не конкретные таблицы/сроки очистки/режимы сброса.

Технические ссылки предыдущей версии остаются справочными, но эта редакция не является новым обзором актуальных релизов СУБД. Новых утверждений о совместимости пакетов или измеренной производительности не добавлено. Ни сервер, ни база, ни документы знаний, ни рабочие данные пользователя этой работой не изменены.
