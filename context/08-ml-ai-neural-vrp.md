# ML/AI для VRP и диспетчеризации: что реально работает (ресерч 2024–2026)

> Назначение: осознанно выбрать роль AI в продукте. Вердикт заранее: **оптимизационное ядро — классические метаэвристики; LLM — поверх, для естественного ввода и человекочитаемых объяснений; предиктивные ML-фичи — простые и честные; нейрокомбинаторику и RL — знать и уметь объяснить, не строить.**

## 2. Neural Combinatorial Optimization: состояние на 2025–2026

Хронология: Pointer Networks (2015) → Attention Model / AM (Kool et al., 2019) → **POMO** (2020, множественные rollouts, сильный бенчмарк на TSP/CVRP) → LEHD, BQ (2023–2024, качество逼近 классики) → NeuOpt (обучение k-opt перемещениям для улучшения решений) → GNN-гибриды.

Честный статус: на **чистых** задачах (TSP/CVRP с фиксированной постановкой) нейрометоды приблизились к классическим эвристикам и выигрывают по инференс-времени; на **богатых VRPTW с гетерогенными ограничениями** (наши навыки, оборудование, мульти-депо, мульти-цели, динамика) они по-прежнему уступают ALNS/HGS/GLS по качеству и, главное, не дают стабильных гарантий допустимости решения. Классические бенчмарки и актуальные сравнения — в литературе 2024–2025 (обзоры neural CO; Solomonic-бенчмарки и репозитории вроде ai4co).

Для нас: время/риск внедрения не окупается; на Q&A достаточно сказать: «следили за neural CO (POMO и далее) — на богатых ограничениях классика пока сильнее и честнее по допустимости; ядро у нас промышленного класса».

## 3. LLM и комбинаторная оптимизация

Направление «LLM как дизайнер эвристик»: FunSearch (DeepMind, 2023–2024) — LLM + эвалюатор эволюционируют программы-эвристики; **ReEvo** (NeurIPS 2024, [OpenReview](https://openreview.net/forum?id=483IPG0HWL), [github](https://github.com/ai4co/reevo)) — «reflective evolution», гипер-эвристики; EoH, HSEvo (AAAI 2025), MCTS-AHD (ICML 2025), MEoH (мульти-целевой поиск эвристик); систематические обзоры: [LLMs for CO (ACM 2026)](https://dl.acm.org/doi/10.1145/3801961), [arXiv:2509.08269](https://arxiv.org/html/2509.08269v1).

Вердикт для хакатона: это research-поток (минуты/часы вычислений на поиск эвристики, нестабильность), не продукт. В презентации — один слайд «мы в курсе направления», не больше.

## 4. Практичные LLM-фичи вокруг надёжного ядра

| Фича | Что делает | Wow | Effort | Риск и митигация |
|---|---|---|---|---|
| **Ввод заявки текстом** (B9) | «К „Атласу“ на Ленина 15 после обеда, заменить роутер, клиент ждёт до 17» → structured JSON заявки (адрес, окно→время, тип работ) | ⭐⭐⭐ | S–M | Галлюцинации → JSON-схема + валидация + подтверждение в UI до сохранения |
| **Полировка объяснений** | Rule-based факты (`11`) → LLM превращает в живой русский текст (детерминированный шаблон — фолбэк) | ⭐⭐ | S | Лёгкий: всегда шаблонный фолбэк |
| **Диалоговый what-if** | «Что если дать Иванову ещё 2 заявки на юге?» → бэк-расчёт → ответ цифрами | ⭐⭐⭐ | M | Средний: LLM только интент-парсинг, расчёт — на бэке |
| **Разбор входящих обращений** | Паста письма/чата клиента → черновик заявки | ⭐⭐ | S | Низкий |

Общий принцип: **LLM никогда не принимает решений и не меняет план** — только переводит текст↔структуру. Все данные для ответов считаются на бэкенде. Это ответ на вопрос жюри «почему нам можно доверять вашему AI».

## 5. ML-предсказания на нашем масштабе

- **Длительность работ:** базовая по типу ± поправки (клиент B2B/B2C, этаж/лифт, день недели). Без истории обучать нечему — делаем **параметрическую эвристику** и честно называем её эвристикой; ML-модель — roadmap (нужна история выездов Билайна).
- **Travel time:** матрица OSRM × коэффициенты часа (пик/межпик) — «time-dependent-lite» (`14` §5.2).
- **Риск SLA:** детерминированный расчёт буферов (ETA + буфер vs окно) — без ML, зато честно и объяснимо (`07` §6).
- Если останется время и желание показать ML: градиентный бустинг на синтетике с честной пометкой «демонстрация подхода» — но это низкий приоритет (см. `12` D-блок).

## 6. RL для динамического диспетчинга — почему нет

Требует: формулировку MDP с богатыми ограничениями, миллионы симуляций, отладку наград, нестабильность результата. На выходе — решение хуже классики за приемлемое время и не объяснимое. Единственное место RL в нашем проекте — раздел «что мы НЕ выбрали и почему» (это плюс к зрелости ответов жюри).

## 7. Локальный LLM (Qwen): практики стабильного structured output

Стек: vLLM или Ollama с OpenAI-совместимым API (наши PRO 6000 — с запасом для Qwen-класса моделей).

1. **JSON Schema / guided decoding** (vLLM: `guided_json`) вместо «попроси модель вернуть JSON» — валидность гарантируется декодером.
2. **Temperature 0–0.3** для экстракции; одна задача — один вызов; многошаговость не нужна.
3. **Валидация после генерации** (pydantic/zod) + один retry с сообщением об ошибке валидации; дальше — ручная форма (фолбэк).
4. **Таймаут 5–8 c** и кнопка «ввести вручную» на виду — LLM не на критическом пути демо.
5. Промпт с 2–3 few-shot примерами реальных формулировок диспетчера (русский, сокращения, «после обеда» → интервалы).
6. Свободные поля (комментарий) — не экстраполировать: модель возвращает только то, что сказано.

## 8. Итог: приоритеты AI для проекта

1. **P0:** правило «AI не касается плана»; structured-ввод заявки с подтверждением; шаблонные причины.
2. **P1:** LLM-полировка объяснений; what-if диалог (интент → бэк-расчёт).
3. **P2:** упоминание neural CO/LLM-эвристик в презентации как осознанно не выбранных путей.
4. Все LLM-фичи — за фичефлагом и с ручным фолбэком.
