# 05. Математическая модель

> Формальная постановка задачи кейса. Всё, что здесь записано, выводится из требований
> `C-01…C-03`, `M-01…M-05`, `D-04` файла `01-case-requirements.md` — и ничего сверх них.
> Цель документа: чтобы разработчик мог закодировать модель, не додумывая, а защищающий —
> ответить на любой вопрос жюри формулой.

## 1. Классификация задачи

Наша постановка в терминах литературы по исследованию операций:

**MD-O-VRPTW со скиллами и гетерогенным парком**, он же частный случай
**TRSP (Technician Routing and Scheduling Problem)**:

| Признак постановки | Откуда берётся | Стандартное имя |
|---|---|---|
| Транспортные средства выезжают из **разных** точек | ТЗ §2.4: «стартовая точка» у каждого инженера | **Multi-Depot** (MD) |
| Маршрут **не возвращается** в стартовую точку | ТЗ §2.4: «возвращение не требуется» (D-04) | **Open** (O) |
| Начало работы должно попасть в окно | ТЗ §2.2 «Время» (C-02) | **VRP with Time Windows** |
| Исполнитель обязан иметь навык заявки | ТЗ §2.2 «Квалификация» (C-01) | **Skill / qualification constraints** |
| Заявка может требовать конкретный транспорт | ТЗ §2.2 «Ресурс» (C-03) | **Heterogeneous fleet, site-dependent** |
| Часть заявок можно не выполнить | ТЗ §2.3: допускаются неназначенные | **Prize-collecting / VRP with optional visits** |
| Минимум задействованного персонала | ТЗ §2.3 (M-01) | **Fleet-size minimization** |
| План перестраивается в течение дня | ТЗ §2.1 п.6 (F-06) | **Dynamic VRP (DVRP)** |

Задача **NP-трудна** (содержит VRPTW как частный случай при |I| = 1 и отсутствии навыков,
а VRPTW сводится к TSP). Это и есть формальное основание ссылаться на ТЗ §2.3:
«не требуется доказывать математический оптимум».

## 2. Обозначения

### 2.1. Множества

| Символ | Смысл |
|---|---|
| `I` | инженеры (исполнители), `i ∈ I`, `n = |I|` |
| `J` | заявки, `j ∈ J`, `m = |J|` |
| `O = {o_i}` | стартовые точки инженеров (каждому своя) |
| `V = O ∪ J ∪ {f}` | узлы графа: старты, визиты и **виртуальный сток** `f` |
| `K = {1, 2, 3}` | справочник навыков (ТЗ §2.4.1) |
| `W = {1, 2, 3, 4}` | справочник типов транспорта (ТЗ §2.4.1) |

### 2.2. Параметры инженера `i`

| Символ | Смысл | Единица |
|---|---|---|
| `S_i` | начало смены | мин от 00:00 |
| `E_i` | конец смены | мин от 00:00 |
| `K_i ⊆ K` | навыки, `1 ≤ |K_i| ≤ 3` | — |
| `w_i ∈ W` | тип транспорта (ровно один) | — |
| `o_i` | стартовая точка | (lat, lon) |

### 2.3. Параметры заявки `j`

| Символ | Смысл | Единица |
|---|---|---|
| `s_j` | длительность работ | мин |
| `[e_j, l_j]` | временное окно | мин от 00:00 |
| `q_j ∈ K` | требуемый навык (ровно один) | — |
| `r_j ∈ W ∪ {∅}` | требуемый транспорт; `∅` = ограничения нет | — |
| `p_j ∈ {1, 2}` | приоритет: 1 — обычная, 2 — срочная | — |
| `(lat_j, lon_j)` | координаты | град |

### 2.4. Параметры дуг

| Символ | Смысл | Единица |
|---|---|---|
| `τ_i(u, v)` | время в пути из `u` в `v` **транспортом инженера `i`** | мин |
| `δ(u, v)` | расстояние из `u` в `v` | м (в модели) / км (в отчёте) |

⚠️ Время в пути зависит от **типа транспорта исполнителя**, поэтому индексируется `i`.
Расстояние `δ` от исполнителя не зависит — это геометрия. Это важно: метрика M-02 (пробег)
считается по `δ`, а ограничение C-02 (время) — по `τ_i`. Модель их не путает.
Как вычисляются `τ_i` и `δ` — в `06-physical-travel-model.md`.

Соглашение для стока: `τ_i(u, f) = 0`, `δ(u, f) = 0` для любого `u`. Это и есть формальная
запись требования D-04 «возвращение в стартовую точку не требуется».

## 3. Множество допустимых исполнителей (статическая совместимость)

Ограничения C-01 и C-03 **не зависят от маршрута** — они проверяются попарно и заранее:

```
A_j = { i ∈ I : q_j ∈ K_i  ∧  ( r_j = ∅  ∨  r_j = w_i ) }
```

| Компонент | Требование ТЗ |
|---|---|
| `q_j ∈ K_i` | C-01 Квалификация |
| `r_j = ∅ ∨ r_j = w_i` | C-03 Ресурс (транспорт), применяется только при заданном `r_j` |

**Следствие 1 (фильтр).** Если `A_j = ∅`, заявка `j` не может быть назначена ни при каком
маршруте. Причина известна **до запуска оптимизатора** и точна:
`нет ни одного инженера с навыком q_j` или `…с транспортом r_j`.

Это даёт первые два кода причин из списка ТЗ (стр. 2) бесплатно и со 100 % достоверностью.

**Следствие 2 (размер модели).** `|A_j|` обычно много меньше `n`, что радикально сокращает
пространство поиска: переменные `y_ij` создаются только для `i ∈ A_j`.

## 4. Переменные решения

| Переменная | Область | Смысл |
|---|---|---|
| `x^i_{uv}` | `{0,1}` | инженер `i` едет напрямую из узла `u` в узел `v` |
| `y_{ij}` | `{0,1}` | заявка `j` назначена инженеру `i` (только для `i ∈ A_j`) |
| `z_j` | `{0,1}` | заявка `j` **не назначена** |
| `u_i` | `{0,1}` | инженер `i` **задействован** (имеет хотя бы одну заявку) |
| `t_j` | `ℝ₊` | **время начала работ** на заявке `j` (мин от 00:00) |

Производные величины (не переменные, а вычисляемые из решения):

```
a_j   = t_j                                  плановое время прибытия/начала (R-01)
c_j   = t_j + s_j                            время завершения работ
wait_j = t_j − (t_prev + s_prev + τ_i(prev, j))   ожидание перед окном
d_i   = Σ_{(u,v)} δ(u,v) · x^i_{uv}          пробег инженера i  (M-02)
```

## 5. Ограничения

### (1) Покрытие заявок

```
Σ_{i ∈ A_j} y_{ij} + z_j = 1                для всех j ∈ J
```

Каждая заявка либо назначена ровно одному допустимому исполнителю, либо явно помечена
как неназначенная. **Третьего состояния нет** — это формальная гарантия требования R-02.

### (2) Связь маршрута и назначения (степени вершин)

```
Σ_{u ∈ V} x^i_{uj} = y_{ij}                 для всех i ∈ A_j, j ∈ J     (входящая дуга)
Σ_{v ∈ V} x^i_{jv} = y_{ij}                 для всех i ∈ A_j, j ∈ J     (исходящая дуга)
```

Исходящая дуга существует всегда, потому что из последнего визита ведёт дуга в сток `f`
с нулевой стоимостью. Это и есть техническая реализация **открытого маршрута**.

### (3) Старт и завершение маршрута

```
Σ_{v ∈ J ∪ {f}} x^i_{o_i v} = 1              для всех i ∈ I      (выезд из своей точки)
Σ_{u ∈ O ∪ J}  x^i_{u f}   = 1               для всех i ∈ I      (маршрут заканчивается в стоке)
```

Инженер без заявок формально едет `o_i → f` с нулевой стоимостью, т.е. остаётся дома.

### (4) Признак задействованности

```
u_i ≥ y_{ij}                                 для всех i ∈ A_j, j ∈ J
u_i ≤ Σ_{j : i ∈ A_j} y_{ij}                 для всех i ∈ I
```

`u_i = 1` ⟺ инженеру назначена хотя бы одна заявка. Это **дословно** определение
метрики M-01 из ТЗ: «количество уникальных исполнителей, которым назначена хотя бы одна заявка».

### (5) Распространение времени вдоль маршрута

```
t_v ≥ t_u + s_u + τ_i(u, v) − M · (1 − x^i_{uv})     для всех i, u ∈ O ∪ J, v ∈ J
```

где `s_{o_i} = 0`, `t_{o_i} = S_i`, а `M` — достаточно большая константа
(корректно взять `M = max_i E_i − min_i S_i + max_{u,v,i} τ_i(u,v)`; на практике `M = 1440`).

Неравенство (а не равенство) допускает **ожидание** перед открытием окна — это физически
корректно: инженер может приехать раньше и подождать.

### (6) C-02a — окно заявки ограничивает НАЧАЛО работ

```
e_j ≤ t_j ≤ l_j                              для всех j ∈ J с z_j = 0
```

⚠️ **Здесь наиболее частая ошибка реализации.** ТЗ говорит: «**начало работы** должно попадать
во временное окно заявки». Верхняя граница `l_j` ограничивает `t_j`, **а не** `t_j + s_j`.
Работа законно может закончиться после `l_j`. Ограничение на завершение даёт только смена — см. (7).

### (7) C-02b — работа укладывается в смену исполнителя

```
t_j + s_j ≤ E_i + M · (1 − y_{ij})           для всех i ∈ A_j, j ∈ J
t_j ≥ S_i + τ_i(o_i, j) − M · (1 − x^i_{o_i j})
```

Первое: любая назначенная работа завершается до конца смены (для последнего визита это и есть
условие завершения маршрута). Второе: первый визит не может начаться раньше, чем инженер
физически доедет от своей стартовой точки после начала смены.

### (8) C-01 и C-03 — уже встроены

Ограничения квалификации и транспорта не записываются отдельными неравенствами: они
**конструктивно** зашиты в область определения переменных через `A_j` (см. §3).
Это и эффективнее, и даёт точные причины отказа.

### (9) Связность маршрута (устранение подциклов)

Формулировка (5) с переменными времени **автоматически** исключает подциклы: любой цикл
`v₁ → v₂ → … → v₁` требовал бы `t_{v₁} > t_{v₁}`. Отдельные ограничения MTZ не нужны.
Это ещё один аргумент в пользу time-indexed формулировки.

## 6. Целевая функция

### 6.1. Три критерия в порядке приоритета

ТЗ задаёт приоритеты явно: сначала «стремиться распределить **все** заявки» (§2.3),
затем «наименьшее количество персонала» (M-01, названа первой), затем «пробег» (M-02).

```
Z₁ = Σ_{j ∈ J} π_j · z_j          → min      невыполненные заявки (взвешенные приоритетом)
Z₂ = Σ_{i ∈ I} u_i                → min      число задействованных исполнителей   (M-01)
Z₃ = Σ_{i ∈ I} d_i                → min      суммарный пробег                     (M-02)
```

где `π_j` — вес приоритета: `π_j = 1` для обычной заявки, `π_j = 3` для срочной
(ТЗ §2.4.1: «срочная заявка имеет более высокий приоритет при перепланировании»).

Требуемый порядок — **лексикографический**: `Z₁ ≻ Z₂ ≻ Z₃`.

### 6.2. Сведение к одному критерию: как подобрать веса корректно

Решаем скаляризованную задачу

```
min   Λ₁ · Z₁ + Λ₂ · Z₂ + Λ₃ · Z₃
```

Чтобы скаляризация **точно воспроизводила** лексикографический порядок, веса должны
доминировать сверху вниз. Выведем условия.

Пусть `D̄` — заведомая верхняя оценка суммарного пробега любого допустимого плана
(например, `D̄ = n · v_max · (max_i E_i − min_i S_i)`, или просто «все ездят весь день
по городу»). Тогда:

**Условие A (исполнитель важнее километров).**
Освобождение одного исполнителя должно окупать любое мыслимое удлинение маршрутов:

```
Λ₂ · 1  >  Λ₃ · D̄
```

**Условие B (выполненная заявка важнее всего).**
Назначение одной дополнительной заявки должно окупать даже привлечение всех исполнителей
и максимальный пробег:

```
Λ₁ · π_min  >  Λ₂ · n  +  Λ₃ · D̄
```

**Утверждение.** При выполнении A и B оптимум скаляризованной задачи совпадает
с лексикографическим оптимумом `(Z₁, Z₂, Z₃)`.

*Обоснование.* Пусть план `P` лучше плана `Q` лексикографически. Если `Z₁(P) < Z₁(Q)`,
то разница хотя бы `π_min`, и по условию B выигрыш `Λ₁·π_min` превышает любой возможный
проигрыш по `Z₂` (максимум `Λ₂·n`) и по `Z₃` (максимум `Λ₃·D̄`). Если `Z₁` равны и
`Z₂(P) < Z₂(Q)`, разница хотя бы 1, и по условию A выигрыш `Λ₂` превышает любой проигрыш
по `Z₃`. Если равны `Z₁` и `Z₂`, сравнение идёт напрямую по `Z₃`. ∎

### 6.3. Конкретные числа для нашей размерности

Масштаб задан ТЗ §6: `n ≤ 15`, `m ≤ 100`.

Работаем в **целых числах** (требование любого MIP/CP-солвера). Единица расстояния —
**10 метров** (даёт точность 0.01 км при сохранении разумного порядка величин).

| Величина | Значение | Обоснование |
|---|---|---|
| `D̄` | 500 000 ед. = **5 000 км** | 15 инженеров × 330 км/день — заведомо недостижимо |
| `Λ₃` | **1** за 10 м | базовая единица |
| `Λ₂` | **1 000 000** | `10⁶ > 1 · 5·10⁵ = D̄` ✔ Условие A с запасом ×2 |
| `Λ₁` | **100 000 000** | `10⁸ · 1 > 10⁶ · 15 + 5·10⁵ = 1.55·10⁷` ✔ Условие B с запасом ×6 |
| `π` обычной | 1 | ТЗ |
| `π` срочной | 3 | ТЗ: «более высокий приоритет» |

Проверка переполнения: максимум целевой ≈ `100 · 3 · 10⁸ ≈ 3 · 10¹⁰` — свободно помещается
в int64, который используют и OR-Tools, и CP-SAT.

⚠️ **Единицы весов зависят от единицы стоимости дуги в реализации.** Числа выше выведены
в абстрактной единице «10 метров». Если в реализации стоимость дуги измеряется не в метрах,
а во времени (секундах), **все три веса надо пересчитать в этой же единице** — иначе условия A
и B перестают выполняться. Пересчёт для секундной единицы выполнен в `07-algorithm-design.md` §3:
там `Λ₂ = 10⁷`, `Λ₁ = 2·10⁹`. Это не другие веса, а те же самые в другой системе единиц.

**Правило:** `Λ₁` и `Λ₂` всегда меняются **одним изменением**. Если поднять фиксированную
стоимость исполнителя, забыв поднять штраф за неназначение, система начнёт **выбрасывать заявки
ради сокращения бригад** — то есть ровно наоборот тому, что требует ТЗ. Это главный
алгоритмический риск проекта (`14-risks-and-assumptions.md` §2.2).

⚠️ **Второе следствие выбора единицы.** Метрика M-02 — это **расстояние в километрах**, а не
время. Если целевая функция минимизирует секунды, то пробег оптимизируется лишь косвенно
(через корреляцию времени и расстояния) и при разных скоростях транспорта может расходиться
с метрикой. Решение — отдельная дистанционная составляющая в стоимости дуги; детали в
`07-algorithm-design.md` §2.

**Интерпретация весов для диспетчера** (это идёт прямо в интерфейс):

> «Не выполнить обычную заявку = 100 единиц штрафа. Вывести лишнего инженера = 1 единица.
> Проехать лишний километр = 0.0001 единицы.»

То есть система никогда не пожертвует заявкой ради километров — и это можно произнести
вслух на защите.

### 6.4. Мягкие критерии-доводчики (tie-break)

При равенстве `Z₁, Z₂, Z₃` план всё ещё может быть неоднозначен. Добавляем член
пренебрежимо малого веса, который делает планы «человечнее»:

```
Z₄ = Σ_j wait_j                      суммарное ожидание (простой инженера у подъезда)
Z₅ = max_i workload_i − min_i workload_i   разброс загрузки (по задействованным)
```

Веса: `Λ₄ = Λ₅ = 1` при `Λ₃ = 1`, но применяются к минутам, а не к десяткам метров.
Эти члены **не влияют** на обязательные метрики и нужны только для эстетики плана.

⚠️ Важное предостережение: **балансировка нагрузки конфликтует с M-01**. Равномерно
загрузить всех — значит задействовать всех, то есть ухудшить первую обязательную метрику.
Поэтому `Z₅` считается **только по задействованным** исполнителям (`u_i = 1`) и имеет
минимальный вес. Об этом конфликте надо сказать на защите первым — это признак понимания задачи.

## 7. Оценки снизу: как показать качество, не доказывая оптимум

ТЗ не требует доказательства оптимума. Но мы можем **бесплатно** предъявить нижние оценки
и сказать: «мы задействовали 7 инженеров, математический минимум для этих данных — 6».
Это даёт огромный эффект на защите при нулевой стоимости реализации.

### 7.1. LB-1: оценка по объёму работ (work-content bound)

Минимальное число исполнителей не может быть меньше, чем суммарный объём работ,
делённый на самую длинную смену:

```
n_min ≥ ⌈ Σ_{j ∈ J} s_j  /  max_i (E_i − S_i) ⌉
```

Оценка игнорирует переезды, поэтому всегда корректна (переезды только ухудшают).

### 7.2. LB-2: энергетическая оценка по временному интервалу

Для **любого** интервала `[a, b]` рассмотрим заявки, которые обязаны быть выполнены
целиком внутри него:

```
J[a,b] = { j : e_j ≥ a  и  l_j + s_j ≤ b }
```

Все они должны уместиться в суммарную ёмкость исполнителей на этом интервале:

```
n_min ≥ ⌈ Σ_{j ∈ J[a,b]} s_j  /  (b − a) ⌉
```

Перебирая `[a, b]` по границам окон (`O(m²)` пар, что при `m = 100` — 10 000 проверок,
доли миллисекунды), получаем лучшую оценку. Это классическое **энергетическое рассуждение**
из планирования (energetic reasoning).

### 7.3. LB-3: оценка по навыкам (и детектор невыполнимости)

Для каждого навыка `k ∈ K` те же две оценки считаются на подмножестве
`J_k = {j : q_j = k}` и подмножестве исполнителей `I_k = {i : k ∈ K_i}`:

```
n_min(k) ≥ ⌈ Σ_{j ∈ J_k} s_j / max_{i ∈ I_k} (E_i − S_i) ⌉
```

Если `n_min(k) > |I_k|` — **план физически невыполним**, и мы знаем это до запуска солвера.

То же для транспорта: `J_w = {j : r_j = w}`, `I_w = {i : w_i = w}`.

### 7.4. Что это даёт продукту

Три оценки превращаются в **агрегированное объяснение невыполнимости** — то, чего
не будет ни у кого:

> «Все заявки выполнить невозможно, и вот почему. В окне **18:00–20:00** сосредоточено
> **34 часа** работ, требующих навыка «Аварийные работы». Инженеров с этим навыком —
> **12**, каждый даёт максимум **2 часа** в этом окне, то есть суммарная ёмкость — **24 часа**.
> Дефицит: **10 часов ≈ 5 заявок**. Ни один алгоритм не разместит их все.»

Это ответ уровня «мы понимаем задачу», а не «алгоритм не смог».

## 8. Расширение модели для перепланирования

Событие происходит в момент `T` (время события из ТЗ D-03). Пусть `P⁰` — действующий план.

### 8.1. Заморозка прошлого

Визиты, которые к моменту `T` уже начаты или выполнены, **не подлежат пересмотру**:

```
F = { j : назначен в P⁰ и t⁰_j ≤ T }
y_{ij} = y⁰_{ij}   и   t_j = t⁰_j          для всех j ∈ F
```

Для каждого инженера пересчитывается новая эффективная стартовая точка и время:

```
o'_i = точка последнего замороженного визита (или o_i, если таких нет)
S'_i = max(T, время завершения последнего замороженного визита)
```

Далее решается **та же задача** на `J \ F` с параметрами `(o'_i, S'_i, E_i)`.
Никакой отдельной «модели перепланирования» не нужно — это та же модель на суженных данных.
Красивое свойство: одна модель, два режима.

### 8.2. Три события ТЗ как модификации входа

| Событие (ТЗ D-03) | Что меняется в модели |
|---|---|
| **Срочная заявка** | `J ← J ∪ {j_new}`, `π_{j_new} = 3` |
| **Отмена заявки** | `J ← J \ {j_cancel}` |
| **Недоступность инженера** | `E_i ← min(E_i, T)`, заявки инженера после `T` возвращаются в пул |

Все три сводятся к правке входных множеств — модель не меняется вообще.
Это сильный ответ на вопрос жюри №3 («корректно ли реагирует на изменение»).

### 8.3. Член стабильности плана

Хороший новый план — не только эффективный, но и **похожий на старый**: диспетчер уже
позвонил абонентам, инженеры уже видят свои задания. Добавляем четвёртый критерий:

```
Z₆ = Σ_{j ∈ J \ F}  [ назначение j изменилось относительно P⁰ ]     → min
```

формально `Z₆ = Σ_j (1 − Σ_i y⁰_{ij} · y_{ij})` по заявкам, назначенным в обоих планах.

**Место в иерархии весов:** между `Z₂` (исполнители) и `Z₃` (пробег).

```
Λ₆ = 2000          (в единицах Λ₃ = 1 за 10 м)
```

Смысл: система переназначит заявку другому инженеру, только если это экономит **больше 20 км**.
Ниже этого порога — стабильность важнее.

Условие непротиворечивости: `Λ₂ > Λ₆ · m + Λ₃ · D̄`, т.е. `10⁶ > 2000·100 + 5·10⁵ = 7·10⁵` ✔.
Сокращение исполнителя по-прежнему важнее любой перетасовки.

⚠️ Это **наша добавка сверх ТЗ**, но добавка защищаемая: без неё перепланирование будет
каждый раз выдавать полностью новый план, и требование R-05 («показать, что изменилось»)
выродится в «изменилось всё». Стабильность — то, что делает diff читаемым.

## 9. Бейзлайн из ТЗ — формальная запись

ТЗ §2.3 задаёт базовый вариант дословно. Формализуем, чтобы реализация была бесспорной:

```
Вход: заявки в порядке входных данных j₁, j₂, …, j_m
      инженеры в порядке входных данных i₁, i₂, …, i_n
Состояние: для каждого инженера — текущая точка cur_i := o_i и текущее время now_i := S_i

для каждой заявки j по порядку:
    для каждого инженера i по порядку:
        если i ∉ A_j:                                    ← навык или транспорт не подходят
            следующий i
        arrive := now_i + τ_i(cur_i, j)
        start  := max(arrive, e_j)                       ← можно подождать открытия окна
        если start > l_j:                                ← C-02a: не попадаем в окно
            следующий i
        если start + s_j > E_i:                          ← C-02b: не помещаемся в смену
            следующий i
        назначить j инженеру i; cur_i := j; now_i := start + s_j
        перейти к следующей заявке
    если никто не подошёл: j помечается как не назначена
```

**Свойства бейзлайна, которые надо знать заранее:**

1. Порядок посещения = порядок назначения (прямо сказано в ТЗ) → маршруты не оптимизируются вовсе.
2. Первый по списку инженер «собирает» непропорционально много заявок, пока не упрётся
   в смену → плохая балансировка и **завышенный пробег**.
3. Число задействованных исполнителей у бейзлайна может оказаться **меньше** нашего,
   если он просто не назначит часть заявок! Поэтому **сравнивать M-01 корректно только при
   равном числе назначенных заявок** — иначе сравнение нечестное.

⚠️ **Это ловушка, в которую попадут другие команды.** Правило корректного сравнения:

> Сначала сравниваем `назначено заявок`. Только если оно равно — сравниваем исполнителей.
> Только если равно и оно — сравниваем пробег.
> То есть сравнение ведётся **в том же лексикографическом порядке**, что и оптимизация.

## 10. Итоговая сводка модели

```
                    min   Λ₁·Σ π_j z_j  +  Λ₂·Σ u_i  +  Λ₆·Z₆  +  Λ₃·Σ d_i  +  ε(Z₄ + Z₅)

  при ограничениях
  (1)  Σ_{i∈A_j} y_ij + z_j = 1                          ∀j            покрытие
  (2)  Σ_u x^i_uj = Σ_v x^i_jv = y_ij                     ∀i,j          связь маршрута
  (3)  Σ_v x^i_{o_i v} = 1,  Σ_u x^i_{u f} = 1            ∀i            старт и открытый финиш
  (4)  y_ij ≤ u_i ≤ Σ_j y_ij                              ∀i,j          задействованность
  (5)  t_v ≥ t_u + s_u + τ_i(u,v) − M(1 − x^i_uv)         ∀i,u,v        время вдоль маршрута
  (6)  e_j ≤ t_j ≤ l_j                                    ∀j: z_j=0     C-02a окно (начало!)
  (7)  t_j + s_j ≤ E_i + M(1 − y_ij)                      ∀i,j          C-02b смена
  (8)  i ∈ A_j ⟺ q_j ∈ K_i ∧ (r_j=∅ ∨ r_j=w_i)                          C-01, C-03
  (9)  y, x, z, u ∈ {0,1};  t ≥ 0
```

| Элемент модели | Требование ТЗ |
|---|---|
| `A_j` через `q_j ∈ K_i` | C-01 Квалификация |
| `e_j ≤ t_j ≤ l_j` | C-02 Время (окно) |
| `t_j + s_j ≤ E_i` | C-02 Время (смена) |
| `A_j` через `r_j = w_i` | C-03 Ресурс |
| `Σ u_i` в целевой | M-01 Минимум персонала |
| `d_i` и `Σ d_i` | M-02 Пробег по каждому и суммарно |
| `z_j = 1` + причина из §3 / §7.3 | F-08, R-03 Неназначенные с причиной |
| Сток `f` с нулевой стоимостью | D-04 Без возврата на базу |
| `π_j = 3` для срочных | ТЗ §2.4.1 Приоритет |
| §8 заморозка + `Z₆` | F-06, R-05 Перепланирование и diff |

## 11. Размер задачи и вычислительная реальность

При `m = 100`, `n = 15`:

| Величина | Оценка |
|---|---|
| Узлов графа | `15 + 100 + 1 = 116` |
| Переменных `y` | `Σ_j |A_j| ≈ 100 × 5 = 500` (а не 1500 — спасибо префильтру) |
| Переменных `x` | `≈ 15 × 116² ≈ 200 000` в полной MIP-формулировке |
| Переменных `t` | 100 |

Полная MIP-формулировка на 200 тысяч бинарных переменных **не решается за секунды** —
и не нужна. Практически задача решается специализированной маршрутной библиотекой
или эвристикой; MIP-запись выше нужна как **спецификация**, а не как способ вычисления.
Выбор вычислительного метода — в `07-algorithm-design.md`.

**Целевой бюджет времени:** первый план ≤ 10 с, перепланирование ≤ 3 с.
Обоснование: ТЗ говорит «диспетчеру нужен новый план за несколько минут» (стр. 1) —
мы даём на два порядка быстрее, и это само по себе тезис для питча.
