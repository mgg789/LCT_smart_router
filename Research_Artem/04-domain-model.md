# 04. Логическая модель предметной области

> Сущности, их состояния, инварианты и решающие таблицы. Это «мир», в котором живёт продукт:
> то, что должно одинаково пониматься аналитиком, разработчиком солвера, фронтендером и
> человеком на защите.

## 2. Сущности

### 2.1. Заявка (Request)

| Поле | Тип | Обязательность | Источник | Примечание |
|---|---|---|---|---|
| `id` | строка | MUST | данные | уникален в пределах дня |
| `lat`, `lon` | число | MUST (после обогащения) | геокодирование адреса | ТЗ разрешает «координаты **или** адрес» |
| `address` | строка | SHOULD | данные | нужен диспетчеру в интерфейсе |
| `district` | строка | MAY | данные | используется как фолбэк геокодирования |
| `service_min` | целое, мин | MUST | норматив по типу работ | в исходных данных отсутствует — см. `03` |
| `window_open` | HH:MM | MUST | данные (`Начало`) | |
| `window_close` | HH:MM | MUST | данные (`Окончание`) | ограничивает **начало** работ |
| `skill` | 1..3 | MUST | маппинг типа заявки | ровно один |
| `vehicle_required` | 1..4 \| ∅ | MAY | правило по типу работ | ∅ = без ограничения |
| `priority` | 1 \| 2 | MUST | 2 для срочных событий | |

**Инварианты:**
- `I-R1`: `window_open < window_close`
- `I-R2`: `service_min > 0`
- `I-R3`: `skill ∈ {1,2,3}` — закрытый справочник ТЗ
- `I-R4`: `vehicle_required ∈ {1,2,3,4} ∪ {∅}`
- `I-R5`: координаты в пределах разумного бокса Москвы и области
  (`54.9 ≤ lat ≤ 56.2`, `36.5 ≤ lon ≤ 38.5`) — защита от ошибок геокодирования

### 2.2. Инженер (Engineer)

| Поле | Тип | Обязательность | Примечание |
|---|---|---|---|
| `id` | строка | MUST | |
| `name` | строка | SHOULD | диспетчер мыслит именами, не ID |
| `start_lat`, `start_lon` | число | MUST | стартовая точка |
| `shift_start` | HH:MM | MUST | |
| `shift_end` | HH:MM | MUST | |
| `skills` | множество из 1..3 | MUST | **от 1 до 3** — дословно ТЗ |
| `vehicle` | 1..4 | MUST | ровно один |
| `available` | булево | MUST | для события «инженер недоступен» |

**Инварианты:**
- `I-E1`: `shift_start < shift_end`
- `I-E2`: `1 ≤ |skills| ≤ 3` — прямое требование ТЗ §2.4.1
- `I-E3`: `skills ⊆ {1,2,3}`, без повторов
- `I-E4`: `vehicle ∈ {1,2,3,4}` — ровно одно значение

### 2.3. Назначение (Assignment)

| Поле | Тип | Смысл |
|---|---|---|
| `request_id` | строка | какая заявка |
| `engineer_id` | строка | кому |
| `seq` | целое ≥ 1 | порядковый номер в маршруте |
| `travel_from_prev_min` | мин | время в пути от предыдущей точки |
| `distance_from_prev_km` | км | расстояние от предыдущей точки |
| `arrive_min` | мин от 00:00 | физическое прибытие |
| `start_min` | мин от 00:00 | начало работ (`max(arrive, window_open)`) |
| `wait_min` | мин | `start_min − arrive_min` |
| `done_min` | мин от 00:00 | `start_min + service_min` |

**Инварианты (это и есть валидатор плана — тот самый ответ на вопрос жюри №1):**

| Код | Инвариант | Требование |
|---|---|---|
| `I-A1` | `skill(request) ∈ skills(engineer)` | C-01 |
| `I-A2` | `vehicle_required = ∅ ∨ vehicle_required = vehicle(engineer)` | C-03 |
| `I-A3` | `window_open ≤ start_min ≤ window_close` | C-02a |
| `I-A4` | `done_min ≤ shift_end(engineer)` | C-02b |
| `I-A5` | `start_min ≥ shift_start(engineer) + travel(start_point → first)` для `seq = 1` | C-02b |
| `I-A6` | `arrive_min(seq k) = done_min(seq k−1) + travel_from_prev_min` | согласованность цепочки |
| `I-A7` | `wait_min ≥ 0` | физика |
| `I-A8` | `seq` образует непрерывную последовательность 1..N без пропусков | целостность маршрута |

⚠️ **Продуктовое решение:** эти восемь проверок реализуются **отдельным модулем-валидатором,
независимым от солвера**, и запускаются на каждом построенном плане. Причина: солвер может
содержать ошибку, а валидатор — независимая вторая пара глаз. На демо мы показываем экран
«Проверка плана: 8 инвариантов × 412 проверенных пар — 0 нарушений». Это материальный ответ
на вопрос «все ли ограничения реально проверяются?».

### 2.4. План (Plan)

| Поле | Смысл |
|---|---|
| `id` | версия плана (v1 — исходный, v2 — после события…) |
| `created_at` | момент построения |
| `routes` | `engineer_id → упорядоченный список Assignment` |
| `unassigned` | список `(request_id, Reason)` |
| `metrics` | см. `10-metrics-and-baseline.md` |
| `explanations` | `request_id → Explanation` |
| `based_on_event` | `ReplanEvent \| ∅` |

**Инварианты плана:**
- `I-P1`: каждая заявка входа встречается **ровно один раз** — либо в `routes`, либо в `unassigned`.
  Это гарантия требования R-02 «назначен исполнитель либо статус не назначена».
- `I-P2`: у каждой записи `unassigned` заполнена причина (R-03).
- `I-P3`: `используемые исполнители = |{i : routes[i] ≠ ∅}|` — дословное определение M-01.

## 3. Состояния и жизненный цикл

### 3.1. Состояния заявки в течение дня

```
                 ┌──────────────┐
                 │  НОВАЯ       │  поступила в датасет / пришла событием
                 └──────┬───────┘
                        │ планирование
              ┌─────────┴──────────┐
              ▼                    ▼
     ┌────────────────┐   ┌────────────────────┐
     │  НАЗНАЧЕНА     │   │  НЕ НАЗНАЧЕНА      │◀──┐
     │  (инженер+seq) │   │  (+ причина)       │   │
     └───┬────────┬───┘   └─────────┬──────────┘   │
         │        │                 │              │
   отмена│        │ переплан        │ переплан     │
         │        └─────────────────┴──────────────┘
         ▼
  ┌──────────────┐
  │  ОТМЕНЕНА    │  (событие «отмена заявки»)
  └──────────────┘
```

Дополнительные состояния для режима «день идёт» (нужны для заморозки, §8 матмодели):
`ЗАПЛАНИРОВАНА → В ПУТИ → ВЫПОЛНЯЕТСЯ → ВЫПОЛНЕНА`.
В MVP достаточно признака `заморожена` (визит начат до момента события).

### 3.2. Состояния инженера

```
ДОСТУПЕН ──событие «недоступен»──▶ НЕДОСТУПЕН
    │                                    │
    │                                    └── его будущие заявки возвращаются в пул
    ▼
ЗАДЕЙСТВОВАН (хотя бы одна заявка) / СВОБОДЕН (ни одной)
```

Различие «задействован / свободен» — не косметика: именно оно даёт метрику M-01.

### 3.3. Версионирование планов

```
Plan v1  ──[Событие E1]──▶  Plan v2  ──[Событие E2]──▶  Plan v3
    └──────── Diff(v1, v2) ────┘ └──────── Diff(v2, v3) ────┘
```

План **никогда не мутирует** — каждое событие порождает новую версию.
Это даёт бесплатно: историю дня, кнопку «откатить», сравнение вариантов (F-09)
и, главное, требование R-05 «показать, что изменилось».

## 4. Решающая таблица допустимости пары (инженер, заявка)

Порядок проверок **строго фиксирован** — от самого «дешёвого и объяснимого» к самому сложному.
Порядок важен: первая же сработавшая проверка становится причиной отказа, а значит
определяет текст, который увидит диспетчер.

| № | Проверка | Условие допустимости | Зависит от маршрута? | Код причины |
|---|---|---|---|---|
| 1 | Навык | `skill(j) ∈ skills(i)` | нет | `SKILL_MISSING` |
| 2 | Транспорт | `veh_req(j) = ∅ ∨ veh_req(j) = veh(i)` | нет | `VEHICLE_MISMATCH` |
| 3 | Доступность | `available(i) = true` | нет | `ENGINEER_UNAVAILABLE` |
| 4 | Пересечение окна и смены | `[e_j, l_j] ∩ [S_i, E_i − s_j] ≠ ∅` | нет | `WINDOW_OUTSIDE_SHIFT` |
| 5 | Достижимость из стартовой точки | `S_i + τ_i(o_i, j) ≤ l_j` | нет | `UNREACHABLE_IN_WINDOW` |
| 6 | Встраивание в существующий маршрут | существует позиция вставки без нарушения окон последующих визитов | **да** | `NO_FEASIBLE_SLOT` |
| 7 | Помещается до конца смены | `start + s_j ≤ E_i` с учётом маршрута | **да** | `SHIFT_OVERFLOW` |

**Ключевое свойство таблицы:** проверки 1–5 **не зависят от маршрута**, поэтому их результат
абсолютен и вычисляется за `O(n·m)` до запуска оптимизатора. Проверки 6–7 зависят от
конкретного плана, поэтому формулируются осторожнее: не «невозможно», а «в этом плане не нашлось места».

⚠️ Это различие обязано быть видно в интерфейсе. Формулировки:

| Тип причины | Формулировка для диспетчера |
|---|---|
| Абсолютная (1–5) | «**Невозможно:** ни один инженер не имеет навыка "Аварийные работы"» |
| Относительная (6–7) | «**Не удалось разместить:** 4 подходящих инженера заняты в это время» |

Честность здесь — часть продукта. Сказать «невозможно» там, где на самом деле «не поместилось
в этот план», значит обмануть диспетчера.

## 5. Таксономия причин неназначения

ТЗ (стр. 2) называет четыре примера причин. Разворачиваем их в полный справочник:

| Код | Текст для диспетчера | Категория | Соответствие примеру ТЗ |
|---|---|---|---|
| `SKILL_MISSING` | Нет инженеров с навыком «{навык}» | Абсолютная | «отсутствует необходимый навык» |
| `VEHICLE_MISMATCH` | Нет инженеров с транспортом «{транспорт}» | Абсолютная | «нет исполнителя с требуемым типом транспорта» |
| `WINDOW_OUTSIDE_SHIFT` | Окно {HH:MM–HH:MM} не пересекается ни с одной сменой | Абсолютная | «работа не помещается во временное окно/смену» |
| `UNREACHABLE_IN_WINDOW` | Ни один подходящий инженер не успевает доехать к {HH:MM} | Абсолютная | «работа не помещается во временное окно» |
| `SHIFT_OVERFLOW` | Работа ({N} мин) не помещается до конца смены | Относительная | «не помещается в смену» |
| `NO_FEASIBLE_SLOT` | Все {N} подходящих инженеров заняты в это время | Относительная | «нет свободных исполнителей на требуемое время» |
| `CAPACITY_DEFICIT` | В окне {HH:MM–HH:MM} объём работ превышает ёмкость смен на {N} ч | Агрегированная | — (наше усиление, см. `05` §7) |

**Правило выбора причины при нескольких сработавших:** берём **самую раннюю по таблице §4**,
то есть самую абсолютную и самую понятную. Диспетчеру важно знать корневую причину,
а не последнюю.

## 6. Модель объяснения (Explanation)

Объяснение — **структура данных**, а не строка. Текст генерируется из структуры шаблонами.
Это принципиально: строка не тестируется, не переводится и не проверяется на правдивость.

```
Explanation
├── verdict           : «назначена / не назначена», кто и когда
├── factors[]         : почему именно этот исполнитель
│     ├── code        : SKILL_MATCH | WINDOW_FIT | PROXIMITY | LOAD | VEHICLE_OK
│     ├── ok          : да / нет
│     ├── value       : измеренное значение (минуты, км, запас)
│     └── weight      : насколько фактор повлиял
├── alternatives[]    : кого ещё рассматривали
│     ├── engineer
│     ├── feasible    : подошёл бы / не подошёл
│     ├── blocked_by  : код причины, если не подошёл
│     └── cost_delta  : на сколько был бы хуже план (км и мин)
└── sequence_reason   : почему такой порядок визитов
```

Такая структура закрывает сразу три требования ТЗ:
`F-07` (почему этому инженеру), `R-06` (какие ограничения повлияли), `F-08`/`R-03` (почему отказ).

Подробнее — в `08-explainability-model.md`.

## 7. Событие перепланирования (ReplanEvent)

Дословно по ТЗ D-03:

| Поле | Тип | Обязательность |
|---|---|---|
| `type` | `URGENT_REQUEST` \| `CANCEL_REQUEST` \| `ENGINEER_UNAVAILABLE` | MUST |
| `at` | HH:MM — время события | MUST |
| `request_id` | строка | MUST для `CANCEL_REQUEST` |
| `engineer_id` | строка | MUST для `ENGINEER_UNAVAILABLE` |
| `payload` | полный объект Request | MUST для `URGENT_REQUEST` |

**Решающая таблица обработки события:**

| Тип события | Что делаем с данными | Что замораживаем | Что ожидаем увидеть в diff |
|---|---|---|---|
| `URGENT_REQUEST` | добавляем заявку с `priority = 2` | все визиты, начатые до `at` | вставка в один маршрут, возможно сдвиг 1–3 соседних визитов |
| `CANCEL_REQUEST` | удаляем заявку | все визиты до `at` | освобождённое окно может «втянуть» ранее неназначенную заявку |
| `ENGINEER_UNAVAILABLE` | `shift_end(i) ← at`, его будущие заявки → в пул | все визиты до `at`, включая визиты этого инженера | перераспределение 2–5 заявок между соседями, возможен рост числа неназначенных |

Третий сценарий — **самый эффектный для демо**: он затрагивает несколько маршрутов сразу
и показывает систему в действии лучше, чем добавление одной заявки.

## 8. Модель различий планов (Diff) — требование R-05

Diff — **первоклассная сущность**, а не визуальный эффект.

```
Diff(P_old, P_new)
├── summary
│     ├── engineers_affected     : сколько маршрутов изменилось
│     ├── requests_moved         : сколько заявок сменили исполнителя
│     ├── requests_resequenced   : сколько сменили порядок у того же исполнителя
│     ├── requests_retimed       : сколько сдвинулись по времени (|Δ| ≥ 5 мин)
│     ├── requests_added         : появились в плане
│     ├── requests_removed       : выпали из плана
│     └── metric_delta           : Δ исполнителей, Δ пробега, Δ назначенных
└── items[]
      ├── request_id
      ├── change : MOVED | RESEQUENCED | RETIMED | ADDED | REMOVED | UNCHANGED
      ├── before : {engineer, seq, start_min}
      └── after  : {engineer, seq, start_min}
```

**Логика классификации изменения** (порядок проверок важен, первое совпадение выигрывает):

| Условие | Класс |
|---|---|
| нет в `P_old`, есть в `P_new` | `ADDED` |
| есть в `P_old`, нет в `P_new` | `REMOVED` |
| сменился `engineer_id` | `MOVED` |
| тот же инженер, сменился `seq` | `RESEQUENCED` |
| тот же инженер и `seq`, `|Δstart| ≥ 5` мин | `RETIMED` |
| иначе | `UNCHANGED` |

Порог 5 минут — чтобы микросдвиги не зашумляли ленту изменений.

## 9. Глоссарий (единый язык команды и защиты)

| Термин | Определение в нашем продукте | Английский эквивалент |
|---|---|---|
| **Заявка** | Единица работы с адресом, окном, навыком и длительностью | Work order / job / task |
| **Инженер / бригада** | Исполнитель со сменой, навыками и транспортом | Technician / field engineer / resource |
| **Временное окно** | Интервал, в который должно **начаться** обслуживание | Time window |
| **Смена** | Интервал доступности инженера | Shift / availability window |
| **Назначение** | Факт «заявка → инженер» с местом в маршруте | Assignment |
| **Маршрут** | Упорядоченная последовательность визитов одного инженера | Route |
| **План** | Совокупность маршрутов + неназначенные + метрики | Plan / schedule |
| **Перепланирование** | Построение новой версии плана после события дня | Re-optimization / re-planning |
| **Задействованный исполнитель** | Инженер, у которого ≥ 1 заявка (метрика M-01) | Used vehicle / active technician |
| **Пробег** | Сумма расстояний по дугам маршрута (метрика M-02) | Route distance / mileage |
| **Бейзлайн** | Жадное последовательное распределение, заданное ТЗ §2.3 | Baseline / greedy FIFO |
| **Объяснение** | Структура факторов и альтернатив, обосновывающая решение | Explanation / decision rationale |
| **Diff плана** | Формализованные различия двух версий плана | Plan delta |
| **Заморозка** | Запрет на пересмотр визитов, начатых до момента события | Frozen visits |
| **Ожидание** | Простой инженера, приехавшего раньше открытия окна | Wait / idle time |

Правило: **в интерфейсе — только русская колонка. В коде — только английская.**
Смешение языков в UI мгновенно выдаёт прототип, собранный наспех.
