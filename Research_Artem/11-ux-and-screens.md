# 11. UX и экраны: проектирование интерфейса

> Этот документ переводит продуктовые принципы (`02-product-vision.md` §4, §6) и сценарий
> демонстрации (`01-case-requirements.md` §9, P-01…P-07) в конкретный макет: зоны экрана,
> состав каждой зоны, поведение при клике и при перепланировании. Формат — ASCII-макеты
> в блоках кода, чтобы фронтендер мог начать вёрстку без дополнительных вопросов.
>
> Технологии заданы: **React + MapLibre GL** (уже используется в `core/studio.html`,
> см. `research-inputs/E-existing-core-audit.md` §7), тайлы OSM. Экран проектируется
> для диспетчерской: широкий монитор, мышь и клавиатура, не телефон.
>
> Главный экзаменатор этого документа — вопрос жюри №2: **«Можно ли понять результат
> без изучения кода?»** Каждое решение ниже проверяется этим вопросом.

---

## 1. Пользователь и контекст использования

### 1.1. Кто это

Диспетчер выездной службы (см. `02-product-vision.md` §3.1): планирует день для 10–15 бригад
и 50–100 заявок. Сегодня делает это в Excel и по телефону. День ломается 3–5 раз за смену —
аварийная заявка, инженер заболел, абонент не открыл дверь.

### 1.2. Какие решения он принимает и с какой скоростью

| Решение | Как часто | Сколько времени есть |
|---|---|---|
| Утвердить план дня или поправить его | 1 раз в начале смены | 2–5 минут на весь просмотр |
| Понять, почему заявка ушла к конкретной бригаде | по запросу (свой или руководителя) | 10–20 секунд, разговор не должен прерываться |
| Отреагировать на срочное событие (авария, отмена, недоступность) | 3–5 раз за день | секунды на решение «согласиться / поправить руками» |
| Объяснить абоненту, почему его заявка не будет выполнена сегодня | несколько раз за день | должен процитировать причину, не выдумывать |
| Доложить руководителю: сколько бригад, сколько км, есть ли просрочки | 1–2 раза за смену | должен назвать три числа не открывая отчёт |

Диспетчер не читает документацию по ходу работы и не имеет времени «разбираться». Экран должен
быть понятен **с первого взгляда**, а не после обучения.

### 1.3. Экран и физический контекст

- Широкий монитор (от 1440×900, целевой дизайн — 1920×1080), сидячее рабочее место, мышь.
- Один экран включён весь день — это не разовая сессия, а фоновая панель, к которой возвращаются
  между звонками. Значит интерфейс должен быть читаем боковым зрением: крупные числа сверху,
  цвет как основной сигнал статуса.
- Никакого тач-интерфейса, сенсорных жестов, мобильной адаптации — не требуется и прямо
  исключено ТЗ (см. §17).

### 1.4. Чем это отличается от работы аналитика

Аналитик изучает данные постфактум: у него есть время, он готов кликать, сравнивать таблицы,
экспортировать в Excel и разбираться самостоятельно. Диспетчер работает **в моменте**: абонент
уже на линии, бригада уже звонит с вопросом «куда мне дальше». Отсюда три следствия для
интерфейса:

1. Ни одного экрана, требующего «сначала загрузите отчёт» — всё видно сразу (принцип 1, §2).
2. Ни одного числа без готового объяснения по клику — не нужно строить гипотезу самому (принцип 2).
3. Действие (переиграть план) и объяснение результата — на одном экране, без переключения
   контекста, потому что переключение контекста для диспетчера означает повешенную трубку.

## 2. Главный принцип компоновки

### 2.1. Почему всё на одном экране

Продуктовый принцип №1 из `02-product-vision.md` §4: **«Один экран — весь день»**. Диспетчер не
должен переключать вкладки, чтобы понять план. Это не эстетическое предпочтение — это
единственный способ пройти демо-сценарий P-01…P-07 за 5–7 минут без пауз «сейчас переключусь
на другой экран» (см. §13).

Это же отраслевой стандарт: все аудированные промышленные FSM-панели (Salesforce Dispatcher
Console, Oracle Field Service, ServiceMax Service Board) построены по одной и той же
трёхзонной схеме — **список заявок ↔ карта ↔ гант по исполнителям**, с панелью нераспределённых
заявок как постоянным «инбоксом» диспетчера (`research-inputs/B-market-and-domain.md` §2.8,
п. 1–2). Мы не изобретаем компоновку — мы используем ту, которую жюри узнает мгновенно, и это
работает в нашу пользу: узнаваемый паттерн не требует объяснения, экономит время демо.

### 2.2. Четыре зоны и их роль

| Зона | Расположение | Отвечает на вопрос | Обязательна по |
|---|---|---|---|
| **Список: бригады + заявки** | слева | «Кто у меня есть и что нужно сделать?» | F-05 |
| **Карта** | центр, самая большая | «Где это физически происходит?» | F-04 |
| **Таймлайн (Гант)** | снизу, во всю ширину | «Когда это происходит и есть ли риск?» | F-05, F-03 |
| **Панель объяснения / деталей** | справа, докована к карте | «Почему именно так?» | F-07, R-06 |

### 2.3. Обоснование пропорций

- **Карта получает больше всего площади** (≈ 50 % ширины по центру), потому что она единственная
  зона, где пространственная плотность данных (83 заявки, 2.1 заявки на дом, регион до 115 км
  от МКАД) требует места для различения объектов. Сжатая карта — нечитаемая карта.
- **Список слева — компактный и текстовый** (≈ 300 px, не проценты — фиксированная ширина, чтобы
  не «плавала» при ресайзе), потому что это преимущественно чтение имён, чисел и статусов —
  плотность важнее ширины.
- **Панель объяснения справа — тоже фиксированная** (≈ 320–360 px), в свёрнутом состоянии
  показывает сводку плана (мини-версия панели §10), в развёрнутом — три уровня объяснения (§8).
  Не резиновая, потому что текст объяснения не должен переливаться при каждом клике.
- **Таймлайн — на всю ширину и не выше ~220–260 px**, потому что он один и должен вместить
  строки всех 12 бригад без скролла в демо-масштабе; при этом высота ограничена, чтобы не
  съедать место у карты — Гант читается по горизонтали (время), а не по высоте.
- **Метрики — тонкая полоса сверху, высотой ~64–80 px**, всегда видна, потому что панель метрик
  видна постоянно (`10-metrics-and-baseline.md` §9) — это прямой ответ на вопрос жюри №4.

## 4. Зона 1: список бригад

### 4.1. Состав карточки бригады

| Поле | Пример | Зачем |
|---|---|---|
| Имя | «Бригада Горбанев» | диспетчер мыслит именами, не ID (`04-domain-model.md` §2.2) |
| Навыки | значки: 🔧 локальные · 🔌 подключение · 🚨 аварийные | видно, что может делать бригада, без клика |
| Транспорт | значок: 🚗 авто / 🚶 пешком / 🚲 велосипед / 🚌 транспорт | важно для «дорогих» точек (Кашира, Домодедово) |
| Смена | `09:00–18:00` | видно окно доступности |
| Число заявок | «6 з.» | плотность работы |
| Загрузка | полоса `▓▓▓▓▓▓▓▓░░ 82%` | доля рабочего времени, занятая визитами + переездами |
| Пробег | «41.2 км» | вклад в M-02 |

### 4.2. Визуальное различие «задействована / свободна» — это метрика M-01

M-01 («задействовано исполнителей») — обязательная метрика ТЗ, и список бригад — единственное
место, где она видна построчно, а не только числом в шапке. Правило:

| Состояние | Индикатор | Стиль строки |
|---|---|---|
| Задействована (≥ 1 заявка) | ● сплошной кружок цвета бригады | обычный текст, полоса загрузки цветная |
| Свободна (0 заявок) | ○ пустой кружок, серый | текст приглушён (серый), подпись «свободна» вместо процента |

Свободные бригады не прячутся вниз списка автоматически — порядок стабилен (по имени или по
исходному списку файла), чтобы диспетчер не терял бригаду из виду при пересчёте. Но визуально
они не спорят за внимание с задействованными.

Отдельный счётчик над списком: `Бригады: 11 / 12 задействованы` — тот же принцип, что и в шапке
метрик, продублированный на уровне зоны.

### 4.3. Выделение бригады на карте при наведении

Наведение курсора на карточку бригады в списке:

- маршрут этой бригады на карте становится ярче и толще (+2 px к линии);
- маршруты остальных бригад гаснут до 25 % непрозрачности (не исчезают — сохраняется контекст);
- маркеры заявок этой бригады получают белую обводку;
- в таймлайне соответствующая строка подсвечивается фоном.

Это работает и в обратную сторону: наведение на маршрут на карте подсвечивает карточку бригады
в списке (прокруткой в видимую область, если нужно). Симметрия обязательна — диспетчер должен
уметь идти от списка к карте и от карты к списку одинаково легко.

Клик по бригаде (не наведение) фиксирует выделение и открывает в правой панели сводку по
бригаде: список визитов по порядку, суммарные метрики, кнопка «показать только этот маршрут».

## 5. Зона 2: список заявок

### 5.1. Группировка и фильтры

Список заявок живёт на той же вкладке зоны 1 (переключатель `[Бригады] / [Заявки]` в шапке
левой колонки — не отдельный экран, а таб внутри одной зоны, чтобы не плодить навигацию).

**Группировка по умолчанию** — по временному окну (10:00–12:00, 12:00–14:00, …), потому что
это то, как диспетчер и абонент мыслят днём. Внутри группы — сортировка по приоритету
(срочные сверху).

**Фильтры** (компактная панель чипов над списком, не модальное окно):

```
[ Навык: все ▾ ]  [ Приоритет: все ▾ ]  [ Бригада: все ▾ ]  [ Район: все ▾ ]  [✓] только не назначенные
```

- Навык — 3 значения справочника ТЗ.
- Приоритет — обычная / срочная.
- Бригада — фильтр «показать заявки этой бригады» (используется вместе с выделением на карте).
- Район — практично при 83 заявках в 15+ районах, включая Домодедово, Кашира, Орехово-Борисово
  Южное, Зябликово.

### 5.2. Компактное отображение окна и цветовое кодирование

Строка заявки — одна строка, без переноса:

```
🔌 №305857695  10–12  Орехово-Борисово Южное          → Мельников  18:20
🚨 №305923527  весь день  Кашира                        ⚠ НЕ НАЗНАЧЕНА
```

| Элемент | Кодирует | Правило |
|---|---|---|
| Значок слева | навык (🔧/🔌/🚨) | тот же значок, что и на карточке бригады и на маркере карты — единый словарь по всему экрану |
| Цвет фона значка приоритета | приоритет | обычная — нейтральный фон; срочная — жёлто-оранжевый акцент, не красный (красный зарезервирован под риск/нарушение, см. §16) |
| Окно | компактный диапазон `10–12` или `весь день` для аварийных с окном 00:01–23:59 | полный `10:00–12:00` — по наведению (tooltip) |
| Правая часть | результат: бригада + время визита, либо статус «не назначена» | одна и та же позиция для быстрого сканирования взглядом сверху вниз |

Статусы заявки (`04-domain-model.md` §3.1) отображаются значком слева от номера, если это
не «обычная назначенная»: `🕓 запланирована`, `🚗 в пути`, `🔧 выполняется`, `✔ выполнена`,
`✖ отменена`.

### 5.3. Блок «Не назначено (N)» — заметный, а не спрятанный

Продуктовый принцип №3 (§4 `02-product-vision.md`): **отказ — это тоже результат**. Блок
«Не назначено» не находится в подвале списка мелким текстом — он закреплён (sticky) под
фильтрами, разворачивается по умолчанию, если `N > 0`, и имеет визуальный вес, сравнимый
с блоком метрик:

```
┌─────────────────────────────────────────────────┐
│ ▼ НЕ НАЗНАЧЕНО (3)                      ⚠ виден  │
│ ─────────────────────────────────────────────── │
│ 🚨 №305923527  Кашира          нет транспорта    │
│ 🔌 №305901188  Домодедово      все бригады заняты│
│ 🔧 №305877340  Зябликово       окно вне смен      │
└─────────────────────────────────────────────────┘
```

Каждая строка кликабельна и открывает полную воронку отказа с рецептом (см. §9). Если `N = 0`,
блок сворачивается до одной строки `✔ Все заявки назначены`, зелёная — это тоже сигнал, а не
пустое место.

## 6. Зона 3: карта

### 6.1. Что рисуем

| Слой | Что | Источник |
|---|---|---|
| Базовые тайлы | OSM растровые | как в `core/studio.html`, см. §17 про офлайн-риск |
| Точки заявок | маркер-круг, цвет = навык, номер = порядок визита внутри маршрута бригады | `Request.lat/lon` |
| Стартовые точки бригад | маркер-треугольник ▲, цвет = бригада | `Engineer.start` |
| Маршруты | линия, цвет = бригада, толщина 3 px (выделенная — 5 px) | последовательность `Assignment.seq` |
| Неназначенные заявки | маркер-круг с серой пунктирной обводкой, без номера | `Plan.unassigned` |
| Риск срыва окна | маркер с оранжевой/красной каймой + значок ⚠ | сравнение `eta` с `window_close` |

### 6.2. Палитра бригад на карте

12 бригад = 12 различимых цветов маршрута. Правило подбора и обоснование — в §16.1. Здесь
важно поведенческое правило: **цвет линии маршрута = цвет кружка бригады в списке слева**
(тот же HEX), это единственная связь, которую диспетчер должен выучить, и она не меняется
между экранами.

### 6.3. Порядок визитов на карте

Каждый маркер заявки несёт номер визита в рамках маршрута своей бригады (`①②③…`), а не сквозной
номер по плану. При наведении на маркер — подсказка: номер, время прибытия, бригада, навык.
Порядок визитов **обязателен на карте**, потому что иначе маршрут читается только как «облако
точек», а F-05 требует «кто, куда и **в какое время** едет» — направление и последовательность
не считываются без нумерации.

### 6.4. Заявки в одном доме (2.1 заявки на дом, до 4 в доме)

Из `03-data-reality-gap.md` §7: 195 уникальных домов на 410 адресов, до 4 заявок в одном доме.
Наложенные друг на друга маркеры нечитаемы и теряют номера визитов.

**Решение — кластер-бейдж с раскрытием:**

```
До раскрытия:              После клика/зума:
                                    ②
      (3)                       ① ⬤    ③
       ⬤                            ⬤
```

- Если в одной точке (± 15 м) больше одной заявки — рисуется один маркер с бейджем числа
  («3»), цвет — навык самой ранней по времени визита заявки, либо, если бригады разные,
  нейтральный серый с делением по секторам («pie marker» — сектор на бригаду).
- Клик по кластеру раскрывает точки веером (spiderfy) на фиксированном небольшом радиусе —
  паттерн, стандартный для картографических кластеров, здесь используется не из-за огромного
  объёма точек, а из-за буквального совпадения координат дома.
- В объяснении назначения для таких заявок отдельно показывается фактор `SAME_BUILDING`
  (см. `03-data-reality-gap.md` §7) — «второй визит не требует переезда вообще»: это самый
  понятный и самый проверяемый на глаз фактор из всех, обязателен в списке факторов на панели
  объяснения (§8).

### 6.5. Приблизительные координаты (фолбэк геокодирования)

Три уровня точности координат (`03-data-reality-gap.md` §5.1): DaData (точный дом) →
Nominatim (точный дом, ниже покрытие) → центроид района + детерминированный джиттер
(«приблизительно»).

**Правило показа:** маркер с точным геокодированием — сплошная заливка (●); маркер, полученный
фолбэком по центроиду района — контурный с полупрозрачной заливкой (◐) и подписью в подсказке
«координата приблизительная — определена по центру района {название}». Скрывать источник
координаты запрещено принципом честности (§5.1 документа 03) — это прямо влияет на доверие
к продукту.

### 6.6. Проблема масштаба: Кашира и Домодедово далеко за пределами основного скопления

Зона «Юго-восток» включает районы Москвы (Орехово-Борисово Южное, Зябликово и т. д.) и города
области — Кашира, Домодедово, Ступино, на 37–115 км от МКАД (`03-data-reality-gap.md` §6.1).
Если карта масштабируется «по всем точкам», основное скопление (город) сжимается до пятна
в углу экрана — теряется главная зона работы.

**Решение — комбинация трёх приёмов:**

1. **Карта по умолчанию открывается по границам основного скопления** (город), а не по
   границам всех точек. Порог — например, 90-й перцентиль плотности точек, вычисляется один
   раз при загрузке плана.
2. **Индикатор «за пределами вида»**: если заявка или бригада не попадает в текущий вид карты,
   у края экрана в соответствующем направлении показывается маленькая стрелка-бейдж с числом
   («→ 3 за МКАД») — клик масштабирует карту, чтобы включить эти точки.

   ```
   ┌──────────────────────────────────────┐
   │                                    ↘2 │  ← 2 заявки юго-восточнее вида (Кашира)
   │            (основная карта)           │
   │                                        │
   │  ↙1                                   │  ← 1 заявка за пределами вида на юго-запад
   └──────────────────────────────────────┘
   ```
3. **Переключатель масштаба** в углу карты: `[ Город ] [ Вся зона ]` — «Город» держит удобный
   зум по плотному скоплению, «Вся зона» показывает всё, включая область, с неизбежно мелкими
   маркерами в городе. Диспетчер переключается за один клик, ничего не теряя.

Дополнительно: при клике на заявку в Кашире/Домодедово из списка (зона 2) карта **всегда**
долетает (flyTo, см. §15) до неё независимо от текущего масштаба — точка не должна быть
«потеряна» только потому, что диспетчер её не видит на экране.

## 7. Зона 4: таймлайн (Гант)

### 7.1. Почему таймлайн обязателен

Карта показывает **где**, но не показывает **когда** — а половина обязательных ограничений
ТЗ (C-02: время в пути + длительность в пределах смены, начало в пределах окна) являются
временными, не пространственными. Без таймлайна диспетчер не может ответить на вопрос
«успевает ли бригада Паршин закрыть день без переработки» глядя только на карту. Это прямое
требование F-05 «кто, куда и **в какое время** едет» и косвенное требование C-02 —
ограничение должно быть не просто соблюдено алгоритмом, но **видно** диспетчеру.

### 7.2. Состав строки

Одна строка = одна бригада, ось X = время (10:00–22:00 для зоны «Юго-восток»).

```
Паршин  10:00              12:00              14:00          16:00
        │░░▓▓▓▓▓░░░▓▓▓▓░░░░░▓▓▓▓▓▓░░░▒▒▒▒▒▒▒▒▒▒▒▓▓▓▓░░░░░░░░░░░░░░░░░
        │  визит1  переезд  визит2   ожидание    визит3
        └────────────────────────────────────────────────────────────
        [====== окно заявки 1 ======]      [====== окно заявки 3 ======]
                                     (подложка, бледный цвет навыка)
```

| Элемент | Визуальный код |
|---|---|
| Визит (работа на месте) | сплошной блок, цвет = навык заявки, подпись при достаточной ширине — номер заявки |
| Переезд | штриховка того же цвета, тоньше по высоте (дорога — не работа) |
| Ожидание (простой до открытия окна) | точечная/сетчатая заливка, приглушённый серый — явно «потерянное» время |
| Временное окно заявки | бледная подложка на фоне всей строки, поверх которой лежит блок визита — видно, попадает ли визит в обещанный диапазон |
| Смена бригады | тёмная граница слева/справа строки — то, что раньше/позже неё, вне доступности |

### 7.3. Как показать нарушение/риск

Таймлайн — основное место, где виден **риск**, а не только факт: если визит начинается позже
`window_close` (что невозможно в допустимом плане, но обязательно при демонстрации отказа
валидатора в §12) или если запас до конца окна меньше 15 минут («на грани», как формулирует
доверительная метрика в `10-metrics-and-baseline.md` §2.4), блок визита получает:

- тонкую оранжевую (риск, запас < 15 мин) или красную (нарушение) обводку;
- значок ⚠/✖ у правого края блока;
- в списке бригад (зона 1) — тот же значок рядом с именем бригады, чтобы риск был виден
  и без скролла к нужной строке таймлайна.

Это прямая реализация отраслевого паттерна **jeopardy** (`research-inputs/B-market-and-domain.md`
§1.5) — «ситуация, при которой работа не уложится в обещанное окно» — только у нас источник
подсветки один: сам валидатор плана (§12), а не отдельное правило.

### 7.4. Взаимодействие

- Клик по блоку визита → открывает панель объяснения (§8) для этой заявки, синхронно
  подсвечивает её на карте и в списке.
- Наведение на строку бригады целиком → та же подсветка маршрута на карте, что и при
  наведении на карточку бригады в зоне 1 (симметрия, см. §4.3).
- Горизонтальный скролл не нужен в демо-масштабе (12 часов на экране ~1600 px даёт
  ~133 px/час — достаточно для блоков от 20 минут).

- Альтернатива — **всегда одна**, самая близкая по стоимости, не список из пяти вариантов:
  диспетчеру нужен один убедительный контрпример, а не исследование пространства решений.
- Текст — шаблонный (структура `Explanation` из `04-domain-model.md` §6), никогда не
  генерируется LLM на лету — детерминизм важнее красноречия (принцип 6, `02-product-vision.md` §4).

## 9. Экран/панель «Не назначено»

### 9.1. Почему это должно быть заметно, а не в подвале

Продуктовый принцип №3: отказ — тоже результат. ТЗ требует (R-03) явную причину понятным
языком для каждой неназначенной заявки, и это единственное место в интерфейсе, где продукт
признаётся в собственном ограничении. Спрятать это в подвале — значит создать у диспетчера
ложное чувство «всё назначено», которое рухнет при первой сверке вручную и разрушит доверие
ко всему остальному интерфейсу разом (ключевой инсайт `02-product-vision.md` §3.3).

### 9.2. ASCII-макет: воронка отказа и рецепт

Разворачивается по клику на строку в блоке «Не назначено (§5.3)» — на всю правую панель
объяснения (§8), заменяя её содержимое:


### 9.3. Устройство воронки

Воронка строится по решающей таблице `04-domain-model.md` §4 — проверки идут в фиксированном
порядке от абсолютных к относительным (навык → транспорт → доступность → окно/смена →
достижимость → встраивание в маршрут → помещение до конца смены), и на экране показываются
**только реально отсеявшие группы**, с числом бригад в каждой. Формулировка различает
абсолютную невозможность («нет ни одной бригады с навыком») и относительную нехватку места
в текущем плане («все подходящие заняты») — это разграничение обязательно и описано в
`04-domain-model.md` §4 как вопрос честности.

Кнопка действия внизу — не решение проблемы «за диспетчера», а конкретный рецепт одним кликом,
который запускает локальный пересчёт (не весь план заново) и показывает результат как обычное
перепланирование с diff (§11).

## 10. Панель сравнения с бейзлайном

### 10.1. Задача — не превратить экран в таблицу из отчёта

Панель сравнения обязана быть на экране постоянно (M-05, вопрос жюри №4), но при этом не может
занимать столько же места, сколько полноценный отчёт. Решение — **две плотности одновременно**:
сжатая версия в шапке метрик (уже показана в §3, строка `vs БЕЙЗЛАЙН`), и разворачиваемая
полная версия по клику на эту строку.

### 10.2. ASCII-макет полной панели (разворачивается поверх карты, полупрозрачная подложка)

```
┌────────────────────────────────────────────────────────────────────┐
│  СРАВНЕНИЕ ПЛАНОВ                                              ✕   │
│ ────────────────────────────────────────────────────────────────  │
│                     Живой диспетчер    Бейзлайн     Наш план       │
│  Выполнено заявок      83 (10 просроч.)  71 / 83     83 / 83  ✅   │
│  Задействовано бригад       12              9           11         │
│  Суммарный пробег           ?             340 км      395 км       │
│  ──────────────────────────────────────────────────────────────── │
│  Пробег на заявку            —            4.79 км    4.76 км ✅   │
│  Заявок на бригаду           —             7.9         7.5         │
│ ────────────────────────────────────────────────────────────────  │
│  ⓘ При равных условиях (наш план на тех же 71 заявке бейзлайна):  │
│     бригад 9 → 7 (−2), пробег 340 → 268 км (−21 %)                 │
│ ────────────────────────────────────────────────────────────────  │
│  ⚠ Бейзлайн задействовал меньше бригад — но не выполнил 12 заявок. │
│     Сравнение корректно только при равном числе выполненных.       │
│  ⚠ Данные диспетчера — оценочная реконструкция, см. допущения.     │
└────────────────────────────────────────────────────────────────────┘
```

### 10.3. Принципы вёрстки этой панели

- **Три колонки, не две** (`10-metrics-and-baseline.md` §4.2, §6) — живой диспетчер обязателен
  как третья колонка, это единственное преимущество, которого не будет ни у кого из конкурентов
  хакатона.
- **Нормированные метрики отделены горизонтальной линией** от абсолютных — читаются как вывод,
  а не как ещё одна строка таблицы.
- **Оговорки внизу, но не мелким текстом** — минимум два предложения-предупреждения всегда
  видны без прокрутки, это не юридическая сноска, а часть продуктовой честности (принцип 25 %
  веса критерия «разумные допущения»).
- Компактная версия в шапке (§3) — не «облегчённая копия», а буквально первая строка этой же
  таблицы: `Выполнено заявок · Бригад · Пробег`, чтобы у диспетчера не было ощущения двух разных
  источников правды.

## 11. Отображение изменений после перепланирования

### 11.1. Принцип: изменение видно, а не найдено

Продуктовый принцип №4 (`02-product-vision.md` §4): после перепланирования diff подсвечивается
сам — диспетчер не ищет отличия глазами. Реализация — три синхронных канала одновременно:
**лента изменений** (текст), **подсветка на карте** (маршруты), **подсветка на таймлайне**
(блоки визитов).

### 11.2. Лента изменений

Появляется в верхней части левой колонки сразу после перепланирования, поверх списка бригад/заявок,
как временная панель с кнопкой сворачивания (не модальное окно — не должна блокировать
дальнейшую работу):

```
┌─────────────────────────────────────────────────┐
│  ЧТО ИЗМЕНИЛОСЬ                     [Свернуть ▲] │
│  Пересчёт занял 4.1 с. Затронуто 3 бригады из 11.│
│ ───────────────────────────────────────────────  │
│  + №305988120  добавлена → Бузань, 19:10         │
│  ↕ №305857695  переставлена: была 3-й, стала 5-й │
│  → №305901188  передана: Мельников → Андреев     │
│  ⏱ №305877340  время сдвинулось: 15:40 → 16:05   │
│ ───────────────────────────────────────────────  │
│  Пробег: 395 → 401 км (+6 км)                    │
│  Срочная заявка обслужена через 18 минут          │
└─────────────────────────────────────────────────┘
```

### 11.3. Классы изменений: цвет и значок

Прямое соответствие классификации `04-domain-model.md` §8:

| Класс | Значок | Цвет | Текст ленты |
|---|---|---|---|
| `ADDED` | `+` | зелёный | «добавлена → {бригада}, {время}» |
| `REMOVED` | `−` | серо-красный (приглушённый, не тревожный) | «снята с плана» |
| `MOVED` | `→` | оранжевый | «передана: {было} → {стало}» |
| `RESEQUENCED` | `↕` | синий | «переставлена: была N-й, стала M-й» |
| `RETIMED` | `⏱` | фиолетовый | «время сдвинулось: {было} → {стало}» |

Эти же значок и цвет используются во всех трёх каналах — ленте, карте, таймлайне — единый
словарь, как и с навыками (§6.1) и с бригадами (§6.2).

### 11.4. Подсветка на карте и в таймлайне

- **Карта:** затронутые маршруты на 1.5–2 секунды получают контрастную обводку цвета своего
  класса изменения (см. таблицу выше) поверх обычного цвета бригады, затем возвращаются
  к обычному виду; незатронутые маршруты приглушаются на это же время, чтобы взгляд сам нашёл
  место события.
- **Таймлайн:** новые/переставленные/сдвинутые блоки визитов получают ту же цветную обводку
  и короткую пульсацию (см. §15); ожидание/переезды, появившиеся из-за пересчёта, отрисовываются
  сразу в обновлённом виде — без анимации промежуточных состояний внутри одной строки, чтобы не
  создавать иллюзию физического «путешествия» блока.

### 11.5. Было → стало

Клик по строке в ленте изменений открывает в панели объяснения (§8) сравнение «было / стало»
для конкретной заявки:

```
БЫЛО:  Мельников, визит 3, прибытие 18:20
СТАЛО: Андреев,   визит 2, прибытие 17:55
Почему: у Мельникова образовалась срочная заявка (авария),
и Андреев уже проезжал мимо этого дома.
```

## 12. Экран «Проверка плана»

Материальный ответ на вопрос жюри №1 («Все ли обязательные ограничения реально проверяются?»),
визуализация валидатора из `10-metrics-and-baseline.md` §7. Открывается отдельной панелью
(кнопка «Проверка плана» в шапке метрик, справа от плашки сравнения с бейзлайном), поверх
карты, полупрозрачная подложка, как и панель сравнения (§10) — те же две панели никогда не
открыты одновременно.

```
┌───────────────────────────────────────────────────┐
│  ПРОВЕРКА ПЛАНА                               ✕   │
│ ─────────────────────────────────────────────────  │
│  ✔ Квалификация            83 / 83 назначений      │
│  ✔ Тип транспорта          83 / 83                 │
│  ✔ Начало в окне           83 / 83                 │
│  ✔ Завершение в смене      83 / 83                 │
│  ✔ Достижимость старта     11 / 11 маршрутов       │
│  ✔ Согласованность времён  83 / 83                 │
│  ✔ Ожидание ≥ 0             83 / 83                │
│  ✔ Нумерация визитов       11 / 11 маршрутов       │
│ ─────────────────────────────────────────────────  │
│  Нарушений: 0 из 545 проверок                       │
│                                                      │
│  [ Показать демонстрацию нарушения ]                │
└───────────────────────────────────────────────────┘
```

Каждая строка кликабельна и раскрывает, какие именно инварианты (`I-A1`…`I-A8`,
`04-domain-model.md` §2.3) она проверяет, простым языком без кодов. Кнопка «Показать
демонстрацию нарушения» — отдельный демо-режим: намеренно назначает заявку неподходящей
бригаде вручную (не через солвер) и показывает, как соответствующая строка становится
красной (✖), а число нарушений — ненулевым. Это единственное место интерфейса, где мы
специально ломаем план, чтобы доказать, что проверка настоящая, а не нарисованная.

## 13. Сценарий демо по шагам P-01…P-07

Суммарная длительность — целевые **5:30–6:30** при лимите 5–7 минут (`01-case-requirements.md`
§9), с запасом на живые паузы и вопросы. Зона демо-данных — Юго-восток (83 заявки, 12 бригад),
обоснование выбора — `03-data-reality-gap.md` §8.

| Шаг | Действие ведущего | Что происходит на экране | Сек. | Реплика |
|---|---|---|---|---|
| **P-01** | Открывает встроенный демо-набор (кнопка «Демо-набор: Юго-восток») | Экран загрузки → главный экран с пустым планом (заявки видны как точки, маршрутов ещё нет) | 15 | «Это реальный день зоны Юго-восток: 83 заявки, 12 бригад, данные "Билайн Бизнес" за 17 августа» |
| **P-02** | Нажимает «Построить план» | Спиннер расчёта 2–8 с → метрики в шапке заполняются, маршруты появляются на карте с анимацией (§15) | 20 | «План строится за секунды. Заявки — 83 из 83, задействовано 11 бригад, пробег 395 км» |
| **P-03** | Обводит курсором карту, затем таймлайн | Наведение на бригаду Паршин подсвечивает маршрут и строку в Ганте | 30 | «Вот маршруты — разные цвета, это бригады. Внизу — Гант: видно, когда каждая едет, работает, ждёт» |
| **P-04** | Кликает по заявке в Орехово-Борисово Южном | Открывается панель объяснения (§8), три уровня видны сразу | 45 | «Почему эта заявка у Мельникова? Навык подходит, бригада рядом, запас по окну — час сорок. А вот у второй по близости бригады получилось бы хуже — на 8 км» |
| **P-05** | Нажимает «Инженер недоступен» → выбирает бригаду Бузань, время 15:00 | Диалог события → подтверждение | 25 | «Бригада Бузань заболела в 15:00. Это реальное событие из данных — так и было в тот день» |
| **P-06** | Нажимает «Перестроить план» | Пересчёт 2–5 с → лента изменений (§11) появляется, карта и таймлайн подсвечивают затронутые маршруты | 40 | «Перестроили за пять секунд. Затронуто 3 бригады из 11, переназначено 4 заявки — вот они, подсвечены. Заявки Бузань не потеряны» |
| **P-07** | Открывает панель сравнения с бейзлайном (§10) | Разворачивается таблица трёх колонок | 40 | «Сравним с базовым вариантом из ТЗ: он берёт первого подходящего по порядку — 71 заявка из 83, 9 бригад. Мы — все 83 заявки, при этом эффективнее на заявку. И вот как это распределил живой диспетчер в тот день» |

Итого шаги: 15+20+30+45+25+40+40 = **215 секунд действия**, оставшиеся ~2.5–4 минуты —
вступление (кто мы, что за кейс), связки между шагами и ответы на вопросы жюри — укладывается
в целевой диапазон 5–7 минут с запасом.

**Правило репетиции:** каждый шаг должен быть выполним без ожидания «пока прогрузится» дольше
2–3 секунд — иначе демо рвётся. Это требование к производительности пересчёта (`solve_ms`),
а не только к интерфейсу, но интерфейс обязан честно показывать спиннер расчёта, а не
замирать без объяснения (см. §14).

## 14. Состояния интерфейса

Принцип: **никогда не показываем пустой экран без объяснения.** Каждое из пяти состояний ниже
имеет собственный, явно спроектированный вид — не «белый экран», не «зависшая кнопка».

| Состояние | Когда | Что показываем |
|---|---|---|
| **Загрузка данных** | после выбора файла/демо-набора, до готовности плана | Скелетон-заглушки на месте списков и карты + текст «Читаем данные: 83 заявки, 12 бригад» — числа известны сразу после парсинга, до решения |
| **Расчёт идёт** | после нажатия «Построить план» / «Перестроить» | Компактный индикатор в шапке метрик (не полноэкранный оверлей — карта и список остаются видны, чтобы не терять ощущение контроля), текст «Строим план… 3 с» с растущим таймером |
| **Пусто (нет данных)** | до первой загрузки | Экран-приглашение: «Загрузите файл или откройте демо-набор», две крупные кнопки, никакой пустой карты и пустых списков без подписи |
| **Ошибка** | не удалось прочитать файл / сбой сети геокодирования | Понятный текст без стектрейса: «Не удалось прочитать файл: не найдена колонка "Окончание"» + кнопка «Попробовать другой файл»; частичная ошибка геокодирования не блокирует весь план — заявка помечается «приблизительно», а не роняет загрузку (§6.5) |
| **План невыполним полностью** | 0 заявок могло быть назначено (гипотетический крайний случай, не ожидается на демо-данных) | Экран не «пуст», а показывает список всех заявок сразу в блоке «Не назначено» с причинами (§9) — план из нулевых маршрутов **валиден** как продукт: он объясняет, почему так вышло |

Общее правило переходов: любое ожидание дольше 1 секунды сопровождается индикатором прогресса
с текстом, а не только спиннером — текст обязан называть, что именно происходит («Строим план»,
«Проверяем 545 условий», «Считаем маршруты»), потому что тишина интерфейса читается диспетчером
как зависание.

## 15. Микровзаимодействия и анимация

Правило: **анимация объясняет изменение, а не развлекает.** Каждая анимация ниже существует,
потому что без неё диспетчер должен был бы «искать взглядом», что как раз запрещено принципом 4.

| Событие | Анимация | Длительность | Что объясняет |
|---|---|---|---|
| План впервые построен | Маршруты «прорисовываются» от старта бригады к первой заявке и далее по порядку (line-draw) | 600–900 мс на весь набор маршрутов, не на каждый по отдельности | Направление и порядок визитов считываются глазом, а не воспринимаются как «внезапно появившиеся линии» |
| Наведение на бригаду/заявку | Плавное изменение непрозрачности остальных маршрутов (100 % → 25 %) | 150 мс | Мгновенный фокус без резкого скачка |
| Перепланирование: маршрут исчез/появился | Старый маршрут гаснет (fade-out), новый проявляется (fade-in), **не перерисовывается мгновенно** | 400 мс каждая фаза, последовательно | Diff «было → стало» физически виден, а не подменяется |
| Затронутое изменением | Контрастная обводка + одна пульсация (яркость 100% → 60% → 100%) | 1.5 с, однократно | Привлекает внимание один раз, не мигает бесконечно (не должно раздражать при долгой демонстрации) |
| Новая заявка добавлена (событие) | Маркер «падает» на карту с лёгким увеличением масштаба (scale 0 → 1) | 300 мс | Заметно как новое событие, а не слившееся с фоном |
| Панель объяснения открывается | Слайд справа налево | 200 мс | Ощущение прямой связи «клик → ответ» |
| Карта долетает до удалённой точки (Кашира) | `flyTo` с плавным зумом | 800–1200 мс (зависит от расстояния) | Диспетчер не теряет ориентацию при телепортации через весь регион |

Запрещено: постоянно вращающиеся/пульсирующие элементы без причины, декоративные переходы
дольше 1 секунды, анимация, которая блокирует взаимодействие (пока идёт fade-out старого
маршрута, диспетчер уже должен мочь кликнуть по новому).

## 16. Цвет, типографика, плотность

### 16.1. Палитра бригад: 12 различимых цветов

При 12 задействованных бригадах нужна категориальная (качественная) палитра из 12 взаимно
различимых оттенков — не последовательная (не «от светлого к тёмному одного цвета», это
годится для чисел, не для категорий). Требования к палитре:

- Различимость при обычной и при дальтонической (протанопия/дейтеранопия) цветовой чувствительности
  — не ставить рядом красно-зелёные пары как единственное различие между двумя бригадами.
- Одинаковая воспринимаемая яркость (равномерная светлота в пространстве HSL/OKLCH), чтобы
  ни одна бригада не «пропадала» бледностью и ни одна не «кричала» на фоне других.
- Устойчивость к светлой и тёмной теме карты (тайлы OSM светлые — палитра проектируется под
  светлый фон, с проверкой контраста каждой линии маршрута к светлому асфальтово-серому фону
  тайла).

Практическая реализация: 12 оттенков, разнесённых по кругу HSL с шагом 30°, с фиксированной
насыщенностью (~65–75 %) и светлотой (~45–55 %) — либо готовая категориальная палитра
12 цветов (аналог ColorBrewer `Paired`/`Set3`, адаптированная под шаг в 12, а не в 8–9).
Обязательно: при **> 12 бригад** (не ожидается на демо-данных, но возможно при загрузке
пользовательского файла) — вторичный признак различения (номер бригады в подсказке маркера,
паттерн линии — сплошная/пунктирная для 13-й и далее) до пересчёта или расширения палитры.

### 16.2. Цвета статусов и риска — фиксированный словарь

| Смысл | Цвет | Не путать с |
|---|---|---|
| Успех / назначено / без нарушений | зелёный | — |
| Срочная заявка (приоритет 2) | оранжево-жёлтый | не путать с риском (ниже) — это разные сигналы, разные оттенки |
| Риск (запас до окна < 15 мин) | оранжевый | — |
| Нарушение / не назначено | красный | зарезервирован **только** для реальной проблемы, не для «обычного» состояния — иначе экран «краснеет» и теряет сигнальность |
| Нейтральный/нет данных/приблизительная координата | серый | — |

### 16.3. Доступность: не полагаться только на цвет

Каждый цветовой сигнал в этом документе дублируется формой или текстом:

- бригада — цвет **и** имя в подписи, цвет **и** позиция в списке;
- навык — цвет значка **и** сам значок-пиктограмма (🔧/🔌/🚨), а не только заливка;
- риск/нарушение — цвет обводки **и** значок (⚠/✖), а не только смена оттенка;
- изменение (diff) — цвет **и** значок класса (`+`/`−`/`→`/`↕`/`⏱`, §11.3).

Это не только вопрос доступности для людей с нарушением цветового восприятия — это ещё и
защита от проекторов и внешних мониторов с плохой цветопередачей на самой презентации.

### 16.4. Типографика и плотность

- Шрифт — системный без засечек (единственный на весь интерфейс), моноширинный — только для
  чисел в таймлайне и в панели метрик, если потребуется табличное выравнивание.
- Крупный кегль — только для чисел метрик в шапке (они должны читаться боковым зрением,
  см. §1.3); списки бригад/заявок — компактный, но не мельче 13–14 px, потому что диспетчер
  смотрит на экран весь день.
- Плотность списка — одна строка = одна заявка/бригада без переноса на вторую строку
  в обычном состоянии; вторая строка (загрузка/пробег у бригады) допустима только как
  вспомогательная под основной.

### 16.5. Язык: только русский

Интерфейс полностью на русском языке — никаких английских кодов, идентификаторов ограничений
или внутренних имён (`skill_missing`, `window_conflict` и подобные коды из
`research-inputs/E-existing-core-audit.md` §4 остаются **только в API и логах**, на экране —
всегда готовый русский текст из справочника причин, `04-domain-model.md` §5). Это прямое
следствие принципа `04-domain-model.md` §9: «в интерфейсе — только русская колонка. В коде —
только английская. Смешение языков в UI мгновенно выдаёт прототип, собранный наспех.»

| Мультитенантность, переключение пользователей | Прямо исключено ТЗ |
| Постраничная навигация/вкладки между экранами плана | Противоречит принципу №1 «один экран — весь день» |
| Полноценный редактор данных (создание заявок и бригад вручную с нуля, вне событий перепланирования) | За пределами MVP; событие «срочная заявка» покрывает добавление данных в рамках сценария |
| Экспорт в PDF/Excel, печать маршрутных листов | Не требуется ТЗ и не входит в демо-сценарий; кандидат на раздел «дальнейшее развитие» в DOC-05 |
| Уведомления/пуши, чат с бригадами | Вне контура задачи — не FSM-платформа, а прототип помощника диспетчера |

Каждая строка этой таблицы — сознательный отказ ради того, чтобы время разработки шло в
объяснимость и в устойчивость прохождения демо-сценария (принцип 7, `02-product-vision.md` §4:
«ничего сверх ТЗ»).

## 18. Чек-лист готовности интерфейса

Привязан к семи шагам демо (`01-case-requirements.md` §9) и к пяти вопросам жюри (§13.1 того же
документа).

**По шагам демо:**

- [ ] P-01: экран загрузки данных/демо-набора не пустой, называет, что именно загружается
- [ ] P-02: расчёт плана виден как процесс (индикатор с текстом), а не как «зависание»
- [ ] P-03: карта и таймлайн видны одновременно с картой без переключения вкладок
- [ ] P-04: клик по любой заявке открывает объяснение уровня «вердикт + причина» за один клик,
      «альтернатива» — за второй
- [ ] P-05: все три типа событий (срочная заявка / отмена / недоступность инженера) доступны
      кнопкой без формы длиннее 3 полей
- [ ] P-06: после перестроения лента изменений, подсветка карты и подсветка таймлайна
      появляются синхронно, без отдельного действия диспетчера
- [ ] P-07: панель сравнения с бейзлайном открывается за один клик и показывает три колонки
      (живой диспетчер / бейзлайн / наш план) с нормированными метриками

**По вопросам жюри:**

- [ ] Вопрос 1 (ограничения проверяются?) — экран «Проверка плана» (§12) с демонстрацией
      нарушения по кнопке
- [ ] Вопрос 2 (понятен результат без кода?) — ни одного английского кода/идентификатора на
      экране (§16.5); панель объяснения не требует знания терминов оптимизатора
- [ ] Вопрос 3 (реакция на изменение корректна?) — diff виден на трёх каналах одновременно
      (§11), «было → стало» доступно по клику на любую затронутую заявку
- [ ] Вопрос 4 (сравнение с бейзлайном?) — плашка сравнения видна в шапке **постоянно**, не
      только по запросу (§3, §10)
- [ ] Вопрос 5 (воспроизводимость) — вне зоны UX-документа, закрывается README (`DOC-01`)

**Общие принципы (сквозная проверка, `02-product-vision.md` §4):**

- [ ] Один экран — весь день: нет модальных окон, блокирующих карту/список дольше клика
- [ ] Ни одного числа без объяснения: каждая цифра в шапке метрик кликабельна
- [ ] Отказ — тоже результат: блок «Не назначено» заметен даже при `N = 0`
- [ ] Изменение видно, а не найдено: анимация diff не пропускается и не требует ручного
      сравнения старого и нового состояния
- [ ] Никогда не показываем пустой экран без объяснения (§14 — все пять состояний реализованы)
