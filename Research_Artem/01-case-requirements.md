# 01. Требования кейса: разбор ТЗ и матрица трассируемости

> Источник: «Билайн Бизнес. Интеллектуальный сервис планирования рабочих маршрутов для инженеров
> с учётом временных окон и сложности проводимых работ». ТЗ ЛЦТ-2026, 8 страниц.
> Этот документ — **дословная декомпозиция ТЗ в проверяемые требования с ID**. Никакой отсебятины:
> всё, что здесь есть, взято из текста ТЗ. Наши решения и допущения — в других файлах.

## 0. Как читать

| Префикс | Что это | Кто закрывает |
|---|---|---|
| `F-*` | Функциональные требования (что сервис делает) | solver + api + web |
| `C-*` | Обязательные ограничения модели | solver |
| `M-*` | Обязательные метрики и сравнение | solver + web |
| `D-*` | Требования к формату входных данных | data + shared |
| `R-*` | Требования к формату результата | shared + web |
| `T-*` | Программно-аппаратные требования | infra |
| `P-*` | Требования к демонстрации | вся команда |
| `DOC-*` | Сопроводительная документация | docs |
| `S-*` | Требования к сдаче | вся команда |
| `EV-*` | Критерии оценки жюри | вся команда |

Статус: `MUST` — без этого решение не засчитают. `SHOULD` — явно упомянуто как желательное/дополнительное. `MAY` — разрешено, но не требуется.

## 1. Главная рамка (стр. 1)

> «**Не нужно создавать промышленную корпоративную систему.** Важно показать работающий алгоритм, понятный интерфейс и убедительную демонстрацию.»
>
> «Цель кейса: сделать прототип **помощника диспетчера**, который предлагает выполнимый план и **простыми словами объясняет своё решение**.»
>
> «Хороший результат — это не самая сложная архитектура, а **завершённый и понятный прототип**, который уверенно решает заявленный сценарий.» (стр. 8)

**Три раза в одном ТЗ повторено одно и то же: полнота сценария и понятность важнее сложности.**
Это главный фильтр для всех наших решений: любую фичу, которая не помогает пройти сценарий
демонстрации из §4 ТЗ, мы режем.

Ключевые слова, которые повторяются в ТЗ и по которым будут оценивать:
`выполнимый план` · `объяснить простыми словами` · `явная причина неназначения` ·
`что изменилось после перепланирования` · `сравнение с базовым вариантом`.

## 2. Функциональные требования (ТЗ §2.1, §2.4.2)

| ID | Требование (формулировка ТЗ) | Статус | Проверяемый критерий приёмки |
|---|---|---|---|
| F-01 | Загружать готовые тестовые данные из **CSV или JSON**, либо использовать **встроенный демонстрационный набор** | MUST | В UI есть и загрузка файла, и кнопка «демо-набор»; оба пути приводят к рабочему плану |
| F-02 | Распределять заявки между инженерами | MUST | Каждая заявка получает исполнителя или явный статус «не назначена» |
| F-03 | Определять порядок посещения адресов для каждого инженера | MUST | Для исполнителя выдаётся упорядоченный список с временем прибытия |
| F-04 | Показывать маршруты и точки заявок **на карте** | MUST | Карта с маркерами заявок и линиями маршрутов, различимыми по исполнителю |
| F-05 | Отображать краткую информацию по плану: **кто, куда и в какое время едет** | MUST | Сводка/таймлайн, читается без объяснений |
| F-06 | Перестраивать план после **одного события на выбор**: срочная заявка / отмена заявки / недоступность инженера | MUST (минимум 1 тип) | Событие → новый план за разумное время, старый план доступен для сравнения |
| F-07 | Объяснять результат маршрута языком диспетчера: **почему заявка назначена этому инженеру**, какие ограничения учтены, почему такой порядок | MUST | Клик по заявке → человекочитаемое объяснение без терминов оптимизатора |
| F-08 | При невозможности выполнить все заявки — **явно показать неназначенные** и по каждой указать причину понятным языком | MUST | Отдельный список «не назначено» с причиной на каждую |
| F-09 | Сравнение нескольких вариантов плана | SHOULD (доп. уровень) | — |
| F-10 | «Красивые метрики» | SHOULD (доп. уровень) | — |
| F-11 | Ручное переназначение | SHOULD (доп. уровень) | Диспетчер может перетащить заявку на другого исполнителя |
| F-12 | Несколько сценариев изменений (а не один) | SHOULD (доп. уровень) | Поддержаны все 3 типа события |
| F-13 | Прогноз опозданий | SHOULD (доп. уровень) | Риск опоздания по визиту |

**Примеры причин неназначения, прямо названные в ТЗ (стр. 2)** — это готовый справочник кодов,
его нужно реализовать 1-в-1:
1. нет свободных исполнителей на требуемое время;
2. отсутствует необходимый навык;
3. нет исполнителя с требуемым типом транспорта;
4. работа не помещается во временное окно / смену.

## 3. Обязательные ограничения (ТЗ §2.2)

> «Минимальная версия должна учитывать **три группы ограничений**. Усложнять математическую модель сверх этого **не требуется**.»

| ID | Группа | Формулировка ТЗ | Формальная проверка |
|---|---|---|---|
| C-01 | **Квалификация** | Требуемый навык заявки должен входить в список навыков инженера | `skill(j) ∈ Skills(i)` |
| C-02 | **Время** | Работа с учётом времени в пути и длительности должна укладываться в смену инженера; начало работы должно попадать во временное окно заявки | `a_j ∈ [e_j, l_j]` и `конец маршрута ≤ конец смены` |
| C-03 | **Ресурс** | Если в заявке указан требуемый тип транспорта, назначенный инженер должен иметь этот тип транспорта | `veh_req(j) = ∅ ∨ veh_req(j) = veh(i)` |
| C-04 | Оборудование | «допускается как дополнительное усложнение» | MAY — не делаем в MVP |

⚠️ **Тонкость C-02, которую легко потерять:** ТЗ говорит «**начало работы** должно попадать во
временное окно». То есть окно ограничивает момент старта, а не завершения. Работа может
законно закончиться позже `l_j`, но не позже конца смены. Это отличается от «классического»
VRPTW-восприятия и это надо явно зафиксировать в модели и в объяснениях.

⚠️ **Тонкость C-03:** ограничение транспорта **односторонее и опциональное** — оно применяется,
только если в заявке указан требуемый тип. Пустое поле = подходит любой транспорт.

## 4. Целевая функция и метрики (ТЗ §2.3)

> «Решение должно **стремиться распределить все заявки** с соблюдением обязательных ограничений. Если это невозможно — допускаются неназначенные заявки с обязательным объяснением причины.»

**Две обязательные метрики для сравнения допустимых планов:**

| ID | Метрика (формулировка ТЗ) | Как считается |
|---|---|---|
| M-01 | Выполнение всех заявок **наименьшим количеством персонала**: «учитывается количество **уникальных исполнителей, которым назначена хотя бы одна заявка**» | число i, у которых маршрут непуст |
| M-02 | **Пробег** по маршруту каждого исполнителя: «расстояние отображается **по каждому исполнителю отдельно и суммарно** по всему плану» | `d_i` для каждого i и `Σ d_i` |
| M-03 | Доп. критерии — минимальное время в пути или макс. число выполненных заявок | MAY |

> «**Не требуется доказывать математический оптимум.** Подойдёт готовая библиотека, простой эвристический алгоритм или собственная понятная логика.»

**Базовый вариант (бейзлайн) задан ТЗ дословно и не подлежит нашей интерпретации:**

> «заявки обрабатываются **по порядку поступления** и назначаются **первому по порядку во входных данных доступному инженеру**, который удовлетворяет обязательным ограничениям; **порядок посещения соответствует порядку назначения**. Глобальная оптимизация в базовом варианте не выполняется.»

| ID | Требование | Статус |
|---|---|---|
| M-04 | Реализовать бейзлайн ровно по этому определению | MUST |
| M-05 | Показать сравнение «наш план vs бейзлайн» по M-01 и M-02 | MUST (прямо в §4.7 и §8.1) |

🎯 **Вывод для стратегии:** целевая функция кейса — **лексикографическая**:
сначала максимум назначенных заявок, затем минимум исполнителей, затем минимум пробега.
Порядок именно такой, потому что «стремиться распределить все заявки» стоит выше метрик сравнения,
а M-01 (персонал) в ТЗ перечислена первой. Это нужно закодировать явно, а не через «сумму весов на глаз».

## 5. Формат входных данных (ТЗ §2.4)

| ID | Сущность | Минимальные поля по ТЗ |
|---|---|---|
| D-01 | **Заявка** | ID; координаты **или адрес**; длительность (мин); начало и конец временного окна; приоритет; требуемый навык; требуемый тип транспорта (при наличии) |
| D-02 | **Инженер** | ID/имя; стартовая точка; начало и конец смены; **от 1 до 3 навыков**; тип транспортного средства |
| D-03 | **Событие перепланирования** | тип события (срочная заявка / отмена / недоступность инженера); время события; ID заявки или инженера; для новой срочной заявки — полный набор полей заявки |

| ID | Правило | Статус |
|---|---|---|
| D-04 | Маршрут **начинается в стартовой точке инженера**; **возвращение не требуется** (open route) | MUST |
| D-05 | Единицы: время `HH:MM`; длительность и время в пути — **минуты**; расстояние — **километры**; координаты — широта/долгота | SHOULD (рекомендованы) |

### 5.1. Справочники (ТЗ §2.4.1) — закрытые, менять нельзя

**Требуемый навык** (в заявке ровно один; у исполнителя от 1 до 3):

| Код | Значение |
|---|---|
| 1 | Локальные работы |
| 2 | Работы на подключение и дозаказы |
| 3 | Аварийные работы |

**Тип транспортного средства** (у исполнителя ровно один; в заявке — только при наличии ограничения):

| Код | Значение |
|---|---|
| 1 | Автомобиль |
| 2 | Пешеход |
| 3 | Велосипед |
| 4 | Общественный транспорт |

**Приоритет заявки**:

| Код | Значение |
|---|---|
| 1 | Обычная |
| 2 | Срочная — «имеет более высокий приоритет при перепланировании» |

⚠️ Приоритет в ТЗ имеет **ровно одну явную семантику**: вес при перепланировании. Мы не имеем
права трактовать его как «жёсткое обязательство выполнить» без оговорки — но использовать его
как больший штраф за неназначение логично и защитимо.

## 6. Формат результата (ТЗ §2.4.2)

| ID | Что должно быть в выдаче | Статус |
|---|---|---|
| R-01 | Для каждого исполнителя — **упорядоченный список заявок, плановое время прибытия/начала работ и пробег** по маршруту | MUST |
| R-02 | Для каждой заявки — назначенный исполнитель либо статус «не назначена» | MUST |
| R-03 | Для неназначенной заявки — **явная причина понятным диспетчеру языком** | MUST |
| R-04 | Для плана в целом — количество задействованных исполнителей, пробег по каждому и суммарный | MUST |
| R-05 | После перепланирования — **наглядное отображение того, какие назначения, порядок заявок или маршруты изменились** | MUST |
| R-06 | Для выбранного маршрута — краткое объяснение, какие ограничения и факторы повлияли на решение | MUST |

R-05 — это **diff двух планов**, отдельная сущность в контракте, а не «перерисовали карту».
Её надо спроектировать заранее, иначе на демо нечего будет показать.

| ID | Требование | Комментарий |

| T-01 | Работает на ноутбуке участника; интернет — для установки библиотек и, «при необходимости», картографического сервиса | Смартфон и серверное оборудование не нужны |

Всё, что мы делаем сверх этого списка, — расходование дефицитного времени.

## 9. Демонстрация (ТЗ §4) — это сценарий приёмки, а не «красивый рассказ»

Формат: **live-демо** (допустима заранее записанная видеозапись). Длительность **5–7 минут**.
Семь шагов, заданных ТЗ дословно:

| ID | Шаг демо | Что должно работать |
|---|---|---|
| P-01 | Загрузите или откройте тестовый набор данных | F-01 |
| P-02 | Запустите автоматическое планирование | F-02, F-03 |
| P-03 | Покажите распределение заявок и маршруты на карте | F-04, F-05 |
| P-04 | Откройте одну заявку и объясните, **почему она назначена выбранному инженеру** | F-07 |
| P-05 | Добавьте срочную заявку / отмените существующую / сделайте инженера недоступным | F-06 |
| P-06 | Перестройте план и **покажите, что изменилось** | R-05 |
| P-07 | Сравните результат **с простым базовым вариантом** по двум метрикам | M-01, M-02, M-05 |

🎯 **Эти семь шагов — и есть определение готовности продукта.** Мы строим продукт как машину
для безотказного прохождения этих семи шагов за 5–7 минут. Всё остальное — вторично.

## 11. Ресурсы и требования к тестовому набору (ТЗ §6)

Рекомендованный организаторами масштаб: **10–15 инженеров, не более 100 заявок** на один рабочий день.

Тестовый набор **должен позволять проверить все обязательные ограничения**:

| ID | Требование к данным | Проверка |
|---|---|---|
| D-06 | встречаются **все три навыка** | ✔ по справочнику |
| D-07 | **разные комбинации навыков** у исполнителей | ✔ не все универсалы |
| D-08 | **все типы транспорта** | ✔ 4 типа присутствуют |
| D-09 | **пересекающиеся временные окна** | ✔ |
| D-10 | **хотя бы один конфликт, при котором простое последовательное распределение даёт менее эффективный план** | ⭐ MUST — это данные, на которых бейзлайн обязан проиграть |
| D-11 | Если готовый набор не предоставлен — можно создать синтетические данные по тем же правилам **и описать принятые допущения** | ⭐ прямое разрешение на синтез |

⭐ **D-10 — самое недооценённое требование ТЗ.** Наш демо-набор должен быть спроектирован так,
чтобы разрыв с бейзлайном был заметен невооружённым глазом. Если на демо разница «на 3 %»,
шаг P-07 провалится.

⭐ **D-11 — юридическое основание** для нашего слоя обогащения реальных данных (инженеры, навыки,
транспорт, длительности), которых в выданном датасете физически нет. Обязательное условие —
**описать допущения**.

## 13. Критерии оценки (ТЗ §8) — куда реально утекают баллы

| Критерий | Вес | Что оценивается | Наш ответ (кратко) |
|---|---|---|---|
| **Подход команды** | **25 %** | Понимание задачи, **разумные допущения**, распределение работы, **завершённость сценария** | Явный документ допущений + сквозной сценарий, отрепетированный до секунды |
| **Техническая реализация** | **30 %** | Работоспособность алгоритма, **корректный учёт ограничений**, качество кода | Валидатор плана, который на демо доказывает: ни одно ограничение не нарушено |
| **Соответствие задаче** | **20 %** | Распределение, карта, перепланирование, объяснение | Все 7 шагов P-01…P-07 |
| **Эффективность и удобство** | **15 %** | Кол-во исполнителей, пробег, **понятность интерфейса**, сравнение с бейзлайном | Панель сравнения «мы vs бейзлайн» на одном экране |
| **Презентация** | **10 %** | Ясный рассказ, демонстрация, **ответы на вопросы** | Заготовленные ответы на вопросы жюри |

Обратите внимание: **55 % веса (25 % подход + 30 % техреализация)** не про красоту интерфейса,
а про корректность и осмысленность. При этом «разумные допущения» — прямая строка в критерии
с весом 25 %: наш документ допущений сам по себе приносит баллы.

### 13.1. Пять вопросов, которые жюри задаст обязательно (ТЗ §8.1, дословно)

> 1. **Все ли обязательные ограничения реально проверяются алгоритмом?**
> 2. **Можно ли понять результат без изучения кода?**
> 3. **Корректно ли решение реагирует на изменение в течение дня?**
> 4. **Есть ли сравнение с базовым планированием по двум обязательным метрикам?**
> 5. **Можно ли воспроизвести запуск по README?**

Это не «на что обратят внимание» — это **чек-лист приёмки**. На каждый из пяти вопросов у нас
должен быть не ответ словами, а **кнопка в интерфейсе или строчка в README**:

| Вопрос жюри | Наш материальный ответ |
|---|---|
| 1. Проверяются ли ограничения? | Экран «Проверка плана»: список всех ограничений с ✓ и числом проверенных пар; отдельно — демонстрация нарушения при искусственном отключении проверки |
| 2. Понятен ли результат? | Панель объяснения на естественном языке + подписи на карте; никаких `var_123` в UI |
| 3. Реакция на изменение? | Кнопки трёх событий + экран diff «было → стало» с подсветкой изменений |
| 4. Сравнение с бейзлайном? | Постоянно видимая плашка: исполнителей 8 → 6, пробег 412 км → 297 км |
| 5. Воспроизводимость? | README с тремя командами; фиксированный сид; golden-план в тестах |
