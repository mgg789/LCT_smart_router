# 13. Как ставить задачи агентам-исполнителям

> Два слоя: **метод** (как формулировать задачу так, чтобы агент сделал нужное с первого раза)
> и **готовые карточки** (15 задач с критериями приёмки, зависимостями и порядком).

---

## ЧАСТЬ I. МЕТОД

## 1. Почему агенту нужна другая постановка, чем человеку

Человек-разработчик, получив задачу «сделай учёт транспорта», сам сходит уточнить,
посмотрит соседний код и спросит в чате. Агент не спросит — он **допридумает**.
И допридумает правдоподобно: заведёт свой справочник транспорта, свою структуру ответа,
своё название поля. Через три такие задачи проект расползается.

| Риск агента | Как проявляется | Противоядие в постановке |
|---|---|---|
| Придумывает словари и имена | `vehicle_type: "car"` вместо справочника ТЗ | Выписать все допустимые значения прямо в задаче |
| Пишет новое вместо переиспользования | второй расчёт расстояния рядом с существующим | Указать точный файл и функцию для переиспользования |
| Расширяет объём | попутный рефакторинг, «заодно улучшил» | Явный раздел «вне объёма» |
| Считает задачу сделанной раньше времени | «реализовано» без запуска | Критерий приёмки в виде команды и ожидаемого вывода |
| Молча меняет поведение смежных частей | golden-план поехал | Требование «golden-тест зелёный или объяснено» |

## 2. Анатомия хорошей задачи агенту — 9 обязательных блоков

```
1. ЗАЧЕМ          Требование кейса (ID из 01-case-requirements.md) и бизнес-смысл в одну фразу
2. ЧТО СДЕЛАТЬ    Результат, а не процесс. Одно предложение
3. ГДЕ            Точные файлы: что менять, что читать, что не трогать
4. ЧИТАТЬ ПЕРЕД   Список документов исследования, которые уже содержат решения
5. ЗАФИКСИРОВАНО  Имена, константы, справочники — списком, без права на творчество
6. КАК ПРОВЕРИТЬ  Команда + ожидаемый результат. Проверяемо, а не «должно работать»
7. ВНЕ ОБЪЁМА     Что НЕ делать. Обычно длиннее, чем кажется
8. ГОТОВО КОГДА   Чек-лист Definition of Done
9. ЕСЛИ ЗАСТРЯЛ   Что считать блокером и к кому идти вместо изобретения
```

### 2.1. Блок 5 «Зафиксировано» — самый важный

Это блок, которого обычно нет, и из-за которого потом переделывают.
Для нашего проекта он почти всегда содержит:

| Категория | Что выписывать |
|---|---|
| Справочники ТЗ | навыки 1/2/3, транспорт 1/2/3/4, приоритет 1/2 — **закрытые, менять нельзя** |
| Единицы | время `HH:MM` на границе, минуты от полуночи внутри, километры, широта/долгота |
| Существующие имена | `SolverInput`, `PlanSolution`, `Engineer`, `Request`, `Assignment`, `shift_start_min`, `window_open_min`, `service_min`, `eta_min`… (полный список — `research-inputs/E-existing-core-audit.md`) |
| Веса и константы | Λ₁ = 10⁸, Λ₂ = 10⁶, Λ₃ = 1 за 10 м, Λ₆ = 2000 (из `05-math-model.md` §6.3, §8.3) |
| Числа физической модели | скорости и коэффициенты из `06-physical-travel-model.md` §13 |

### 2.2. Блок 6 «Как проверить» — правило формулировки

❌ Плохо: «должно корректно учитывать временные окна»
✅ Хорошо: «`python -m pytest core/tests/test_windows.py -q` → 12 passed. В тесте есть случай,
где заявка с окном 10:00–12:00 и временем в пути 40 мин от стартовой точки при смене с 11:30
попадает в неназначенные с причиной `UNREACHABLE_IN_WINDOW`»

Разница в том, что второе **нельзя выполнить не сделав**.

### 2.3. Антипаттерны формулировок

| Формулировка | Чем плоха | Замена |
|---|---|---|
| «Сделай красиво» | не проверяемо | макет из `11-ux-and-screens.md` + список состояний |
| «Оптимизируй алгоритм» | нет целевой | «сократи время расчёта до ≤ 10 с на наборе `real`, метрики не хуже текущих» |
| «Добавь поддержку транспорта» | не сказано какого и где | «реализуй C-03 по справочнику ТЗ: 4 значения, проверка только при заданном `vehicle_required`» |
| «Исправь баг с окнами» | неизвестно, в чём баг | «окно ограничивает НАЧАЛО работ (`t_j ≤ l_j`), сейчас ограничивает завершение — исправить, тест добавить» |
| «Сделай, как считаешь правильным» | гарантированный конфликт с проектом | сослаться на документ с решением |

## 3. Правило одного источника истины

У каждого решения должен быть **ровно один документ-владелец**. Агент, получив задачу,
читает документ-владельца, а не переспрашивает и не выводит заново.

| Область решения | Документ-владелец |
|---|---|
| Что требует кейс | `01-case-requirements.md` |
| Продуктовые приоритеты | `02-product-vision.md` |
| Что делать с данными, допущения | `03-data-reality-gap.md` |
| Сущности, инварианты, коды причин | `04-domain-model.md` |
| Формулы, веса, целевая функция | `05-math-model.md` |
| Скорости, коэффициенты, надбавки | `06-physical-travel-model.md` |
| Алгоритм и API солвера | `07-algorithm-design.md` |
| Тексты и структура объяснений | `08-explainability-model.md` |
| Перепланирование и diff | `09-replanning-model.md` |
| Метрики и бейзлайн | `10-metrics-and-baseline.md` |
| Экраны и макеты | `11-ux-and-screens.md` |
| Демо-данные | `12-dataset-design.md` |

**Если агент обнаружил, что документ-владелец неполон или неверен** — он не решает сам,
а сообщает об этом. Изменение документа — отдельное решение, а не побочный эффект задачи.

### T-03 · Матрица времени и расстояния по типам транспорта

| | |
|---|---|
| **Зачем** | C-02 (время), M-02 (пробег) |
| **Что** | Расчёт `δ(u,v)` и `τ_i(u,v)` с учётом типа транспорта инженера |

### T-06 · Минимизация числа задействованных исполнителей

| | |
|---|---|
| **Зачем** | ⚠️ M-01 — **первая обязательная метрика ТЗ**, и сейчас она вообще не оптимизируется |
| **Что** | Добавить фиксированную стоимость задействования исполнителя, согласованную с иерархией весов |
| **Читать перед** | `05-math-model.md` §6.2–6.3 (условия A и B на веса), `07-algorithm-design.md` §3 |
| **Зафиксировано** | Иерархия: заявки ≻ исполнители ≻ пробег. Λ₁ = 10⁸, Λ₂ = 10⁶, Λ₃ = 1 за 10 м. Условие A: `Λ₂ > Λ₃·D̄`. Условие B: `Λ₁ > Λ₂·n + Λ₃·D̄`. **Штраф за неназначение надо поднять согласованно — иначе система начнёт жертвовать заявками ради сокращения бригад.** Это главный риск задачи |
| **Как проверить** | На наборе, где решение возможно и 9, и 7 бригадами, выбирается 7; **число назначенных заявок при этом не уменьшается ни на одну** (отдельный тест); метрика M-01 падает относительно текущего состояния |
| **Вне объёма** | Балансировка нагрузки — она конфликтует с M-01, только как tie-break минимального веса |
| **Готово когда** | Тест «сокращение бригад не ценой заявок» зелёный |

### T-08 · Метрики и панель сравнения

| | |
|---|---|
| **Зачем** | M-01, M-02, R-04, M-05 |
| **Что** | Расчёт всех метрик и корректное сравнение трёх планов |
| **Читать перед** | `10-metrics-and-baseline.md` целиком |
| **Зафиксировано** | M-01 = исполнители с ≥ 1 заявкой. M-02 = пробег по каждому **и** суммарно, без возврата на базу, с выездом из стартовой точки. **Сравнение лексикографическое: заявки → исполнители → пробег.** Обязательны нормированные метрики (пробег на заявку). Режим «при равных условиях» — наш план на подмножестве бейзлайна. Колонка «живой диспетчер» из `Бригада` контрольного файла |
| **Как проверить** | Панель показывает три строки, а не две; при разном числе назначенных заявок сравнение не объявляет победителем того, кто сделал меньше работы |
| **Вне объёма** | Нижние оценки LB — отдельная задача |
| **Готово когда** | Четыре оговорки о корректности сравнения с диспетчером присутствуют в интерфейсе или в документации |

### T-09 · Независимый валидатор плана

| | |
|---|---|
| **Зачем** | Вопрос жюри №1 «все ли ограничения реально проверяются» — материальный ответ |
| **Что** | Модуль проверки инвариантов, **написанный независимо от солвера** |
| **Читать перед** | `04-domain-model.md` §2.3 (I-A1…I-A8), §2.4 (I-P1…I-P3), `10-metrics-and-baseline.md` §7 |
| **Зафиксировано** | Валидатор реализуется **по определениям из ТЗ**, а не по коду модели. Он не должен импортировать логику солвера — иначе повторит его ошибку |

## 6. Правила приёмки работы агента

| Проверка | Почему |
|---|---|
| Запусти сам то, что агент назвал критерием приёмки | «Реализовано» ≠ «работает» |
| Сверь имена полей с `research-inputs/E-existing-core-audit.md` | Расползание контракта — самый дорогой дефект |
| Проверь, что golden-план не поехал молча | Недетерминированность убивает репетицию демо |
| Найди в диффе то, о чём не просили | Побочные изменения = будущие сюрпризы |
| Попроси перечислить, что **не** проверено | Честный список важнее уверенного «всё готово» |

**Правило потолка объёма:** одна карточка = одно логическое изменение.
Если агент просит расширить объём — это новая карточка, а не дополнение к текущей.
