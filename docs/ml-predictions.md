# Предикты ситуации: робастность плана и риск опоздания заявки (2026-09-23)

> Назначение: сухие вероятностные оценки для применённого плана — без ML в критическом
> пути, без внешних вызовов, без мутаций плана. Продолжение позиции `context/08` §5 и
> эксперимента `~/Projects/LCT/ml-lab` (калибровка подтверждена на официальном датасете).
> Статус: ядро, гейтвей и модалка «Метрики плана» на дашборде диспетчера. Бейдж
> риска в карточке заявки и предиктивный алерт — ещё не в интерфейсе.

## 1. Что это и зачем

Симулятор «проживает» применённый план N раз (по умолчанию 300) под реализм-шумом:
режим дня (обычный/дождь/тяжёлый), разброс времён перегонов вокруг точечного прогноза
(`moscow-radial-v1` через `quote_at`), разброс длительностей работ, отмены заявок.
Из N прогонов получаются честные частоты: какая доля дней прошла без единого опоздания,
какая заявка срывается чаще других, какая команда перегружена. Порядок визитов
фиксирован — контур **ничего не перепланирует и не предлагает**, только измеряет.

Ключевое свойство: при нулевом разбросе и нулевых отменах результаты совпадают с
детерминированным расписанием бит-в-бит (тест `core/tests/test_robustness.py`), то есть
«опоздание» в предиктах означает то же, что в плане. Одинаковый вход даёт байт-в-байт
одинаковый отчёт (сид выводится из хеша плана, калибровки и ситуации, не из времени).

Семантика срыва (уточнено 2026-09-24): визит считается сорванным, когда он выходит за
окно **за пределами того же допуска, который принимает сам план**
(`window_lateness_tolerance_sec` + терминальные 20 минут для последнего визита
маршрута). Финиш внутри допуска — принятый планом запас, а не провал дня.

### Полосы светофора: ожидаемые опоздания, а не «дни без срывов»

Доля дней без единого опоздания экспоненциально падает с размером дня: при 50+ визитах
она близка к нулю для любого честного плана, и полоса на ней почти всегда красная —
ровно это и показал демо-стенд. Поэтому диспетчерская шкала — **ожидаемое число
опоздавших заявок**: «меньше одной заявки за день» — зелёный, «до трёх» — жёлтый,
больше — красный (с относительной защитой по доле визитов; `robustness` остаётся в
ответе справочно). Домен полос: `apps/web/src/domain/planQuality.ts`.

Калибровка проверена на контрольном распределении организаторов: симулированные
просрочки реального плана попадают в порядок величин реальных (восток 1 [IQR 0–2]
против 4; ЮВ 12 [10–15] против 6; ЮЦ 2 [1–3] против 0) — без подгонки под цель.

## 1.1 Самокалибровка (2026-09-24)

Параметры разброса живут в `core/predict_calibration.py` (заводские значения —
лабораторные допущения ml-lab). Контур самокалибровки заменяет их измеренными:

- **Данные**: подтверждённые факты исполнения (`request_facts`:
  started/finished/arrived). Длительность работы = `finished − started`; перегон =
  `arrived − finished` предыдущей работы; отмены — по жизненному циклу заявок.
- **Обучение**: остаточный лог-разброс длительностей относительно плановых оценок (σ),
  CV перегонов по бакетам дистанции (<25 км / дальше), частота отмен со сглаживанием
  Лапласа. Режимы дня остаются заводскими, пока нет погодно-связанной истории — это
  честно помечено в `learned_from`/`assumptions`.
- **Гарантия честности**: ниже минимума наблюдений (10 работ) выученная калибровка не
  применяется — работает заводская. Прогресс-бар «Точность самонастройки» в настройках
  AI показывает покрытие фактами (100% ≈ 50 работ + 100 переездов).
- **Хранение**: выученная калибровка — машинно-локальное состояние
  (`predict-calibration.json` рядом с файлом `serve --settings`; по умолчанию
  `.router/predict-calibration.json`, в compose — `/app/state/predict-calibration.json`
  в томе `router-state`). Заводская калибровка — в коде; после смены каталога
  `--settings` старую обученную калибровку нужно перенести отдельно либо обучить заново.
- **Сброс**: полный сброс данных откатывает и модель до заводской (факты удалены, в
  Router пушится factory-документ).
- **По умолчанию**: выключено в dev, включено в production; явный переключатель
  диспетчера в настройках AI старше окружения. Чтение и запись настроек отдают
  последний известный индикатор сразу; пересчёт фактов не держит запрос.

## 2. API Router Core (приватный, `core/robustness.py`)

### `POST /v1/situation-predict`

Тело (pydantic `SituationPredictRequest`):

| Поле | Тип | Описание |
|---|---|---|
| `input_hash` | str(64) | хеш публикации, как в `/v1/manual-evaluation` |
| `router_context_version` | str | CAS контекста; сверяется до и после расчёта |
| `routes` | dict[engineer_id → [request_id]] | фиксированный порядок визитов |
| `simulations` | int 100–2000, default 300 | |
| `as_of` | unix sec, опционально | «сейчас» для прогноза остатка дня |
| `completed` | dict[engineer_id → [request_id]], опционально | факт-префикс маршрута (строгая проверка префикса) |
| `cancel_rate` | float 0–1, опционально | override калибровки отмен (default 0.10 — эмпирика контроля) |

Ответ: `plan` (`robustness` = доля симуляций без срывов — справочная; полосы UI считаются
по `expected_late`/`expected_late_share` относительно `visits_total`), `requests`
(`breach_prob` — доля симуляций с выходом за окно сверх допуска, `expected_late_sec` —
средний сырой перебор окна, `p90_late_sec`, `cancel_rate_sim`), `engineers`
(`overrun_prob` — финал маршрута за пределом смены), `assumptions` (провенанс всех
параметров, включая `source: factory|learned`), `calibration_version`.

### `GET/PUT /v1/config/predict-calibration`

Активная калибровка симулятора. PUT — полная замена документа (`operation_id`,
`expected_version?` — оптимистическая блокировка, `calibration`); несовпадение версии
даёт `409 CALIBRATION_VERSION_CONFLICT`. Используется AI-контуром sys
(`apps/api/src/orchestrator/ai/ai.service.ts`): он считает калибровку из фактов
исполнения и пушит её в Router, когда включено дообучение; при выключенном переключателе
или после сброса данных возвращает заводскую.

Ошибки: `409 PUBLICATION_CHANGED` (CAS, как у manual-evaluation),
`409 UNKNOWN_MANUAL_ENGINEER / INVALID_MANUAL_REQUESTS / EMPTY_PREDICT_PLAN /
COMPLETED_NOT_A_PREFIX`, `422 PREDICT_PLAN_TOO_LARGE`, `503 ACTIVE_PUBLICATION_UNAVAILABLE`.

Семантика окна — как у `RouteEvaluator`: срыв — это финиш позже конца окна **сверх
допуска** (последняя заявка маршрута — с терминальным допуском 20 мин).

Производительность: 300 симуляций × 60 визитов ≈ 55 мс (StraightTravel в конструкции,
кэш цитат по 10-минутным бакетам времени выезда).

## 3. API System Layer (`apps/api`)

### `POST /api/dispatch/predictions/situation` — `@Roles('dispatcher')`

Прозрачный прокс: camelCase-вход (`inputHash`, `routerContextVersion`, `routes`,
`simulations`, `asOf`, `completed`, `cancelRate`) → гейтвей `RouterClient.predictSituation()`
→ core. Ответ — сухие числа, плана внутри нет. Identity-связанность та же, что у
policy-comparison: предикт невозможно приложить к чужой ревизии.

Кто собирает `routes`/`completed`: применённый план (`AppliedPlanService.currentRoster`)
и факты дня — композиция в live-слое; контроллер остаётся тонким.

## 4. UI-дизайн для диспетчера (проект реализации)

Принцип: **ни одного ML-термина**. Никаких «Монте-Карло», «сигм», «вероятностных
распределений» — только «проверили», «риск», «надёжность».

### 4.1 Кнопка «Метрики плана» (между «+» и политикой)

Кнопка открывает модалку. Сверху светофор: «План отличный», «Можно работать»,
«Высокий риск». Ниже цифры плана и некликабельная кнопка «Оптимизировать» — задел
под AI, план она не меняет. Лучшая строка на экране политик помечена «Топ»:
это фиксированная взвешенная оценка уже посчитанного сравнения
политик (покрытие важнее короткой дороги), а до таблицы — правила по симптомам
плана. Уже включённую политику повторно не предлагаем. Запрос уходит только в
момент открытия и только если в плане есть визиты. Номер заявки в тексте — ссылка.
Эскиз карточки:

```
Надёжность дня:  7 из 10 дней — без опозданий      [жёлтая зона]
«Мы мысленно прожили день 300 раз с разным трафиком
 и длительностями работ. Это доля удачных дней».

Слабые места:
 • Заявка #50104 — Кузьминки, окно 12:00–14:00 — опоздает
   в половине вариантов            [показать на карте]
 • Команда 03 — не уложится в смену в 7 днях из 10
```

Пороги-светофор (2026-09-24): по **ожидаемому числу опоздавших заявок** — зелёный
«План надёжный» (<1 заявки и <5% визитов), жёлтый «Можно работать» (≤3 и <12%), красный
«Высокий риск» (остальное). Прежняя шкала «X из 10 дней без опозданий» экспоненциально
жестока на длинных планах и почти всегда показывала красный — именно поэтому заменена.

### 4.2 Бейдж риска в карточке заявки

Показывается **только при высоком риске** (breach_prob ≥ 50%): красная метка
«Высокий риск опоздания» + одна строка человеческим языком: «Если день пойдёт
типично, к 14:00 не успеем». Средний риск (20–50%) — жёлтая точка без текста.
Ниже порога — ничего: интерфейс не шумит.

### 4.3 Предиктивный алерт в LIVE (существующая очередь алертов)

Триггер: предикт ситуации (as_of + выполненный префикс) даёт breach_prob ≥ порога
для ещё не начатой заявки. Алерт формулируется от ситуации, не от модели:

```
Похоже, не успеем: заявка #137 (окно до 16:00)
Команда 07 отстаёт от плана на 25 минут после утреннего пика.
[Перенести на другого] [Сдвинуть окно] [Проверить план заново]
```

Кнопки ведут к существующим жестам (reassign/reorder в MANUAL) — алгоритм действий
уже освоен диспетчером, нового обучения не требуется.

### 4.4 Словарь и правила показа

| Внутреннее | В UI |
|---|---|
| `robustness` | «Надёжность дня: X из 10 дней без опозданий» |
| `breach_prob` | «Риск опоздания: высокий/средний» (только ≥20%) |
| `overrun_prob` | жёлтая точка «смене грозит переработка» на карточке команды |
| `simulations`, σ, CV, калибровка | не показываются (в тултипе «данные расчёта» — для экспертизы) |

Когда пересчитывать: по кнопке + автоматически после применения плана/реплана; в LIVE —
на событиях (старт/финиш/отклонение), не по таймеру. Диспетчер ничего не обязан
делать: контур только информирует (D-11 — система советует, решает человек).

## 5. Честные границы

- Разбросы и режимы — калиброванные допущения (`assumptions` в ответе; валидация
  тремя точками контроля). При появлении реальной истории исполнения — пересчёт
  калибровки, контур не меняется.
- Дальний кластер ЮВ датасета принципиально не помещается в день — предикты это
  показывают (R≈0 при любом плане); это находка для диспетчера, а не баг.
- Обученный в ml-lab GBM-предиктор в контур v1 не входит: MC даёт точные частоты
  дешевле, чем стоит инференс; GBM возвращается как быстрый приближатель, если
  понадобится перерасчёт чаще события.
