# Ручное управление MANUAL — DRO-70

MANUAL передаёт диспетчеру назначения и порядок ещё не начатых заявок. Рабочий план
хранится в PostgreSQL. Router может продолжать расчёт, но его результаты не заменяют
ручные решения. Доступ к System Layer и БД нужен; доступ к Router для ручных операций
не нужен, в том числе до появления первого автоматического плана.

## Как работать

1. В меню политики нажать **«Ручное управление»** и ввести причину. Пустая строка и
   пробелы не принимаются. **«Отмена»** закрывает диалог, оставляя AUTO.
2. В MANUAL открыть **«Управление планом»**. Выбрать инженера. Неначатые заявки можно
   переставлять перетаскиванием или стрелками; заявка другому инженеру назначается
   через селект либо из её карточки.
3. Проверить последствия одного действия: итоговую очередь и предупреждения.
   **«Сохранить ручное изменение»** создаёт новую рабочую ревизию; группового черновика
   с несколькими несохранёнными действиями нет.
4. В **«Журнале ручного управления»** видны переходы, причины, авторы, время и ревизии.
   Журнал читается с сервера, поэтому сохраняется после обновления страницы и рестарта.
5. **«Вернуть AUTO…» → «Подтвердить AUTO»** явно разрешает снова принимать Router.
  До пригодного результата остаётся виден ручной план. Перестроение или выбор политики
  не включают AUTO скрытно.

После возврата в AUTO завершённые визиты могут отсутствовать в новом плане будущих работ.
Общая таблица берёт их исполнителей из сохранённой истории LIVE; действующие назначения
по-прежнему читаются из рабочего плана.

Если другой диспетчер изменил план или инженер начал работу, сервер отклоняет устаревшее
действие. Редактор предлагает **«Обновить план»**, после чего нужно снова проверить
действие. Он не подставляет новую версию за спиной пользователя.

## Что гарантирует сервер

- Переходы и ручные записи проходят под той же блокировкой, что приёмка Router.
  Начало работы и изменение заявки используют согласованный порядок блокировок.
- Переназначение удаляет прежнюю остановку, добавляет её в конец выбранной очереди,
  обновляет назначение и состояние заявки одной транзакцией. Можно назначить и новую
  заявку, которой ещё не было в предыдущем плане.
- Перестановка принимает каждую доступную неначатую заявку ровно один раз. Пропуски,
  повторы и попытки переставить защищённую работу отклоняются. Начатые/завершённые
  работы и нерабочие остановки сохраняют свои места.
- Подтверждённые факты и история не переписываются. Завершённые по правилу молчания
  визиты также защищены. Будущая ETA-бронь при ручной правке освобождается, чтобы прежний
  инженер не смог начать уже переназначенную заявку через старую бронь.
- Проверяются навыки, транспорт, регион, доступность, окна начала и границы смены.
  Предупреждения сохраняются с действием; диспетчер может осознанно принять их.
  Проверка времени использует нижнюю границу без дороги, а не новый оптимизационный расчёт.
- `operationId` обозначает одно намерение. Повтор, включая одновременную доставку,
  возвращает исходный результат без второй ревизии. Другой payload с тем же ID отклоняется.
- Чтение алертов и статуса смены не ожидает внешнюю оценку ручного плана. Оценка выполняется
  в фоне, запросы объединяются, повтор ограничен интервалом 15 секунд. Недоступная оценка
  не считается доказательством ухудшения плана.

## Время, карта и объяснения

Вручную изменённые маршруты имеют `timingStatus: "unverified"`. Числовые значения
расписания и метрик в API остаются архивными; у нового назначения без прежней остановки
временные поля содержат границу клиентского окна и норматив, а не расчёт дороги.
Использовать эти значения как свежий ETA нельзя.
Геометрия старого порядка удаляется. Карта показывает соединение текущих точек и явно
указывает, что дороги после правки не пересчитаны. В дашборде пробег обозначен `—`,
в приложении инженера неначатые визиты — **«Без ETA»**. Фактическое начало/завершение
продолжает отображаться. Таймлайн следует ручной последовательности, не сортирует её
повторно по старому времени и не возвращает переназначенную заявку из запоздавшего LIVE-ответа.

Коды `MANUAL_PLAN` / `MANUAL_ASSIGNMENT` отделяют ручное решение от прежних автоматических
проверок. Исходные объяснения Router остаются в предыдущей неизменяемой ревизии.
LIVE не выводит молчаливое начало/завершение или новый обед из устаревшего ручного расписания.
Явные факты инженера и уже начатый обед сохраняются.

## HTTP-контракт

Все пути ниже имеют префикс `/api/v1/dispatch` и требуют роль диспетчера.

| Метод и путь | Тело / результат |
|---|---|
| `GET /plan` | `mode`, `modeVersion`, `plan.revision` и рабочий план |
| `POST /mode` | `operationId`, `mode`, `expectedModeVersion`, `expectedPlanRevision`, `reason` для MANUAL |
| `POST /plan/reassign` | `operationId`, `requestId`, `engineerId`, обе ожидаемые версии |
| `POST /plan/reorder` | `operationId`, `engineerId`, `requestIds` всех редактируемых работ, обе версии |
| `POST /plan/manual-preview` | То же тело плюс `kind: "reassign" | "reorder"`; возвращает `sourcePlanRevision`, `queues`, `warnings`, `timingStatus`; не пишет план |
| `GET /plan/manual-history` | Последние 100 записей переходов/правок: `at`, `actorId`, `operationId`, `action`, `details` |

`expectedPlanRevision: 0` означает отсутствие первого плана. Для алертов `keep_manual`
и `restore_auto` также обязательны обе версии; причина `keep_manual` проверяется сервером.
Старые клиенты, отправлявшие только `mode` или идентификаторы заявки, нужно обновить.

`409 VERSION_CONFLICT` означает изменившуюся версию; `409 WORK_ALREADY_STARTED` —
защищённое исполнение; `409 MODE_AUTO` — попытку редактирования вне MANUAL.
Неверный состав очереди и пустая причина дают `422 VALIDATION_FAILED`.

Постоянный аудит использует существующий `audit_log`: `control.transition` сохраняет
причину, исходную ревизию и смену режима; `plan.manual` — действие, очереди до/после,
ревизии и предупреждения. Автор, источник и время записаны рядом с `operationId`.
Новая миграция БД для MANUAL не требуется.

## Воспроизводимый набор 4/2

Исходный файл: [`data/demo/manual-control.json`](../data/demo/manual-control.json).
Четыре точки взяты из тех же проверенных узлов графа Восток, которые использует smoke.
Два инженера, автомобиль, навыки подключения/локальных работ/аварий; смена 09:00–18:00,
окна 09:00–16:00, по 30 минут работы. Платные API карт не нужны.

В исходном JSON дата **24.09.2026**. Для прогона в другой день сформировать файл с датой
локального стенда — иначе LIVE создаст текущий день без соответствующих смен:

```powershell
pnpm --filter api test:build
New-Item -ItemType Directory -Force artifacts | Out-Null
node apps/api/dist-test/scripts/manual-demo.js 2026-09-21 | Set-Content -Encoding utf8 artifacts/manual-control-today.json
```

Без аргумента генератор использует сегодняшнюю дату Москвы. Он только создаёт JSON в stdout;
не подключается к API, не сбрасывает данные и не читает пароли. Загрузить файл через
дашборд в отдельный пустой локальный контур. Инженерам привязать тестовые адреса через
карточки сотрудников; для локальных кодов нужен `AUTH_DEV_EXPOSE_CODES=true` в тестовом
окружении. Для полного дня за 30 реальных минут задать `speed_up_work_stub=1800`
**до начала дня**. Начать день диспетчером, затем сразу вывести обоих инженеров на линию.
