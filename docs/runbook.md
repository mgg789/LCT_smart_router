# Runbook — запуск, тесты и диагностика

## Запуск скачанного пакета через лаунчер

Для отдельной локальной установки используйте четыре входа из `launch/`:
Windows GUI/консоль и Unix GUI/консоль. Мастер проверяет Python/Tkinter, Docker,
целостность пакета, занятые порты и доступную версию. Существующий экземпляр
можно перезапустить с сохранёнными настройками или изменить его параметры.
Обычное удаление сохраняет БД; удаление данных требует отдельного подтверждения.
Установки из разных папок получают отдельные Compose-проекты.

Подготовка офлайн-образов, управление экземпляром и приватные файлы `.launch/`:
[launcher.md](launcher.md). Публичная версия релиза и PIN-пакет настроек:
[distribution.md](distribution.md). Границы фактической проверки платформ:
[launcher-validation.md](launcher-validation.md).

Redis-beta в лаунчере включён по умолчанию и по-прежнему помечен как
экспериментальный. Он кэширует каталог политик и ответы route3.
`--no-redis-beta` возвращает обычный режим с сохранением БД. Размер кэша и
выключатель — в дашборде, «Настройки → Основные». Подготовка образа для
офлайн-контура, диагностика отказа и замеры: [redis-beta.md](redis-beta.md).

## Подготовка LIVE-проверки

Спецификация и шаги: [live.md](./live.md). Для локального демо в `.env`:
`speed_up_work_stub=1800` (плановый день за 30 минут) или `3600` (за час),
`AUTH_DEV_EXPOSE_CODES=true` при `NODE_ENV=development`. В production выдача
демо-кодов запрещена. Пустая скорость означает обычные часы. Новая скорость
применяется к новому дню.

Публичный стенд `navix.droidje.com` включает `DEMO_STAND=true` и
`speed_up_work_stub=1800` только в серверном `.env`. Тогда API само поддерживает
сегодняшний набор 14 заявок / 3 инженера, сдвигает окна на текущую дату Москвы
и по окончании дня или кнопке «День заново» возвращает исходный набор, снимая
почту инженеров. Сессия диспетчера сохраняется. Локальный compose этого стенда
включает `DEMO_STAND` по умолчанию, чтобы день с заявками поднимался сам. Код входа
при этом виден, если в `.env` стоят `NODE_ENV=development` и
`AUTH_DEV_EXPOSE_CODES=true`. На публичном хосте `NODE_ENV=production`, и код в ответ
не попадает.

Локальный compose включает `DEMO_STAND=true` по умолчанию, поэтому после
`pnpm compose:up` день 14 заявок / 3 инженера поднимается автоматически. Для
пустого обычного контура перед запуском явно задайте `DEMO_STAND=false`. Затем
воспроизводимый день можно загрузить так:

```powershell
pnpm --filter api test:build
node apps/api/dist-test/scripts/live-demo.js
```

Скрипт использует учётные данные диспетчера из окружения/`.env`, не выводит их,
отказывается очищать существующие заявки и допускает только loopback-адрес.
`LIVE_DEMO_BASE_URL` меняет адрес локального API, `LIVE_DEMO_DATE` — дату набора.
Границы — 09:00–20:00 Москвы; старт дня скрипт не нажимает.
Почту инженеру привязать через реестр инженеров диспетчера; вход — `/engineer/`.

LIVE API объединяет одновременные проходы координатора и HTTP-чтений в один
`advanceOnce` (single-flight). Чтение инженера вычисляет только его проекцию,
а не состояния всей бригады. Это устраняет очередь одинаковых транзакций на
`live_workdays FOR UPDATE`; браузерский лимит 12 секунд не увеличен.
Для проверки переходов без браузера используется `test/integration/live.test.ts`
на отдельной тестовой БД. Не направлять этот тест в рабочий стенд: он очищает LIVE-проекции.

## 2. Первый запуск

```bash
git checkout dev && git pull
cp .env.example .env          # затем задать DISPATCHER_EMAIL и DISPATCHER_PASSWORD (≥8 символов)
pnpm install --frozen-lockfile
pnpm compose:up               # docker compose -f infra/docker-compose.yml up -d --build
```

Затем:

```bash
pnpm compose:ps               # postgres healthy, api healthy
curl localhost:8000/health/live
curl localhost:8000/health/services
```

Интерактивная документация API: <http://localhost:8000/docs>.
Машинночитаемая схема: <http://localhost:8000/docs/openapi.json>.
Дашборд диспетчера: <http://localhost:5173> (сервис `web` в контуре).

`health/services` сообщает реальное состояние каждой интеграции. `router` пингует
Router Core, который контур запускает отдельным сервисом (порт 8100, читает
опубликованный снимок под read-only ролью в БД); `ai` сообщает `not_configured`.
`smtp` — `not_configured` без `SMTP_HOST`, иначе проба внешнего контура
(см. [smtp.md](./smtp.md)). Диспетчер входит паролем независимо от почты. Клиенту
и инженеру для входа по одноразовому коду нужен SMTP либо локальный
`AUTH_DEV_EXPOSE_CODES=true` при `NODE_ENV=development`; в production код в ответ
не выдаётся. Отказ почты не отменяет сохранённые заявки и план.

## 3. Повседневные команды

| Команда | Что делает |
|---|---|
| `pnpm compose:up` | Собрать и запустить контур в фоне |
| `pnpm compose:logs` | Следить за логами контейнеров |
| `pnpm compose:down` | Остановить контур, сохранив том данных |
| `pnpm --filter api build` | Скомпилировать сервис через `tsc` и проверить актуальность OpenAPI |
| `pnpm --filter api test` | Собрать `src` + `test` и прогнать последовательно под `node:test` |
| `pnpm --filter api typecheck` | Только типы, без вывода |
| `pnpm --filter web dev` | Дашборд в dev-режиме на 127.0.0.1:5173 (vite) |
| `pnpm --filter web test` | Тесты дашборда (vitest) |
| `pnpm lint` | Biome, i18n, OpenAPI и пороги покрытия тестами API/web |
| `pnpm format` | Переформатировать файлы через Biome; команда пишет изменения |

Запуск сервиса вне Docker, против базы из compose:

```bash
pnpm install --frozen-lockfile
pnpm --filter api exec prisma generate
pnpm --filter api build
node apps/api/dist/src/main.js
```

Переменные окружения, относящиеся к ядру (все опциональные, см. `.env.example`):
`ROUTER_BASE_URL` (где шлюз ищет Router Core; в compose — `http://router:8100`),
`ROUTER_BUDGET_MS` (начальный CLI-бюджет ядра в Compose; по умолчанию 6000 мс),
`ROUTER_POLL_INTERVAL_MS` (период чтения результата Router шлюзом, по умолчанию 500 мс),
`ROUTER_REQUEST_TIMEOUT_MS` (HTTP-таймаут шлюза, по умолчанию 3000).

Router Core имеет собственный CLI (`solve`, `serve`, `benchmark`, `bench-suite`,
`geocode`, `project`, `export-map`, `prepare-2gis`) и отдельный генератор схем
`python -m core.schema`. Офлайн-ресурсы, быстрый старт
и acceptance-бенчмарки: [core/README.md](../core/README.md). Сервис `router` в
контуре запускается как `serve --official-regions east southeast south_central`
с durable-технастройками в томе `router-state`.

Планирование дня сначала получает пакетную автомобильную матрицу `/matrix2?planning=1`
с временными режимами прогноза, затем выполняет поиск только по подготовленным данным
в памяти. В compose адрес Router-процесса задаётся `ROUTER_ROAD_API_URL` (по умолчанию
`http://road-api:8123`); для API-геометрии приоритетен `API_ROAD_API_URL` (по умолчанию
`http://road-api:8123`), а `ROUTER_ROAD_API_URL` остаётся legacy-fallback при отсутствии
явного API-адреса. У переменных разные задачи: Router получает матрицу до поиска, API
запрашивает полилинию выбранного плеча после него. При недоступности матрицы используется подготовленный региональный
граф с сохранённым происхождением стоимости. Автомобильный граф вендорен в
`services/route-engine3/graphs/car/` и
поднимается вместе с контуром двумя сервисами compose:
`osrm` (граф MLD в tmpfs) и `road-api` (HTTP `/route2`). Отдельно:

```bash
docker compose -f infra/docker-compose.yml up -d osrm road-api
```

Подробнее — [services/road-api/README.md](../services/road-api/README.md).

Повторный запрос матрицы читает локальный кэш; при отказе сервиса остаётся
подготовленный региональный граф. Внутри поиска HTTP-вызовов нет.
Для полностью автономного чтения этого кэша задайте процессу Router
`ROUTER_ROAD_API_OFFLINE=true`. После смены карты или модели прогноза увеличьте
`ROUTER_ROAD_API_MAP_VERSION`. Точная линия запрашивается основным бэкендом после готового
плана, до четырёх рёбер сразу. Пока `road-api` не отвечает (граф ещё прогревается),
на карте остаётся пунктир; отказ сокета повторяется через несколько секунд, а
настоящая дорога и честная прямая за МКАД держатся часами. Пока фаза роутера
`building` или `error`, это видно в уведомлении. Вход, запись почты инженера и
статусы не ждут ни дорожный запрос, ни блокировку приёмки плана.

System one (`/v1/choice`, `/v1/noul`) ищется по `JEV_API_URL`. На машине
разработчика это `jev-local` на хосте (`http://host.docker.internal:12444`). На
демо-стенде — сервис compose `sys1` (`services/sys1`, в сети compose
`http://sys1:12444`, наружу не публикуется): он отвечает тем же контрактом через
зеркало OpenRouter; задаются `SYS1_LLM_BASE_URL`, `SYS1_MODEL` (по умолчанию
`typesafe/jev-1.13`), токен — `LLM_PROXY_TOKEN`. Без `SYS1_LLM_BASE_URL` `sys1`
отвечает 503, и короткие AI-вызовы сообщают `not_configured`.

## 4. Загрузка датасета

При `DEMO_STAND=false` обычный контур стартует пустым; Compose по умолчанию
включает демо 14/3. В дашборде используйте подготовку импорта с просмотром
замечаний перед подтверждением. Прямой API-импорт одного, нескольких или всех
регионов организаторов:

```bash
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/dispatcher/password   -H 'content-type: application/json'   -d '{"email":"dispatcher@example.test","password":"<пароль из .env>"}' | jq -r .token)

# один регион
curl -s -X POST localhost:8000/api/v1/dispatch/data/import   -H "authorization: Bearer $TOKEN" -H 'content-type: application/json'   -d '{"operationId":"'$(uuidgen)'","region":"east"}'

# всё сразу (205 заявок, 35 инженеров: east + southeast + south_central)
curl -s -X POST localhost:8000/api/v1/dispatch/data/import   -H "authorization: Bearer $TOKEN" -H 'content-type: application/json'   -d '{"operationId":"'$(uuidgen)'","regions":"all"}'
```

Регионы: `east`, `southeast`, `south_central` (`regions` принимает и явный список).
Опциональный объект `engineerCountPerRegion` ограничивает число бригад по регионам
(потолок выше фактического числа бригад датасета — ошибка 422). Импорт атомарен по
всем запрошенным регионам.

**Геокод-пакет обязателен.** Файл `data/dataset/geocoded/<регион>.json` должен
существовать и покрывать каждый адрес заявки плюс депо; файлы монтируются в контейнер
read-only, так что обновлённый пакет не требует пересборки. Импортированные заявки
получают реальные адресные точки (геокоды LocationIQ/Nominatim из пакета 2026-09-29
с записанным происхождением), а окна бенчмарка ребейсятся на живой горизонт —
датасет от 17.08 планируется от «сейчас» без правки CSV. Опубликованная задача и её диагностика:
`GET /api/v1/dispatch/debug/snapshot`.

## 5. Данные и перезапуски

`docker compose down` сохраняет именованный том `postgres-data`, поэтому обычный
перезапуск хранит бизнес-данные, рабочий план, режим управления и обеденные факты
(`context/43` §11.3).

`docker compose down -v` уничтожает этот том. **Это не «полный сброс» приложения.**
Продуктовый сброс — подтверждаемое действие диспетчера со своим объёмом и
пост-условиями (`context/37` §9.4); удаление тома просто стирает базу и никому об
этом не сообщает.

## 6. Диагностика

**Контейнер `api` сразу перезапускается.** Окружение не прошло валидацию. Первая
строка лога называет каждый проблемный ключ. Сверьте `.env` с `.env.example`.

**`Cannot find module .../typescript/bin/tsc` при сборке образа.** Хостовый
`node_modules` попал в контекст сборки. `.dockerignore` его исключает; проверьте,
что файл не удалили — `node_modules` pnpm — дерево симлинков в локальный стор,
внутри контейнера оно бесполезно.

**`pnpm install --frozen-lockfile` падает в образе.** `package.json` и
`pnpm-lock.yaml` разошлись. Выполните `pnpm install` на хосте и закоммитьте
обновлённый lockfile; не ослабляйте флаг — его смысл в том и состоит, чтобы падать
на расхождении.

**Порт занят.** Переопределите `API_PORT`, `ROUTER_PORT`, `POSTGRES_PORT` или
`WEB_PORT` в `.env`. Postgres и router остаются на `127.0.0.1`. На демо-хосте MGG
живой ремап: `API_PORT=18080` и `ROUTER_PORT=18100`; compose привязывает API к
`127.0.0.1` (`docs/ci.md`).

**Health-эндпоинты отвечают, а функциональности нет.** Сверьтесь с таблицей блоков
в [architecture.md](./architecture.md) §2 и списком контрактов в §5.

## 7. Почему тесты идут последовательно

`--test-concurrency=1` — намеренно. У System Layer есть настоящие глобальные
синглтоны — строка AUTO/MANUAL и указатель на опубликованный снимок — и именно они
объект нескольких тестов. Параллельный запуск файлов против одной базы заставляет
каждый файл наблюдать публикации соседей: корректный в изоляции набор падает
случайно. Отдельная база на файл позволила бы параллельность; пока это не стоит
настройки, честнее последовательное исполнение, чем ослабленные проверки.

Родственная ловушка при написании тестов: каждый timestamp — целая секунда, поэтому
«самая свежая строка» неоднозначна, когда две строки записаны в одну секунду.
Определяйте строку по её собственному id или уникальному для неё значению, никогда
по `orderBy: { createdAt: 'desc' }`. Два перемежающихся падения случились именно
из-за этого.

При заданном `TEST_DATABASE_URL` тестовый bootstrap использует его как `DATABASE_URL`
и не читает локальный `.env`. Остальные обязательные тестовые параметры
(`DISPATCHER_EMAIL`, `DISPATCHER_PASSWORD`, `NODE_ENV=test`) передаются явно.
Используйте отдельную одноразовую БД: часть сценариев сбрасывает бизнес-данные.

## 8. Smoke-гейт

Предпочтительный воспроизводимый запуск — одноразовый контур, который сам
применяет миграции, выполняет smoke, браузерные сценарии и проверку отказа Router:

```bash
pnpm test:regression
```

На Windows запускайте из Git Bash либо `pnpm.cmd test:regression`, если Git Bash
доступен в PATH. `C:\Windows\System32\bash.exe` — вход WSL и не является Git Bash.
В PowerShell можно явно указать установленный Git Bash:

```powershell
& 'C:\Program Files\Git\bin\bash.exe' scripts/ci/run-regression.sh
```

Результаты и очистка временных ресурсов — `artifacts/regression/<run-id>/`.
Для отдельного smoke уже поднятого одноразового контура выполните `pnpm smoke`;
`SMOKE_BASE_URL` должен указывать именно на его API.

`pnpm smoke` (AGENTS.md §11.1) прогоняет весь хребет по HTTP против **работающего
контура**, а не в процессе: проверяется тот артефакт, который реально поставляется —
миграции применены, конфигурация прочитана, датасет смонтирован, каждый сервис
достижим.

Проверки по порядку: контур жив и готов; диспетчер входит без SMTP; данные
сбрасываются; активна политика из каталога; синтетический восточный сектор
публикуется; Router считает и sys принимает первый план;
все заявки в состоянии `assigned`; затем **событие** — срочная заявка через
`POST /api/v1/dispatch/requests` — публикует новый сектор и даёт вторую
принятую ревизию, в которой срочная заявка назначена. Это шаг 6 демо ТЗ
(одно событие перестраивает день). В UI то же событие показывают отключением
инженера; в smoke — срочной заявкой, потому что для неё уже есть API.

**Смоук деструктивен**: сначала он сбрасывает данные приложения, поэтому ему место
на контуре разработки или демо и нигде больше. `SMOKE_BASE_URL` указывает на другой
адрес вместо `http://localhost:8000`.

## 9. Подготовка резервного показа

Полное описание режимов, карты, диагностики и проверок:
[Резервный показ и диагностика](./demo-fallback.md).

Перед демонстрацией:

1. При доступной сети установить зависимости и собрать `apps/web`:
   `pnpm --filter web build`.
2. Запустить локальный просмотр:
   `pnpm --filter web preview --host 127.0.0.1 --port 5186 --strictPort`.
3. Открыть `http://127.0.0.1:5186/?demo=1`, проверить карту и переключение сценариев.
   Для первого открытия без интернета локальный сервер должен оставаться запущенным.
4. Если планируется резерв через кеш сайта, заранее дождаться загрузки приложения и
   локальной карты, затем проверить reload без сети в отдельном тестовом браузере.
5. В обычном режиме заранее войти и загрузить рабочий план. Его резервная копия
   привязана к сессии текущей вкладки; после выхода или истечения сессии она недоступна.

При сбое API сначала остаётся сохранённый рабочий план для просмотра. Для продолжения
подготовленного рассказа явно выбрать «Открыть демо». «Вернуться к серверу» снова
загружает рабочие данные; учебные изменения на сервер не отправляются.

Если улиц не видно, проверить подпись карты и готовность локального источника.
При наличии сети можно выбрать «Повторить онлайн-карту». Сохранённый OSM-набор
покрывает район демонстрационных точек; за его границами полнота подложки не обещана.
Не повторять неподтверждённую операцию записи до сверки состояния на сервере.
Для передачи ошибки разработчику открыть «Диагностика» и скопировать её сведения.

## Месячные отчёты NAVIX (22.09.2026)

Применить миграции rewards и категории `dispatcher_monthly_report`, затем обычную
сборку API: `pnpm --filter api build`. Она копирует встроенные TTF-шрифты из
`src/notifications/assets` в `dist/src/notifications/assets`; PDF работает без сети.
Шрифты получены из уже используемых в вебе Inter WOFF2; конвертация не нужна на сервере.

Координатор при запуске и раз в час проверяет календарный месяц Москвы. Первый запуск
инициализирует курсор текущим месяцем; после его окончания создаются замороженный
отчёт и по одному письму каждому диспетчеру с включёнными уведомлениями. После простоя
пропущенные месяцы догоняются. Идемпотентность — месяц + получатель.
Письмо использует существующие SMTP-настройки. Без настроенного SMTP намерение остаётся
в `pending_submission`; `accepted_by_server` подтверждает приём почтовым сервером,
а не доставку в ящик. Ошибка подготовки PDF сохраняет письмо для повторной попытки.

В `DEMO_STAND=true` автоматическая рассылка отключена; PDF можно скачать вручную.
В тестах координатор не запускает таймер. «День заново» очищает тестовый журнал баллов
вместе с данными дня. Продовый сброс данных не использовать для месячного обнуления: оно
происходит выборкой нового месяца и сохраняет историю. Методика: `docs/performance.md`.

`pnpm test:regression` использует Bash 4+ (`${run_id,,}`). На macOS с системным Bash 3.2

smoke-набор во время входа. Логи и браузерные артефакты — в игнорируемом
`artifacts/regression/<run-id>/`.

Границы готовности к выкладке:

- Удаление учётных данных из файлов не отзывает их и не очищает историю Git.
  Действующий ранее опубликованный пароль должен заменить владелец стенда.
- Приложение не доверяет произвольному `X-Forwarded-For`. До явной настройки
  доверенных прокси пользователи за общим reverse proxy делят IP-бюджет; для
  нескольких API-процессов нужен общий внешний лимитер. См. [api.md](./api.md).
- Production, SMTP и живые LLM-провайдеры в этом аудите не проверялись и не менялись;
  нагрузочный прогон и восстановление production из резервной копии не выполнялись.
- Vite сообщает о крупном JS-бандле; Python-зависимости выдают предупреждения
  об устаревающих API. Это зафиксированные ограничения, а не пропущенные падения тестов.
