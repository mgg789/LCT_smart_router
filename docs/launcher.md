# Лаунчер Navix

В `launch/` четыре точки входа:

| Платформа | Окно | Консоль |
| --- | --- | --- |
| Windows | `windows-gui.cmd` | `windows-shell.cmd` |
| Linux / macOS | `unix-gui.sh` | `unix-shell.sh` |

Нужны Python 3.10+, Docker с Compose и полный пакет с данными. Для окна нужен
Tkinter (Linux: python3-tk, macOS/Windows: Python с Tcl/Tk). Это переносимые
лаунчеры, а не установщики Python и Docker. Проверка зависимостей объясняет,
чего не хватает; настройки системы автоматически не меняются.

## Первый запуск

Распакуйте пакет в отдельную доступную для записи папку. В Windows откройте
нужный .cmd; в Unix выполните `sh launch/unix-gui.sh` или
`sh launch/unix-shell.sh`. Мастер проверяет целостность исходников, Docker,
сервис дистрибуции и доступную версию, затем предлагает настройки запуска.

Full запускает UI, API, БД и планировщик. Headless исключает UI и требует порт
API; MCP доступен на нём по /api/v1/mcp. В Full публикация API необязательна:
UI использует внутренний nginx. Все опубликованные порты слушают только
127.0.0.1. Занятый чужим процессом порт обнаруживается до изменения контейнеров.

OSRM включается отдельно. Без него расчёт использует комплектные региональные
графы, а неметро-геометрия отображается схемой между концами плеч. Автозапуск
задаёт Docker restart policy unless-stopped; сам Docker в ОС он не запускает.

Redis-beta — отдельный экспериментальный флажок, изначально выключенный. Он
сохраняется в настройках и меняется при перезапуске. Кэш может повторно использовать
каталог сравнения политик после перезапуска Router при неизменном входе и контексте.
Обычный расчёт новых входов от этого не ускоряется. Подробности и замеры:
[redis-beta.md](redis-beta.md).

Настройки получают по PIN с https://distribute.droidje.com, импортируют из .env
или вводят вручную. При первоначальной настройке почта и пароль диспетчера
запрашиваются отдельно и имеют приоритет над credentials из пакета. Значения
.env не исполняются как shell. Поддерживаются обычные имена переменных, в том
числе speed_up_work_stub; подстановки и команды не выполняются.

Недоступность сервиса дистрибуции не означает отсутствие всей сети: получение
PIN-пакета недоступно, но режим запуска по-прежнему выбирает оператор. При ошибке
сертификата TLS проверка не отключается и новые сведения о версии не принимаются.

## Версия и целостность

Версия пакета хранится в launch/release.json. Лаунчер отдельно читает публичный
GET /navix/version, не передавая PIN. Старый пакет показывает установленную и
доступную версии и ссылку на опубликованный релиз. Самообновления нет.
Недоступная проверка не блокирует запуск; сохранённые сведения явно подписаны
датой прошлой проверки, а не выдаются за свежие.

При упаковке опубликованного релиза оператор задаёт его фактическую версию:

```sh
python3 -m launch.update_manifest --version 1.7.0
```

Без --version команда обновляет только хеши. В рабочей ветке channel=development
обозначает сборку разработки на базе указанной версии. Она не объявляется
актуальным стабильным релизом и не сравнивается как более старый prerelease.
При явной упаковке с --version канал становится release.
manifest.json покрывает перечисленные исходники и ресурсы сборки. Переводы
строк LF/CRLF в текстовых файлах не считаются повреждением; бинарные ресурсы
проверяются побайтно. Хеши не заменяют подпись издателя.

Имена подготовленных Docker-образов включают отпечаток фактических входов сборки.
Это позволяет повторно использовать образы того же пакета и не запускать старый
код другого пакета в офлайн-режиме. После изменений исходников обновляйте манифест.

## Существующая установка

При следующем открытии видны состояние и действия: запуск с сохранёнными
настройками, изменение настроек, удаление экземпляра или полное удаление данных.
Состояния различают работающий, остановленный, частично подготовленный экземпляр
и удалённый экземпляр с сохранёнными данными. Недоступный Docker обозначается
ошибкой проверки, а не отсутствием установки.

У каждой новой установки свой Compose-проект `navix-launch-<id>`, случайные
пароли БД и метки принадлежности контейнеров/томов. Старый проект navix-launch
распознаётся только вместе с его локальной конфигурацией и identity-файлом.
Смена режима или порта сохраняет базу. Одновременные операции GUI и консоли
блокируются файловой блокировкой; после сбоя процесса её освобождает ОС.

При изменении настроек пустой пароль сохраняет собственный ранее введённый пароль.
Смена email может создать другой аккаунт диспетчера по существующим правилам API;
для сохранения профиля оставьте прежнюю почту.

Обычное удаление останавливает и удаляет контейнеры/сети экземпляра, сохраняя тома
данных и настройки для повторного запуска. Полное удаление требует ввода
`DELETE <имя-проекта>` и удаляет только повторно проверенные собственные тома и
известные файлы состояния. Docker, Python, исходный пакет и общие образы не удаляются.
Ни одна операция не выполняет глобальный prune.

Консольные действия (Windows: py -3, Unix: python3):

```sh
python3 -m launch.cli --action status --offline
python3 -m launch.cli --action start
python3 -m launch.cli --action configure
python3 -m launch.cli --action remove
python3 -m launch.cli --action purge
```

Удаление требует интерактивного подтверждения. --action start допускает явные
переопределения режима, портов, OSRM, Redis-beta и автозапуска. --offline имеет приоритет над
сохранённым онлайн-режимом и исключает обращения к дистрибуции при подготовке.

## Офлайн и локальное состояние

Первая сборка требует сети. До переноса в закрытый контур подготовьте образы
онлайн, затем перенесите их через docker save / docker load вместе с тем же
пакетом и геоданными. Лаунчер перечисляет недостающие образы; офлайн-запуск не
выполняет pull/build. Можно запускать OSRM офлайн, если его образ и граф подготовлены.

Для Redis-beta заранее подготовьте также образ Redis, указанный в Compose.
Отсутствующий или неисправный Redis не блокирует базовые сервисы: показывается
предупреждение, каталог считается обычным способом. Redis слушает только внутри
сети установки; у него нет опубликованного порта или постоянного тома. Пароль
хранится в собственном identity.json и сохраняется при переключении режима.

Офлайн-контур отключает AI и внешние интеграции, изолирует сеть backend-контейнеров
и ограничивает запросы браузера через CSP. UI использует локальную карту. Если
публикуется API, отдельный gateway соединяет опубликованный порт с внутренней сетью.

В игнорируемом .launch/ сохраняются identity, настройки, разрешённый Compose и
диагностика. Эти файлы содержат секреты и не предназначены для публикации.
В Windows используйте папку с доступом только своей учётной записи. Не копируйте
.launch в другую папку как способ создания второй установки: проверка принадлежности
это отклонит. Потеря identity при сохранённой БД требует восстановления файла,
а не генерации новых паролей поверх существующих данных.

Сбой Docker возвращает путь к .launch/docker.log; лог может содержать настройки.
Проверка готовности опубликованных loopback-портов обходит системный HTTP-прокси,
не меняя настройки прокси пользователя.

## Проверки

```sh
python3 -m unittest discover -s launch -t . -v
python3 -m unittest discover -s services/distribution -v
```

GUI-тестам нужен нативный Tk display; в Linux CI подходит Xvfb. Проверки без
дисплея и фактический запуск ОС различаются в отчёте. Результаты чистого запуска,
переключений и сохранения данных: [проверка лаунчера](launcher-validation.md).
