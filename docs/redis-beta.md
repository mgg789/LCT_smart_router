# Redis-beta: экспериментальный кэш каталога

Режим выключен по умолчанию. Он сохраняет рассчитанный каталог сравнения политик
между процессами Router на короткое время. Основной план, авторизация, AI-чаты и
бизнес-состояние не переносятся в Redis.

## Почему выбран каталог

Исходный профиль без Redis на официальном East66: 10 918,6 мс wall,
10 916,9 мс CPU и 299 812 КиБ peak RSS. Из этого covering занял 6169 мс.
При этом повторное чтение в живом Runtime уже обслуживается локальным кэшем.
Поэтому проверяемая гипотеза ограничена повторным открытием того же каталога
после перезапуска процесса. Новая публикация, другой контекст или новый бюджет
всё равно требуют обычного расчёта.

Дорожные провайдеры уже имеют постоянные кэши матриц; исходный профиль не дал
оснований заменять их Redis. Сессии, rate limiting, AI-чаты и pub/sub не включены
в этот эксперимент: для них нет измеренного узкого места в выбранном сценарии.

## Контракт кэша

- Порядок чтения: текущий кэш Runtime → Redis → обычный полный расчёт.
- Одна запись содержит семь политик с полными планами и сводкой. Незавершённый
  расчёт не записывается. Запись атомарна; формат JSON, без pickle.
- Ключ включает namespace установки, версию кода/зависимостей/Python, идентификатор
  публикации, SHA-256 точных входных байтов, контекст Router, бюджет и хеш дорожного
  графа с полными настройками поиска. Ключ не содержит адресов и других полей заявок.
- TTL по умолчанию 600 с, допустимый диапазон 1–86400 с. Переключение входа или
  контекста даёт другой ключ; старый истекает. Нет глобального FLUSHALL.
- Namespace лаунчера: `<installation-id>:<package-fingerprint>`. Пароль отдельный
  для установки, хранится в `.launch/identity.json`, не попадает в API-контейнер.
- Максимальный размер записи 8 МиБ. Целостность проверяется HMAC-SHA256 с ключом
  установки и привязкой к ключу записи, затем Pydantic проверяет структуру, контекст
  и соответствие сводок планам. Это защита от повреждения/подмены кэша, не шифрование
  хранимых маршрутов.
- При отказе чтение ограничено connect/read timeout 150/250 мс без повторов;
  выполняется обычный расчёт. Неудачная запись не прерывает ответ. Предупреждения
  ограничены по частоте и не выводят URL, пароль или данные задач.
- Перед выдачей Runtime повторно проверяет актуальность публикации и контекста.
  Чтение сравнения не меняет рабочий план и не запускает операцию выбора политики.

У внешних дорожных провайдеров остаётся действующее требование обновлять версию
карты при смене ресурса. Redis не может обнаружить незаявленное изменение удалённой
карты за тем же endpoint/version.

## Запуск и отказ

В GUI включите Redis-beta; в консоли выберите его в мастере или выполните:

```sh
python3 -m launch.cli --action start --redis-beta
python3 -m launch.cli --action start --no-redis-beta
```

Выбор сохраняется. При отключении останавливается только Redis этой установки;
БД и её пароли сохраняются. При повторном включении пароль Redis не меняется.
Redis без постоянного тома: после пересоздания кэш холодный. Это ожидаемо.

Compose-профиль `redis-beta` содержит Redis 8.2 с зафиксированным digest,
лимитом памяти контейнера 192 МиБ, `maxmemory 128mb`, `allkeys-lru`, без AOF/RDB
и без host-порта. Процесс работает от пользователя redis, filesystem read-only,
`/data` — ограниченный tmpfs. Доступ только во внутренней сети установки.
Router не зависит от healthy Redis для своего запуска.

Для ручного Compose задайте `REDIS_PASSWORD`, `ROUTER_REDIS_BETA=true`,
`ROUTER_REDIS_URL=redis://:<URL-encoded-password>@redis:6379/0`, уникальный
`ROUTER_REDIS_NAMESPACE`, затем включите профиль `--profile redis-beta`.
Секреты держите в приватном `.env`; пример в репозитории пустой.

В офлайн-контур перенесите образ Redis вместе с образами приложения. Если образ
не подготовлен или Redis не запускается, лаунчер предупреждает и запускает
основные сервисы. Планирование и каталог работают обычным способом.

## Воспроизведение измерений

Нужны Windows PowerShell, Docker и подготовленная лаунчером установка с Redis-beta.
Из корня той же версии исходников:

```powershell
./infra/benchmark-redis.ps1 -InstallationRoot 'F:\Navix' `
  -OutputDirectory 'F:\Navix-bench-results' -Repeats 3 -BudgetMs 1000
```

Используйте отдельный пустой каталог результатов для каждого набора.
Каждый trial — новый Linux-контейнер с лимитами 2 CPU / 1536 МиБ, той же версией
Python и зависимостей. Исходники монтируются read-only. Контейнер читает официальный
East66 и поднимает настоящий внутренний HTTP API с ProcessPool-решателем.
Redis off и холодный miss меняются местами между повторами; hit следует за miss
с тем же уникальным namespace. Пять следующих запросов измеряют уже локальный
кэш того же Runtime. Дополнительно измеряются `/v1/result-status`, `/v1/result`,
время от загрузки данных до готового основного плана, cgroup CPU/peak memory всего
дерева процессов и Redis INFO CPU/RSS до и после каждого trial.

Время готовности не включает импорт Python, Docker pull/build и создание
контейнера. Cgroup CPU включает координатор и solver subprocess, Redis учитывается
отдельно. Сумма пиков — верхняя оценка, не одновременно измеренный пик всей системы.
Фоновая нагрузка хоста не контролируется, поэтому малые различия не объявляются
ускорением. Это измерение внутреннего API на локальном графе, не end-to-end задержки
публичного стенда, OSRM или браузера.

Скрипт сохраняет сырые JSON каждого trial и manifest. Сравниваются полные планы,
сводки, вход, граф и версия кода; исключаются только `computed_at`, `calculation_ms`
и случайный `result_id`. Несовпадение прекращает успешное завершение набора.

Для проверки тайм-аутов в отдельной тестовой установке выполните тот же скрипт
с `-Outage -Repeats 1` и другим каталогом результатов. Он временно ставит только
Redis выбранной установки на `docker pause` и снимает паузу в `finally`.
Новый Router не имеет локального кэша, поэтому проверяется настоящий fallback,
а не ответ из памяти. Ожидаются два отказа кэша (чтение/запись), обычный успешный
HTTP-ответ и те же semantic digests, что в наборе off/miss/hit.

## Результат 28.09.2026

Windows, Docker Engine 29.7.2, Python контейнера 3.14.7, Intel Core Ultra 7 265KF.
Docker доступно 20 CPU / 16 567 869 440 байт RAM; каждый trial ограничен 2 CPU /
1536 МиБ. Бюджет каталога 1000 мс, strict windows, остальные настройки одинаковы
и сохранены в JSON. Этот бюджет отличается от штатных 8000 мс в Compose; результат
не экстраполируется на другой бюджет или объём данных.

Проверено 3 повтора каждого режима и отдельный отказ Redis. Одинаковый отпечаток
исходников `a273a5b5abf8472af1d8`, входа, графа, активного плана, семи полных планов
каталога и сводки подтверждён во всех десяти процессах. Runtime-image предоставляет
одинаковые зависимости, исходники trial монтируются из проверяемой рабочей версии.
Сырые файлы и [машиночитаемая сводка](benchmarks/redis-beta-20260928/summary.json)
хранятся в `docs/benchmarks/redis-beta-20260928/`.

| Измерение | Redis off | Redis on, холодный miss | Redis on, готовая запись |
| --- | ---: | ---: | ---: |
| Готовность основного плана, медиана | 6,02 с | 5,36 с | 5,69 с |
| Первый HTTP-запрос каталога, медиана | 14,13 с | 11,54 с | 0,57 с |
| Диапазон первого запроса | 12,17–14,72 с | 11,54–12,09 с | 0,55–0,74 с |
| Повторный запрос в том же процессе, медиана 15 запросов | 496 мс | 425 мс | 431 мс |
| CPU на первый запрос каталога | 14,68 с | 11,94 с | 0,53 с |
| CPU процесса и его дочерних процессов за trial | 25,03 с | 19,97 с | 9,15 с |
| Пик памяти дерева процессов Router | 707,76 МиБ | 720,09 МиБ | 565,84 МиБ |
| RSS отдельного Redis | 20,83 МиБ | 20,97 МиБ | 21,56 МиБ |
| CPU отдельного Redis за trial | 0,094 с | 0,078 с | 0,051 с |
| `/v1/result-status`, p95 из 60 запросов | 1,82 мс | 1,47 мс | 1,44 мс |
| `/v1/result`, p95 из 30 запросов | 165,98 мс | 170,08 мс | 42,74 мс |

CPU/память в таблице — медианы трёх trials. CPU trial считается между первым и
последним снимками cgroup; p95 — nearest rank по объединённым запросам.
Redis оставался запущен на протяжении набора, включая off, чтобы использовать
один сервер для следующих miss/hit. В off приложение к нему не обращалось; строка
RSS/CPU показывает фоновую стоимость этого тестового сервера. В обычной установке
`--no-redis-beta` его останавливает.

**Подтверждённый выигрыш:** готовый каталог после смены процесса при точном
совпадении входа — около 24,8 раза по медиане HTTP и 27,6 раза по CPU выбранного
запроса. Здесь не выполняется повторный поиск. Пик Router вместе с отдельно
измеренным RSS Redis оценивается сверху примерно в 587,4 МиБ; пики не синхронны.

**Без доказанного выигрыша:** запуск основного плана, холодный каталог, повторные
чтения живого Runtime и обычные result/status API. Miss всё равно выполняет полный
поиск. Наблюдаемая разница off/miss и отдельные выбросы p95 зависят от фоновой
нагрузки; три повтора не позволяют приписать их Redis. Для тёплого Runtime уже
действует локальный кэш, поэтому Redis не участвует в повторном запросе.

**Цена и ухудшения:** отдельные ~21 МиБ RSS Redis; при холодном кэше пик Router
выше на ~12 МиБ, с Redis суммарная верхняя оценка примерно 741 МиБ против 708 МиБ
одного Router. Появляются операции сериализации, проверки целостности и сетевого
чтения/записи. При зависании Redis добавляются ограниченные тайм-ауты. В отдельном
outage trial запрос занял 12,32 с, зарегистрировано два отказа кэша, обычный ответ
и все semantic digests совпали; Redis после проверки восстановлен в healthy.

Качество: пять фиксированных политик назначили 59/66 заявок, из них 9/13 срочных;
FIFO — 27/66 и 1/13; covering — 66/66 и 13/13 с разрешённым добавлением ресурса.
Совпадение полных маршрутов и всех сводок важнее этих сокращённых чисел: оно
проверено отдельно и ускорение не получено ослаблением ограничений.

Рекомендация остаётся экспериментальной: включать для повторного чтения того же
каталога после рестартов, если запись ещё жива. Новый вход или пересоздание Redis
обнуляет эту пользу. Оснований включать Redis по умолчанию по этим данным нет.

## Интеграционная проверка установки

Windows-консоль переключила Full online + Redis → Headless offline без Redis →
Full offline + Redis. Идентичность, пароль Redis и контрольная запись PostgreSQL
сохранились. В off контейнер Redis не работал; в on он healthy, `6379/tcp` не
опубликован на хосте. В обоих режимах `pnpm smoke` прошёл 21/21.

Через настоящий `/api/v1/dispatch/policy-comparison` проверен тот же каталог после
рестарта Router: ответ совпал полностью, Redis `keyspace_hits` вырос на один.
Намеренно остановленный Router при устаревшем кэше technical settings не завершает
API; сохранённые настройки возвращаются HTTP 200, после восстановления каталог
снова доступен. [Санитизированный результат](benchmarks/redis-beta-20260928/installed-api-probe.json).
В этой проверке исправлен ранее существовавший необработанный отказ фонового
обновления настроек API; регрессионный тест сначала воспроизвёл сбой, затем прошёл.

Проверки кода: 318 тестов ядра, 27 тестов лаунчера на Windows и Linux/Tk/Xvfb,
5 тестов distribution на Linux, 13 тестов HTTP-клиента Router, Ruff всего `core`,
Ruff лаунчера/distribution, Pyright изменённых Python-модулей, Biome изменённых
TypeScript-файлов. Полный интерактивный GUI→Docker прогон, macOS и публичное
развёртывание distribution остаются ограничениями [DRO-153](launcher-validation.md).
