# Гайд по интеграции: свои клиентские и инженерные приложения поверх API

> Для внешних разработчиков, которые встраивают LCT Smart Router в свои продукты:
> подключают своё клиентское приложение (заявки), своё приложение инженера (рабочий день
> и факты) или свой дашборд. Всё, что умеет наш интерфейс, доступно программно — с теми
> же правилами, проверками и журналом операций (`context/41`).
>
> Смежные документы: [api.md](./api.md) — полный каталог эндпоинтов и конвенций;
> OpenAPI-схема — `GET /docs/openapi.json` на работающем бэкенде, интерактивно — `/docs`;
> пример клиента без зависимостей — [`examples/external-api-client.mjs`](../examples/external-api-client.mjs).

---

## 1. Две модели подключения

Выберите модель по тому, как аутентифицируются пользователи **вашего** приложения:

| | **Модель А — «по id»** | **Модель Б — «по сессии»** |
|---|---|---|
| Когда выбирать | У вашего приложения **своя аутентификация**: вы сами знаете, какой клиент или инженер действует | Вы хотите использовать **нашу аутентификацию**: вход по email + одноразовому коду |
| Учётные данные запроса | API-токен (`Authorization: Bearer <токен>`) | Токен сессии, полученный обменом кода (`Authorization: Bearer <токен сессии>`) |
| Как определяется субъект | **Явно в запросе**: `clientEmail` для клиентских действий, `engineerId` для инженерных | **Из сессии**: субъект — владелец учётной записи; передавать `clientEmail`/`engineerId` запрещено (403) |
| Чьи это функции | Категория токена решает, что можно делать; объект выбирает payload | Роль сессии (client / engineer / dispatcher) решает, что можно делать |
| Для чего подходит | Встраивание в существующие системы: колл-центр, CRM, мобильное приложение подрядчика, мониторинг | Своё приложение с нашим входом: клиент заказал услугу в вашем UI, но логинится у нас |
| Ключевое правило | Токен принадлежит диспетчеру и **не** является пользователем: id в запросе выбирает объект, а не «авторизует» пользователя (`context/41` §3.2) | Роль выдаётся, а не заявляется: код по адресу инженера работает, только если диспетчер создал этого инженера (`context/36` §7) |

Модели можно комбинировать в одной системе: например, заявки принимать в вашем UI по
модели А (токен колл-центра), а инженеров подключить по модели Б (они входят нашими кодами).

## 2. Шаг 1. Получение токена (модель А)

Токены создаёт **диспетчер** — из дашборда или по API.

### В дашборде

Вкладка **Настройки → API-токены → «Создать токен»**: название, тип, срок действия
(«никогда» или дата сгорания). После создания показывается секрет — **один раз**.
Скопируйте его и передайте разработчику интеграции по защищённому каналу; больше он
нигде не показывается, в базе лежит только SHA-256-хэш.

### По API (из своего пайплайна)

```bash
# Вход диспетчера (пароль из конфигурации развёртывания)
curl -s -X POST https://<host>/api/v1/auth/dispatcher/password \
  -H 'content-type: application/json' \
  -d '{"email":"dispatcher@example.test","password":"…"}'
# → {"token":"<сессия диспетчера>","role":"dispatcher","expiresAt":…}

# Создание токена
curl -s -X POST https://<host>/api/v1/auth/tokens \
  -H "authorization: Bearer $DISPATCHER_SESSION" -H 'content-type: application/json' \
  -d '{"name":"Мобильный клиент Билайн","category":"client_eng","expiresAt":1790979599}'
# → {"id":"…","name":"…","category":"client_eng","createdAt":…,
#    "expiresAt":1790979599,"token":"RVN5KuLi…"}   ← секрет виден только здесь
```

### Типы токенов и что они открывают

| Тип | Категории функций | Типичное применение |
|---|---|---|
| `client` | клиентские | своё приложение заказчика |
| `eng` | инженерные | своё приложение бригады / подрядчика |
| `client_eng` | клиентские + инженерные | один ключ на оба своих приложения |
| `master` | клиентские + инженерные + **диспетчерские, админские и системные/отладочные** | интеграция дашборда, колл-центр «видит всё», отладка |

Правила:

- Срок действия: `expiresAt` — целые секунды Unix; не указан или `null` — **никогда**.
  Дата в прошлом отклоняется (`VALIDATION_FAILED`); истёкший токен перестаёт работать
  так же, как отозванный (401).
- Полный доступ **внутри категории**: никаких под-скоупов и разрешений на отдельный
  эндпоинт не существует (`context/41` §6.1).
- Ключи `client`/`eng`/`client_eng` **не** получают диспетчерских функций; `master`
  получает всё.
- Перечисление (`GET /api/v1/auth/tokens`) показывает метаданные, но никогда не
  повторяет секрет. Отзыв — `DELETE /api/v1/auth/tokens/:id` из сессии диспетчера
  (сам токен отзывать ключи не может).
- Потеряли секрет — отзовите ключ и создайте новый. Это штатный путь, а не авария.

**Хранение у интегратора:** секрет равнозначен паролю диспетчера внутри своей категории.
Держите его в секрет-хранилище, не в коде и не в репозитории, не кладите в URL и не
пишите в логи запросов (`context/41` §12).

## 3. Модель А — «по id»

Каждый запрос несёт токен и **явно называет объект**:

- клиентские действия — `clientEmail` (адрес заказчика, от имени которого создаётся
  заявка);
- инженерные действия — `engineerId` (идентификатор инженера, чей день/профиль/факты).

Адрес, которого ещё нет в системе, создастся при первой заявке так же, как это делает
сам диспетчер. `engineerId` должен существовать: инженеров создаёт диспетчер
(`POST /api/v1/dispatch/engineers`), и без профиля в системе действовать от его имени
нельзя.

Сессиям, наоборот, передавать `clientEmail`/`engineerId` **запрещено** — сессия всегда
действует от своего владельца. Это защита от подмены субъекта, а не ограничение.

Проверить, что за вами стоит токен и что он может:

```bash
curl -s https://<host>/api/v1/auth/session -H "authorization: Bearer $TOKEN"
# → {"kind":"api_token","source":"external_api","role":"client",
#    "roles":["client","engineer"],"accountId":null,"tokenCategory":"client_eng"}
```

## 4. Модель Б — «по сессии»

Вход выполняется одноразовым кодом на адрес электронной почты:

```bash
# 1. Запросить код (ответ одинаков для известного и неизвестного адреса)
curl -s -X POST https://<host>/api/v1/auth/login-code \
  -H 'content-type: application/json' -d '{"email":"client@example.test"}'
# → {"email":"client@example.test","expiresAt":…}

# 2. Обменять код на сессию
curl -s -X POST https://<api-host>/api/v1/auth/login-code/verify \
  -H 'content-type: application/json' \
  -d '{"email":"client@example.test","code":"123456","role":"client"}'
# → {"token":"<токен сессии>","role":"client","expiresAt":…}
```

- `role` — какой контур вы открываете: `client`, `engineer`, `dispatcher`.
- Клиентская учётная запись создаётся при первом успешном входе. Инженером войти «по
  желанию» нельзя: роль инженера выдаёт только диспетчер.
- Код живёт ограниченное время, принимается один раз и перестаёт работать после
  нескольких неверных вводов. В продакшене код доставляется письмом; поле `devCode`
  в ответе существует только в dev-контуре без SMTP.
- Сессия конечна (`expiresAt`); выход — `DELETE /api/v1/auth/session`.
- В сессии **не передавайте** `clientEmail`/`engineerId`: субъект берётся из сессии.
  Передача чужого адреса — 403.

## 5. Сценарий: своё клиентское приложение (модель А)

Полный жизненный цикл заявки без нашего UI:

```bash
TOKEN="<client- или client_eng/master токен>"

# 1. Справочник видов работ (код работы определяет навык и длительность — их выбирает
#    система, не пользователь)
curl -s https://<host>/api/v1/client/work-types -H "authorization: Bearer $TOKEN"
# → {"workTypes":[{"code":"connection_request","title":"…"}, …]}

# 2. Подготовить заявку (черновик). clientEmail — чья это заявка
curl -s -X POST https://<host>/api/v1/client/requests \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{
    "operationId":"0c9fd52a-…-uuid",
    "clientEmail":"client@example.test",
    "contactName":"Иван Петров",
    "addressText":"Москва, Пресненская наб., 12",
    "workType":"connection_request",
    "windowStartAt":1790985600,
    "windowEndAt":1790996400,
    "urgent":false
  }'
# → {"request":{"id":"…","version":1,"lifecycle":"draft", …}}

# 3. Подтвердить содержимое и отправить (черновик не планируется — только отправленная
#    заявка попадает в задачу планирования)
curl -s -X POST "https://<host>/api/v1/client/requests/$ID/submit" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"operationId":"<новый uuid>"}'
# → {"request":{…,"lifecycle":"submitted","assignmentState":"pending", …}}

# 4. Активные заявки этого адреса
curl -s "https://<host>/api/v1/client/requests?clientEmail=client@example.test" \
  -H "authorization: Bearer $TOKEN"

# 5. Перенос окна по той же заявке (до начала работ)
curl -s -X POST "https://<host>/api/v1/client/requests/$ID/reschedule" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"operationId":"<новый uuid>","windowStartAt":…,"windowEndAt":…}'
```

Что важно знать:

- **`operationId` — ваш ключ повторa.** Один и тот же `operationId` с тем же телом
  повторяет первый исход без повторной работы: потеряли ответ на таймауте — просто
  повторите запрос. Тот же id с **другим** телом — `OPERATION_ID_REUSED` (409), это
  баг вызывающей стороны. Генерируйте UUID v4 на каждое новое намерение.
- **Жизненный цикл:** `draft → submitted → in_progress → completed` (или `cancelled`).
  Черновик ничего не делает: не публикуется, не пишется в план, писем не порождает.
- **`assignmentState` — отдельная ось:** `pending` (ожидает актуального плана),
  `assigned`, `in_progress`, `done`, `unassigned`. `pending` — это не отказ: идущий
  пересчёт или недоступность Router не превращают заявку в «отклонённую».
- Пользователь выбирает только вид работы, адрес и окно. Навык, длительность,
  оборудование — система выводит сама; `urgent` может поднять приоритет и никогда не
  опускает.
- После старта работ заявка закрывается для переносов и отмен: `WORK_ALREADY_STARTED`.
- Отмена до старта: `POST /api/v1/client/requests/:id/reschedule` для переноса,
  отмена — через диспетчерский контур (`POST /api/v1/dispatch/requests/:id/cancel`,
  нужен `master`).
- Координаты (`lat`/`lon`) можно не передавать: заявка сохранится с пометкой «ждёт
  геокодирования» и попадёт в планирование после того, как система получит точку.
  Координаты никогда не выдумываются.

## 6. Сценарий: своё приложение инженера (модель А)

```bash
TOKEN="<eng-, client_eng- или master-токен>"
ENG="<engineerId — идентификатор инженера в системе>"

# Профиль инженера
curl -s "https://<host>/api/v1/engineer/profile?engineerId=$ENG" -H "authorization: Bearer $TOKEN"

# Текущий день: смена, доступность, обед (первое обращение создаёт день)
curl -s "https://<host>/api/v1/engineer/day?engineerId=$ENG" -H "authorization: Bearer $TOKEN"

# Выход на линию / офлайн
curl -s -X POST https://<host>/api/v1/engineer/availability \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{\"operationId\":\"<uuid>\",\"engineerId\":\"$ENG\",\"availability\":\"online\"}"

# Техническая остановка 15 минут
curl -s -X POST https://<host>/api/v1/engineer/technical-break \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{\"operationId\":\"<uuid>\",\"engineerId\":\"$ENG\"}"

# Обед: фактический старт и возврат
curl -s -X POST https://<host>/api/v1/engineer/lunch/start \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{\"operationId\":\"<uuid>\",\"engineerId\":\"$ENG\"}"
curl -s -X POST https://<host>/api/v1/engineer/lunch/finish \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{\"operationId\":\"<uuid>\",\"engineerId\":\"$ENG\"}"

# Рабочий план этого инженера: его маршрут, остановки, карточки заявок маршрута
curl -s "https://<host>/api/v1/engineer/plan?engineerId=$ENG" -H "authorization: Bearer $TOKEN"

# Одна заявка маршрута
curl -s "https://<host>/api/v1/engineer/requests/$REQ?engineerId=$ENG" \
  -H "authorization: Bearer $TOKEN"

# Факты исполнения (система фиксирует время, отклонения и риски следующих заявок)
curl -s -X POST "https://<host>/api/v1/engineer/requests/$REQ/facts" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{\"operationId\":\"<uuid>\",\"engineerId\":\"$ENG\",\"kind\":\"arrived\"}"
# kind ∈ arrived | arrived_blocked | started | finished | problem
```

Что важно знать:

- **Все действия проходят через общие системные проверки.** Нельзя взять тех-паузу
  дважды, начать обед вне дня, отметить факт по чужой схеме — ответы будут теми же,
  что и в нашем UI.
- `engineerId` обязателен в каждом вызове модели А и должен существовать
  (несуществующий — `NOT_FOUND` 404).
- Факты `arrived` / `started` / `finished` двигают исполнение заявки;
  `arrived_blocked` — честное «на месте, но начать нельзя»; `problem` — проблема с
  комментарием. Время можно передать (`occurredAt`, секунды Unix) или довериться
  серверному «сейчас».
- **Смена и обед задаются диспетчером** (`POST /api/v1/dispatch/engineers/:id/workday`),
  не приложением инженера. Приложение сообщает факты, а не редактирует нормативы.
- Изменение профиля (навыки, транспорт, стартовая точка) из приложения инженера —
  `PATCH /api/v1/engineer/profile` c `engineerId`. Смена адреса входа
  (`/engineer/email-change*`) — только по нашей сессии (модель Б), у ключа нет аккаунта.
- План работает от **применённого** плана системы (AUTO — автоматического, MANUAL —
  ручного). Прямого доступа к сырым результатам Router нет и не будет.

## 7. Сценарий: свой дашборд / колл-центр (`master`)

`master`-токен открывает диспетчерский контур: день целиком, планы и причины, политики,
данные и отладку.

```bash
TOKEN="<master-токен>"

# Весь день: включая начатые, завершённые и отменённые заявки
curl -s "https://<host>/api/v1/dispatch/requests" -H "authorization: Bearer $TOKEN"

# Применённый план и режим управления (auto/manual)
curl -s "https://<host>/api/v1/dispatch/plan" -H "authorization: Bearer $TOKEN"

# Создать заявку от имени клиента (то же, что client prepare+submit, но одним вызовом)
curl -s -X POST https://<host>/api/v1/dispatch/requests \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"operationId":"<uuid>","clientEmail":"…","contactName":"…","addressText":"…",
       "workType":"connection_request","windowStartAt":…,"windowEndAt":…,"urgent":false}'

# Объяснения: почему заявка без назначения
curl -s "https://<host>/api/v1/dispatch/requests/$ID/history" -H "authorization: Bearer $TOKEN"

# Политики планирования и активная
curl -s "https://<host>/api/v1/dispatch/policies" -H "authorization: Bearer $TOKEN"
```

Полный каталог — в [api.md](./api.md) §5–§10. Границы, которые не исчезают ни с каким
токеном:

- **Разрушительный сброс данных** (`data/reset`) и подтверждаемые действия требуют
  сессии диспетчера из дашборда — токен не заменяет человеческое подтверждение.
- **Внешних AI-вызовов нет даже у `master`**: чат с моделью не входит в API
  (`context/41` §9).
- Все записи идут через один конверт операций и попадают в журнал с пометкой источника
  `external_api` — разбор инцидентов видит, каким ключом что сделано.

## 8. Общие правила вызовов

| Правило | Что делать |
|---|---|
| **Времена — секунды Unix** | Все абсолютные метки и длительности — целые секунды Unix (`context/33` §4). Никаких ISO-строк и миллисекунд. Окна заявок — `windowStartAt`/`windowEndAt` |
| **`operationId` на каждую запись** | UUID на одно бизнес-намерение. Повтор безопасен и возвращает первый исход; тот же id с другим телом — `OPERATION_ID_REUSED` |
| **`expectedVersion` при правках** | Если действие опирается на прочитанное состояние, передайте `version` объекта. Кто-то изменил объект раньше вас — `VERSION_CONFLICT` с `currentVersion`: перечитайте и подтвердите заново. Молчаливых перезаписей нет |
| **Ошибки — один конверт** | `{"error":{"code","message","details","requestId"}}`. Код — контракт: `UNAUTHENTICATED` 401 (нет/просрочен/отозван токен), `FORBIDDEN` 403 (категория/роль не та; сессия пытается подменить субъект), `NOT_FOUND` 404, `VALIDATION_FAILED` 422 (в `details.issues` — пути полей), `VERSION_CONFLICT`/`OPERATION_ID_REUSED`/`WORK_ALREADY_STARTED` 409, `MODE_MANUAL`/`MODE_AUTO` 409 (планом владеет другой режим), `SERVICE_NOT_CONFIGURED` 503 |
| **`requestId` для поддержки** | Передавайте свой `X-Request-Id` — он вернётся в ошибке и попадёт во все логи запроса |
| **Таймауты и повторы** | Повторять безопасно любой запрос с тем же `operationId`. Чтения (`GET`) идемпотентны сами по себе |
| **Очередь планирования** | В AUTO запись с действительным триггером формирует новую задачу планирования; Router обнаруживает её сам. Реакция на изменение — не мгновенный ответ в том же HTTP-вызове, а новый применённый план, который видно через `GET /dispatch/plan` |

## 9. Безопасность

1. **Токен — секрет.** Храните в секрет-хранилище; не в коде, репозитории, JSON на
   диске без шифрования, логах и аналитике.
2. **Только заголовок.** `Authorization: Bearer …`, никогда не в URL — URL попадает в
   журналы доступа и историю браузера.
3. **Минимальная категория.** Приложению заявок не нужен `master`: берите `client`.
   Комбинированный `client_eng` — для случая двух своих приложений с одним хранилищем
   секретов.
4. **Ограниченный срок.** Для интеграций с известным жизненным циклом задавайте
   `expiresAt` — сгорание страхует забытый ключ лучше любой памятки.
5. **Ротация = создать новый + отозвать старый.** Отзыв мгновенно останавливает новые
   вызовы и ничего не удаляет из истории.
6. **TLS обязателен** на любом контуре, доступном извне; токен в открытом канале
   эквивалентен паролю.
7. **`devCode` не бывает в продакшене.** Поле выдачи кода в ответе `login-code`
   существует только в dev-контуре без SMTP; в продакшене приложение с ним не
   стартует.

## 10. Чеклист интеграции

- [ ] Выбрана модель: «по id» (токен) или «по сессии» (наш вход), либо комбинация
- [ ] Диспетчер создал токен нужной категории и разумного срока; секрет передан защищённо
- [ ] `GET /auth/session` возвращает ожидаемые `roles` для токена
- [ ] Клиентский сценарий: `work-types` → `prepare` (с `clientEmail`) → `submit` → `list`
- [ ] Инженерный сценарий: `profile`/`day`/`availability` (с `engineerId`) → `facts`
- [ ] `operationId` генерируется на каждое намерение; повторы после таймаута — с тем же id
- [ ] `expectedVersion` передаётся в правках; `VERSION_CONFLICT` обрабатывается перечтением
- [ ] Обработаны коды 401/403/404/409/422/503 из конверта ошибок
- [ ] Токен не пишется в логи и не попадает в URL
- [ ] Известен план отзыва: `DELETE /auth/tokens/:id` из сессии диспетчера

Вопросы и разбор ошибок: прикладывайте `requestId` из ответа — по нему находится вся
цепочка в журнале операций.
