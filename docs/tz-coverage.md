# Как ядро закрывает официальное ТЗ

Источник требований — официальный PDF кейса (9 страниц, упрощённая постановка;
полный разбор — `context/31-official-case-dataset.md`, «Обезличенный» датасет
организаторов в `data/Датасет/`). Документ идёт по каждому пункту ТЗ и показывает
**как именно** он закрыт в Navix: какой механизм, какие компоненты, где проверить.
Проверяемое ядро и его границы — [core-and-extensions.md](core-and-extensions.md);
сценарий проверки — [tz-acceptance.md](tz-acceptance.md); всё сверх ТЗ —
[features.md](features.md).

## 1. Загрузка данных (CSV/JSON или демо-набор)

**Требование:** читать тестовые данные; форматы организаторов — CSV `cp1251` с
разделителем `;`, один рабочий день 17.08.2026, три региона.

**Как решено:** импортёр канонизирует файлы организаторов с явным декодированием и
обработкой всех известных аномалий датасета (пустые строки, пустые окна, окна
`0:01–23:59` = весь день, пустой район, дробные адреса «д. 128 к 5»). Справочник
инженеров, которого нет в датасете, синтезируется из контрольного распределения
бригад (11–13 на регион), навык выводится из типа работ HD (16 типов → 3 навыка ТЗ),
срочность — из типа («Авария», «Нет линка»). Координаты — из офлайн-геокод-каталога.
Поверх — панель табличной загрузки CSV/TSV/XLSX с сопоставлением колонок и
предпросмотром; готовые демо-наборы — `data/samples/`.
**Где:** дашборд → «Загрузка данных»; импортёр — `apps/api/src/orchestrator/imports/`,
ядро импорта — `core/official.py`.

## 2. Распределение заявок по квалификации и доступности

**Требование:** требуемый навык заявки входит в навыки инженера (у заявки один навык,
у инженера 1–3); учитывается доступность/смена.

**Как решено:** жёсткая проверка на уровне планировщика: `required_skill ∈ skills`
инженера, доступность против смены и горизонта (`release_at`), регион. Проверка не
декларируется, а выполняется при каждом кандидате — и независимо перепроверяется
валидатором готового плана. Оптимизация: OR-Tools 9.15 + собственный детерминированный
ограниченный поиск (вставка + локальная оптимизация), целевая функция лексикографическая —
сначала покрытие (срочные → обычные), затем число задействованных исполнителей и пробег.
**Где:** ядро — `core/schedule.py` (`eligible`, `_matches_static_constraints`),
`core/engine.py`; перепроверка — `validate_plan`; тесты ограничений — `core/tests/`.

## 3. Порядок посещения адресов

**Требование:** для каждого инженера — порядок посещения адресов.

**Как решено:** маршрут инженера — упорядоченный список остановок с плановым временем
прибытия, начала и конца работы, ожиданием и обедом; порядок выбирается оптимизатором
(вставка + локальное улучшение), а не порядком поступления.
**Где:** дашборд → маршрут инженера (таймлайн + список остановок); данные —
`EngineerRoute.stops/legs` в `core/contracts.py`.

## 4. Маршруты и точки заявок на карте

**Требование:** визуализировать маршруты и точки на карте.

**Как решено:** точки заявок и дорожная геометрия плеч (вендоренный граф МКАД +
OSRM-профили, подложка всех официальных регионов) рисуются для каждого инженера;
маршрут — по улицам, не пунктирной хордой. Метки навыков и статусов на точках.
**Где:** дашборд → карта дня; геометрия — `core/export.py`, `docs/web.md`.

## 5. Краткая информация по плану: кто, куда, в какое время

**Требование:** видеть по плану исполнителя, адрес и время.

**Как решено:** карточка инженера: смена, число заявок, пробег, таймлайн с временем
каждой остановки; карточка заявки: инженер, плановое время, окно, статус. Всё из
опубликованного плана, без пересчёта на клиенте.
**Где:** дашборд → список инженеров и заявок.

## 6. Перепланирование после события

**Требование:** одно событие на выбор — срочная заявка / отмена заявки / инженер
недоступен.

**Как решено:** все три типа событий поддержаны и замерены: публикация события →
мгновенный пересчёт ограниченным поиском → показ диффа → применение. Срочная заявка
повышает приоритет при перепланировании; отмена освобождает слот; офлайн бригады
перераспределяет её хвост дня. На бенчмарках перепланирование занимает доли секунды
и сохраняет 52–84% назначений дня неизменными.
**Где:** дашборд → «Заявки» (срочная, отмена), «Инженеры» (недоступен); SSE-обновления;
замеры — [benchmarks/solver-suite](benchmarks/solver-suite-20260928/README.md), §события.

## 7. Объяснение человеческим языком

**Требование:** почему заявка у этого инженера, какие ограничения учтены, почему такой
маршрут; для неназначенной — явная причина.

**Как решено:** каждое назначение сопровождается структурированными факторами ядра
(навык, запас по окну, дорога, альтернативы и коды причин отказа у кандидатов), из
которых собирается человеческая формулировка; AI-кнопка пересказывает те же факты
языковой моделью. Неназначенные заявки получают явную причину из словаря ТЗ:
нет исполнителя на время / нет навыка / нет транспорта / не влезает в окно или смену.
**Где:** дашборд → карточка заявки/инженера → «Почему»; неназначенные — жёлтая панель;
`core/evidence.py`.

## 8. Ровно три обязательных ограничения

| Группа ТЗ | Как проверяется в Navix |
|---|---|
| Квалификация | `required_skill` должен входить в навыки инженера — жёсткая фильтрация кандидатов; заявка с уникальным навыком остаётся неназначенной с причиной «нет навыка» |
| Время | работа + время в пути укладываются в смену инженера; начало работы внутри окна заявки. Режим «Строгие окна ТЗ» (по умолчанию для новых настроек) — без допусков; мягкие допуски включаются явно |
| Ресурс (транспорт) | тип транспорта инженера = требуемый тип заявки, **если требование указано явно**; в официальном CSV колонки требования нет — и алгоритм не выдумывает её из типа работ (задокументированная граница) |

Все три проверяются при отборе кандидатов и повторно — валидатором готового плана;
регресс-тесты покрывают отказ по каждой из групп.

## 9. Две обязательные метрики и сравнение с базовым вариантом

**Требование:** минимизировать количество задействованных исполнителей; показывать
пробег по каждому и суммарный; сравнивать с базовым вариантом, определённым ТЗ
(заявки по порядку поступления → первому подходящему инженеру, без оптимизации).

**Как решено:** FIFO-бейслайн встроен как точный режим «базового варианта» и
показывается рядом с оптимизированным планом на тех же данных, том же штате и тех же
ограничениях. Обе метрики — в панели метрик и сравнения политик: задействованные
исполнители, пробег по каждому инженеру и суммарный. Замер на официальном датасете
(Восток, продуктовые допуски): FIFO закрывает 28 из 66 заявок силами всех 12 бригад,
Navix — 62 из 66 тем же штатом.
**Где:** дашборд → «Политики» → сравнение с FIFO; [benchmarks/solver-suite](benchmarks/solver-suite-20260928/README.md).

## 10. Единицы, допущения и допустимые упрощения

**Требование:** время HH:MM, длительности и пути в минутах, расстояние в км,
координаты lat/lon; расстояние допускается считать упрощённо (гаверсинус × коэффициент)
с описанием допущения; доказывать математический оптимум не требуется.

**Как решено:** единицы соблюдены на границах API; гаверсинус × коэффициент остаётся
как fallback-провайдер, но рабочие планы считаются по дорожным временам (OSRM-граф +
калибровка против реальных поездок: отклонение от Яндекс Карт ±8%, запас планирования
×2,4). Оптимальность не декларируется: отличаем доказанный отказ от ненайденного
назначения, зазор к точному оптимуму измерен на микро-инстансах.
**Где:** `core/geo.py` (fallback), [benchmarks/roads-vs-yandex](benchmarks/roads-vs-yandex-20260929/README.md),
[benchmarks/solver-suite](benchmarks/solver-suite-20260928/README.md) §точный перебор.

## 11. Пять вопросов экспертов из ТЗ — короткие ответы

1. **Ограничения реально проверяются?** Да: фильтрация кандидатов + независимый
   валидатор плана + регресс-тесты по каждой группе ограничений.
2. **Результат понятен без изучения кода?** Да: объяснения на карточках, причины
   неназначения человеческим языком, дифф перестроек.
3. **Реакция на изменение в течение дня?** Да: три типа событий, пересчёт за доли
   секунды, дифф и откат.
4. **Сравнение с базовым планированием по двум метрикам?** Да: FIFO рядом, исполнители
   и пробег — по каждому и суммарно.
5. **Воспроизведение по README?** Да: one-command запуск контура (`launch/`), демо-наборы
   и сценарий проверки — [tz-acceptance.md](tz-acceptance.md).
