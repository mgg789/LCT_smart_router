# API — эндпоинты, конвенции и недостающие контракты

## LIVE-день

Правила и приёмка: [live.md](./live.md). Все времена в ответах — целые Unix-секунды.
`liveNow` — рабочее время, `startedAtWallSec` — реальное время начала сеанса.
Чтение live, выдача кода входа и запись почты инженера (`link-account`,
смена и снятие логина) не берут блокировку `control_state`: её держат только
записи, которые публикуют или принимают план. Сохранение почты не ждёт ни ход
часов, ни приёмку маршрута. Опрос экрана (`GET /dispatch/live`, `GET /engineer/live`)
дожидается хода часов (`advanceOnce`), чтобы ответ не показал день до его
автоматических переходов (неявка, превышения, завершение по концу смены).
В `workday` живого ответа есть `planRevision`, `calculating`, `routerPhase`
(`building` / `ready` / `error`), `routerMessage`, `geometryDone` и `geometryTotal`.
Это запись основного бэкенда: чтение live и плана не вызывает роутер и не ждёт
дорожный API. Пока фаза `building`, экран показывает прогресс. При `error` —
текст ошибки. Точные линии дорисовываются по одному ребру уже после готового плана.

Ответы `GET /engineer/live` и `GET /dispatch/live` содержат
`engineer.canFinishDay` / `engineers[].canFinishDay`: персональную готовность
инженера завершить работу после 17:00. Это не статус всего `workday`: чужая работа
и алёрты диспетчера не блокируют персональную готовность. Собственная незавершённая
работа, новый назначенный визит, пересчёт, обед и техперерыв её блокируют.

Решения алёртов переводят время операции в `liveNow` ровно один раз. Последующие
публикации после снятия/добавления инженера, изменения окна и решения по обеду
передают уже рабочее время (`businessTime: true`). Повторное преобразование в
ускоренном режиме сдвигало дату за горизонт смены и публиковало пустой план.
Снятие уже `offline` инженера без изменения входных данных Router не публикует
новую ревизию; назначения остальных инженеров не теряются из-за этого действия.

Уточнение 20.09: `online` отправляется только явной кнопкой выхода; `GET` не
подтверждает явку. Действие `on_time` удалено. Состояние инженера содержит
`lineStartedAt`, `noShowAt` и `lunchInterval: {startAt,endAt} | null` для неизменной
истории смены. Решение `keep_as_is` доступно у риска времени и не меняет план.
Сроки LIVE-алертов используют рабочие, а не настенные часы.

| Метод | Путь `/api/v1` | Назначение |
|---|---|---|
| GET | `/dispatch/live` | Рабочий день, счётчик заявок, состояния инженеров |
| POST | `/dispatch/live/start` | Идемпотентный старт (`operationId`) |
| GET | `/engineer/live` | Свой рабочий день, ближайшая заявка, маршрут и перерывы |
| POST | `/engineer/live/actions` | Действие инженера под серверными рабочими часами |

Тело действия: `operationId` (UUID), `kind`; для интеграционного ключа также
`engineerId`, для сессии субъект определяется авторизацией. Значения `kind`:
`handoff_confirm` (принимает `handoffId`), `online`, `eta`, `start`, `finish`,
`problem`, `break_start`, `break_finish`.
Действия с заявкой принимают `requestId`; `eta` — `etaAt`.
`problem` принимает `problemKind` (`delay`, `missing_equipment`, `other`, `impossible`),
обязательный `note`; задержка — `additionalDurationSec`, оборудование —
`missingEquipment` (`router`, `set_top_box`, `smart_speaker`).
Задержка до старта визита увеличивает `serviceDurationSec` и `technicalDurationSec`
на одну и ту же величину (CHECK `service = technical + documentation` сохраняется)
и при необходимости сдвигает конец окна. На уже начатой заявке обе колонки
двигаются вместе с новым прогнозом: `expectedCompletionAt` и
`continuationAvailableAt` — логическое время, не смесь с настенными часами.
Время факта клиент не передаёт. Действия возвращают актуальное представление LIVE.

`DispatchLiveView.history` сохраняет выполненные, отменённые и пройденные по графику
заявки и несёт фактический `terminalAt`; `breaks` содержит
`{id, engineerId, startedAt, plannedEndAt, endedAt}`.
История техперерывов берётся из журнала успешных операций и переживает перестройку.
Состояние инженера содержит `routeState`, итоговые `stats` и `progress`: фазу движения,
неизменяемую вершину начала дня `origin`, последнюю достигнутую вершину `anchor`, следующую
точку `next` и опциональную вершину `lunch`. `lunch` присутствует на всём составном переходе
`anchor → lunch → next`, а не только пока часы находятся внутри обеда. Версия плана сама по
себе эти факты не меняет. После нормативного конца обеда первая следующая заявка защищена
пятиминутным логическим интервалом передачи: явный `start` очищает lunch-курсор сразу,
а молчаливое следование расписанию возобновляется по окончании интервала.
Завершённый день возвращает `finishedAt`, `completionReason` и агрегированную статистику.
ETA, при котором нормативное завершение выходит за `windowEndAt + 600`, снимает
резервацию, публикует перестройку и создаёт диспетчерский alert
`LIVE_WINDOW_COMPLETION_RISK` с заявкой и инженером; повторный опрос не дублирует alert.
До принятия более новой ревизии плана эта заявка не возвращается инженеру из устаревшего
маршрута, а `routeState=awaiting_plan` явно показывает ожидание пересчёта.
`EngineerLiveView.route/current` включает закреплённую ETA и начатую заявку, даже
когда Router уже исключил её из оставшейся задачи. Детали такой заявки доступны
только её инженеру через прежний `GET /engineer/requests/:id`.
Во время LIVE прежние инженерные API отметок блокируются; возврат после техперерыва
подтверждается через `break_finish`. Диспетчер меняет доступность в рабочих часах;
legacy-прогноз возврата и legacy-техперерыв при запущенном LIVE отклоняются.

Клиенты опрашивают состояние раз в две секунды и интерполируют часы по
`speedFactor`; окончательное разрешение каждого перехода проверяет сервер.

## Базовая защита

API ответы проходят через `helmet`. Для JSON, health и Swagger поверх обычного ответа
выставляются `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
`Cross-Origin-Resource-Policy` и остальные безопасные заголовки Helmet. CSP здесь
отключён намеренно: `/docs` — отдельная developer-поверхность Swagger с inline
bootstrap-кодом. Фронтенд не раздаётся API: в Docker `/api` проксируется web-контейнером,
а в публичном контуре nginx проксирует запросы к web; CSP для HTML остаётся зоной web.
HSTS включается только при `NODE_ENV=production`, поэтому локальный HTTP-контур не
переключается браузером на HTTPS.

Лимиты публичных и платных маршрутов хранятся в PostgreSQL в `rate_limit_buckets`.
Атомарный fixed-window upsert считает запросы общими для нескольких API-процессов;
старые buckets удаляются после суток. Идентификатор клиента — `req.ip`: при текущем
отсутствии доверия к proxy chain все пользователи за одним reverse proxy делят bucket,
а поддельный `X-Forwarded-For` не может обойти лимит. Настройка trusted proxy должна
появиться только вместе с явной моделью доверенных hops.

## 1. Конвенции

**Префикс.** Всё живёт под `/api/v1`. Три health-эндпоинта — вне его, потому что проба
не должна знать версию API.

**Время.** Каждый абсолютный момент и каждая длительность в полезной нагрузке — целое
число секунд Unix (`context/33` §4). Никаких ISO-строк, никаких миллисекунд, никаких
локальных дат. Форматирование для человека происходит на клиенте, с явно выбранной зоной.

**Аутентификация.** Bearer-учётные данные в заголовке `Authorization`, никогда в URL,
где они попали бы в журналы доступа и историю браузера (`context/41` §12):

```
Authorization: Bearer <session token | integration key>
```

Оба вида резолвятся через один и тот же guard в одного `Actor`. UI-сессия и
интеграционный ключ различаются происхождением, а не тем, какой обработчик выполняется:
бизнес-правило существует ровно в одном месте, и UI, интеграционный API и (позже)
AI-инструмент не должны обрасти тремя расходящимися его версиями (`context/36` §2).

**Роли.** Сессия действует от одной роли. Интеграционный ключ вместо этого имеет
категорию, отображаемую на набор ролей, чьи UI-действия она заменяет:

| Категория ключа | Роли, которые она несёт |
|---|---|
| `client` | `client` |
| `eng` | `engineer` |
| `client_eng` | `client` + `engineer` — один ключ для встраивания обоих приложений |
| `master` | `dispatcher` + `client` + `engineer` — дашборд, админские и системные/отладочные функции поверх обоих app-контуров |

Ключ `client` или `eng` никогда не получает диспетчерских функций лишь потому, что им
владеет тот же человек; граница проходит между категориями функций, а не между
личными аккаунтами (`context/41` §5, правка 2026-09-19 — D-31).

**Закрыто по умолчанию.** Guard глобальный и по умолчанию запрещает, если эндпоинт
не помечен публичным. Новый маршрут без декоратора недостижим, а не открыт. Единственные
публичные маршруты помечены `@Public()`: среди них вход по коду/паролю, health и
интерпретация клиентской заявки. MCP имеет собственную проверку PIN/dispatcher
credential; публичный декоратор не даёт анонимного доступа к инструментам.

**Ограничение попыток.** Лимиты используют `req.ip` Express, а не присланный клиентом
`X-Forwarded-For`. Доверенные прокси в bootstrap пока не настроены: пользователи за
одним reverse proxy делят его бюджет. Для нескольких экземпляров API нужен общий
лимитер на внешнем контуре: текущие счётчики хранятся в памяти одного процесса.
MCP POST ограничен 30 запросами в 60 секунд до проверки credentials, поэтому неверные
Bearer и `X-MCP-Pin` расходуют один бюджет. `RATE_LIMIT_MULTIPLIER` масштабирует лимиты;
в тестовом контуре он повышен. Превышение возвращает 429 `RATE_LIMITED`.

Выдача одноразового кода сериализуется транзакционной блокировкой по нормализованному
email. Параллельные запросы оставляют один активный код; новый отзывает предыдущий.

**Ошибки.** Один конверт, всегда:

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "Request changed since it was read; refresh and confirm again",
    "details": { "expectedVersion": 3, "currentVersion": 5 },
    "requestId": "0f0f…"
  }
}
```

**Код** — контракт, а не статус. Несколько различных отказов делят 409 и должны
оставаться различимыми без разбора прозы:

| Код | Статус | Значение |
|---|---|---|
| `VALIDATION_FAILED` | 422 | Полезная нагрузка не прошла свою схему; `details.issues` перечисляет пути |
| `UNAUTHENTICATED` | 401 | Учётных данных нет или они уже недействительны |
| `FORBIDDEN` | 403 | Актор известен, роль или категория токена неверны |
| `NOT_FOUND` | 404 | Такого объекта нет или он не виден этому актору |
| `VERSION_CONFLICT` | 409 | Кто-то изменил объект после того, как актор его прочитал |
| `OPERATION_ID_REUSED` | 409 | Тот же operation id повторён с другими аргументами |
| `WORK_ALREADY_STARTED` | 409 | Инженер зафиксировал старт; обычные изменения закрыты |
| `MODE_MANUAL` / `MODE_AUTO` | 409 | Рабочим планом владеет другой режим управления |
| `SNAPSHOT_STALE` | 409 | Результат относится к снимку, который больше не опубликован |
| `RESULT_NOT_APPLICABLE` | 409 | Завершён, но не должен становиться рабочим планом |
| `CONFIRMATION_REQUIRED` | 409 | Разрушающее действие без явного подтверждения |
| `SERVICE_NOT_CONFIGURED` | 503 | Опциональная интеграция не подключена в этом развёртывании |
| `INTERNAL_ERROR` | 500 | Неожиданная ошибка; детали в логах, а не в ответе |

`requestId` повторяет `X-Request-Id`, если вызывающий его передал, и генерируется
в противном случае. Тот же id появляется в каждой строке лога этого запроса.

## 2. Любое изменение: конверт операций

Каждая запись проходит через один конверт (`context/36` §1, §8 и §12). Эндпоинты,
меняющие состояние, принимают эти поля наряду со своей полезной нагрузкой:

| Поле | Обязательность | Значение |
|---|---|---|
| `operationId` | да | Стабильный id одного бизнес-намерения, выбранный вызывающим (UUID). Повтор после потерянного ответа повторяет его |
| `expectedVersion` | когда действие следует из предварительного чтения | `version` объекта, который видел актор |
| `confirmation` | для действий, требующих явного подтверждения | Ссылка на подтверждённое намерение |

**Повтор безопасен и является задуманным поведением.** Тот же `operationId` с теми же
аргументами возвращает первый исход, не выполняя работу заново, — один запрос, один
`requestId`, одно письмо. Отказ тоже сохраняется, поэтому повтор после потерянного
ответа возвращает тот же отказ, а не пытается выполнить работу второй раз.

**Тот же `operationId` с другими аргументами отклоняется** с `OPERATION_ID_REUSED`.
Это ошибка вызывающего, а не новая запись.

**`expectedVersion` — способ сделать конкурентные правки видимыми.** Если объект
изменился после того, как актор его прочитал, ответ — `VERSION_CONFLICT` с
`expectedVersion` и `currentVersion`; клиент обновляется и подтверждает заново.
Ничто никогда не перезаписывается молча. Проверяются только данные, на которых основана
операция, — постороннее сообщение в чате не делает действие недействительным
(`context/36` §8).

Бизнес-изменение, запись о том, кто его сделал, и требуемая им последующая работа
коммитятся вместе. Ожидание Router, AI или SMTP намеренно вне этой единицы: сетевой
вызов никогда не держит транзакцию открытой, а сбой почты не превращает уже сохранённую
заявку в несуществующую.

## 3. Health

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/health/live` | Процесс поднят |
| GET | `/health/ready` | Обязательные зависимости работоспособны; иначе 503. Готовность определяет только база данных |
| GET | `/health/services` | Каждая зависимость, включая те, которых в этой сборке нет |

`not_configured` — настоящий ответ, а не сбой. В этом контуре проба `router` пингует
`/health` Router Core через настроенный `ROUTER_BASE_URL`, поэтому сообщает реальную
достижимость Python-сервиса. `ai` сообщает `not_configured`. `smtp` остаётся
`not_configured`, пока не задан `SMTP_HOST`; при заданном хосте это проба
watchdog/транспорта, а не доказательство доставки в ящик. Недостижимые SMTP или LLM
никогда не должны делать приложение «лежащим» —
парольный вход диспетчера обязан работать именно тогда, когда почтовый контур сломан
(`context/43` §11.3).

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| POST | `/api/v1/auth/login-code` | публичный | Запросить одноразовый код для адреса |
| POST | `/api/v1/auth/login-code/verify` | публичный | Обменять код на сессию |
| POST | `/api/v1/auth/dispatcher/password` | публичный | Войти диспетчеру без SMTP |
| GET | `/api/v1/auth/session` | любой актор | Описать актора за учётными данными |
| DELETE | `/api/v1/auth/session` | любой актор | Выйти; идемпотентно |
| POST | `/api/v1/auth/tokens` | диспетчер | Создать интеграционный ключ |
| GET | `/api/v1/auth/tokens` | диспетчер | Перечислить ключи без их секретов |
| DELETE | `/api/v1/auth/tokens/:id` | сессия диспетчера | Отозвать ключ |

### Поведение, которое стоит знать до интеграции

- **Запрос кода ничего не раскрывает.** Ответ одинаков, известен адрес или нет; иначе
  эндпоинт стал бы справочником клиентов, инженеров и диспетчера.
- **Роль выдаётся, а не заявляется.** `role: "client"` создаёт учётную запись при первой
  успешной верификации. `role: "engineer"` работает, только если диспетчер создал этого
  инженера; иначе ответ неотличим от неверного кода, поэтому список персонала не утекает
  (`context/36` §7.2). `role: "dispatcher"` открывает ту же учётную запись, что и
  парольный запасной путь — роль уже есть после старта API (`DISPATCHER_EMAIL`).
  Сессия инженера живёт `ENGINEER_SESSION_TTL_SEC` (30 суток по умолчанию); сессия
  диспетчера остаётся на `SESSION_TTL_SEC`.
- **Смена почты инженера** — `POST /engineer/email-change` + `/confirm`: код уходит на
  новый адрес тем же контуром login-code; логин меняется только после подтверждения.
- **Код одноразовый**, истекает, отзывается, когда для того же адреса выпущен более
  новый, и перестаёт работать после `LOGIN_CODE_MAX_ATTEMPTS` неверных попыток. Попытки
  считаются против кода, а не адреса, поэтому третья сторона не может кого-то заблокировать.
- **`devCode` в ответе** появляется при `AUTH_DEV_EXPOSE_CODES=true` и
  `NODE_ENV`, отличном от `production`. Ноутбучный стенд с `DEMO_STAND=true` тоже
  показывает код: почтового ящика нет. Публичный хост остаётся в `production`, где
  флаг запрещён схемой и приложение не стартует; там код уходит письмом, диспетчер
  входит паролем.
- **Интеграционные ключи** принимают имя, категорию (`client`, `eng`, `client_eng`,
  `master`) и опциональный срок действия — `expiresAt` в целых секундах Unix; пропуск
  или `null` означает «никогда» (`context/41` §3–5, правка 2026-09-19 — D-31). Дата в
  прошлом отклоняется `VALIDATION_FAILED`; истёкший ключ перестаёт авторизовать новые
  вызовы так же, как отозванный, — ответ `UNAUTHENTICATED`. Ни скоупов, ни привязки к
  конечному пользователю. Секрет показывается один раз, при создании; в БД лежит только
  SHA-256-хэш; перечисление никогда не раскрывает секрет повторно. Отзыв останавливает
  новые вызовы и не удаляет созданное ключом.
- **Ключи не управляют ключами.** Создание — функция категории master, но отзыв требует
  сессии диспетчера: управление ключами — действие Дашборда.

### Схема авторизации токеном — для внешних интеграций

1. Диспетчер создаёт ключ в Дашборде (Настройки → API-токены) или через
   `POST /api/v1/auth/tokens` с сессией диспетчера и передаёт секрет разработчику
   интеграции по защищённому каналу. Секрет больше нигде не показывается.
2. Каждый запрос несёт `Authorization: Bearer <ключ>`. Ключ никогда не кладут в URL.
3. Источник истины по своим правам — `GET /api/v1/auth/session`: он отвечает `kind`,
   `role`, `roles` (все роли ключа), `tokenCategory`.
4. Просроченный или отозванный ключ даёт `401 UNAUTHENTICATED` на любом закрытом
   эндпоинте; чужая категория — `403 FORBIDDEN` с `requiredRoles`/`actorRoles` в
   `details`.

Внешнее приложение работает с системой одним из двух способов (D-32): **«по id»** —
токен в заголовке, объект (`clientEmail`/`engineerId`) называется в самом запросе, своя
аутентификация у внешнего приложения; **«по сессии»** — наш вход email + одноразовый
код, субъект берётся из сессии. Полный гайд с пошаговыми сценариями:
[integration-guide.md](./integration-guide.md).

Готовый пример клиента без зависимостей: [`examples/external-api-client.mjs`](../examples/external-api-client.mjs) —
ключевой сценарий «описать актора → прочитать план дня → создать заявку» по одному ключу.

### Правила, которые эти эндпоинты гарантируют

- **Три состояния, а не одно.** Ответ несёт `lifecycle` (деловая стадия) и
  `assignmentState` (исход распределения) отдельно, а факты живут в своей таблице.
  `pending` означает «ожидает актуального результата» — это не отказ, и идущий расчёт
  или ошибка Router никогда не превращают его в `unassigned` (`context/36` §3).
- **Черновик — не задача.** Он не в свободном пуле, не порождает почты и не публикуется.
  Только подтверждение делает его настоящим.
- **Заказчик никогда не вводит параметры маршрутизации.** Требуемый навык, ожидаемая
  длительность и любое транспортное ограничение выводятся из вида работ
  (`context/32` §4.1). Срочность может поднять приоритет и никогда его не понижает.
- **Длительность берётся из профиля норм и хранится в разбивке.** Каждый из 16 видов
  работ отображается на один из четырёх профилей (`connection_base`, `outage_tkd`,
  `equipment_order`, `local_repair`); импортёр хранит код профиля плюс его техническую
  и документационную составляющие, чья сумма — `serviceDurationSec`, и нормативную
  добавку на перемещение (1200 с). Разбивка видна на экране заявки, а не пересчитывается
  при чтении.
- **Перенос сохраняет один id заявки и одно живое окно.** Прежние условия уходят
  в историю, которая — журнал, а не второе обещание заказчику. У каждой строки есть
  `actor` из `audit_log` (кто, откуда, какое действие), если запись журнала есть;
  иначе `actor` равен `null`. Тот же объект отдаёт MCP `get_request`. Прежнее назначение не
  подтверждает новые условия, поэтому исход возвращается в `pending`. Если новое окно
  не находит назначения, старое автоматически *не* восстанавливается (`context/36` §4).
- **Как только инженер зафиксировал старт, обычные изменения закрыты** — перенос, правки
  и отмена отвечают `WORK_ALREADY_STARTED` через любой путь: устаревший экран, ссылку
  в старом письме, новую сессию или интеграционный ключ (`context/42` DF-05).
- **Отмена — изменение состояния с собственным штампом времени**, никогда не удаление
  и никогда не следует автоматически из ухода заявки в нераспределённые.
- **Заказчик видит только свои заявки.** Чужая сообщается как отсутствующая, а не
  запрещённая, потому что подтвердить её существование — само по себе раскрытие.
- **Заявка без координат сохраняется и помечается**, затем исключается из опубликованного
  снимка с посчитанной диагностикой. Координаты никогда не выдумываются.

### Почтовый каталог переходов заявки (2026-09-20)

Каждый видимый заказчику переход заявки имеет письмо; интент пишется в той же
транзакции, что и переход, отправку ведёт SMTP-gateway (`notification_intents`,
состояния без `delivered`). Один бизнес-переход — одно письмо (ключ `businessEventKey`).
Письмо с кодом входа остаётся макетом 32:2931 / 32:2930. Информационные письма
(назначение, выполнение) и предупреждения (перенос, отмена, новое согласование)
собраны по макету 189:208 и 189:229: по центру текст, компактная жёлтая кнопка,
у предупреждения событие вынесено в плашку заголовка.

| Категория | Когда записывается | Кому |
|---|---|---|
| `request_received` | подтверждение заявки | заказчику |
| `engineer_assigned` | заявка назначена принятым планом | заказчику |
| `engineer_confirmed` | инженер отметил `started` (на месте, начал работу) | заказчику |
| `request_rescheduled` | заказчик сам изменил окно: письмо подтверждает новое время | заказчику |
| `visit_change_required` | диспетчер изменил согласованное окно: письмо с двумя кнопками — «Выбрать новое время» и «Отменить заявку» (глубокие ссылки в карточку заявки) | заказчику |
| `request_completed` | инженер отметил `finished` | заказчику |

### Правила, которые эти эндпоинты гарантируют

- **Инженера создаёт только диспетчер.** Ввод адреса на экране входа инженера никогда
  не порождает роль. Профиль можно создать без адреса; роль и доступ появляются только
  если адрес передан при создании или позже через `link-account`. Создать доступ и получить человека, для которого Router может
  планировать, — разные результаты: навыки, транспорт и точка старта должны быть
  настоящими значениями, а недостающие никогда не выдумываются (`context/42` DF-03).
- **Вход — это доступ, а не свойство профиля.** `link-account` выдаёт логин уже
  существующему профилю (бригада из импорта): аккаунт создаётся, роль инженера
  выдаётся, но навыки, транспорт и точка старта не меняются (`context/37` §3.1, D-30).
  `unlink-account` делает обратное: роль и сессии снимаются, профиль остаётся.
  Замена email через `PUT /engineers/:id/email` атомарно переносит инженерную роль на
  новый адрес и отзывает сессии старого, не меняя параметры маршрутизации.
  Эти три записи не берут блокировку плана: пересчёт маршрута их не задерживает.
  Повторная привязка и адрес, уже являющийся логином другого инженера, отклоняются;
  повторное «добавление» по тому же адресу возвращает существующего инженера, а не
  второй профиль.
- **Удаление профиля — архивирование, а не физическое стирание.** Исторические планы и
  подтверждённые факты остаются связаны с инженером, а новый снимок Router его уже не
  содержит. Роль и сессии отзываются. Активного на LIVE-линии или занятого инженера
  удалить нельзя: сначала его нужно снять с линии и завершить работу.
- **Профиль и рабочий день раздельны.** Факты смены, доступности и обеда принадлежат
  одному дню, поэтому «уже пообедал» не может стать постоянным свойством человека.
- **Обед нельзя включить без длительности и полного окна**, и весь обед должен
  помещаться внутрь окна. Часы никогда не были согласованы, а включённая функция не
  должна работать на выдуманной норме (`context/32` §8). `required` вместе с
  `enabled: false` противоречиво и отклоняется.
- **`lunchTaken` ставится только инженером, фактически начавшим обед** — не публикацией
  расписания. Это значит, что единственный обед дня израсходован, а не что он закончился,
  и это переживает перезапуск, переключение режима и выключение-включение функции.
- **`online` — рабочая доступность**, не сетевое состояние и не «свободен прямо сейчас».
  Уход в offline не завершает работу в руках и не переназначает её. `expectedOnlineAt` —
  прогноз: его достижение не создаёт факта online.
- **Инженер и диспетчер правят один профиль через один обработчик**, поэтому их
  конкурентные правки встречают одну проверку версии, и никто молча не перезаписывает
  другого. Кто из них может менять навыки, транспорт и офис — явно ещё открытый вопрос
  (`context/36` §14.2); ограничение живёт в контроллере, чтобы меняться, не трогая логику.

Маршрут инженера на день — применённый рабочий план (`GET /api/v1/engineer/plan`), а
отмечать инженер может факты исполнения этого плана (раздел 8). Отслеживание
местоположения вообще не входит в продукт: сбор GPS удалён решением (`context/50` §2),
и нет ни эндпоинта позиции, ни таблицы, ни живого слоя.

### Что публикуется, а что — нет

Публикация происходит только по перечисленному бизнес-триггеру — подтверждённая заявка,
изменившиеся условия, отмена, созданный или отредактированный инженер, изменение смены
или доступности, фактически начатый обед, смена политики, факт исполнения с существенными
временными последствиями (`request.execution_started`, `request.execution_variance`,
`request.execution_overrun`), импорт или сброс. Список — закрытый enum в
`publication-triggers.ts`.

Намеренно **не** триггеры, каждый по названной причине:

| Событие | Почему нет |
|---|---|
| Течение времени | Таймера перепланирования нет; `planning_as_of` не тикает. Единственное намеренное исключение — поллер превышений исполнения: он только *обнаруживает* превышение уже начатой задачи и публикует её проекцию, план он никогда не перестраивает |
| Рядовое завершение без существенного отклонения | Следование текущему плану не требует реоптимизации; финиш внутри обоих допусков не сдвигает ни одного якоря, который видел бы Router |
| Молчание инженера | Истёкшая оценка не становится `null`, offline или отказом |
| Любое чтение | Чтение ничего не публикует и не двигает указатель |

И даже по настоящему триггеру проекция, байт-в-байт совпадающая с опубликованной, **не**
публикуется повторно, и `planning_as_of` не сдвигается. Перезапись того же содержимого
не должна порождать бесконечную серию штампов времени (`context/33` §7).

### Hash и хранение

Документ сериализуется один раз по каноническим правилам
[contracts/snapshot-canonical.md](./contracts/snapshot-canonical.md); та же строка
сохраняется и хешируется.

Хранятся два дайджеста, и это различие важно. `input_hash` покрывает **весь документ,
включая `planning_as_of`** — именно с ним сопоставляется результат Router.
`task_fingerprint` покрывает задачу **без** этого штампа времени, и именно он отвечает
на вопрос «изменилась ли задача на самом деле». Сравнение `input_hash` сообщало бы об
изменении каждую секунду, потому что штамп времени находится внутри хешируемого; правило
«ничего не изменилось» не срабатывало бы никогда, и `planning_as_of` тикал бы. Контракт
ставит проверку изменения до простановки времени (`context/33` §7), и fingerprint —
способ это обеспечить. Строка снимка и переключение указателя коммитятся в одной
транзакции с заблокированным указателем, поэтому медленный издатель не может откатить
активную задачу к более старой проекции. Опубликованные снимки неизменяемы и хранятся;
двигается только указатель.

### Диагностика

`debug/snapshot` возвращает `diagnostics`, вычисленные **живьём** из текущих данных,
плюс `diagnosticsAtPublication`, замороженный в документе. Различие важно: заявка, всё
ещё ждущая координат, не может быть спроецирована, поэтому она не меняет задачу и не
вызывает публикацию — счётчик, замороженный на момент публикации, никогда бы её не
упомянул. Живая диагностика сообщает, что исключено прямо сейчас и почему:

| Поле | Значение |
|---|---|
| `requestsWithoutLocation` | Поданная работа без координат; они никогда не выдумываются |
| `requestsOutsideHorizon` | Работа, чьё окно целиком лежит вне периода этой задачи |
| `engineersWithoutStartLocation` | Нет пригодной точки старта, поэтому маршрут не мог бы начаться |
| `engineersWithoutShift` | Рабочий день есть, но смену никто не задал |
| `engineersWithoutWorkday` | Для этого горизонта рабочего дня нет вовсе |
| `engineersOverrun` | Инженеры, выведенные из задачи, потому что их начатая работа превысила допуск (`overrunDetectedAt` установлен) |

Инженер без смены исключается, а не получает выдуманную: значение по умолчанию «весь
календарный день» позволило бы планировать работу на три часа утра.

### Технические настройки Router, управляемые из sys

Принадлежащие Router регуляторы, задающие версию расчётного контекста, —
`lunchesEnabled` (выключен по умолчанию с `context/50`), два допуска ревалидации,
`travelTimeMode` (`graph_with_access_buffer` или `fixed_normative`), `accessBufferSec`,
`fixedTravelTimeSec`, `earlyFinishReplanThresholdSec` и `taskOverrunToleranceSec` —
читаются и заменяются как одна ревизия:

`strictTimeWindows` (Python: `strict_time_windows`, по умолчанию `false`) —
общий переключатель «Строгие окна ТЗ». При `true` эффективные допуски выезда,
начала/окончания работы и переработки равны нулю, включая терминальное расширение
окна, смены и горизонта. Численные настройки сохраняются и снова действуют после
выключения переключателя. Флаг проходит тот же CAS, что остальные настройки;
старые сохранённые настройки без него читаются как `false`.

Операционные часы дня, пороги LIVE-alert и ключи 2ГИС/Яндекс живут отдельно в
`app_state` (`dispatcher.settings`) и не входят в ревизию Router: `GET`/`PUT
/api/v1/dispatch/settings`. Секреты карт не читаются обратно. `GET /plan`
параллельно зовёт 2ГИС и Яндекс, если ключи заданы: при двух ответах берётся 2ГИС,
иначе Яндекс; нога получает `geometryProvider`. Без ключей остаётся геометрия
Router (геоцентры / OSRM). `GET /dispatch/geocode` — LocationIQ autocomplete (`LOCATION_IQ_TOKEN`);
без токена тот же поиск идёт в Nominatim. Заявка с координатами получает
`region` ближайшего геоцентра уже существующих заявок региона.

- `GET /api/v1/dispatch/router/technical-settings` читает их из `GET /v1/context` Router
  вместе с активной `router_context_version`; read-through не кешируется как состояние.
- `PUT /api/v1/dispatch/router/technical-settings` идёт через конверт операций и
  `executeExternal`: строка журнала резервируется как `outcome_unknown`, удалённый
  `PUT /v2/config/technical-settings` (с `operation_id` и `expected_context_version`)
  выполняется **вне** любой транзакции базы данных, а журнал затем финализируется в
  `applied`, `conflict` или `rejected`. Повторенный `operationId` возвращает сохранённый
  исход, не обращаясь к Router снова; сбой между вызовом и финализацией оставляет строку
  ожидающей повтора, а собственные durable-квитанции операций Router делают повторный
  вызов идемпотентным. HTTP 409 от Router проступает как `VERSION_CONFLICT` с
  сохранённым `detail` Router.

Тот же шаблон внешней операции (зарезервированная строка журнала, удалённый вызов вне
транзакции, финализация после) стоит за `engineer.technical-break` и `data.import`,
поэтому потерянный ответ никогда не повторит побочный эффект и не потеряет его записи.

### Алерты и уведомления

`GET /dispatch/alerts` возвращает `kind: "alert" | "notice"`, неизменяемые данные
ситуации и состояние решения: `actions`, `resolutionAction`, `resolutionReason`,
`resolutionDelaySec`, `workDate`. У `notice` список действий пуст и он не блокирует
смену. Первый 180 секунд `resolutionDelaySec=null`; после решения в нём записываются
секунды сверх этого льготного интервала.

У `POST /dispatch/alerts/:id/resolve` обязательны `operationId` и одно действие из
списка строки. `reschedule`, `move_window` (оба `windowStartAt`/`windowEndAt`) и
`add_engineer` (доступный `engineerId`) применяют изменение входа Router; для
`keep_manual` нужна причина. `extend` требует `minutes`, а для `shift_no_show` строго
15. Возможного позже выбора AI в API пока нет: сервер не принимает выдуманный вариант.
Повтор с тем же `operationId` возвращает сохранённый результат.

Детекторы создают решения для `time_risk`, `unassigned`, `plan_degraded`,
`lunch_conflict`, `engineer_overdue` и `shift_no_show`; обычное событие
`plan_rebuilt` приходит как `notice`. Открытый день нельзя закрыть при хотя бы одном
неразрешённом блокирующем алерте (`SHIFT_CLOSE_BLOCKED`). `seen` меняет только факт
просмотра, никогда не `resolvedAt`.

Пока Router не публикует в результате свой применённый допуск окна, `time_risk`
создаётся только при расчётном старте позже конца окна более чем на 300 секунд. Это
защита от шума расписания, а не изменение обещанного клиенту окна.

Ручной план проверяется через `POST /v1/manual-evaluation` Router: порядок визитов
переоценивается на актуальном снимке и текущей политике тем же расчётом стоимости,
что использует оптимизатор. Результат кэшируется по ревизии плана, хешу входа и
версии контекста. Если сравнение недоступно, появляется `plan_review_required` с
явным подтверждением диспетчера вместо недоказанного утверждения о деградации.
`restore_auto` остаётся нерешённым до фактического применения автоматического плана.

Первые 180 секунд не входят в `resolutionDelaySec`: решение на 181-й секунде
записывает 1 секунду задержки. Исчезнувшие условия получают `superseded`; повторное
возникновение создаёт новый эпизод. Отметка просмотра и исчезновение toast не решают
алерт. После переноса окна или вызова инженера назначение переходит в `pending`:
повторный routing fail определяется по следующему реальному результату Router.

  ### Приёмка: пять независимых проверок

Результат становится рабочим планом, только если выполняется **всё** из этого
(`context/33` §7):

1. режим это позволяет — в MANUAL шина Router → sys разомкнута;
2. `input_hash` совпадает со снимком, опубликованным **сейчас**;
3. `router_context_version` совпадает с действующей **сейчас** версией — результат не
   может отчитаться о собственной актуальности, поэтому активная версия читается отдельно;
4. `main.is_usable` — завершённый ответ не автоматически применимый, а `false` не
   доказывает, что визиты невозможны;
5. нет конфликта с явными фактами — начатая, завершённая или отменённая работа не
   перераспределяется, а использованный обед не планируется заново.

У каждого отказа свой код, поэтому устаревший ответ, непригодный план и отказ в ручном
режиме остаются различимыми. Отклонённые пакеты сохраняются вместе с причиной: отказ
должен быть объясним потом, а не невидим.

**Когда результат конфликтует с фактами, sys его не чинит.** Он отказывается применять
конфликтный результат и публикует вместо него актуальную проекцию. Выбор назначений —
работа Router и остаётся ею.

Повторное чтение того же `result_id` не применяет его снова, не возвращает завершённую
работу в пул и не повторяет письмо. Единственное исключение — явный возврат в AUTO: он
может применить всё ещё пригодный результат, который система уже видела.

### Сам план

Каждая приёмка добавляет **неизменяемую ревизию**; указатель называет действующую
(D-10). Ревизия несёт `planAsOf` — момент, который план описывает. Пока пересчёт идёт,
интерфейс продолжает показывать последний применённый план с тем самым моментом, а не
очищает день и не занимает штамп времени снимка, который ещё не вычислен
(`context/36` §6). `origin` равен `auto` или `manual`, поэтому ручной план никогда не
выглядит свежим расчётом.

### Ручное управление

Ручной режим отключает ровно одну вещь: доставку результата Router в sys. Router
продолжает считать, сектор продолжает читаться, заявки продолжают приходить; ответы
просто остаются внутри Router. Диспетчер становится автором плана и получает два жеста,
reassign и reorder, — без группового черновика, без кнопки «применить изменения» и без
обязательной ETA. Старые автоматические времена не пересчитываются и не подаются так,
будто были пересчитаны: sys не запускает скрытого оптимизатора.

Возврат в AUTO — явный переход. Текущий результат заменяет *будущее* распределение; он
не сливается с ручным планом и не отменяет ничего случившегося.

### Факты

`arrived`, `arrived_blocked`, `started`, `finished`, `problem` — каждая из них явная
отметка от инженера. Ничто не создаёт факт из расписания или из молчания — единственное
исключение, снова намеренное, обнаружение превышения ниже: оно выводит *диагностику* и
никогда — завершение. Прибытие и старт — отдельные события, поэтому тот, кто на месте,
но не может начать, сообщает именно это. Завершение работы, которая никогда не
начиналась, отклоняется, а не выводится. `occurredAt` (когда, по словам инженера, это
произошло) и сохраняемый `recordedAt` держатся раздельно.

Инженер может отмечать только работу, назначенную ему **применённым планом**.

### Тайминг исполнения

Факт старта — то место, где прогноз встречается с реальностью, и строка заявки несёт
создаваемое им состояние: `expectedCompletionAt` (момент старта + длительность
обслуживания), `continuationAvailableAt` (когда инженер сможет взять следующую задачу)
и, когда что-то идёт не так, `overrunDetectedAt`.

- **Старт** записывает одну активную задачу на инженера (второй старт отклоняется),
  ставит `expectedCompletionAt` и `continuationAvailableAt` и публикует
  `request.execution_started`.
- **Финиш** отклоняется, если предшествует старту (422). Иначе отклонение
  классифицируется по двум допускам, принадлежащим Router: финиш минимум на
  `earlyFinishReplanThresholdSec` раньше, более чем на `taskOverrunToleranceSec` позже
  или после обнаруженного превышения — **существенное отклонение**:
  `continuationAvailableAt` переносится на фактический финиш и публикуется
  `request.execution_variance`. Поглощённое отклонение (например, на 14 минут раньше)
  не сдвигает ни одного якоря и ничего не публикует.
- **Превышение** обнаруживает фоновый координатор (`ROUTER_POLL_INTERVAL_MS`, в тестах
  отключён): он помечает `overrunDetectedAt` на находящихся в работе заявках, вышедших
  за `expectedCompletionAt + taskOverrunToleranceSec`, и публикует
  `request.execution_overrun`. Инженер исчезает из следующего опубликованного снимка
  (считается в `engineersOverrun`); факт финиша никогда не выдумывается.

### Сухие предикты ситуации (2026-09-23)

`POST /api/dispatch/predictions/situation` — Монте-Карло-прогноз применённого плана
(300 прогонов дня под шумом трафика/длительностей/отмен): ожидаемое число опоздавших
заявок, риск по каждой заявке, перегрузка команд. Срыв — выход за окно сверх допуска,
который принимает сам план; полосы светофора считаются от ожидаемых опозданий, а не от
«дней без срывов». План не возвращается и не меняется; вход identity-связан с
публикацией так же, как policy-comparison. Полный контракт, семантика «опоздания» и
UI-дизайн — [ml-predictions.md](./ml-predictions.md).

### Контур AI: самокалибровка оценки плана (2026-09-24)

`GET/PUT /api/dispatch/ai` — переключатель дообучения оценки плана (по умолчанию
выключено в dev, включено в production), плюс URL, модель и токен для LLM (OpenAI SDK)
и System one (Jev API). Токен в ответе — только последние четыре символа. Ответ несёт
последний известный статус самонастройки; пересчёт фактов и пуш в Router идут после
ответа, чтобы переключатель не ждал индикатор. Ни модель, ни LLM план не меняют.
Выученная калибровка пушится в Router (`GET/PUT /v1/config/predict-calibration`); ниже
минимума наблюдений работает заводская; полный сброс данных откатывает модель до
заводской. Подробно — [ml-predictions.md](./ml-predictions.md) §1.1.

Короткие вызовы не ходят через чат-харнес. `POST /api/v1/dispatch/ai/explain` просит
языковую модель (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_TOKEN`; при зеркале с токеном
прокси — ещё `LLM_PROXY_TOKEN`; без режима рассуждений)
двумя-четырьмя фразами пересказать уже посчитанный контекст: причины выбора или
слабость плана. `POST /api/v1/dispatch/ai/optimize` сначала прогоняет симулятор по каталогу
политик, переключателям обеда, метро, пробок и оборудования и одному инженеру вне линии,
затем System one выбирает один рычаг по этим дельтам. Если ни один прогон не лучше, ответ —
«План уже оптимален». Окна клиентов этот вызов не двигает. `POST /api/v1/dispatch/alerts/:id/ai-resolve` выбирает действие
с плюсами и минусами; сдвиг окна берёт только предложение Router, а если его нет —
варианта нет. Для переноса неназначенной заявки в состояние добавляется, сколько
других открытых заявок имеют пересекающиеся окна завтра: полный подсчёт в БД и до шести
примеров. Пересечение окон не означает одновременное обслуживание и не определяет
число инженеров; для этого нужны длительности, дорога, навыки и смены. `?apply=0` возвращает выбор и не применяет его: экран сначала
показывает обводку, затем сам вызывает обычный resolve. Без параметра вызов
применяет решение сразу. Причина таких решений: «Решено с AI автоматически».
Ответ вне списка отклоняется. `POST /api/v1/client/interpret` публичный: из текста
истории кандидаты достаёт разбор строки, тему, окно, имя и адрес выбирает System one,
пробелы добирает один вызов языковой модели и проверяет схемой.

`GET /api/v1/ai/conversations/:id/messages` вместе с хвостом сообщений возвращает
саму беседу, чтобы клиент видел текущий режим. У каждого сообщения в этом ответе и
в потоке чата есть `conversationId`. Перезапуск демо-дня закрывает открытые диалоги
этого диспетчера: следующий заход в AI начинает пустую беседу. Для чат-провайдера
thinking по умолчанию выключен (`LLM_CHAT_REASONING_EFFORT=none`). Значение `low`
включает минимальное рассуждение на совместимом DeepSeek endpoint. Оно допускается
только при `LLM_PROVIDER=openai_chat` и `LLM_FALLBACK_PROVIDER=none`: смешивать
протоколы рассуждения провайдеров нельзя. `max_tokens` общий на рассуждение и ответ, поэтому
лимит нужно выбирать с запасом (в примере конфигурации — 4096). Пустой или
оборванный на рассуждении ответ завершает ход явной ошибкой, а не публикацией
служебного текста. В сообщение и SSE попадает только `content`.

Точное рассуждение провайдера сохраняется в закрытом контексте, чтобы продолжать
tool calls и следующие реплики без нарушения протокола. Старые ответы без этого
поля передаются как цитаты истории; отсутствующее рассуждение не синтезируется.
После бюджета инструментов предусмотрен один финальный ход без права новых
вызовов. Незавершённый tool call из оборванного потока не выполняется. Подробности
миграции и ограничений хранения — [data.md](./data.md#приватный-контекст-ai-диалога-27092026).

Объяснения назначений отделяют подтверждённую допустимость от причины выбора:
попадание в окно или наличие навыка само по себе не доказывает преимущество перед
другим инженером. Непроверенная альтернатива прямо обозначается как непроверенная.
`evaluate_manual_order` сохраняет остальные маршруты применённого плана и меняет
только очередь указанного инженера. Ответ содержит версию применённого плана,
`inputHash`, версию контекста Router и пределы проверки. Поле `before` относится к
автоматическому результату Router; его нельзя выдавать за отдельную оценку текущего
ручного плана. При смене входных данных или контекста во время оценки результат
отклоняется. Контракт углубления ассистентов — [assistant-improvements.md](./assistant-improvements.md).

`explain_entity` собирает проверяемые факторы заявки, маршрута, дорожного плеча,
обеда или плана. У фактора есть источник, версия, основание и ссылка на уточняющий
вопрос. Отсутствующий факт помечается как недоступный; плановый обед не доказывает,
что другое время обеда невозможно. Сохранённое evidence используется как текущее
только при совпадении входа и контекста автоматического принятого результата.
При изменении состояния во время чтения ответ помечается устаревшим.

`compare_assignments` проверяет от одного до трёх закреплений заявки через
симулятор Router. Только `insertion` подтверждает запрошенное закрепление:
fallback `bounded` запускает общий поиск без этого ограничения. Такие строки
помечаются непроверенными, а их метрики не приписываются выбранному инженеру.
При смешанных результатах доступны подтверждённые строки со статусом `partial`.
Ответ называет исходные и рассчитанные метрики, версии входа и контекста; исходная точка сравнения — базовый
план Router. Результат не доказывает глобальное превосходство назначения и не
подменяет отдельную оценку текущего ручного плана. Точное альтернативное время
выезда или обеда этим инструментом не поддерживается. `simulate_change` также
возвращает структурированные метрики и происхождение, сохраняя краткий текст;
неподтверждённое закрепление/снятие назначения после общего поиска не выдаёт за
успешный контрфакт.

`verify_operation_effect` повторно читает журнал операции в рамках текущей беседы и
аккаунта. Отдельно возвращаются факт применения, состояние исходного алерта, до 20
связанных открытых алертов и соответствие применённого плана опубликованному входу.
Прочитанные данные согласованы одной транзакцией. Применённая операция или закрытый
алерт не доказывают улучшение метрик маршрутов; итог требует оценки. Если новый план
ещё не применён, ассистент должен назвать ожидание перерасчёта, а не обещать устранение
проблемы. Сырые параметры операции инструмент не раскрывает.

`search_documentation` сохраняет источник найденной карточки: путь, раздел, указанную
дату обновления документа и checksum версии. Дата карточки не заменяет чтение живого
состояния. Отсутствие результата поиска означает отсутствие найденного источника;
ассистент не должен дополнять это выдуманным руководством производителя.

Ответ диспетчеру и инженеру — простым языком, без кодов и имён инструментов. Технический перерыв инженера блокируется только визитом, который уже начат; ожидающий окно визит его не запрещает. При отсутствии устройства перенос на завтра не доказывает, что устройство будет выдано: нужны подтверждённые данные, а доступный остаток склада инструментом не представлен. Режим хода повторяется после истории диалога, чтобы старые реплики «только чтение» не перебивали переключатель. В режиме fix у диспетчера и в чате инженера инструмент сам выполняет запись. Внутри вызова System one
(тот же `noul`) проверяет действие: обычное применяется до возврата инструмента,
рисковое держит вызов открытым, пока диспетчер не разрешит или не отклонит его
в модалке. Ход чата просит до 4096 токенов вывода: прежний потолок 1024 обрывал
русский ответ на полуслове и не оставлял место на вызов инструмента. `POST /api/v1/ai/conversations/:id/assist-mode` переключает открытый
диалог диспетчера между `help` и `fix` и ту же глобальную полосу. `POST
/api/v1/ai/conversations/:id/clear` закрывает диалог; следующий заход начинает
пустой, в той же полосе. Поддержка в клиентском приложении и вкладка «Чаты» у
диспетчера закрыты. Инструмент `call_dispatch_helper` моделям не предлагается.

`GET /api/v1/engineer/weather` — тот же кэш прогноза, что у диспетчера, для экрана
выхода на смену.

`GET /api/v1/dispatch/weather` отдаёт кэш Open-Meteo по Москве: вид погоды, градус и
множитель автомобильного времени. Дождь — ×1,08, снег и ледяной дождь — ×1,15, гроза —
×1,18. Ясно и облачно множитель не поднимают. Кэш 30 минут; если прогноз недоступен,
множитель остаётся 1 и значок показывает «Нет прогноза».

Оба порога читаются из технических настроек Router (`ExecutionTimingPolicy`) со
значениями по умолчанию 900 и 600 секунд, когда Router не настроен, — так классификатор
остаётся честным о том, чьи числа использует.

## 9. Данные: импорт и два сброса

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/dispatch/data/state` | Инициализировано ли приложение, как именно, и что импортировано |
| POST | `/api/v1/dispatch/data/import` | Загрузить один, несколько или все регионы официального датасета |
| POST | `/api/v1/dispatch/data/upload` | Атомарно загрузить JSON-пакет для нового региона или дописать заявки в существующий регион |
| POST | `/api/v1/dispatch/data/reset` | Сбросить к тестовым данным или к пустому рабочему набору |
| POST | `/api/v1/dispatch/data/restart-demo` | Только `DEMO_STAND`: вернуть сегодняшний 14/3, сохранив сессию диспетчера |

### Импорт

Файлы организаторов — windows-1251 с разделителями `;` и русскими заголовками, и они —
нетронутый источник истины. Импортёр обрабатывает аномалии, которые они реально содержат:
пустые строки, региональный офис, спрятанный в последней строке, выглядящей пустой,
пустые и полнодневные окна (отсутствующее окно трактуется как полный исходный день, а
дата выводится из строк), отсутствующие районы, четыре варианта написания московского
префикса и невозможные окна (`31.02` — ошибка, а не догадка).

`POST /api/v1/dispatch/data/import` принимает `region` (один) **xor** `regions`
(`"all"` или явный список из `east`, `southeast`, `south_central`), плюс опциональное
ограничение `engineerCountPerRegion`, которое не должно превышать число бригад, реально
содержащихся в датасете. Вся пачка — каждый запрошенный регион — применяется атомарно
или никак, и сводка сообщает результаты по каждому региону. Для `regions: "all"` это
205 заявок и 35 инженеров по трём регионам.

Три правила из `context/37` §9.1:

- **пакет проверяется до того, как что-либо применено** — включая SHA-256 каждого байта
  источника и геокода; повторный импорт того же источника с другими байтами — 422,
  а не тихая перезапись;
- **ошибка означает, что не применено ничего** — полузагруженный файл оставляет
  состояние, которое никто не выбирал. Вид работ, которого нет в каталоге, — ошибка,
  потому что отображение на ближайший знакомый молча послало бы не того инженера;
- **повтор пакета не создаёт дубликатов** — пакеты распознаются по происхождению и
  содержимому, а не по имени файла.

Чего датасет не содержит, важно не меньше. Нет справочника инженеров, длительностей,
приоритетов и координат (`context/18` §6.3). Бригады берутся из колонки `Бригада`
контрольного распределения; их навыки и транспорт выводятся по заявленному
детерминированному правилу и хранятся с `origin = synthesized`, поэтому выведенное
значение никогда не выглядит данными. **Координаты приходят только из версионированного
геокод-пакета** в `data/dataset/geocoded/<region>.json` (строгая схема, по записи на
адрес каждой заявки плюс депо); импорт отказывается выполняться без пакета, покрывающего
каждый адрес, и импортированные заявки создаются с реальными точками — ничего не
остаётся в `needsGeocoding`. Окна бенчмарка перепривязываются к живому горизонту
(сдвигаются так, чтобы начинаться через 60 секунд после импорта), поэтому датасет от
17.08 планирует относительно «сейчас» без правки CSV.

### JSON-загрузка диспетчера

`POST /api/v1/dispatch/data/upload` принимает один строгий документ
`schemaVersion: "1.0"`. `mode: "new_region"` требует депо, минимум одного инженера и
минимум одной заявки; `mode: "append_requests"` принимает только заявки и требует, чтобы
названный регион существовал. Браузер выполняет те же структурные проверки ради
немедленной обратной связи, но источник истины — сервер. Координаты — WGS84, все
времена — секунды Unix.

Весь пакет выполняется в транзакции операции. Дубликаты ID внутри файла, неизвестная
структура, невозможный временной интервал, изменённая строка под существующим внешним ID
или несоответствие режима и региона отклоняют весь пакет. Точный повтор пакета
идемпотентен. Совпадающая с существующей заявка пропускается с предупреждением; тот же
внешний ID с другими деловыми данными — конфликт. Успешный импорт публикует один новый
снимок Router и возвращает его `publicationId` и `inputHash`.

Форма запроса и исполняемый пример лежат в
[`data-upload-example.json`](./data-upload-example.json). Загруженные инженеры получают
стандартное опциональное 30-минутное обеденное окно 11:20–15:00 по локальному времени.
Участвуют ли эти обеденные входы в расчёте, по-прежнему решает глобальный переключатель
Router. Необязательный `equipmentStock` у инженера (`router`, `setTopBox`, `smartSpeaker`)
задаёт утренний запас явно. Если поле есть хотя бы у одного инженера пакета, круговая
раздача по заявкам не используется: у остальных запас считается нулём. Этот запас
сохраняется, пока принятый план не назначил инженеру ни одной заявки: пустой план
импорта его не обнуляет.

Если новый регион в одном исходном пакете явно содержит и `walk`, и `transit`, эти
профили сохраняются раздельно: `walk` получает признак «без ОТ», а `transit` может
использовать общественный транспорт. Пакет без такой явной пары и уже существующие
профили сохраняют прежнюю совместимую трактовку пешего маршрута. Ограничение транспорта
заявки никогда не выводится из этого признака и не подменяется при импорте.

### Сбросы

Добавление данных, сброс к тестовым данным и полный сброс — три разных действия, и оба
сброса требуют явной подтверждающей фразы, называющей, что будет затронуто:

| Действие | Подтверждение |
|---|---|
| `kind: "demo"` | `reset to test data` |
| `kind: "empty"` | `erase all application data` |

При отказе перечисляется, что действие удалило бы и что оставило бы, поэтому
подтверждение — информированное. Интеграционный ключ не может подтвердить сброс: он
несёт полномочия диспетчера, но не его подтверждение; AI может подготовить любое из этих
действий, но никогда не подтверждает его от имени диспетчера (`context/42` DF-24).

Сброс очищает **данные, а не приложение**. Исходный код, `.env`, схема и источники
знаний остаются, а учётная запись диспетчера восстанавливается из конфигурации, а не из
скрытого архива старых пользователей. Сессии он очищает — включая ту, что подтвердила
сброс, поэтому Дашборд просит войти заново. После пустого сброса startup-профиль
фиксирует, что пустота была намеренной: пустая таблица `requests` — не доказательство,
что настройка никогда не проводилась, и перезапуск не должен тихо перезагрузить
демо-данные (`context/37` §9.5).

Перед удалением транзакция берёт блокировки в фиксированном порядке: все строки
`live_workdays`, затем `control_state`, затем `routing_current`. LIVE `advanceOnce`
держит день и затем может публиковать снимок (тот же `routing_current`). Обратный
порядок давал Postgres deadlock и HTTP 500 на `empty` reset, если предыдущий
`GET /dispatch/live` ещё не отпустил день. Smoke повторяет пустой сброс при 500/503
(не при 409 `CONFIRMATION_REQUIRED`).

## 10. Недостающие контракты

Перечислены, а не заменены заглушками с выдуманными формами (AGENTS.md §10.3).

### HTTP-поверхность Router Core — реализована

**Больше не отсутствует.** Router Core V2 (D-22) публикует свой приватный сервисный API;
он воспроизведён в разделе 11 ниже с машиночитаемыми полезными нагрузками в
`core/schemas/`. HTTP-клиент шлюза (`http-router-client.ts`) покрывает его целиком:

| Что нужно `ROUTER-gateway` | Эндпоинт Router |
|---|---|
| Текущий результат | `GET /v1/result` |
| Активная версия контекста и технические настройки | `GET /v1/context` |
| Заменить технические настройки (CAS, идемпотентно) | `PUT /v2/config/technical-settings` |
| Достижимость | `GET /health` |

Формы полезных нагрузок писались независимо на обеих сторонах по `context/33` и
совпадают поле в поле: `plan`, `engineer_route`, `route_stop`, `route_leg`,
`assignment`, `lunch_result`, `route_metrics`, `plan_metrics`, `planning_alert`,
`reason` и `diagnostic` в `result.types.ts` имеют ровно те свойства, что и
соответствующие `$defs` в `core/schemas/router-result-1.0.json`, в обе стороны. То же
верно для опубликованной задачи: золотой вектор в `docs/contracts/fixtures/`
валидируется против `core/schemas/router-task-snapshot-1.0.json`, включая каждый enum.

Маршруты применённого плана сохраняют плечи Router, а не восстанавливают перемещения
в UI. Каждое плечо раскрывает `travelSource` (`approximate`, `road_matrix`, `route_api`
или `traffic_api`), `trafficFactor`, расстояние, длительность и опциональную геометрию
провайдера. `road_matrix` означает, что дорожные расстояние и время известны; это не
подразумевает, что была возвращена отрисовываемая дорожная полилиния.

Приёмка сверяет `input_hash` **и** `input_publication_id` со снимком, опубликованным
сейчас, плюс версию контекста. Что намеренно остаётся открытым:

* **Пакет обоснований пока не потребляется.** Router также возвращает
  `input_publication_id`, `policy_id`, `policy_criteria`, `search_path`,
  `technical_settings`, `main_evidence` и `baseline_evidence`. `routerResultSchema`
  сохраняет их (это loose object), но пока ничто ниже по потоку не действует на
  обоснования — а пакет обоснований и есть поддерживаемый вход для объяснений на карте.
  Подключение его к UI — следующий контракт, а не тихое слияние.

Отладочный эндпоинт `POST /api/v1/dispatch/debug/router-result` остаётся тестовым входом,
прогоняющим те же самые проверки приёмки, — никогда вторым способом применить план.

### Сериализация снимка — общая с Router Core

sys и Router должны хешировать **одни и те же байты** одного документа, иначе
`input_hash` никогда не совпадёт. Побайтовое правило записано в
[contracts/snapshot-canonical.md](./contracts/snapshot-canonical.md), золотой вектор —
в [contracts/fixtures/](./contracts/fixtures/); воспроизведены независимо в TypeScript
и Python.

На практике общий путь вообще не зависит от пересериализации: sys публикует точные
байты и их SHA-256, а Router хеширует полученные байты (`core/runtime.py`,
`SnapshotPublication`). Спецификация нужна, чтобы будущий пересериализатор на любой из
сторон не разошёлся, и она остаётся правилом.

### Вне скоупа этой сборки

Протокол инструментов `AI-gateway` и транспорт `SMTP-gateway`. sys будет записывать
почтовые интенты; доставка — дело внешнего почтового сервера, который в этот контур не
входит.

## 11. Приватный API Router Core

### Граница

Router открывает приватный сервисный API для System Layer. Аутентификация и деловая
авторизация остаются в sys. Router не принимает ни одного эндпоинта, который напрямую
назначал бы работу, менял порядок маршрута или применял план.

### Эндпоинты чтения

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/health` | Живость плюс текущий статус координатора и технический контекст. |
| `GET` | `/v1/context` | Активная `router_context_version`, поколение, состояние расчёта, путь поиска и полные технические настройки. |
| `GET` | `/v1/result` | Последняя атомарная публикация `RouterResult`. |

`RouterResult.status` — размеченное состояние:

- `pending` не содержит планов, обоснований или диагностик;
- `ready` содержит ID, точный input hash, штампы времени, версию контекста, политику,
  технические настройки, путь поиска, упорядоченные критерии политики, основной/базовый
  планы и обоснования обоих планов;
- `error` содержит хотя бы одну диагностику и не содержит планов и обоснований.

Пакет обоснований содержит факты выбранного расписания и по каждому инженеру-кандидату:
навык, транспорт, доступность, осуществимость соло, осуществимость добавления в конец
маршрута, дельту перемещения и блокеры. Это поддерживаемый вход для детерминированных
объяснений в UI и для LLM, которая только объясняет. LLM не должна менять план.

### Технические настройки

`GET /v1/context` возвращает активную `router_context_version` плюс полную техническую
ревизию. `PUT /v2/config/technical-settings` заменяет эту ревизию целиком — частичные
обновления отклоняются:

```json
{
  "operation_id": "settings-42",
  "expected_context_version": "<sha256>",
  "lunches_enabled": false,
  "departure_lateness_tolerance_sec": 120,
  "task_start_lateness_tolerance_sec": 60,
  "travel_time_mode": "graph_with_access_buffer",
  "access_buffer_sec": 600,
  "fixed_travel_time_sec": 1200,
  "early_finish_replan_threshold_sec": 900,
  "task_overrun_tolerance_sec": 600
}
```

По умолчанию: `lunches_enabled=false`, оба допуска ревалидации `0`,
`graph_with_access_buffer` с буфером доступа 600 секунд, `fixed_travel_time_sec=1200`,
`early_finish_replan_threshold_sec=900`, `task_overrun_tolerance_sec=600`; каждое поле
ограничено сверху значением 86400.

Операция использует compare-and-swap против активного контекста и идемпотентна —
надёжно (durable), а не только внутри процесса: принятые операции сохраняются как
квитанции в том же атомарном документе, что и настройки (схема `1.0`), поэтому повтор
после перезапуска возвращает исходный исход вместо конфликта. Запись отклоняется с
`SETTINGS_STORE_UNAVAILABLE`, когда у Runtime нет постоянного хранилища настроек.
Каждое изменение создаёт новую версию контекста и делает недействительным более старый
результат, находящийся в полёте.

`travel_time_mode` решает, как оценивается каждое ненулевое плечо, поверх связного
дорожного графа и без изменения его путей и расстояний: `graph_with_access_buffer`
добавляет `access_buffer_sec` к длительности по графу; `fixed_normative` заменяет
длительность на `fixed_travel_time_sec`. Плечо с нулевым расстоянием остаётся нулевым
в обоих режимах. Обёртка владеет производной версией (`версия базового графа +
конфигурация тайминга`), поэтому изменение одного только тайминга всё равно делает
результаты недействительными.

Переключатель обедов — жёсткая системная политика. Когда он false — значение по
умолчанию с `context/50` — ни опциональный, ни обязательный обед не планируется ни в
основном, ни в базовом плане; входные байты, принадлежащие sys, и факты обедов остаются
неизменными. Два допуска ревалидации решают лишь, может ли изменившееся расписание
использовать `REVALIDATE`. `early_finish_replan_threshold_sec` и
`task_overrun_tolerance_sec` потребляются политикой тайминга исполнения в sys, чтобы
классифицировать отклонение финиша и обнаруживать превышения (раздел 8). Ни одно из
этих значений никогда не расширяет окна заказчиков или смены инженеров.

`PUT /v1/config/tolerance` остаётся алиасом совместимости для допуска опоздания
отправления. Конфликтующие id операций или устаревшие версии контекста возвращают
HTTP `409`; некорректные тела — `422`.

### Версионирование

Версия сервиса — `2.0`. Полезная нагрузка обмена с sys остаётся `schema_version="1.0"`,
потому что V2 добавляет выходные метаданные и принадлежащий Router контекст, не меняя
формы `RouterTaskSnapshot`. Неизвестные поля и неизвестные id политик отклоняются.

Проверяемые интеграционные артефакты лежат в `core/schemas/`. Перегенерация — командой
`python -m core.schema`; CI/тесты должны считать diff схемы изменением контракта.

## Настройки и показатели сравнения (18.09.2026)

Техническая ревизия Router содержит `windowLatenessToleranceSec` (0…1200 секунд, продуктовый default 600), `trafficEnabled` и `equipmentEnabled` (default true); Python использует snake_case. Передача — через существующие endpoint технических настроек и CAS contextVersion. Предыдущие поля обязательны и сохраняются. Окно клиента остаётся исходным; допуск ограничивает нормативное завершение после закрытия окна и отличается от допусков revalidation.

Метрики сравнения дополнены `lateAssignedCount`, `totalLatenessSec`, `minWindowSlackSec` (null без назначений), `workloadSpreadSec`, `maxWorkloadSec`. Веб-клиент требует эти поля: отсутствие измерения больше не подменяется нулём. Записанные демосравнения пересобраны штатным генератором. Полный смысл и формулы — `docs/solver.md`, сверочные значения — `docs/policy-efficiency.md`.

# Подбор окна заявки (21.09.2026)

`GET /api/v1/dispatch/alerts/:id/window-proposal` — только диспетчер, как остальные
dispatch-маршруты. Read-only: свежая проекция фактов передаётся приватному Router
`POST /v1/window-proposal`, рабочий план и опубликованный snapshot не изменяются.
Ответ: `{status: "available", requestVersion, proposal, proposals}` либо
`{status: "none", requestVersion, proposal: null, proposals: []}`.
`proposal` — самый ранний слот для ручной формы. `proposals` — до восьми разных
слотов того же поиска: инженер, окно, соседние заявки (`neighborRequestIds`) и
запас до конца окна (`slackSec`). Поиск по-прежнему ограничен 8 секундами.
Время — Unix seconds. `none` означает отсутствие вставки с сохранением назначенного порядка;
недоступность Router возвращается ошибкой, а не `none`. При изменении фактов расчёт отвергается.
Лимиты приватного расчёта: до 500 заявок в проекции, 100 маршрутов и 200 назначенных посещений,
8 секунд на перебор; ответ не является резервированием слота.

`POST /api/v1/dispatch/alerts/:id/resolve` с `action: "move_window"` сохраняет окно и
запрашивает пересчёт, но возвращает открытый алёрт с `resolutionAction: "move_window"`.
Для этого действия обязателен `expectedRequestVersion` из прочитанной заявки/предложения:
устаревшая форма получает `409 VERSION_CONFLICT` и не перезаписывает более свежее окно.
Одинаковые preview-входы кешируются до 10 секунд (до 32 ключей); ошибки не кешируются.
Карточка закрывается только после подтверждённого назначения/терминального состояния заявки.

## Симулятор «что будет, если» (25.09.2026)

`POST /api/v1/dispatch/simulate` отвечает, что изменится, и не записывает рабочий план.
Тело — проверенный патч: политика, технические флаги (обед, метро, трафик, оборудование),
вызов одного инженера вне линии (`bringOnlineEngineerId` — только копия снимка),
сдвиг окна одной заявки, закрепление инженера или снятие назначения. Каталог всех стратегий
для карты — `{ "catalog": true }` и только он. Повтор того же патча на том же снимке читает
таблицу `plan_simulations` (ключ: хеш публикации, версия контекста, хеш патча).

Одно окно или одно переназначение переставляется вставкой. Смена политики или настроек —
один прогон не дольше 8 секунд. Карта стратегий берёт общий набор кандидатов, а не семь
холодных прогонов. Геометрия запрашивается только когда открыта карта. Инструмент
`simulate_change` возвращает русскую сводку дельты и тоже ничего не применяет.
В сводке есть «инженеров в работе» и «дополнительных экипажей»: резерв `covering`
не является людьми со смены. Политика «полное покрытие» не обещает назначить каждую заявку. Если для
смены политики, окна, технических настроек или вызова инженера ответ уже лежит в складе,
проверка System one добавляет к состоянию фразу «опозданий было N, станет M» и сама
солвер не запускает. Кнопка «Оптимизировать» до выбора прогоняет каталог политик,
переключение обеда, метро, пробок и проверки оборудования и одного подходящего
инженера вне линии. System one выбирает один рычаг по этим дельтам. Если ни один
прогон не улучшает план, кнопка пишет «План уже оптимален». После применённого рычага
кнопка пишет «Оптимизировано»; состав изменений — в карточке diff по «Подробнее»
в уведомлении, а не в подписи кнопки.

## Паспорта зданий и месячные баллы (22.09.2026)

Паспорт общий для всех заявок здания. Чтение: `GET /engineer/requests/:id/passport`
для своей текущей или назначенной заявки; `GET /dispatch/requests/:id/passport` для
диспетчера. Ответ `{passport,canFill,unavailableReason?}`; даты — Unix seconds.

`POST /engineer/requests/:id/passport` принимает `operationId`, `connectionType`
(`fiber|ethernet|dsl|radio|other`), `difficulty` (1…3) и необязательные `equipment`,
`accessNotes`, `comment` (до 2000 символов каждое). Сохранить можно только паспорт
текущего LIVE-визита после факта `started`, если он отсутствует или старше 45 суток. До
старта чтение возвращает `canFill:false` и `unavailableReason:"WORK_NOT_STARTED"`. Проверка повторяется
в транзакции; блокировка здания предотвращает две награды при конкурентном заполнении.
Ответ содержит паспорт, `pointsAwarded:35`, `monthlyPoints`, `canFill:false`.
Повтор того же намерения идемпотентен, в том числе после перехода к следующему визиту.

`GET /engineer/points` и `GET /dispatch/engineers/:id/points` возвращают
`{monthlyPoints,month}` за текущий московский месяц. С первого числа сумма начинается
с нуля без удаления журнала начислений. «День заново» очищает журнал вместе с
демоданными и создаёт 11 свежих паспортов для 14 зданий.

Явный адрес нормализуется без квартиры/офиса; корпус и строение различаются.
Для точек без адреса применяется тот же LocationIQ в обратном направлении, с
постоянным кешем и таймаутом 4 секунды. Неопределённый дом не объединяется по близости.
Подробные DTO и состояния — `docs/frontend-api.md`, таблицы — `docs/data.md`.

## Награды инженеров (22.09.2026)

Единый immutable ledger хранится в `engineer_rewards`: категории `arrival`,
`completion`, `passport`, `penalty`; `operationId` и `dedupKey` идемпотентны.
Для arrival/completion ключом остаётся пара `(requestId, category)`, для penalty —
связка `(requestId, factId)`, поэтому два разных подтверждённых факта одной заявки
дают два отдельных штрафа. Существующие записи `engineer_passport_points` переносятся миграцией
в категорию `passport`, а legacy endpoint баллов продолжает возвращать
`{monthlyPoints, month}`.

`GET /api/v1/engineer/rewards` и
`GET /api/v1/dispatch/engineers/:id/rewards` возвращают московский месяц,
`monthlyPoints`, `earnedPoints`, `penaltyPoints`, `teamAverage`, `teamRatio`,
суммы по категориям и последние записи. `teamAverage` и `teamRatio` равны `null`,
если нет положительного среднего. В среднем учитываются архивные инженеры с
активностью месяца и действующие инженеры без начислений; деление на ноль запрещено.

`GET /api/v1/engineer/rewards/day?workdayId=...` и
`GET /api/v1/dispatch/engineers/:id/rewards/day?workdayId=...` возвращают награды
одного LIVE workday. Прибытие начисляет 40 за факт `start`/`arrived`, если он не
позже замороженного планового старта; принятый заранее ETA даёт 30 только при
факте в интервале `[ETA-600, ETA]`. Завершение начисляет 40 в пределах исходного
норматива или 30 по заранее принятому продлённому обещанию в том же коридоре.
Автоматические отметки LIVE не начисляют баллов. В evidence сохраняются wall-time
месяца и logical-time действия.

«Проблема → нужно больше времени» доступна во время работы, в том числе до
нормативного срока. Дополнительные минуты продлевают более позднее из текущего
ожидаемого завершения и текущего бизнес-времени; раннее сообщение не сокращает
норматив. Для награды фиксируется первое обещание, повторный перенос его не заменяет.

`GET /api/v1/dispatch/engineers/:id/reward-facts` показывает явные факты для
аудированной санкции. `POST /api/v1/dispatch/engineers/:id/rewards/penalty`
принимает `operationId`, `requestId`, `factId` и причину минимум 30 символов и
создаёт ровно одну запись `-50`; автоматических отрицательных начислений нет.

Контракты оценки дня (`/dispatch/performance/day`, `/engineer/performance/day`) и
месячного PDF (`/dispatch/reports/monthly/YYYY-MM`) описаны в [performance.md](./performance.md).

### Метро и транспортные профили

Технические настройки Router поддерживают `metro_enabled` (по умолчанию `false`);
публичные GET/PUT настройки диспетчера используют `metroEnabled`. Изменение
проходит прежний CAS по версии контекста и запускает пересчёт.
Профиль `transit` сохраняется в загрузке и публикуемом снимке. Исторический `walk`
остаётся совместимым с метро через признак `transit_eligible`; только `walk` из
пакета, где источник явно различил оба пешеходных профиля, получает `false` и не
использует метро. Поэтому планировщик не выдаёт такому инженеру работу с требованием
`transit`, а UI показывает «Пешеход (без ОТ)».

Router leg может содержать `segments`: `{geometry: {points}, travel_source,
duration_sec, distance_m}`. Публичный план сохраняет их как `{geometry,
travelSource, travelTimeSec, distanceKm, geometryProvider?}`. Новый источник
`metro` требует сегментов; API проверяет стыки и суммы времени/расстояния до
применения результата. Старые обычные планы без сегментов продолжают читаться.

Уточнение геометрии 2GIS/Яндекс выбирает профиль инженера (`driving`, `walking`,
`bicycle`) и не меняет стоимость уже принятого плана. Метро-сегмент не отправляется
в автомобильный роутер; отдельно уточняются пешие подход и выход. При расстоянии
между концами до 300 м включительно внешний API карт не вызывается.

## Оборудование и личные передачи (22.09.2026)

`dispatch/settings` хранит `equipmentCapacityWalk=5`, `equipmentCapacityBike=12`,
`equipmentCapacityCar=30` — суммарный максимум любых устройств у одного инженера.
Лимит не является обязательным количеством. Сначала выдаётся потребность назначенных
работ, затем по одной запасной единице используемого типа, пока есть место. Снижение
лимита ниже уже выданного запаса активной смены отклоняется, физические устройства
не исчезают при изменении настройки.

Политика `equipmentTransfersEnabled` выключена по умолчанию. Принятый план может
содержать два `handoff`-стопа одной встречи: одинаковая точка, время и 300 секунд.
`PlanStop.handoff` сохраняет контракт Router: `handoff_id`, `donor_engineer_id`,
`receiver_engineer_id`, `request_id`, `items` (`router`, `set_top_box`, `smart_speaker`).
LIVE-ответы содержат `handoffs` с camelCase идентификаторами, координатами, `meetingAt`,
`donorConfirmedAt`, `receiverConfirmedAt`, `completedAt`.

`POST /engineer/live/actions` принимает `{operationId, kind:"handoff_confirm", handoffId}`.
Участник определяется авторизованной сессией. После первого подтверждения сохраняется
резерв; после второго в одной транзакции меняются оба остатка и фиксируется завершение.
Донор и получатель всегда разные. Два ранних подтверждения не сокращают занятость:
следующая работа разрешена не раньше `max(completedAt, meetingAt + 300)`.
Повторный запрос не переносит оборудование снова. Начало последующих работ и ручная
перестановка маршрутов с незавершённой встречей блокируются. Автоматическое течение
дня не подтверждает получение оборудования. «День заново» удаляет встречи вместе с
остальными данными дня. Передачи между регионами запрещены.

Пакет Router со статусом `partial` включает `regional_progress`: готовые регионы
применяются сразу, маршруты ожидающих регионов сохраняются из текущего плана.
Проверка конфликтов фактов затрагивает только новый региональный результат; уже
начатая работа в сохранённом регионе не мешает приёмке. Защита publication/hash/context
действует и для частичного результата. Идентификаторы остановок сохраняются также
при переходе в ручной режим.

## Импорт дорожного ресурса OSRM (22.09.2026)

`POST /dispatch/data/road-import` доступен роли `dispatcher` и принимает
`{operationId, profile, source?, payloadBase64}`. В payload передаётся UTF-8 native
OSRM JSON или его gzip-байты. Core также поддерживает raw binary на `/v1/road-import`
с заголовками `X-Operation-Id` и `X-Road-Profile`.

Поддерживаются OSRM Table (`durations`/`distances`), OSRM Route (`routes[].geometry`)
и переносимый граф `nodes`/`edges`. Профили ограничены `car`, `walk`, `bike`,
`transit`; ребро направленное. Импорт сливает профильные costs в одну пару
координат, но повтор профиля, конфликт координаты, расстояния или геометрии отклоняет.
Максимальный распакованный payload — 64 MiB. Граф и журнал operation id заменяются
атомарно; ответ возвращает `inputSha256`, количество узлов/рёбер и новый
`routerContextVersion`. Этот hash участвует в реальном planning travel provider и
инвалидирует устаревший план.

## MCP-сервер дашборда (24.09.2026)

Диспетчер может подключить своего ИИ-агента к дашборду по MCP (Model Context Protocol):
агент работает от его имени — читает обстановку и объяснения плана, разбирает алерты,
меняет политики и настройки, ведёт LIVE-день.

**Настройки (роль `dispatcher`)**: `GET /dispatch/mcp` возвращает
`{enabled, pinSet, pinLast4, activeNow, lastToolName, lastToolCallAt, endpoint}`;
`PUT /dispatch/mcp` принимает `{operationId, enabled, pin?}`. Включение без пина
отклоняется; смена пина ротирует ключ; выключение отзывает ключ — пин перестаёт работать
везде сразу, включая прямой REST. Пин хранится только хешем: это настоящая строка
`ApiToken` категории `master` (имя `MCP dashboard pin`), поэтому `Authorization: Bearer <пин>`
резолвится штатным auth-engine как обычный интеграционный ключ. Второй вариант — заголовок
`X-MCP-Pin: <пин>` для клиентов, которые не могут подменить bearer. Журнал операций
и аудит фиксируют все изменения агента (`api_token`, `external_api`).

**Транспорт**: `POST /api/v1/mcp` — stateless JSON-RPC 2.0 по схеме streamable HTTP,
ответы всегда JSON (SSE-потоков нет; `GET`/`DELETE` отвечают 405). Поддерживаются
`initialize` (переговоры версий `2025-06-18`, `2025-03-26`, `2024-11-05`), `ping`,
`notifications/*` (ответ 202), `tools/list`, `tools/call`. Ошибка инструмента — это
результат с `isError: true`, а не протокольная ошибка. Пока сервер выключен, эндпоинт
отвечает 404. Каждый `tools/call` обновляет маркер активности: `activeNow` в настройках
живёт 30 секунд после последнего вызова — по нему в шапке дашборда мигает робот.

**Инструменты** (23): `get_dispatcher_context`, `get_routing_principles`,
`get_situation`, `get_plan` (опционально с геометрией), `get_plan_explanations`
(факторы решателя и `whyNot` альтернатив — подробнее, чем видит человек),
`list_requests`, `get_request` (с историей условий), `list_alerts`, `resolve_alert`,
`ai_resolve_alert` (System one выбирает действие из допустимых), `list_engineers`,
`set_engineer_availability`, `get_policies`, `select_policy`,
`get_router_controls`, `set_router_controls` (обеды, метро, пробки, оборудование),
`set_control_mode` (`auto` / `manual`),
`simulate_plan_change` (тот же набор рычагов, что у `POST /dispatch/simulate`:
каталог, политика, переключатели, вызов инженера вне линии, окно, закрепление, снятие;
в тексте дельты есть число инженеров в работе и резервных экипажей `covering`),
`review_action` (самопроверка: та же дельта и вердикт `allowed` / `risk`,
подписи «Разрешено» / «Риск»; действие не применяется; при «Риск» агенту сказано
ждать согласия диспетчера),
`get_dispatcher_settings`, `update_dispatcher_settings`, `start_workday`, `close_shift`.

Все записи идут через конверт операций с серверным `operationId` — повтор вызова
инструмента не повторяет изменение. Сброс данных и перезапуск демо-дня через MCP
недоступны принципиально: это подтверждаемые человеком действия (`account`-сессия).
Ключи карт через MCP не читаются и не меняются.

## Подготовка дорожных стоимостей (DRO-140)

Приватный Road API поддерживает `GET /matrix2?planning=1&points=lat,lon;...&departure=<epoch>`.
Ответ содержит исходный порядок `points`, `model_version`, `forecast_timezone`,
`forecast_band_starts` и квадратную `matrix`. В ячейках `road` указаны
`base_duration_s`, `distance_m` и `forecast_duration_s` по временным режимам.
`self` означает нулевое плечо, `unreachable` — отсутствие пути;
`straight`/`out_of_scope` оставляют решение о fallback региональному провайдеру.
Этот контракт используется только при подготовке расчёта Router; публичные DTO
плана и симуляции не изменены. Подробнее — [solver.md](solver.md).


## История и точное восстановление плана (26.09.2026)

Оба маршрута доступны только диспетчеру:

- `GET /api/v1/dispatch/plan/previous` — `{current, previous, eligibility}`.
  Планы могут быть `null`; `eligibility` содержит `eligible` и `reason`.
- `POST /api/v1/dispatch/plan/restore` — `{operationId, expectedRevision}`.
  Ответ: `{fromRevision, restoredRevision, origin: "restore"}`.

Восстановление создаёт новую неизменяемую ревизию с прежними маршрутами,
временами, геометрией и назначениями. История сохраняется, оптимизатор не запускается.
Смена политики сама по себе допустима; новые/изменённые заявки, горизонт,
задействованные инженеры, факты исполнения, обед, оборудование или несовместимый
контекст Router запрещают возврат. CAS и проверка журнала изменений контекста
проходят под штатными блокировками UnitOfWork; удалённый Router читается до транзакции.
Два одновременных запроса для одной ожидаемой ревизии не могут оба примениться.
Карта «До / После» читает сохранённые ревизии, поэтому доступна после reload.

Внутренний `validatedInputHash` восстановленной ревизии отделяет проверенный
текущий вход от происхождения маршрутов. `/plan.calculating` и LIVE freshness
сравнивают его с опубликованным снимком; после следующего изменения входа обычное
ожидание нового плана снова действует. Исходный `appliedResult` не подменяется.
