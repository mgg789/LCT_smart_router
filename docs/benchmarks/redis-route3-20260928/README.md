# Redis-beta: повторный замер с route-engine3, 28.09.2026

Измеряется польза Redis для повторного чтения каталога политик после смены
процесса Router. Основной план действительно проходит через route-engine3.
Это локальный эксперимент на официальном East66, а не измерение публичного
стенда или реальной доли попаданий в кэш.

## Результат

**Готовый каталог после смены процесса возвращается в 20–21 раз быстрее по HTTP
и требует в 22–23 раза меньше CPU на этот запрос.** Холодный miss не дал
подтверждённого ускорения. Запуск основного плана, локальный warm-кэш и обычные
result/status-запросы также не показывают устойчивой пользы от Redis.

Все 20 trials прошли проверку полных semantic digests внутри своего бюджета.
Каждый выполнил 57 успешных HTTP-запросов `/route3`, всего 1140. Были использованы
профили car, bike и transit; оба графа сервиса были готовы. Активный план остался
неизменным после чтения каталога. Временные контейнеры и сеть удалены после серии.

### Цена, отказ и качество

Redis занимал **16,89–22,02 МиБ RSS** по всей серии; к концу в нём осталось шесть
каталогов. При 8000 мс верхняя оценка «пик Router + отдельно измеренный RSS Redis»
для miss составляет 746,49 МиБ против 723,43 МиБ одного Router в off. Для hit —
617,23 МиБ. Это не синхронно измеренный общий пик. route3 нужен обоим вариантам:
его память после trials 596,53–610,16 МиБ, накопленный пик всего запуска 614,44 МиБ.
Запуск route3 до ready занял отдельно 5,84 с; он не входит во время готовности Router.

При pause Redis каталог вернулся за **12,880 с** на бюджете 1000 и **13,146 с**
на бюджете 8000. В обоих случаях зарегистрированы два отказа кэша, ноль hit,
успешный HTTP-ответ и совпадение полных результатов с обычными режимами.
Сервис снят с паузы и ответил на INFO перед удалением. По одному outage trial
нельзя достоверно измерить добавленную задержку отдельно от фоновой вариации.

Основной hybrid-план на обоих бюджетах: 57/66 заявок, 9/13 срочных, без опозданий.
В каталоге пять фиксированных политик назначили 59/66 заявок: **9/13 срочных при
1000 мс и 10/13 при 8000 мс**. Это эффект бюджета поиска, а не Redis. FIFO на обоих
бюджетах — 27/66 и 1/13; covering — 66/66 и 13/13 с разрешённым добавлением ресурса.
Различие основного плана и каталога объясняется описанной ниже
границей hybrid-интеграции. Равенство off/miss/hit/outage проверено для всех полных
маршрутов, ограничений и сводок, а не только для этих сокращённых метрик.

Рекомендация: оставить Redis-beta выключенным по умолчанию. Выгода подтверждена
для готового каталога при точном совпадении публикации и контекста, например при
рестарте в пределах TTL. Частота такого сценария в эксплуатации не измерялась.
Новая публикация требует пересчёта; живой Runtime уже имеет локальный кэш.
Старые числа без route3 из `redis-beta-20260928` нельзя использовать для оценки
ускорения новой версии: изменились код и режим основного планирования.

## Что именно делает система

`runtime.calculate` при `ROUTER_HYBRID=1` строит быстрый основной план, проверяет
его участки через route-engine3 и при необходимости пересчитывает его один раз.
`calculate_policy_catalog` использует `planning_travel` и поиск напрямую: у него
пока нет такого прохода через hybrid. В этой конфигурации каталог опирается на
региональный граф, а внешний road-api не задан.

Redis хранит готовый каталог с семью полными планами. Поэтому hit экономит
пересчёт каталога, но не первоначальное построение и проверку основного плана.
Назначения основного плана и каталога могут отличаться из-за этой границы
интеграции. Сравнение off/miss/hit проверяет их по отдельности, не объявляет
каталог проверенным route3 и не меняет алгоритмы ради одинаковых результатов.

## Методика

На каждый бюджет выполнены три off, три cold miss, три hit и один outage.
Каждый trial запускает новый Linux-контейнер и настоящий HTTP API Router с
ProcessPool. Публикация, её байты, время планирования, граф, настройки и версия
кода фиксированы. В первой и третьей тройках порядок off → miss → hit, во второй
miss → off → hit. У каждого повтора свой namespace; miss и следующий hit делят
запись. Клиентский дисковый кэш route3 у нового контейнера пуст.

Измеряются готовность основного плана, первый `/v1/policy-comparison`, пять
последующих обращений в том же процессе, 20 `/v1/result-status` и 10 `/v1/result`.
Warm обозначает локальный кэш Runtime; внешнее Redis-чтение повторно не нужно.
Outage — реальная пауза отдельного Redis на время нового Router: ожидаются два
тайм-аута, полный обычный расчёт и успешный ответ. Пауза снимается в `finally`.

Время готовности начинается до загрузки East66, но после импорта модулей Python;
Docker pull/build/create в него не входят. CPU Router — счётчики cgroup всего
дерева процессов, включая служебные процессы контейнера. CPU первого каталога
считается между снимками непосредственно до и после этого HTTP-запроса. CPU всего
trial — между первым и последним снимками. Redis измеряется через INFO, route3 —
через cgroup с OSRM-процессами. Служебные чтения счётчиков route3 добавляют небольшой
CPU. Для Redis показан RSS процесса; для Router/route3 — учтённая cgroup память.

Redis и route3 остаются запущены во всех режимах, включая off. В off приложение
к Redis не обращается; его RSS показывает стоимость работающего тестового сервера.
В обычной установке выключение Redis-beta останавливает Redis. route3 прогрет
между trials. Его peak — накопленный пик за жизнь сервиса, а не пик отдельного
запроса. Сумма отдельно измеренных пиков даёт только верхнюю оценку общей памяти.

В Redis накапливаются записи разных namespace — до шести каталогов в пределах
TTL, а не один каталог на весь сервер. Поэтому рост RSS к концу серии нельзя
приписывать бюджету 8000 мс. `keyspace` и `used_memory_bytes` до/после каждого
trial позволяют видеть фактическое число записей. Redis CPU включает фоновую
работу за время trial и не является чистой стоимостью GET/SET.

Другие контейнеры и программы хоста продолжали работать. Их нагрузка не
контролировалась; три повтора не дают оснований приписывать малые различия Redis.
Парные режимы используются для крупного эффекта hit. Будущую производительность
на другом объёме данных и эксплуатационный hit rate этот эксперимент не оценивает.

## Воспроизведение и проверка данных

Нужны Python 3.11+ и Docker. Получите измеренный commit, затем из его корня:

```sh
docker build -t navix-redis-bench-router:route3 -f core/Dockerfile .
docker build -t navix-redis-bench-route3:current services/route-engine3
python infra/benchmark_redis_route3.py --output /absolute/path/to/empty-results --repeats 3 --budgets 1000 8000
```

На Windows используйте `py -3` и, например, `F:/Temp/redis-route3-results`.
Стенд создаёт внутреннюю сеть без внешнего доступа и host-портов, использует
одноразовый пароль и удаляет только свои контейнеры и сеть. Сборка образов
производится заранее и может обращаться к реестрам. Все исходники монтируются
read-only. Паролей в опубликованных JSON нет.

Полные результаты сравниваются внутри каждого бюджета: вход, граф, код,
основной план с доказательствами и hybrid-отчётом, каталог и все семь его планов.
Из hash исключаются только `computed_at`, `calculation_ms`, `result_id`.
Чтение каталога дополнительно проверяется на неизменность активного плана.
Стенд отклоняет пропавший hybrid-отчёт, отсутствие реальных успешных HTTP-вызовов
route3, неподходящие счётчики Redis и любое расхождение semantic digests.

Сводка пересчитывается из JSON этой папки, без новых замеров:

```sh
python docs/benchmarks/redis-route3-20260928/summarize.py
```

Используются медианы trials; warm и p95 объединяют запросы одного режима.
p95 — nearest rank. Точные значения, единицы и все счётчики доступны в
[summary.json](summary.json), исходные параметры и ресурсы — в manifest.

## Проверки и ограничение сборки

28 профильных тестов Redis, hybrid, route3 и стенда прошли; Ruff изменённых
Python-файлов и `git diff --check` прошли. Отдельный пилот из четырёх trials
проверил стенд до основной серии; его времена не включены в сводку.

Чистая Docker-сборка API остановилась на существующем повреждении lockfile:
`ERR_PNPM_LOCKFILE_MISSING_DEPENDENCY`, отсутствует `lodash.camelcase@4.3.0`.
Оба frozen install шага упали одинаково. [Команда и ошибка](build-gate.json)
сохранены отдельно. Lockfile в этой задаче не менялся. Новый `pnpm smoke` на
чисто собранном приложении не выполнен; предыдущие smoke-проверки лаунчера не
выдаются за проверку этой сборки. Данное ограничение не препятствует реальным
HTTP-измерениям Python Router и двух отдельных сервисов, но блокирует слияние
ветки по требованию зелёного smoke gate в AGENTS.md.
