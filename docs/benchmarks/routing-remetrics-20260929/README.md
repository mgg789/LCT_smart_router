## Почему Юго-Восток и Восток выглядят иначе

1. **Покрытие графов.** Текущие графы ограничены Москвой/МКАД. За пределами покрытия OSRM
   может вернуть успешный `road`, привязав координату к краю графа. Все 32 исключённые заявки:
   Кашира — 16, Домодедово — 12, Ступино — 4. Максимальная ошибка конца маршрута — **93,35 км**.
   Эти же 32 точки не проходят даже порог 5 км. Это не небольшая погрешность геокодирования.
2. **Разная нагрузка.** Восток: 66,2 ч нормативных работ на 124 ч смен; полный Юго-Восток:
   93,8 ч на те же 124 ч; Юг/Центр: 59,5 ч на 112 ч. Переезды и ограничения окон добавляются
   сверх этой нагрузки. Нельзя объяснять разницу одним качеством оптимизатора.
3. **Строгие окна.** Завершение работы должно поместиться в окно и смену, без 10-минутного
   допуска и терминального послабления. Старые 60/66 и +122% к FIFO измеряли другой режим
   и приблизительную дорожную матрицу.
4. **Ограниченный поиск.** Остаток получает `NO_FEASIBLE_ASSIGNMENT_FOUND`: это результат
   ограниченного поиска, а не доказательство невозможности. Особое слабое место — срочные
   заявки Юга/Центра: **8/16**. Общий процент не должен скрывать эту цифру.
5. **Входные допущения.** Координаты обновлены из LocationIQ, но 3 адреса Востока и 2
   Юго-Востока сопоставлены с улицей, а не зданием; на Юге/Центре есть строительный участок.
   Бригады, транспорт, смены, навыки и длительности частично восстановлены из допущений.

## Что обнаружено и исправлено в ходе измерения

Hybrid проверял поездку к работе по `job`-остановке. При ожидании открытия окна входящее плечо
на самом деле заканчивается на `wait`, поэтому подставлялось `planning_as_of` вместо фактического
времени выезда. Теперь проверяются реальные `RouteLeg`, их начало, конец и `departure_at`.
Автомобильное микроплечо до 300 м проверяется как пешее, согласно действующей политике.
Диагностика задержки проходит через ожидания и проверяет завершение работы; строгая допустимость
подтверждается отдельно валидатором плана и независимым аудитом.

Регрессионный тест сначала воспроизвёл неправильное время (0 вместо 9000), затем прошёл после
исправления. `pre-wait-fix.json` и `pre-fix-audit.json` сохранены **только как отрицательное
доказательство**: их счётчик `verified` не означал совпадение фактических времён.

## Диагностика усилия поиска

На той же строгой матрице при увеличении бюджета с 3 до 10 с число назначений
осталось **59 / 45 / 47** по регионам. Увеличение `solution_limit` со старых 32 до
стандартных 10000 также не подняло эти региональные показатели. Это наблюдение для
данных запусков, не доказательство оптимальности.

Одиночный маршрут строится для каждого из 7 неназначенных заданий Востока и каждого
из 9 на Юге/Центре; на покрытом Юго-Востоке — для 5 из 6. Значит, объяснять все потери
«невозможными исходными заявками» нельзя: нужно исследовать совместное расписание,
приоритеты и шаги улучшения поиска. Проверка одиночного маршрута не доказывает,
что все эти задания удастся добавить одновременно. Доказательства: `search-effort.json`.

## Одинаковые условия сравнения

- `strict_time_windows=true`, `solution_limit=10000`, `time_limit_ms=3000`, политика `compact`.
- Метро и модель дорожного трафика включены; погода зафиксирована как ясная, множитель 1.
- Буфер доступа **600 с** на ненулевое плечо включён в показатель дороги.
- Обеды выключены одинаково у всех алгоритмов; дополнительный персонал не создаётся.
- FIFO — самостоятельный алгоритм. Он тоже проходит verify → replan до проверки всех выбранных
  плеч; сравнение не использует старый матричный FIFO против проверенного Hybrid.
- Помимо FIFO сохранены nearest и urgency greedy, но их строки `*_matrix` — **предварительные
  матричные оценки**, не доказанный результат полной Route3-проверки.
- Порог 250 м в `coverage.json` — предварительный аудит точек от офиса. Отдельно проверены
  **все реально выбранные направленные плечи**, включая метро и переходы между заявками.
- Полный Юго-Восток и полный набор 205 сохранены в диагностических строках, но помечены
  `INVALID_GRAPH_COVERAGE_RAW_DIAGNOSTIC_ONLY` и исключены из публикационных чисел.

## Алгоритм и оставшиеся упрощения

OSRM использует предобработанный MLD-граф дорог. Route3 отдаёт матрицы и маршруты;
для автомобиля поверх базовых скоростей применяются модельные множители трафика.
Router Core строит и улучшает план, затем Hybrid запрашивает точные плечи Route3 по времени
выезда и пересчитывает план до сходимости. Это ограниченный эвристический поиск, не доказанный
глобальный оптимум. Бизнес-критерии учитывают категории работ и приоритеты раньше вторичных
целей расстояния и числа бригад; один только максимум числа заявок не описывает функцию цели.

«Точные плечи» здесь означает согласованность с выбранной моделью Route3, **не точность реального
времени поездки**. Трафик не является live-пробками; пешая скорость 5 км/ч, велосипедная —
15 км/ч на пешеходном графе. Метро имеет интервальную модель, условный общий старт в 05:30,
закрытие 01:00–05:30; это не реальное расписание каждого направления. Геометрия перегонов
обновлена, а времена поездов остаются модельными. Маршруты бригад открытые, без возвращения
в офис после последней заявки. Исторические «8% к Яндексу» по пяти ручным примерам не
перепроверены для этой версии и не являются её подтверждённой точностью.

## Артефакты и воспроизведение

- `coverage.json`: 416 запросов, версии графов, все точки и ошибки привязки.
- `strict.json`: строгие региональные планы, исходные снимки, настройки, хеши файлов,
  матричные повторения, проверенные Router/FIFO, измеренное время и память.
- `strict-audit.json`: независимая сверка 240 выбранных плеч и ограничений региональных планов.
- `strict-union.json`: единый запуск, 205 в диагностике / 173 в публикационном расчёте,
  встроенный аудит выбранных плеч. Пиковая память Python — около 400,3 MiB.
- `tolerant-matrix.json`: отдельное сравнение допусков без смешения со строгими результатами.
- `sensitivity.json`: детерминированный стресс фиксированного совместного плана.
- `run_remetrics.py`: запуск без изменения пользовательского плана и базы стенда.
- `lab/audit_graph_coverage.py`, `lab/audit_remetrics_plans.py`: проверки покрытия и результатов.

```sh
export PYTHONPATH=.
export ROUTE3_URL=http://127.0.0.1:8128
export ROUTE3_CACHE=.codex/remetrics-cache
python -m lab.audit_graph_coverage --output docs/benchmarks/routing-remetrics-20260929/coverage.json
python docs/benchmarks/routing-remetrics-20260929/run_remetrics.py \
  --coverage docs/benchmarks/routing-remetrics-20260929/coverage.json \
  --output docs/benchmarks/routing-remetrics-20260929/strict.json \
  --regions east southeast south_central
python -m lab.audit_remetrics_plans \
  --input docs/benchmarks/routing-remetrics-20260929/strict.json \
  --output docs/benchmarks/routing-remetrics-20260929/strict-audit.json
```

Измеренный исходный код идентифицирован SHA-256 в JSON: объединены `d8d763c` (исправления)
и `fc84180` (новый dev с геоданными), затем исправлена проверка ожиданий.
Счётчик оконной диагностики дополнительно уточнён после регионального замера; независимый
аудит подтвердил времена и ограничения сохранённых планов без расхождений.
Стенд/нагрузка других пользователей не являются контролируемой лабораторной средой.
Браузер, production, нагрузочный soak, полевое выполнение и свежая внешняя ETA-сверка
в этом проходе не проверялись. Старые результаты exact-gap, Monte Carlo и Redis-бенчмарков
не переносятся автоматически на новую версию и не выдаются за свежие измерения.
