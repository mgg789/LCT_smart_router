# Ручной режим диспетчера

Manual сохраняет работу LIVE и автоматический пересчёт. Включение требует причины; сама активация не меняет назначения. После первого включения браузер показывает обзор возможностей.

Диспетчер может закрепить заявку за инженером на линии или оставить без назначения, изменить окно заявки, будущий обед и смену инженера. Изменение клиентского окна проходит существующее подтверждение. Аварии не имеют редактируемого окна. Начатые/выполненные работы и принятые передачи оборудования защищены от ручной перестановки.

Решения хранятся отдельно от исходных данных, в `AppState[manual.session]`, с версией и рабочей датой. Новый выбор получает верхний уровень приоритета; повторное изменение того же параметра заменяет выбор. Роутер сначала ищет план со всеми ограничениями, затем совместимый набор по порядку приоритетов. Это ограниченный поиск допустимого плана, а не доказательство математической невозможности: отсутствие найденного варианта также требует решения диспетчера. Физическая доступность, навыки, оборудование и выполненные факты остаются обязательными.

При конфликте результат содержит принятые, отклонённые решения и участников конфликта. До подтверждения диспетчером сохраняется последний применённый план. В панели «Конфликт приоритетов» карточки можно перетаскивать, удалять и применять порядок; конфликтующие карточки выделены красным. «Приоритеты» после «Настройки» в системном меню открывает панель заранее и отображается только в Manual. Новое решение сбрасывает подтверждение; новые участники конфликта после LIVE требуют повторного просмотра.

Возврат в Auto удаляет решения и публикует новый расчёт по исходным условиям и текущим фактам. Уже выполненные работы не возвращаются. Восстановление прошлой ревизии при активных ручных решениях запрещено, поскольку она не учитывает текущие ограничения.

## API и контракт роутера

- `POST /api/v1/dispatch/mode`: `mode`, `operationId`, обязательный `reason` при входе в Manual.
- `GET /api/v1/dispatch/manual`: версия сессии, причина, решения, результат проверки, `needsReview`.
- `POST /api/v1/dispatch/manual/decisions`: `operationId`, `expectedVersion`, `kind` (`assignment`, `window`, `lunch`, `shift`), `targetId`, `engineerId` (включая `null`) либо `startAt/endAt` (epoch seconds).
- `POST /api/v1/dispatch/manual/priorities`: точная перестановка `decisionIds`, версия, operationId.
- `DELETE /api/v1/dispatch/manual/decisions/:id`: версия и operationId.

Все записи защищены ролью диспетчера, идемпотентностью и CAS. Snapshot содержит необязательный `manual_decisions`; результат — `main.manual_resolution`. Старый snapshot без решений сохраняет прежнюю автоматическую семантику. Оригинальные окна в snapshot нужны для контроля устаревших результатов; Core применяет ограничения в приватной копии.

## Встроенный AI

Оба профиля диспетчера знают возможности и издержки Manual. Консультант остаётся только читающим. Для агента `request_manual_mode` отправляет успешное событие `tool_result`, которое открывает ту же модалку входа, что и кнопка в политиках. Событие означает запрос подтверждения, а не включение режима. Повторно доставленное SSE-событие не открывает модалку повторно; при уже активном Manual запрос игнорируется интерфейсом.

После фактического входа в Manual агенту доступны `get_manual_state`, `prepare_manual_decision`, `prepare_remove_manual_decision`, `prepare_manual_priorities`. Каталог обновляется при работе агента; сервер повторно проверяет режим при исполнении. Перед изменением читается версия; сохраняются проверки доступности, начатых работ и согласия на изменение окна. Агент не должен использовать Manual как обычный способ удовлетворить запрос: сначала объясняет, почему штатных средств Auto недостаточно, и предупреждает о снижении эффективности и конфликтах.

Внешний API использует приведённые выше маршруты `/api/v1/dispatch/mode` и `/api/v1/dispatch/manual` с авторизацией диспетчера. Браузерная модалка для API не нужна; обязательная причина входа, идемпотентность и версия решений проверяются сервером.

## MCP

Диспетчерский MCP предоставляет `set_control_mode` (`mode`, обязательная причина для Manual), `get_manual_state`, `edit_manual_decision`, `remove_manual_decision`, `reorder_manual_priorities`. Временные интервалы для MCP передаются в epoch seconds; изменение и удаление требуют `expectedVersion`, приоритеты — всех `decisionIds` в нужном порядке. Используются те же системные операции и проверки, что в HTTP API. При изменении окна сначала возвращается challenge с точными границами: после согласия пользователя MCP повторяет `edit_manual_decision` с `windowChangeConfirmation`, а HTTP-клиент — исходный запрос с `X-Window-Change-Confirmation`. Это подтверждение конкретного изменения, а не модалка переключения режима.

MCP не показывает браузерную модалку. Инструкция `set_control_mode` требует сначала объяснить последствия и получить **явное подтверждение пользователя**; это обязанность вызывающего агента, а не серверная имитация UI-согласия. Нельзя включать Manual по умолчанию ради любого редактирования плана. Возврат в Auto удаляет все ручные решения и также требует осознанного выбора.
