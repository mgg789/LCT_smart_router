# Совместное планирование диспетчера и AUTO — DRO-125

В режиме **«Ручные корректировки»** диспетчер задаёт ограничения, а Router продолжает
строить и применять план вокруг них. Вход требует непустой причины; причина, автор и
время сохраняются в журнале. Это основной путь изменения назначений в новом интерфейсе
`apps/frontend`. Аварийный [MANUAL](manual-control.md) остаётся отдельным режимом.

## Работа диспетчера

1. Открыть меню политики → **«Ручные корректировки»**, указать причину →
   **«Начать корректировки»**. Режим сервера становится `assisted`.
2. Открыть заявку на плане дня. Выбрать исполнителя или изменить порядок стрелками.
   Сервер сначала рассчитывает предложение со всеми остальными работами дня.
3. Если существенных последствий нет, одно действие сразу применяет проверенное решение.
   Иначе открывается **«Проверьте последствия»**: назначения до/после, потерянные назначения,
   смена исполнителей, сдвиги времени, порядок маршрутов и дополнительные ресурсы.
   До **«Подтвердить и применить»** текущий план не меняется.
4. **«Отменить изменение»** сохраняет текущий план и закрепления. **«Пересчитать»**
   обновляет предложение, после чего применение снова требует отдельного нажатия.
5. **«Закончить корректировки»** возвращает `auto`, сохраняя закрепления. Для их снятия
   снова открыть корректировки и использовать **«Снять закрепление»** в заявке либо
   **«Снять все закрепления»** на плане. Снятие также проверяется перед применением.

Назначение закрепляет конкретную заявку за инженером, но не фиксирует время её начала.
Перестановка закрепляет исполнителя и относительный порядок всей доступной очереди
выбранного инженера. Свободные заявки могут вставляться между закреплёнными. Начатая,
завершённая, отменённая или уже зарезервированная LIVE-работа не редактируется этим путём.
В Router уходят только закрепления оставшихся работ текущего дня. Сброс данных очищает
закрепления и предложения; обычный переход режима этого не делает.

## Когда нужно дополнительное подтверждение

Порог задаёт `ASSISTED_IMPACT_LIMITS` в System Layer. Сейчас существенным считается хотя
бы одно из следующих последствий относительно действующего плана оставшихся работ:

| Последствие | Порог |
|---|---|
| Ранее назначенная заявка остаётся без инженера | Любая заявка, включая обычную |
| Меняются исполнители | Не менее 3 заявок |
| Меняется относительный порядок | В инверсиях участвует не менее 3 заявок |
| Начало работы сдвигается позже | Не менее 30 минут |
| Завершение выходит за клиентское окно | Новое нарушение хотя бы одного окна |
| Появляются резервные ресурсы политики `covering` | Любой новый используемый ресурс |

Это продуктовые пороги данной реализации, а не доказательство математической
критичности или оптимальности. Сравнение времени отключено для исходного аварийного
ручного плана: его приближённая ETA не выдаётся за проверенный график.

Подтверждение разрешает принять перечисленные последствия, но не отменяет жёсткие
ограничения. Если Router не нашёл допустимый план с закреплением, предложение имеет
состояние `blocked` и не применяется даже с `confirmCritical=true`. Для такого случая
нужно изменить исполнителя/порядок или снять конфликтующее закрепление. Сообщение
«не найден допустимый план» не является доказательством отсутствия решения.

При новых внешних событиях AUTO тоже учитывает закрепления. Если готовый пригодный
результат с действующими закреплениями вызывает существенные последствия, System Layer
сохраняет его как автоматическое предложение. На плане появляется кнопка просмотра;
старый план остаётся действующим до решения диспетчера. При несовместимости закреплений
показывается ошибка расчёта. Отмена предложения не устраняет внешнюю причину, например
офлайн инженера: диспетчеру всё ещё нужно устранить конфликт или снять закрепление.

## API

Все пути ниже имеют префикс `/api/v1` и доступны диспетчеру.

| Метод и путь | Назначение |
|---|---|
| `POST /dispatch/mode` | `mode: auto / assisted / manual`; для `assisted` и `manual` обязательна причина |
| `GET /dispatch/assisted` | Режим/версии, закрепления, `editableRequestIds`, актуальное предложение и блокирующие причины |
| `POST /dispatch/assisted/preview` | Рассчитать и сохранить предложение без изменения рабочего плана |
| `POST /dispatch/assisted/apply` | Повторно проверить и атомарно применить предложение |
| `POST /dispatch/assisted/cancel` | Отменить предложение без изменения плана |

Вход в режим использует существующие `expectedModeVersion` и `expectedPlanRevision`.
Прямой переход из аварийного `manual` в `assisted` отклоняется: сначала нужен явный AUTO.

Запрос `preview`:

```json
{
  "operationId": "UUID",
  "expectedModeVersion": 2,
  "expectedPlanRevision": 7,
  "expectedConstraintsVersion": 1,
  "change": { "kind": "assign", "requestId": "request-id", "engineerId": "engineer-id" }
}
```

Варианты `change`: `assign`; `reorder` с `engineerId` и полной `requestIds` доступной
очереди; `release` с `requestIds`; `release_all`; `replan`. Редактирование требует
`assisted`, а повторный расчёт доступен также в `auto`.

Ответ предложения: `proposalId`, `previewFingerprint`, `source` (`dispatcher` или
`automatic`), `state`, `createdAt`, `expiresAt`, `canApply`, `requiresConfirmation`,
`versions`, `change`, `constraints`, `impact`, `blockers`. `impact` содержит `lost`,
`moved`, `reorderedRoutes` с порядком до/после, `delayed`, `newlyLate`,
`addedEngineerIds`, `criticalReasons`, `timingsCompared` и счётчики назначений.
Клиент не передаёт план, оценку последствий или доказательства допустимости.

```json
{
  "operationId": "NEW-UUID",
  "proposalId": "UUID-OF-PREVIEW",
  "expectedPreviewFingerprint": "64-lowercase-hex-characters-from-response",
  "confirmCritical": true
}
```

`apply` возвращает `proposalId`, `state: applied`, `planRevision`, `constraintsVersion`
и фактически принятый `impact`. Для некритичного действия `confirmCritical=false`.
`cancel` принимает отдельный `operationId` и `proposalId`.

## Согласованность и отказоустойчивость

- Предложение действительно 5 минут реального времени и связано с автором (для ручного
  намерения), поколением базы, версией режима, ревизией плана, версией закреплений,
  фактами задачи и контекстом карт/настроек Router.
- Перед применением выполняется новый расчёт на текущем логическом времени. Новые либо
  усилившиеся существенные последствия требуют новой карточки и нового подтверждения.
  Допуски при повторном расчёте: сдвиги сравниваются по корзинам 15 минут, опоздания
  по корзинам 5 минут. Новые затронутые заявки, новые исполнители при массовом переносе
  и другой массовый порядок прежним подтверждением не покрываются.
- `expectedPreviewFingerprint` связывает нажатие с конкретной карточкой. Повтор старого
  подтверждения не принимает обновлённую карточку с тем же `proposalId`.
- Сетевые расчёты находятся вне транзакций записи. Под блокировкой проверяются версии,
  факты, точный hash публикации; закрепления, публикация снимка, обычная приёмка результата
  и аудит записываются одной транзакцией. Частично применённого закрепления нет.
- Повтор одного `operationId` возвращает результат первой операции. Другой payload с тем
  же ID отклоняется. Два конкурирующих изменения не перетирают друг друга.
- `VERSION_CONFLICT` требует нового расчёта. `CONFIRMATION_REQUIRED` возвращает карточку
  в `error.details.proposal`. `RESULT_NOT_APPLICABLE` обозначает неприменимое предложение;
  `ROUTER_UNAVAILABLE` — недоступный расчёт. Во всех этих случаях рабочий план сохраняется.
- Отдельный private endpoint Router `POST /v1/dispatcher-preview` проверяет точные байты
  публикации и ожидаемый `router_context_version`. Он не заменяет текущий вход/результат
  Runtime. Схема: `core/schemas/dispatcher-plan-preview-v1.json`.

## Хранение и совместимость

Миграция `20260923190000_assisted_dispatch` добавляет `ControlMode.assisted`, JSON
`control_state.dispatcher_constraints`, `constraints_version` и таблицу
`dispatch_plan_proposals`. В ней сохраняются происхождение, состояния, source-версии,
review fingerprint, точный вход, кандидат, последствия, срок и принятая ревизия.
Журнал `plan.assisted` хранит закрепления до/после и факт подтверждения; переход режима
остаётся в `control.transition`. Прочитать оба можно через `GET /dispatch/plan/manual-history`.

В снимке Router поля `requests[].pinned_engineer_id` и `pinned_orders` опциональны.
Без закреплений они отсутствуют, поэтому прежняя сериализация и golden-набор сохраняются.
Закрепления проверяют все политики и приёмка System Layer независимо от доверия к Router.
`origin` рабочего плана остаётся `auto`: его расписание построил Router, а режим
редактирования и аудит показывают участие диспетчера.

Новый UI реализован в `apps/frontend`; прежний `apps/web` понимает значение `assisted`,
но его редактор остаётся аварийным MANUAL. Новые endpoints доступны обоим клиентам.
Нужен согласованный выпуск API, Router и нового UI после миграции. Внешние сервисы,
LLM и онлайн-геокодер для этой функции не требуются.

## Проверка

Покрытие: закрепления/порядок во всех шести политиках, независимая проверка результата,
private preview без изменения Runtime; PostgreSQL-тесты атомарности, версий, повторов,
подтверждений, отказов и отмены; UI-тесты явного подтверждения и намерений карточки заявки.
Сквозная проверка использует отдельную базу и настоящий Router. Личная приёмка
пользователя (DRO-112) остаётся самостоятельным незавершённым этапом.
