# Проверка лаунчеров — 28.09.2026

DRO-153, рабочая ветка от `dev@2d76472`. Проверялись исходные переносимые
лаунчеры и изменения этой задачи. Результаты ниже относятся к локальному
изолированному контуру, а не к публичному стенду или новой версии релиза.

## Воспроизведённые ошибки

| Сценарий | Причина и исправление |
| --- | --- |
| Проверка пакета на Windows | CRLF отличался от LF в манифесте. Хеширование текстовых файлов нормализует только переводы строк; изменение содержания по-прежнему обнаруживается |
| Docker есть, но подготовка Compose падает | Ограниченное окружение убирало PROGRAMFILES и связанные переменные Windows, поэтому Docker не находил Compose plugin. Системные пути сохранены без импорта настроек приложения в окружение Docker CLI |
| Все контейнеры healthy, лаунчер сообщает недоступный порт | Системный HTTP-прокси перехватывал localhost. Loopback readiness использует прямое соединение; системные настройки не меняются |
| Порт опубликован другим Docker-контейнером | Windows bind мог пройти из-за Docker Desktop NAT. До изменений проверяются и локальный socket, и опубликованные Docker-порты |
| Повторная настройка офлайн-экземпляра | Консоль не позволяла снова выбрать online. Переход теперь доступен с сохранением прежних значений по умолчанию |
| Закрытие/повторное создание Tk-формы в тестах | Таймер отменяется при уничтожении; фоновые операции передают данные через очередь и не удерживают объекты Tk |
| API завершается при чтении настроек во время рестарта Router | Отказ фонового обновления устаревших technical settings оставался необработанным Promise rejection. Обработчик сохраняет прежний кэш; первый запрос без кэша по-прежнему возвращает ошибку. Регрессионный тест воспроизводит отказ до исправления |
| Python в Windows отклоняет действительный сертификат distribution | В локальном CA-хранилище найден истёкший cross-sign ISRG Root X2. HTTPS-контекст использует действующую часть уже доверенных CA, сохраняя проверку цепочки/имени хоста; системное хранилище не меняется |
| Манифест из нового dev ссылается на отсутствующие файлы чистого клона | В манифест попал локальный `.mimosa` другого рабочего каталога: 41 отсутствующий файл. Каталог исключён генератором, добавлен регрессионный тест |

Изначальное общее имя `navix-launch` создавало риск пересечения разных папок.
Новые экземпляры получают отдельные идентичности и метки ресурсов; старый
экземпляр распознаётся с сохранением его базы. Это не попытка имитировать
параллельную установку через произвольное удаление чужих контейнеров.

## Практические прогоны

Среда: Windows, Python 3.13.3 для cmd/Tk, Python 3.12.10 для части тестовых
драйверов, Docker Engine 29.7.2, Compose 5.5.0. Пакет распакован из Git-архива
в отдельные каталоги, без `.launch` и без состояния предыдущей установки.
Два экземпляра Navix и посторонние контейнеры сосуществовали на разных портах.

- Чистый Windows-консольный запуск: Full, online, OSRM выключен, ручной ввод
  параметров и учётной записи; API и UI готовы. Оба Windows-входа выполняют `--help`.
- Full с OSRM: контейнеры, API, вход диспетчера, старт дня, 14 заявок и три
  инженера проверены в браузере; карта маршрутов отображается.
- Переход Full online → Headless offline с изменением порта API: успешен,
  identity БД и контрольная запись сохранены.
- Переход Headless offline → Full offline через Windows-консоль: успешен,
  подготовленные образы повторно использованы без pull/build.
- Обычное удаление → повторная установка: контрольная запись, пароли БД и
  идентичность установки сохранены.
- Полное удаление после отдельного подтверждения: собственные тома удалены,
  локальная identity удалена, состояние стало new. Контрольная запись другого
  экземпляра Navix и работа посторонних контейнеров сохранены.
- После ошибки публикации занятого порта экземпляр распознан как частичный
  и восстановлен на прежнем свободном порту с сохранением данных.
- `pnpm smoke` через офлайн-gateway: **21/21**, включая публикацию снимка,
  автоматическую приёмку и перестроение после новой срочной заявки.
  Для smoke у проверочного экземпляра отдельно выключался DEMO_STAND.

Измерения отдельных этапов разработки: первая сборка образов 449,24 с;
повторный запуск старой установки с обновлением 125,92 с; переход в Headless
offline 62,88 с; удаление с сохранением и восстановление 67,09 с. Это прогоны
с разным состоянием кэша, а не парный benchmark скорости лаунчера.
Машиночитаемая сводка: [launcher-validation-20260928.json](benchmarks/launcher-validation-20260928.json).

контейнеры в этом тесте не запускаются. Ruff применён с проектным набором
