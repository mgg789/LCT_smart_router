# Два расширения ML-контура: контролёр качества импорта и режимы дня (проект реализации, 2026-09-24)

> Статус: **проект реализации** — ничего не обучено, только дизайн. Существующий контур
> оценки плана и его самокалибровка описаны в [ml-predictions.md](./ml-predictions.md).
> Этот файл добавляет две следующие зоны так, чтобы ML был распределён по проекту как
> инструмент, а не стоял в одном месте: скрининг входных данных (зона 1) и дообучение
> коэффициентов в процессе работы (зона 2).

Карта ML-паттернов проекта после обеих зон:

| Паттерн | Где | Статус |
|---|---|---|
| Монте-Карло оценка плана + самокалибровка по фактам | `core/robustness.py`, `orchestrator/ai` | работает |
| Скрининг входа: правила + статистика батча + ученик | импортеры sys | зона 1, этот файл |
| Дообучение в процессе: режимы дня из фактов + погоды | `core/predict_calibration.py` | зона 2, этот файл |
| Учитель → ученик (дистилляция решающей модели) | конвейер разметки для зоны 1 | зона 1, этот файл |

## Зона 1. Гибридный контролёр качества импорта (алгоритм + статистика + ML)

### 1.1 Принцип: предупреждаем, а не судим

Контролёр **неблокирующий**. После разбора загружаемого файла, до записи в рабочее
множество, он показывает модалку с находками и двумя кнопками — **«Загрузить так»** и
**«Отменить»**. Тон формулировок — «мы просто информируем на всякий случай», никогда
«ошибка». Мотивация: официальный датасет организаторов содержит легитимные
«странные» данные (Кашира и Ступино за МКАД, окна 0:01–23:59, дробные адреса) —
детектор обязан их **показать как особенности**, а не отвергнуть, иначе получаем минус
«не принимаем официальный датасет». Данные принимаются как есть; решение всегда за
диспетчером (D-11).

### 1.2 Три слоя проверки

| Слой | Что ловит | Механизм | Обучение |
|---|---|---|---|
| Алгоритмический | известные форматы-аномалии | детерминированные правила импортера (`context/18` §6.2): пустые строки/окна, маркер «весь день», пустой район, нестандартные префиксы адресов | нет |
| Статистический | «выбивается из данных» | робастные оценки на самом батче: медиана/MAD в лог-пространстве по признакам (длина окна, удалённость от офиса после геокодинга, длительность по карте работ, адрес-дубликаты) | нет — считается на батче, детерминирован |
| ML-слой | «серая зона» семантики | выученный ученик-классификатор «битая строка»: обрезанные адреса, двусмысленные окна, мусор в полях, где хрупкие правила проигрывают языковой модели | да, один раз на этапе разработки |

Разделение ответственности принципиально: правила ловят *известно-битое* (и молча
чинят, как сегодня), статистика и ученик ловят *неожиданное, но валидное* — и только
показывают. Кашира — легитимна и остаётся в данных; контролёр честно скажет «9 заявок
за МКАД — день для них особенный».

### 1.3 ML-слой: учитель → ученик (дистилляция решающей модели)

- **Критерии битости** формулируются как таксономия: уровень 1 — неисправимо
  (ловят правила), уровень 2 — серая зона (профиль ученика), уровень 3 — чисто.
- **Разметка**: внешняя решающая модель (Jev, режимы choice/score; аналоги — laya-mlx,
  kev) получает строку + определение битости и возвращает вердикт с уверенностью.
  Оставляем только высокоуверенные метки; 20–30 строк выборочно проверяет человек.
- **Данные для разметки**: официальные строки (синтетика + контроль, 205 + 205) плюс
  ~1–2k возмущённых полу-синтетических (генератор с фиксированным сидом: перестановка
  полей, обрезка, сломанный префикс, потерянная квартира).
- **Ученик**: логистическая регрессия на интерпретируемых признаках (длины полей,
  доли цифр/букв, паттерны префиксов, наличие координат). Веса — JSON рядом с
  импортером; инференс — в TS, офлайн, миллисекунды, детерминирован.
- **Формулировка для документации и Q&A**: «обучающая разметка выполнена внешней
  решающей моделью; на инференсе внешний API не используется». Экономика доказуема:
  батч-разметка один раз на этапе разработки против вызовов API на каждом импорте;
  локальный инференс — требование офлайн-контура (`context/15` §4). Прямой ответ на
  вопрос «как обучали»: классическая дистилляция решающей модели в локальный
  классификатор.
- **Модель не валидна вечно**: смена критериев битости = переобучение ученика и bump
  версии весов (см. 1.5).

### 1.4 UI: модалка перед записью

```
Проверка данных: 3 находки в 66 заявках

• Особенности региона — 9 заявок за МКАД (Кашира, Ступино).
  Это легитимно, но дорога ~1,5 ч в одну сторону: день для них особенный.
• Необычные окна — 11 заявок «весь день» (0:01–23:59) — обрабатываются как
  окно на всю смену.
• Подозрительные адреса — 2 строки: «г.Город Москва, …» — вероятно, норм,
  но проверьте геокодинг.

[Загрузить так]  [Отменить]
```

- Каждая находка — человекочитаемая причина + счётчик + 2–3 примера; никаких «ML», σ
  и скор-чисел в тексте (скор и слой — в подсказке «данные проверки»).
- Находок нет → модалка не открывается, импорт идёт сразу.
- «Загрузить так» — данные пишутся как есть, без флагов в заявках; отчёт остаётся в
  журнале импорта. Контролёр никогда не блокирует, не чинит и не удаляет.

### 1.5 Точки встраивания и приёмка

- Вызов: `dataset-import` / `upload-import` после парсинга и геокодинга, до записи;
  стат. слой и ученик — чистые функции в TS (без новых зависимостей), конвейер
  разметки учителем — скрипт в `~/Projects/LCT/ml-lab` (вне репо).
- Приёмка: фиксированные батчи дают известные находки; σ=0-аналог — на чистом батче
  контролёр молчит; детерминизм повторного прогона; веса ученика версионированы.
- Оценка объёма: разметка 0,5 дня + генератор 0,5 + ученик и интеграция 1 + UI 0,5.

## Зона 2. Дообучение режимов дня из фактов и погоды

### 2.1 Что добираем

Единственное место, где самокалибровка пока капитулирует: режимы дня
(`PredictCalibration.regimes`) — заводские допущения (normal 0.65 / rain 0.30 ×1.12 /
heavy 0.05 ×1.25) с честной пометкой «пока нет погодно-связанной истории». Зона 2
заменяет их измеренными — это **четвёртый блок** существующей петли
`computeFromFacts` (σ длительностей, CV перегонов, отмены → + режимы). Датасет не
нужен: онлайн-оценка в процессе работы.

### 2.2 Метод

1. **Перегоны**: факты `arrived(заявка i) − finished(заявка i−1)` уже собираются
   AI-контуром.
2. **Нормировщик**: сырые секунды несравнимы между маршрутами — делим на
   `normativeTravelDurationSec` заявки прибытия (поле уже в схеме). Работаем в
   лог-отношении «факт/норматив».
3. **Погодная атрибуция дней**: архив Open-Meteo за даты фактов, качается один раз и
   кладётся в вечный per-day кэш appState — после первого скачивания контур полностью
   офлайн. Альтернатива для LIVE-демо: логировать текущий прогноз за рабочий день.
4. **Оценка**: группы дней по погодному коду (ясно/облачно vs дождь vs снег/гроза);
   множитель режима = `exp(среднее лог-отношение группы − среднее лог-отношение ясных
   дней)`. Вероятности режимов — доли дней в истории.
5. **Минимумы честности**: меньше ~15 перегонов или ~2 дней в группе — множитель
   группы остаётся заводским; ниже общего минимума — вся калибровка режимов заводская.
   Прогресс-бар «Точность самонастройки» получает строку покрытия по погодным группам.

### 2.3 Потребители (два)

1. **Монте-Карло**: `PredictCalibration.regimes` — гнездо готово, predictions сразу
   учитывают измеренные режимы.
2. **Время в пути в солвере**: сегодня погодный множитель живёт в фиксированной
   таблице core (`/v1/weather`: дождь ×1,08, снег ×1,15, гроза ×1,18). Выученные
   множители расширяют калибровку полем `weather_multipliers`, и погодный код core
   читает её вместо констант — заводская таблица остаётся фолбэком.

### 2.4 Честность и демо

- Провенанс как у всей калибровки: `source: learned`, `learned_from` (перегоны, дни,
  погодные группы), `assumptions`; версия калибровки входит в сид предиктов; сброс
  данных откатывает режимы до заводских вместе с фактами.
- Контур никогда не меняет план сам: режимы — параметры оценщиков, решение за
  диспетчером/солвером (D-11).
- Демо-сценарий: два LIVE-дня, ясный и дождливый → система сама сообщает «в дождь
  едем на ~9% дольше, чем предполагали» и сужает оценку надёжности дня. Это слайд
  «ML замыкает петлю на самом себе».
- Оценка объёма: архив погоды с кэшем 0,5 дня + оценка и минимумы 0,5 + погодный
  потребитель core 0,5 + UI-строка прогресса 0,25.

## Общие правила обеих зон

- Неблокирующие и немутирующие план: флаги и коэффициенты, never decisions (D-11).
- Детерминизм при фиксированных входах; версии (весов ученика, калибровки) входят в
  идентичность отчётов там, где на них опираются числа.
- Честные минимумы и провенанс; при недоверии данным — откат к заводским значениям.
- Офлайн-контур не нарушается: сетевые шаги (разметка учителем, архив погоды) —
  одноразовые шаги разработки с постоянным кэшем, инференс всегда локальный.
