# Соответствие ТЗ: текущий dev и проверяемые сценарии

Сверено с кодом цикла 2.0 от 26.09.2026. Это карта возможностей репозитория,
а не подтверждение версии публичного стенда. Исходные требования:
[официальный кейс](../context/26-case-source.md),
[датасет и MVP](../context/18-official-case-dataset.md),
[ответы организаторов](../context/48-official-facts-2026-09-16.md).
История старой приёмки 18.09 остаётся в Git; утверждения той версии об отсутствии
Engineer App и LLM больше не действуют.

## Семь шагов демонстрации

| Шаг | Действие в интерфейсе | Что действительно происходит |
|---|---|---|
| 1. Загрузка | «Загрузить данные» → встроенный набор ТЗ или свой JSON/gzip | Импортируются три официальных региона либо выбранная часть; собственный пакет проходит серверную валидацию. Прямой пользовательский CSV пока не поддержан: это отдельный C-8, исключённый из текущего прохода |
| 2. Распределение | «План дня» после импорта / применения политики | System Layer публикует снимок; Router рассчитывает его; сервер принимает результат только для актуальных данных и контекста |
| 3. Порядок визитов | Выбрать инженера и его маршрут | Показаны последовательность заявок, плановые времена, ожидания и обед, если он включён |
| 4. Карта | Карта дня → точка заявки / маршрут инженера | Видны точки, геометрия и происхождение плеч; локальная OSM-подложка покрывает три региона, включая дальние южные точки |
| 5. Кто, куда, когда | Открыть заявку и досье инженера | Навыки, окно, нормативная длительность, назначение, статус и объясняющие факторы |
| 6. Событие | «Инженеры» → «Снять со смены» / «Вернуть на смену»; создание или отмена заявки | Факт меняет опубликованную задачу и вызывает перепланирование. Дельта отражает реальные назначения; карта позволяет сравнить сохранённые ревизии «До / После» |
| 7. Объяснение | Карточка заявки → причины; AI-пересказ при настроенном провайдере | Основа — структурированные факторы ядра. LLM переформулирует их, но не назначает инженеров и не определяет допустимость плана |

Вход диспетчера использует собственные `DISPATCHER_EMAIL` / `DISPATCHER_PASSWORD`.
Опубликованных паролей в инструкции нет. Автономные записанные сценарии отделены
от живого дня: воспроизведение не выдаётся за свежий расчёт.

## Ограничения и политики

| Требование / решение | Реализация и границы |
|---|---|
| Навыки | Квалификация проверяется до назначения; отсутствие навыка не компенсируется лучшим пробегом |
| Окно и смена | Проверяется завершение обслуживания, а не только прибытие. «Строгие окна ТЗ» в панели политик отключает обычный допуск, терминальные 20 минут окна/смены и допуски стабильности пересчёта; выключение восстанавливает сохранённые числа |
| Транспорт, если указан | `requiredTransport` проверяется. Официальный CSV не содержит пожелания клиента о транспорте, поэтому импорт не выдумывает его. Для JSON с обоими типами `walk` и `transit` пешеход помечается «Пешеход (без ОТ)»; исторические профили сохраняют совместимость |
| Обед / оборудование | Включаются явными настройками; оборудование, ёмкость и согласованные передачи учитываются ядром. Передачи не должны нарушаться восстановлением старого плана |
| Минимизация людей | Политика compact ставит этот критерий выше пробега. Другие политики имеют другой лексикографический порядок; равенство старших критериев разрешается младшими |
| Оптимальность | Поиск ограничен бюджетом. Отсутствие найденного назначения не является математическим доказательством невозможности |

Производные ограничения дальности/погоды из C-7 в этот проход **не входят**.
Наличие транспортной модели не следует выдавать за реализацию этих дополнительных правил.

## Сравнение с FIFO

«Политики» и кнопка «Сравнить политики» в «Метриках плана» открывают одну витрину.
Сравнение не применяет чужой план. FIFO и обычные политики используют один снимок,
состав инженеров и контекст стоимостей. Заголовочные показатели нормированы на
назначенную заявку; покрытие и абсолютные пробег, время и число исполнителей
остаются доступны. При нуле назначений удельное значение отсутствует, а не равно нулю.
Покрывающая политика с синтетическим резервом отделена от сравнения фиксированного
штата. Больший абсолютный пробег при большем покрытии не скрывается.

Расчёт многоступенчатый: сиды → собственный поиск с точной оценкой всего маршрута →
каноническая валидация. При включённом прогнозе пробок статические OR-Tools-стадии
не выполняются; при выключенном прогнозе OR-Tools генерирует кандидаты.
Расширение OR-Tools из раздела B контекста №51 не включено автоматически в эту работу.

## Сохранённый план и восстановление

`GET /dispatch/plan/previous` возвращает текущую и предыдущую сохранённые ревизии
с признаком допустимости восстановления. «Вернуть прежний план» обращается к
`POST /dispatch/plan/restore` с ожидаемой текущей ревизией. Создаётся **новая**
ревизия с `origin=restore`, копирующая прежние маршруты, времена и геометрию;
журнал не переписывается, повторный запуск оптимизатора не подменяет восстановление.

Изменившиеся заявки, условия инженеров, начатые работы, использование обеда,
несовместимый технический контекст и оборудование могут запретить возврат.
Сервер проверяет это повторно внутри операции; видимая доступность кнопки не
заменяет проверку. Будущие реальные события могут снова вызвать автопересчёт.

## Дороги и офлайн

Router готовит пакетные дорожные матрицы **до** поиска; внутри поиска сеть не
вызывается. По умолчанию compose использует `http://road-api:8123` для стоимости
Router и геометрии System Layer. При недоступности провайдера используются кеш и
подготовленный региональный граф; происхождение стоимости сохраняется.

Вендоренный дорожный граф ограничен МКАД. Офлайн-подложка трёх регионов не расширяет
его автоматически: вне дорожного покрытия возможна явно обозначенная аппроксимация.
Не следует путать точную нарисованную улицу со стоимостью плеча в оптимизаторе.
Источники геокодирования и матриц описаны в [данных](./data.md), режимы — в
[solver](./solver.md), происхождение подложки — в
[паспорте карты](../apps/web/public/maps/README.md).

## Дополнительные приложения и границы проверки

Engineer App существует: мобильный вход, свой день, выполнение заявок и профиль.
Клиентское приложение существует; AI-функции зависят от настроенного провайдера
и не заменяют ручной ввод. Ситуационные предикты рассчитывает ядро, а не LLM.
Наличие закрытых пунктов интерфейса не означает отсутствия этих приложений.

Проверки запускаются по [CI](./ci.md) и [runbook](./runbook.md): тесты модулей,
сборка, smoke и ограниченный браузерный регресс в одноразовом Docker-контуре.
Браузерные проверки не заменяют проверку SMTP, настоящего LLM, нагрузочное
тестирование, ручную визуальную приёмку и проверку конкретной production-версии.
