# Соответствие ТЗ: что есть и куда нажать

Документ для проверки без додумывания. Формулировки ТЗ — из
`context/18-official-case-dataset.md` §3 и §5. Здесь только то, что реально
можно увидеть в прототипе. Чего нет — сказано прямо.

Публичный стенд: <https://navix.droidje.com>. Локально: <http://127.0.0.1:5173>
после `pnpm compose:up`.

Контур просит логин диспетчера (`DISPATCHER_EMAIL` / `DISPATCHER_PASSWORD` из
`.env`). ТЗ авторизацию не требовал — это наша защита стенда, не пункт кейса.
На экране входа есть кнопка «Открыть автономный демо-сценарий»: она показывает
записанный день и **не** подгружает официальный CSV.

## Семь шагов ТЗ через UI

Демо ТЗ (5–7 минут): загрузка → автоплан → карта → объяснение → событие →
новый план с дельтой → сравнение с базой. Ниже — те же семь пунктов как
последовательность кликов. Отдельной кнопки «Построить план» в интерфейсе нет:
план считается сам после импорта, смены политики или отключения инженера.

### 1. Загрузка тестовых данных

ТЗ: загрузка CSV/JSON или встроенный демо-набор.

**Что есть.** Официальный датасет лежит в репозитории
(`data/dataset/anonymized/`, три региона, 205 заявок / 35 инженеров). Кнопка
в UI вызывает `POST /api/v1/dispatch/data/import` с `regions: "all"` — curl
не нужен.

**Куда нажать.**

1. Войти диспетчером.
2. В узком сайдбаре слева нажать **+** (подпись «Загрузить датасет из ТЗ или свой файл»).
3. В открывшемся окне нажать жёлтую кнопку **«Использовать датасет из ТЗ»**.
4. Дождаться зелёного статуса: заявки и инженеры созданы. Экран обновится сам.
   Если день уже загружали вчера — нажать ту же кнопку ещё раз: окна и смены
   переедут на сегодня, дублей не будет.

Свой JSON по-прежнему можно перетащить в ту же модалку. Это не датасет
организаторов.

После импорта контур публикует снимок и применяет план. Отдельного шага
«посчитать» нет — это и есть автопланирование из ТЗ.

### 2. Распределение заявок между инженерами

ТЗ: по квалификации и доступности.

**Что есть.** Алгоритм не назначает заявку, если нет навыка, нет доступного
инженера в смене или (когда в заявке задан транспорт) нет нужного транспорта.
В официальном CSV требуемый транспорт пустой — ограничение в коде есть, на
этом датасете жюри его почти не увидит.

**Куда нажать.** Остаться на вкладке **«План дня»** (иконка карты). Слева:
список инженеров с числом заявок в плане и пробегом. Сверху — счётчик
«N заявки · M назначены · K без назначения · X км суммарный пробег» по
видимому региону. Селектор «Регион» сужает день до Востока / Юго-востока /
Юго-центра.

### 3. Порядок посещения адресов

ТЗ: порядок адресов для каждого инженера.

**Что есть.** У каждого инженера — плановый маршрут со стопами по времени.

**Куда нажать.** В списке слева кликнуть инженера. Под картой откроется
таймлайн: последовательность заявок этого человека. «Все маршруты» снимает
фокус.

### 4. Маршруты и точки на карте

ТЗ: маршруты и точки заявок на карте.

**Что есть.** MapLibre: точки заявок, порядок обхода, линия маршрута.
Восток считается по заготовленной OSRM-матрице (реальные дорожные времена).
Юго-восток и Юго-центр в образе — центроиды районов (гаверсинус × 1.25,
28 км/ч); на карте это видно как пунктир и плашку «точек по центроидам
районов». Если в одном дне есть и OSRM-точки, и центроидные, плечо берёт
лучший доступный источник. Живой OSRM/пробки подключаются только если задан
`ROUTER_OSRM_URL` — в публичном образе его нет.

**Куда нажать.** Карта в центре «Плана дня». Клик по точке открывает заявку.

### 5. Кто, куда, в какое время

ТЗ: краткая информация по плану.

**Что есть.** Карточка заявки и строка инженера.

**Куда нажать.** Клик по заявке на карте или в списке слева. Правая панель:
номер, тип работ, адрес, окно, длительность, статус «Назначена» / «Без
назначения» или «Почему {полное имя бригады}?». Объяснение всегда из трёх
блоков: факты → как влияют → результат; для маршрута — «Почему маршрут такой»,
для простоя — почему смена без заявок при остатке в зоне. В списке инженера —
пробег, навыки и «План: N заявок».

### 6. Перепланирование после одного события

ТЗ просит **одно** событие на выбор: срочная заявка / отмена / инженер
недоступен.

**Что есть в UI.** Событие «инженер недоступен». Срочной заявки и отмены
кнопками нет — не утверждаем обратное. Регресс на перестройку после срочной
заявки есть в `pnpm smoke` (`POST /api/v1/dispatch/requests` с `urgent: true`).

**Куда нажать.**

1. Запомнить текущий план (кто где, счётчики слева).
2. Сайдбар → вкладка **«Инженеры»** (каска).
3. У любого инженера со статусом «На линии» выключить переключатель
   (**«Отключить …»**). Это имитирует поломку / больничный / снятие с линии.
4. Дождаться «Перестраиваем…». Система считает план **без этого человека**.
5. Вернуться на **«План дня»**: на карте новая раскладка, сверху плашка
   «План пересобран…» (сколько заявок переданы и сдвинуты).
6. «Просмотрено» закрывает плашку. «Вернуть прежние настройки» включает
   инженера обратно и пересчитывает снова.

Включить инженера тем же переключателем — второе событие того же типа.

### 7. Объяснение человеческим языком

ТЗ: почему заявка у этого инженера, какие ограничения учтены, почему
неназначенная не назначена.

**Что есть.** Структурированные коды солвера, в UI по-русски: навык, транспорт,
окно, оборудование, «поиск не нашёл допустимого назначения».

**Куда нажать.**

- Назначенная заявка → правая панель **«Почему {имя}?»** — факторы.
- Неназначенная → блок слева «заявки без назначения», клик по строке →
  **«Почему без назначения»**. Не читайте общую фразу над списком как
  единственную причину: точная причина — в карточке этой заявки.

## Сравнение с базовым планом из ТЗ

ТЗ: две метрики (исполнители и пробег) рядом у оптимального плана и у
базового FIFO (заявки по очереди поступления → первому подходящему
инженеру).

**Что есть.** FIFO считается в каждом расчёте ядра. На экране сравнение —
вкладка **«Политики»**.

**Куда нажать.**

1. Сайдбар → **«Политики»**.
2. **«Сравнить»** (или «Пересчитать»). Это не меняет рабочий план.
3. Первая строка таблицы, песочный фон, бейдж **«сравнение с ТЗ»** — это
   **Базовая из ТЗ**. Смотреть колонки «Назначено», «Инженеры», «Пробег».
4. Остальные строки — рабочие политики на том же снимке и том же составе
   людей. Активная политика помечена «активная».

Базовую FIFO в модалке политик выбрать нельзя — она не рабочий режим, а
линейка сравнения.

Рабочие политики (шапка, кнопка «Политика»): Компактнее, Быстрее, SLA,
Ровнее, Короче пробег, **Покрывающая**. «Покрывающая» оставляет уже
назначенное и одним проходом закрывает хвост синтезированными инженерами
(лишних без работы отбрасывает). После применения они во вкладке
«Инженеры» как «Резерв …». Резерв живёт только пока активна покрывающая
политика: в compact/fast/sla/eco и в таблице сравнения его нет. Сама
покрывающая политика в таблицу сравнения тоже не входит — иначе строки
перестали бы быть сравнимыми. Если авторежим был выключен, перестроение
само включает AUTO. Первое сравнение политик может занять до полутора минут.

## Обязательные ограничения ТЗ

| Правило ТЗ | Как у нас | Как увидеть |
|---|---|---|
| Навык заявки ∈ навыки инженера | Жёсткое ограничение ядра | Неназначенная с кодом «Нет нужного навыка»; покрывающая политика обходит это, добавляя человека со всеми навыками |
| Работа + дорога в смене; старт внутри окна | Жёсткое ограничение ядра | Карточка: окно и времена стопа; неназначенная «Назначение не найдено», если в окно/смену не влезает |
| Транспорт заявки = транспорт инженера, **если указан** | Ограничение в коде есть | В официальном CSV поле пустое — на датасете ТЗ почти не проявляется |

Оборудование — необязательное усложнение ТЗ. У нас учитывается, если заявка
его требует.

## Что из ТЗ в UI ещё не кликается

Пишем, чтобы не искать несуществующее.

- Кнопки «срочная заявка» и «отмена заявки» нет. Событие дня для проверки —
  отключение инженера (§6).
- Кнопки «Построить план» нет. План строится после импорта / политики /
  отключения.
- Режим «Вручную» в шапке переключается, жестов перетаскивания назначения
  на карте нет.
- `packages/shared` пуст: контракт живёт в `apps/api` + `apps/web/src/api`.
- Engineer App и LLM в ToDo — сверх ТЗ, в этом прототипе их нет.

## Дороги: что стенд реально использует

| Регион | Времена и путь | Откуда |
|---|---|---|
| Восток | Дорожная матрица OSRM | `core/scenarios/east-v1/road-matrix.json` |
| Юго-восток | Центроиды районов | `core/scenarios/southeast-v1/road-matrix.json` |
| Юго-центр | Центроиды районов | `core/scenarios/south_central-v1/road-matrix.json` |
| Смешанный день | Часть плеч по OSRM, часть по центроидам | Общий граф трёх регионов |
| Если задан `ROUTER_OSRM_URL` | Живой OSRM на центроидных и неизвестных точках | Не включён в публичный образ |

ТЗ разрешает упрощённое расстояние. OSRM на Востоке — преимущество, не
требование.
