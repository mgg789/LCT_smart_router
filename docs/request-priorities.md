# Типы заявок и очередность работ

Изменение от 27.09.2026 по уточнению заказчика: **Авария → Подключение → Ремонт / Дозаказ**.
Сетевая авария — отдельный тип `outage`. Неисправность отдельного подключения («Нет линка»,
«Разрывы» и т. п.) относится к ремонту. Навык инженера `emergency` и прежний флаг
`priority=urgent` не являются группой заявки.

## Единственный каталог и импорт

Источник — `apps/api/src/orchestrator/requests/work-type.catalog.ts`.
Публичный read-only `GET /api/v1/client/work-types` отдаёт код, название, группу, русское
название группы, норматив выполнения и требуемый навык. Обе формы используют этот endpoint.
AI и MCP получают `workCategory` в обычном представлении заявки.

Офлайн-импорт Python читает генерируемый `core/work-types.json`. Обновление:
`pnpm --filter api test:build && node scripts/export-work-types.cjs`.
Тест проверяет полное совпадение выгрузки с API-каталогом.

Известные коды и точные алиасы классифицируются каталогом. Для неизвестного непустого
`workType` в JSON нужен явный `workCategory: emergency | connection | service`.
В табличном импорте группа задаётся колонкой или значением по умолчанию.
Исходное незнакомое название сохраняется и показывается в UI, без нечёткого угадывания.
Навык и длительность по-прежнему задаются явно; для группы аварии норматив фиксирован — 6000 секунд.
Для старых пакетов без названия типа сохранена совместимость: `urgent` → emergency,
`normal` → service. Новые именованные типы должны иметь явную группу.

Нормализация группы и 100 минут происходит **до предпросмотра** импорта и повторно перед
применением. Подтверждается тот же норматив, который сохраняется в БД.

## Авария и перепланирование

- Выполнение — **100 минут на объекте**, дорога считается отдельно. Профиль
  `network_emergency`; прежний `outage_tkd` (80 минут работы) остаётся у индивидуальных неисправностей.
- `receivedAt` — время поступления по бизнес-часам; `submittedAt` остаётся аудитом по реальным часам.
  В ускоренном LIVE используется время симуляции. Черновик не запускает реакцию: время фиксируется при подтверждении.
- В импортном плане без отдельного времени поступления аварии считаются известными с начала
  соответствующего дня. JSON может передать `receivedAt` явно. Будущий день не попадает в текущий расчёт.
- Сначала сохраняется покрытие аварий, затем минимизируется суммарная задержка начала от
  поступления, затем покрытие подключений, прежних срочных и остальных заявок. Только после
  этого сравниваются дорога, баланс и другие критерии выбранной политики.
- Начатая работа исключается из свободного пула. Её исполнитель доступен после завершения
  в конечной точке работы. Ускорение аварии не отменяет фактов выполнения.
- Ориентир реакции — **до 2 часов**, не жёсткий дедлайн отсечения. Даже поздняя авария остаётся
  в очереди. Если нет подходящего исполнителя, назначение не выдумывается: остаётся неназначенная заявка.
- Перенос аварии на другой слот/завтра запрещён в сервисах изменения условий и резолва алертов.
  Такие действия не предлагаются AI и в списке алертов; нужна доступная подходящая бригада.
- FIFO остаётся честным исходным сравнением. Оптимизатор получает отдельный приоритетный стартовый план.

Это ограниченный детерминированный поиск, не доказательство глобально оптимального маршрута.
Квалификация, смена, транспорт, регион и оборудование остаются обязательными ограничениями.

## Контракт и миграция

`Request.work_category` хранит группу, `received_at` — необязательное исходное время поступления.
В `RequestView` добавлены `workCategory`, `receivedAt`. Router принимает необязательные
`work_category`, `received_at`, `source_window_start_at`, `source_window_end_at`.
Последние два поля сохраняют исходное окно для проверки устаревшего результата: расчётное
окно аварии может отличаться от обещанного ранее окна. Старые снимки поддерживаются.
JSON Schema пересоздаётся через `python -m core.schema`.

Миграция классифицирует известные существующие типы и меняет норматив только у ещё не начатых
аварий. Исторические, выполняемые и закреплённые LIVE-факты не переписываются.
После развёртывания необходима новая публикация/пересчёт плана: миграция сама не создаёт назначения.

## Явный приоритет диспетчера

Действие «Приоритет» у неназначенной заявки добавляет один приоритет на рабочий день:
аварии и время их реакции → выбранная заявка и время её начала → подключения →
остальные заявки. Навыки, окна, начатые работы и физическая выполнимость сохраняются.
Действие запускает AUTO-перестройку и снимает отложенность только выбранной заявки.
Алерт закрывается после подтверждённого назначения, не после запуска расчёта.

Замена приоритета требует подтверждения версии из `GET /dispatch/request-priority?workDate=...`
в `expectedPriorityVersion` операции `prioritize`. Сервер отклоняет устаревшее подтверждение.
В автоматическом массовом решении этот вариант не выбирается: чат-агент может предложить
его только по явному указанию, что заявка точно важнее остальных обычных; замену подтверждает
диспетчер в UI. Состояние хранится в AppState по дню, а Router получает необязательный
`dispatcher_priority` (по умолчанию false).
