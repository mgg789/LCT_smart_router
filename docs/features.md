# Фичи проекта — полный каталог

Всё, что команда построила **сверх обязательных пяти пунктов ТЗ** (распределение по
квалификации, окна, транспорт/оборудование, маршруты с SLA, автоперепланирование,
карта с причинами). Каждый блок: проблема роли → как решает → где посмотреть в
приложении. Формат для быстрого обхода на защите: «фишка → боль → выгода → где кликнуть».

Не включены: `route-engine3` (отдельный opensource-артефакт, Apache 2.0 —
[route3.md](route3.md) и [services/route-engine3](../services/route-engine3/README.md))
и базовый контур из ТЗ.

## Паспорт объекта

**Проблема:** у каждого адреса есть особенности — код домофона, где щитовая, куда
класть пропуск, «не звонить до 9» — они живут в головах ветеранов и бумажных записках;
новый инженер каждый раз наступает на одни и те же грабли, а клиент раздражается от
одних и тех же вопросов.
**Решение:** паспорт объекта: ключевые сведения, что делали раньше, что знать при
выезде, контроль даты заполнения (устаревший паспорт помечается). Паспорт автоматически
показывается инженеру перед выездом — знания перестают зависеть от памяти людей.
**Где:** приложение инженера → карточка заявки → паспорт объекта; дашборд → объект.

## Планирование и ядро

### Прогноз пробок на момент выезда
**Проблема:** план, построенный на «средней скорости», разваливается — утренний и
вечерний пик дают разное время в пути по одной и той же улице.
**Решение:** время каждого перегона оценивается на фактическое время выезда:
радиальные полосы суток с учётом направления «к центру / из центра / поперёк»,
отдельные коэффициенты для МКАД/ТТК/Садового (×2,6 в узкие окна пиков), магистралей
(×1,8) и улиц (×1,2).
**Где:** дашборд — маршрут инженера, фактор трафика виден в расчёте плеча; на демо-стенде
`route-engine3` — переключатель «Трафик» и дата выезда.

### Погода в роутинге
**Проблема:** дождь и снег удлиняют поездки, а план об этом не знает; в грозу пешком
ходить опасно.
**Решение:** Open-Meteo по Москве поднимает время в пути (дождь ×1,08, снег ×1,15,
гроза ×1,18); пешеходу в грозу ходьба дорожает ×2,4 и метро становится предпочтительнее;
офлайн — честная деградация в 1,0, бейдж погоды виден на карте.
**Где:** бейдж погоды на карте; в плане инженера — погодная подсказка («возьмите зонт»).

### Метро для пешеходных маршрутов
**Проблема:** пешая доставка 8 км по прямой — нереалистична; без метро пешеходные
заявки закрываются хуже.
**Решение:** офлайн-граф московского метро (линии, пересадки с калибровкой 60 с,
поезда 50 км/ч) встраивается в пеший маршрут, если составной путь быстрее прямого.
**Где:** переключатель `metro_enabled` в настройках роутинга; в маршруте видны
сегменты «пешком → метро → пешком».

### Гибридный расчёт маршрутов
**Проблема:** точный расчёт по дорогам медленный, быстрый по прямым — неточный.
**Решение:** быстрый солв на калиброванных прямых + метро, затем верификация выбранных
плеч через дорожный граф с трафиком v2 и один повторный солв при пробитии окна.
**Где:** включается переменной `ROUTER_HYBRID=1`; отчёт верификации — в
`RouterResult.verification`.

### Дорожные матрицы до поиска
**Проблема:** искать маршруты, дёргая карту на каждый шаг — секунды ожидания.
**Решение:** перед поиском собирается одна пакетная матрица с режимами прогноза
(≈21 мс при тёплом кэше против ≈5 с поштучных вызовов) — единый источник цен для
плана, сравнения политик и what-if.
**Где:** прозрачно ускоряет всё; видно по латентности пересчёта (<0,5 с).

### Шесть политик планирования + FIFO-линейка
**Проблема:** «оптимально» — разное в разные дни: то сжать штат, то закрыть всё, то
не перегрузить лучших.
**Решение:** шесть стратегий (fast / compact / sla / balanced / eco / covering) на одних
ограничениях, каждая улучшает свою цель; FIFO доступен только как линейка сравнения.
**Где:** дашборд → «Политики» → сравнение колонками; смена политики пересчитывает план.

### Сравнение политик и обзорные графики
**Проблема:** непонятно, чем одна политика лучше другой, пока не применил.
**Решение:** сравнение на текущем снимке без записи в план: назначенные, срочные,
ожидание, пробег — дельтами к FIFO, зелёным отмечены совпадающие лучшие значения,
плюс резерв мощности.
**Где:** дашборд → «Политики» → «Сравнение политик»; обзорные графики с дельтами.

### Симулятор «что если»
**Проблема:** любое «а что если перенести окно» в живом плане — риск сломать день.
**Решение:** смена политики или сдвиг окна сначала считается в отдельном контуре —
рабочий план не меняется, дифф с экипажами показывается до применения.
**Где:** дашборд → карточка симуляции / «Пересчитать» в сравнении политик.

### Оценка плана на риск (Монте-Карло)
**Проблема:** план выглядит оптимально, но хрупок — один затор и каскад опозданий.
**Решение:** модель сотни раз проживает день с этим планом под реалистичным шумом
(пробки, длительности, отмены) и выдаёт полосу риска красный/жёлтый/зелёный с
объяснением по заявкам; калибровка уточняется по фактам исполнения.
**Где:** панель «Метрики плана» на дашборде.

### История плана и откат
**Проблема:** после аварийной перестройки непонятно, что именно поменялось, и откатиться нельзя.
**Решение:** каждая перестройка пишет снимок «до/после» (назначения, пробег, экипажи);
возврат на предыдущую ревизию с транзакционной проверкой допустимости.
**Где:** дашборд → история планов (кнопка восстановления ревизии).

### Ручные фиксации и допуски
**Проблема:** алгоритм не знает «этого клиента закрепили за Иваном» и не даёт тонкую
настройку строгости.
**Решение:** ручная фиксация инженера за заявкой учитывается оптимизацией; переключатели
строгих окон, допусков (окно, старт, переработка), бюджетов поиска и обедов.
**Где:** дашборд → карточка заявки (фиксация), «Настройки» (допуски, строгий режим).

### MANUAL-режим: диспетчер планирует сам
**Проблема:** в особых случаях диспетчер хочет назначить вручную («этот клиент — только
к Ивану»), но боится нарушить окно, навык или смену.
**Решение:** MANUAL-режим: диспетчер назначает — система проверяет допустимость решения
(окна, навыки, смены, транспорт) и считает маршрут по ручным назначениям; AUTO/MANUAL
переключает, потребляет ли система автоматический план.
**Где:** дашборд → карточка заявки → назначить вручную; переключатель режима системы.

### Аварии и срочные заявки
**Проблема:** авария у клиента — «весь план в мусорку» и звонки всем бригадам.
**Решение:** срочная заявка публикуется мгновенно, движок перепланирует за доли секунды,
сохраняя 52–84% назначений дня; диспетчер видит дифф и подтверждает.
**Где:** дашборд → «Заявки» → срочная заявка; SSE-поток пересчёта в реальном времени.

### LIVE-контур: день в реальном времени
**Проблема:** бумажный план не видит реальности: инженер опаздывает, заявку закрыли
заранее, бригада встала — план об этом узнаёт вечером.
**Решение:** LIVE отслеживает исполнение дня: статусы визитов, опоздания, сдвиги;
отклонения становятся триггерами перепланирования; утренний вход в день и вечерний
итог — частью того же контура.
**Где:** дашборд → LIVE-день (статусы, точки, события) → триггеры пересчёта.

### Передача оборудования между инженерами
**Проблема:** для заявки нужен роутер, а единственный свободный — в машине коллеги.
**Решение:** handoffs: план включает встречу для передачи оборудования с проверкой
смен обоих инженеров и наличия на складе.
**Где:** дашборд → подсказки handoff в плане; карточки инженеров.

## Объяснимость и доверие

### Объяснения назначений «почему этот инженер»
**Проблема:** диспетчер не может ответить клиенту/начальнику, почему заявка у этого
инженера и почему альтернативы отклонены.
**Решение:** каждое назначение раскрыто по цепочке «факты → влияние → результат»:
навык, запас по окну, дорога, рассмотренные альтернативы и коды причин отказа;
факты — расчётные, без домыслов.
**Где:** дашборд → карточка инженера/заявки; кнопка AI — пересказ фактами.

### Детальный дифф перепланирования
**Проблема:** после пересчёта непонятно, что именно поменялось и кого задело.
**Решение:** показываются переносы между инженерами, сдвиги времени, дельты пробега —
только факт и его эффект.
**Где:** дашборд → карточка «План перестроен» → дифф.

### Алерты с вариантами решений и ценой действий
**Проблема:** алерт «политика не покрывает» без вариантов — просто тревога.
**Решение:** алерт показывает варианты решения с ценой действий последнего шанса и
несколькими окнами того же дня; при недоступности LLM работает детерминированный
черновик.
**Где:** дашборд → колокольчик алертов → карточка решения.

### ИИ-оптимизация плана
**Проблема:** диспетчер видит алерт, но не знает, какой рычаг дёрнуть и чем это
закончится.
**Решение:** System one (Jev) по алерту предлагает конкретный рычаг — смену политики,
сдвиг окна, оптимизацию — и применяет его после подтверждения диспетчера; внешний
агент через MCP может дать вердикт «можно/рискованно» до применения.
**Где:** дашборд → алерты → «Решить с AI»; сравнение политик → «Оптимизировать».

### Итоги дня и оценка работы
**Проблема:** конец дня — «и что мы сегодня сделали?»; оценка диспетчера и инженера
субъективна и спорна.
**Решение:** итоги дня: закрыто/перенесено/опозданий, вклад каждого инженера, оценка
работы диспетчера и инженера по метрикам; завтрашняя нагрузка и переносы видны до
закрытия дня; за месяц — PDF-отчёт.
**Где:** дашборд → карточка конца дня / итоги; PDF-отчёт за месяц.

## AI-контур

### AI-ассистенты диспетчера и инженера (help/fix)
**Проблема:** диспетчеру и инженеру негде спросить «что это значит» и «сделай за меня».
**Решение:** help-режим объясняет и ищет по базе знаний; fix-режим применяет обычные
записи сам, рисковые держит карточкой до подтверждения (порог решает хук безопасности
System one/Jev). LLM никогда не принимает планировочных решений; в чате можно
уточнять и углубляться (drill-down).
**Где:** кнопки AI в дашборде и приложениях; уточняющие вопросы в чате ассистента.

### Заявка свободным языком
**Проблема:** клиент описывает проблему словами, а не полями формы.
**Решение:** гибрид локального разбора, System one (тема, окно, имя, адрес из текста)
и LLM (окно, которое regex не взял) — поля заполняются из текста.
**Где:** клиентское приложение → «Новая заявка».

### База знаний ассистентов
**Проблема:** типовые вопросы «как оформить перенос» каждый раз уходят людям.
**Решение:** статьи по ролям с индексацией при старте и полнотекстовым поиском,
сегменты доступа клиент/инженер/диспетчер.
**Где:** чат ассистента → вопросы по базе знаний.

### Бюджеты AI и replay-режим
**Проблема:** платные токены можно выжечь, а демо не должно зависеть от сети.
**Решение:** дневные лимиты сообщений и стоимости с резервом/возвратом; replay-режим
даёт полностью офлайн-демо ассистентов.
**Где:** настройки AI; `LLM_PROVIDER=replay` для демо без ключей.

### MCP-сервер дашборда (Bring Your Own Agent)
**Проблема:** внешний ИИ-агент не может безопасно работать с системой.
**Решение:** полноценный MCP-сервер дашборда: внешние агенты (Codex, Claude, Grok-Bot)
работают инструментами дашборда; MCP-ревью даёт вердикт «можно/рискованно» до
применения изменения; бюджеты до авторизации.
**Где:** подключение агента по документации MCP; ревью рычага перед применением.

## Приложения

### Клиентское приложение
**Проблема:** клиент звонит диспетчеру, чтобы узнать статус или перенести заявку.
**Решение:** заявка свободным языком с распознаванием полей, список и история своих
заявок, подтверждение кодом из письма, перенос и отмена, чат с диспетчером.
**Где:** `/client/` — веб-приложение клиента.

### Приложение инженера
**Проблема:** инженер узнаёт о смене планов по звонку, забирает не то оборудование.
**Решение:** дневной план с временем и адресами, «что взять перед выездом»
(оборудование), погодные подсказки, паспорта объектов, баллы за смену, кнопки
«опоздаваю/приступил», чат с диспетчером.
**Где:** `/engineer/` — приложение инженера.

### Система поощрений: баллы за смену
**Проблема:** инженеру всё равно, отмечаться ли и помогать ли коллегам — а от его
отметок зависит точность всей системы и плана соседей.
**Решение:** баллы за отметки «приступил/выполнил», пунктуальность и помощь
(передача оборудования, подхват заявок); накопленные баллы видны инженеру, а
диспетчеру — рейтинг и точные факты для планирования. Итог месяца — PDF-отчёт.
**Где:** приложение инженера → баллы; дашборд → рейтинг инженеров и месячный PDF.

### Чаты диспетчер ↔ клиент/инженер
**Проблема:** согласование «подъезд — код — этаж» идёт по личному телефону.
**Решение:** чаты в обоих приложениях (бэкенд готов полностью, интеграция в UI —
текущий релиз).
**Где:** приложения клиента и инженера → чат с диспетчером.

## Операционные инструменты

### Добавление инженеров и регионов через интерфейс
**Проблема:** новый сотрудник или новый участок = правка файлов и БД руками разработчика.
**Решение:** инженер (навыки, смена, транспорт) и регион/участок заводятся через UI
и сразу попадают в снимок планирования и на карту.
**Где:** дашборд → «Инженеры» → добавить инженера; создание участка/смены.

### Панель табличной загрузки заявок
**Проблема:** заявки приходят в Excel/CSV с произвольными колонками и кодировками.
**Решение:** CSV/TSV/XLSX (UTF-8/UTF-16/Windows-1251, разделители авто), сопоставление
колонок мышью, предпросмотр с геокодированием, демо-наборы в `data/samples/` для
мгновенной проверки.
**Где:** дашборд → «Загрузка данных» → табличная загрузка.

### Импорт ТЗ с переносом окон
**Проблема:** повторная загрузка вчерашнего файла ломает окна на прошлую дату.
**Решение:** импорт переносит окна на живой горизонт планирования, версия и
предупреждения — в предпросмотре.
**Где:** дашборд → «Загрузка данных».

### «День заново» для демо
**Проблема:** после демо/тестов система в грязном состоянии.
**Решение:** одна кнопка сбрасывает данные на стартовый день (с одинаковым порядком
блокировок — безопасно при живом LIVE).
**Где:** дашборд → reset (демо-контур).

### Полностью офлайн-контур
**Проблема:** демо и внедрение зависят от интернета и платных API.
**Решение:** дорожные графы, метро, геокод-каталог и подложка карты всех официальных
регионов вендорены в репозиторий; план, объяснения и ассистенты (replay) работают без
сети. Замер точности против Яндекса — ±8%.
**Где:** весь контур поднимается без внешних сервисов; см. [benchmarks](benchmarks/roads-vs-yandex-20260929/README.md).

### Внешний API и headless-режим
**Проблема:** у заказчика ERP/CRM, а работает система только «руками в браузере».
**Решение:** внешний API с токенами (идентификаторный доступ или сессии) для
интеграции заявок и планов; headless-режим: расчёт и обслуживание планов без UI —
CLI (`solve`/`serve`), контейнеры, приватный Router API.
**Где:** [integration-guide.md](integration-guide.md); `python -m core solve|serve`.

### Наблюдаемость и надёжность
**Проблема:** «упало — непонятно что»; публичные эндпоинты abused.
**Решение:** Prometheus-метрики, OTLP-трейсы и Sentry (все три выключаются независимо),
health-эндпоинты для оркестратора, per-IP лимиты на публичных эндпоинтах, прокси
OpenRouter с инжектом ключа на прокси, self-hosted CI с полным регрессом.
**Где:** `/health/live|ready|services`, `/metrics`; `docs/observability.md`.
