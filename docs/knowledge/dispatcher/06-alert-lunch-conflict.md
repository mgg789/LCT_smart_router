## Обед — не ручная отметка на дашборде

Обед следует плану автоматически: диспетчер не ставит отметки «пообедал» руками. Router
решает, входят ли обеды в расчёт (`lunchesEnabled`, по умолчанию **false**), а
`EngineerDay` инженера несёт фактическую длительность и окно обеда. `lunchTaken`
ставится только инженером, фактически начавшим обед в LIVE, — не публикацией
расписания — и это переживает перезапуск, смену режима и переключение флага.

## Когда возникает lunch_conflict

Есть два источника, оба канонизируются в один и тот же дашборд-код `lunch_conflict`:
системная проверка (обед инженеру нужен — `lunchRequired=true` — но `lunchStatus`
применённого маршрута не `scheduled`) и коды, которые может вернуть сам Router
(`required_lunch_unplaced`, `lunch_not_placed`, `lunch_skipped_for_work` — все три
превращаются в `lunch_conflict` функцией `canonicalRouterCode`). Отдельного
дашборд-кода «обязательный обед не помещается» не существует — это тот же
`lunch_conflict`.

## skip_lunch vs keep_lunch

Оба действия — единственные, разрешённые для этого кода. `skip_lunch` снимает
`lunchEnabled` и `lunchRequired` для дня этого инженера — обед в расчёт больше не
идёт. `keep_lunch` ставит `lunchRequired=true`, заставляя Router искать для него
слот при следующем пересчёте — без гарантии, что слот найдётся: если маршрут слишком
плотный, конфликт может вернуться тем же кодом. Диспетчер должен видеть последствия до
подтверждения: нельзя обещать, что отмены одной конкретной заявки достаточно, чтобы
гарантированно освободить место под обед.

## Включение обеда после старта дня и технастройки

Обед можно включить в любой момент дня — но только для инженеров, ещё не
использовавших его; начавшийся обед — уже факт и не создаётся повторно. Включение
идёт через `PUT /dispatch/router/technical-settings` с `lunchesEnabled: true` —
это **полная замена ревизии всех восьми полей** (CAS по `expectedContextVersion` из
свежего `GET`), а не точечный переключатель одного флага: отправка неполного набора
затрёт остальные настройки. Стандартная длительность загруженного через JSON
инженера — опциональные 30 минут в окне 11:20–15:00 по местному времени; произвольно
заданная длительность рабочего дня сохраняется как есть.
