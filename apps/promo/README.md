# Navix Router — презентационный ролик

Ролик примерно на две минуты: моушен-дизайн Remotion поверх **настоящих интерфейсов**
продукта. Ни один экран в ролике не нарисован заново — дашборд диспетчера,
приложение инженера и клиентское приложение снимаются с работающего стенда
браузером, который сам печатает, сам водит курсором и сам нажимает кнопки.
Remotion добавляет камеру, курсор, перебивки, музыку, стол в финале — и больше ничего.

## Как это устроено

```
capture/   Playwright ведёт живой стенд по сценарию и пишет кадры + метки
encode/    ffmpeg пересобирает кадры в ролики 60 fps с точным таймингом
src/       Remotion монтирует шоты по меткам и рисует моушен поверх
```

Порядок имеет значение — `capture/prepare.ts` перематывает день и включает то, что
сценарий показывает, а `День заново` внутри съёмки затёр бы добавленную работу:

```bash
pnpm --filter promo prepare-stand:restart   # перемотать день и настроить стенд
pnpm --filter promo capture                 # снять стенд (≈20 минут)
pnpm --filter promo encode                  # собрать public/footage + src/footage.json
pnpm --filter promo music                   # сгенерировать public/audio/reel.m4a
pnpm --filter promo studio                  # смотреть и править монтаж
pnpm --filter promo render                  # out/navix-reel.mp4
```

### 0. Подготовка стенда (`capture/prepare.ts`)

Три вещи, которые сценарий показывает, стенд по умолчанию не делает — не потому что
их нет, а потому что соответствующие возможности роутера выключены:

- **обед** — без него в дне инженера нет строки «Обед», мимо которой он прокручивает;
- **метро** — фиолетовый участок на карте: пеший инженер едет под землёй вместо того,
  чтобы идти час пешком;
- **передача оборудования** — синяя встреча: два инженера сходятся в одной точке,
  потому что у одного есть деталь, которая нужна другому.

Скрипт включает их через `PUT /dispatch/router/technical-settings` и дописывает пару
заявок через собственную загрузку диспетчера: одну достаточно далеко, чтобы метро
выиграло у пешком, и одну, требующую детали, которой у этого инженера нет. Дальше
решает роутер — поэтому скрипт печатает, что **действительно** оказалось в плане:

```bash
node capture/prepare.ts --check     # ничего не менять, только показать состояние
```

Передача оборудования появляется не всегда: спасательный проход вставляет встречу
только когда крюк реально помещается в смену, а запас оборудования у инженера через
API диспетчера не задаётся — он приходит с импортом региона. Поэтому оборудование
в `WANTED` оставлено **выключенным**: включить его — значит оставить без назначения
каждую заявку, деталь для которой инженер не везёт, и половина дня на доске уходит
в «без назначения». Это не продукт в работе, это следы съёмки.

Отдельно скрипт подбирает **окно допуска опоздания** так, чтобы план получил
жёлтую оценку. Это не подкрутка ради картинки: кнопка, которая отдаёт оценку
ассистенту, рисуется только для жёлтой и красной полосы — у идеального плана нечего
объяснять, и объяснять его нечем. Ручка тут не та, на которую похоже:
`windowLatenessToleranceSec` — не порог оценки, а планировочный допуск, и чем он шире,
тем плотнее солверу разрешено набивать день и тем больше визитов реально опаздывает.
Скрипт идёт по лестнице вверх и останавливается на первой жёлтой оценке.

### Что нужно для «Решить с AI»

Кнопка «Решить с AI» на алерте ходит не в чат-модель, а в **System one** — отдельный
решающий сервис по контракту `POST /v1/choice` (`services/sys1`, порт 12444).
На стенде без него `POST /dispatch/alerts/{id}/ai-resolve` честно отвечает
`503 System one недоступен`, кнопка нажимается, но кольцо вокруг выбранного варианта
не загорается и алерт остаётся на месте. Чтобы снять этот кадр, нужно:

```
JEV_API_URL=http://sys1:12444     # api ходит в sys1 по сети compose
SYS1_LLM_BASE_URL=<OpenRouter или его зеркало>
LLM_PROXY_TOKEN=<X-Proxy-Token зеркала>
SYS1_MODEL=typesafe/jev-1.13
```

Без этого сценарий закрывает алерт **вручную** — той же кнопкой варианта, которую
нажал бы диспетчер: карточка всё так же улетает с доски со своей анимацией, просто
без кольца выбора. В логе съёмки видно, какой из двух кадров снят.

### 1. Съёмка (`capture/`)

`capture/run.ts` поднимает Chromium, логинится настоящими одноразовыми кодами
(стенд отдаёт их в ответе `POST /auth/login-code`, потому что
`AUTH_DEV_EXPOSE_CODES=true`) и проходит сценарий: смена открывается, инженер
выходит на линию и закрывает визит, клиент создаёт аварийную заявку, план
пересобирается, алерт закрывается через AI, политики сравниваются, день закрывается.

Каждый дубль пишется через CDP-скринкаст: кадр приходит тогда, когда страница
действительно перерисовалась, и вместе с моментом, когда это случилось. Скрипт
дополнительно сохраняет **метки** (`marks`) — именованные мгновения вроде
`codeArrived` или `aiRing` — и **путь курсора**. Монтаж режет по меткам, а не по
секундомеру, поэтому дубль, который сыграл на полсекунды дольше, не ломает ролик.

Несколько сцен сняты **одним непрерывным дублем намеренно**, потому что раскадровка
просит движение, а не склейку: зум в уже показанную карту, нажатие «Подробнее» и
отъезд к панели, которую оно открыло, проход по шапке от селектора политик к метрикам
плана и объяснению AI. Разрезать такую сцену на два шота — и получается вспышка.

Две вещи, из-за которых первый проход снял нерабочие кадры и которые теперь
проверяются явно:

- дашборд гасит **все** записи, пока снапшот в полёте, а карточка алерта рисует свои
  кнопки серыми, а не прячет их — поэтому `pressable()` ждёт, пока кнопка станет
  нажимаемой, а не просто появится;
- панель уведомлений (колокольчик) лежит поверх всего дашборда, и её ловушка кликов
  накрывает поле ввода ассистента — поэтому в сценах AI она не открывается вовсе, а
  `resetBoard()` закрывает её, если она осталась от предыдущей сцены.

Разрешение выбрано по тому, сколько кадров успевает отдать скринкаст: 21 к/с на
3840×2160, 37 на 2880×1620, 60 на 1920×1080. Дашборд снимается на **2880×1620** —
его артборд 1920×1080 масштабируется CSS-зумом, так что это ровно полуторный рендер
макета.

Телефоны снимаются на **430×932**, то есть в своём родном размере. Поднять планку
колонки до 1176 и получить втрое больше пикселей заманчиво — почти всё внутри
считается от переменной `--eu` и честно масштабируется. Почти: оверлей выхода на
смену задаёт несколько размеров обычными пикселями, и на широкой колонке «Выйти на
смену» и «Выйти на линию» перестают попадать в общий масштаб. Это был бы ролик про
вёрстку, которой в приложении нет. Родной размер оставляет экраны честными, а
скринкаст на нём идёт ~60 к/с — для набора текста и прокрутки это ценнее лишних
пикселей. В ролике телефон около 870 px высотой, так что это почти один к одному.

Полезные флаги:

```bash
node capture/run.ts --only=client,replan   # переснять только часть
node capture/probe.ts                      # прогнать рискованные места без съёмки
```

`capture/probe.ts` открывает те же страницы, что и сценарий, и печатает, что на них
на самом деле доступно: включены ли действия алертов, есть ли у плана оценка, которую
AI может объяснить, заполняется ли сравнение политик. Пятнадцать минут съёмки, чтобы
выяснить, что кнопка была серой, — дорого.

### 2. Сборка материала (`capture/encode.ts`)

Кадры дубля превращаются в CFR-видео 60 fps через concat-демультиплексор ffmpeg:
каждый кадр держится ровно столько, сколько держался на экране. Неподвижный кусок
стоит один кадр, вспышка анимации сохраняет все свои. Результат — `public/footage/*.mp4`
и манифест `src/footage.json` с длительностями, метками и треком курсора.

### 3. Музыка (`capture/music.ts`)

Ролик под чужой трек — ролик, который нельзя опубликовать, поэтому музыка пишется
здесь: 124 удара в минуту, ля минор, из осцилляторов и огибающих и больше ни из чего.
Аранжировка разложена по секциям ролика, всё детерминировано — на любой машине
получается тот же файл. Результат: `public/audio/reel.m4a`.

### 4. Монтаж (`src/`)

- `Reel.tsx` — монтажный лист: шоты, переходы, движения камеры, подписи.
- `components/Camera.tsx` — камера в координатах самого дубля: «поставь точку
  78 % по ширине в центр кадра на 1.6×». Скорость движения подмешивает блюр.
- `components/Footage.tsx` — шот на весь кадр (дашборд) и шот в корпусе телефона.
- `components/Cursor.tsx` — курсор, которого в headless-съёмке нет: он рисуется
  обратно по записанному пути, с кольцом нажатия там, где был настоящий клик.
- `components/transitions.tsx` — хлыст, проброс сквозь кадр и вспышка.
- `components/Cards.tsx` — перебивки: у каждой своя палитра, своя абстракция и свой
  способ появиться.
- `components/Caption.tsx` — подписи поверх шота.
- `scenes/Intro.tsx` — логотип собирается и садится ровно туда, где его показывает
  **первый кадр следующего шота** (не сам дубль: шот ведёт над ним камеру, и именно
  она решает, где локап окажется на сцене) — поэтому стык не виден.
- `scenes/Outro.tsx` — отъезд на стол. Сцена начинается с того же кадра, которым
  закончился предыдущий шот, в том же размере, и просто отъезжает от него, пока экран
  не оказывается ноутбуком.

Длительность композиции считается из монтажного листа (`REEL_FRAMES`), так что
изменение любого шота само пересчитывает ролик.

## Что нужно на машине

- работающий стенд: `pnpm compose:up`, дашборд на `http://127.0.0.1:5173`;
- `speed_up_work_stub=1800` в `.env` — документированное демо-ускорение. Без него
  логический день идёт один к одному, инженер доезжает до первой заявки только
  через полтора часа, и кнопку «Приступить» снять нечем;
- Chromium для Playwright: `npx playwright install chromium`.

Адреса и почты берутся из окружения, если заданы: `PROMO_WEB`, `PROMO_API`,
`PROMO_DISPATCHER_EMAIL`, `PROMO_ENGINEER_EMAIL`, `PROMO_CLIENT_EMAIL`.

## Если интерфейс изменился

1. Поправьте селектор в `capture/FLOWS.md` и в сценарии.
2. Переснимите только затронутый дубль: `node capture/run.ts --only=<scene>`.
3. `pnpm --filter promo encode` — остальные дубли не перекодируются заново.
4. Проверьте шот в `studio`; метки обычно уже на месте, и монтаж не поедет.
